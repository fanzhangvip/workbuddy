01一张图看懂：它们不在同一层

先把位置摆正。这几个判断记牢，后面就不会乱：

  • MCP 解决"Agent 怎么用手边的工具和数据"——纵向的，从上往下够。
  • A2A / ANP 解决"Agent 怎么找到别的 Agent 并派活、拿结果"——横向的，从旁边递过去。
  • AG-UI 解决"用户怎么看见 Agent 在干什么、怎么中途干预"——面向用户的那一端。
  • Agora 解决"通信协议本身从哪来"——它在协议下面，是生产协议的元层。
工具接入层
MCP
Agent ↔ 工具 / 数据 / 资源。把 M×N 次集成变成 M+N 次。
协作层 · 可信域
A2A
Agent ↔ Agent 的任务发现、委派与交付，跨厂商跨框架。
协作层 · 开放网络
ANP
公网上陌生 Agent 的去中心化身份、发现与协商。
元协议层
Agora
让 Agent 在运行时协商并生成通信协议，而不是预先约定。
用户交互层
AG-UI
Agent 后端与用户界面之间的双向事件流，任意前端 × 任意框架。

02MCP — 工具接入层的赢家

Anthropic · 2024-11AAIF 创始项目事实标准

是什么

Model Context Protocol，2024 年 11 月由 Anthropic 开源的开放协议，常被称作"AI 世界的 USB-C"。它定义的是一个 Agent 如何接入外部的工具、数据和资源。

架构

经典的 Host / Client / Server 三段式：Host（宿主，如 IDE、桌面客户端）内运行 Client，Client 通过 JSON-RPC 2.0 连接 MCP Server。服务端暴露三类原语，后续版本又引入了 Sampling、Roots、Elicitation、Tasks。

它真正解决了什么

在 MCP 之前，每个 AI 应用每接一个工具就要写一次私有适配。MCP 把 M × N 次集成压缩成 M + N 次。所以它赢得很彻底——目前公开的 MCP Server 已超过 1 万个，TypeScript 与 Python 官方 SDK 累计下载双双破 10 亿，月下载接近 5 亿。

2026-07-28 规范：MCP 历史上最大的一次修订

核心变化是：MCP 从"有状态双向协议"改成了无状态请求 / 响应协议。

变化内容为什么重要
取消握手删除 initialize / initialized 与 Mcp-Session-Id请求可落到任意实例，直接挂普通轮询负载均衡
请求自描述协议版本、客户端身份、能力放进 _meta无需共享会话存储，Server 可纯 Serverless
头部路由强制 Mcp-Method、Mcp-Name 头网关 / WAF / 限流器不解析 JSON body 即可路由鉴权
MRTRMulti Round-Trip Requests 替代长连接 elicitation工具中途要用户确认，返回 input_required 后重试即可
可缓存list 结果带 ttlMs / cacheScope客户端可缓存工具目录，上游 prompt cache 更稳定
授权加固校验 RFC 9207 iss，CIMD 取代 DCR补上授权服务器混淆漏洞；DCR 正式弃用
扩展框架Tasks / MCP Apps / EMA 移出核心配 12 个月最低弃用窗口，升级可排期

一次无状态请求长什么样

POST /mcp HTTP/1.1
Mcp-Method: tools/call
Mcp-Name: search_customers
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

{
  "jsonrpc": "2.0",
  "id": "req-1",
  "method": "tools/call",
  "params": {
    "name": "search_customers",
    "arguments": { "region": "SE", "segment": "enterprise" },
    "_meta": {
      "protocolVersion": "2026-07-28",
      "client": { "name": "my-app", "version": "1.0" },
      "capabilities": { "tools": {}, "resources": {} }
    }
  }
}

每个请求自带全部上下文，不再需要"粘性会话 + 共享会话存储 + 网关深度包解析"。工程上的收益很直接：迁移到无状态运行时的团队普遍报告 p95 延迟明显下降，纯粹来自去掉了会话绑定。

安全上必须知道的事。MCP 第一年积累了 40 多个 CVE，并形成了"工具投毒"（tool poisoning）这一攻击类别。核心教训只有一句：MCP Server 的返回内容是不可信输入——它会把 prompt injection 直接送进你的模型上下文。协议本身不负责内容净化。

典型场景

  • Coding Agent 接入本地文件系统、Git、终端
  • 企业 Agent 接入数据库、内部系统、知识库
  • Agent 调用搜索、地图、支付等第三方能力（PayPal、Stripe、Stripe、Cloudflare 等均发布了官方 MCP Server）
  • IDE 与桌面客户端把企业内部系统暴露给模型

一句话：单个 Agent 能力不够时，加一个 MCP Server，而不是写一个插件。

03A2A — Agent 之间的"外交协议"

Google · 2025-04AAIF 正式项目生产可用

是什么

如果 MCP 是"手"，A2A 就是"嘴和耳朵"。它解决的是：两个各自有推理、有规划、有自己任务生命周期的 Agent，怎么互相发现、互相派活、互相交付结果——而且跨厂商、跨框架、跨组织，双方都不需要了解对方的内部实现。

核心数据模型：只有五个对象

对象作用
Agent CardAgent 的"简历"，发布在 /.well-known/agent-card.json，声明 name、description、version、provider、supportedInterfaces、capabilities、defaultInputModes / outputModes、skills、securitySchemes、signatures
Task有状态的工作单元，带明确定义的生命周期。这是关键对象——它不是一次无状态 API 调用
Message / Part一个对话轮次，来自客户端或 Agent；Part 是类型化内容（文本 / 结构化数据 / 文件引用）
Artifact任务的交付物，由 Part 组成，可流式增量下发
PushNotificationConfig客户端注册的 webhook，用于超长任务的状态回调

一次完整交互

  1. 客户端向目标域发起 GET /.well-known/agent-card.json，发现能力与鉴权方式
  2. 按 Card 中声明的 securitySchemes 协商凭证（API Key / HTTP Bearer / OAuth 2.0 / OpenID Connect / mTLS），版本协商走 A2A-Version 头
  3. 发送 SendMessage，携带一个或多个类型化 Part
  4. 服务端创建 Task，初始态 submitted；客户端通过 SSE 接收状态更新，或轮询 tasks/get，或等待 webhook 推送
  5. 任务到达终态，返回 Artifact，SSE 流关闭

任务状态机

有个设计细节值得注意：终态不可重启。要基于已完成的任务继续细化，必须在同一 contextId 下开一个新的 task id。这听着别扭，但它逼着双方对"什么算做完"达成一致——而这恰好是多 Agent 系统最先崩的地方。

A2A v1.0（2026 年 3 月）：让它真正生产可用的那一步

  1. Signed Agent Card——用 JWS（RFC 7515）对凭证做签名，规范化用 JCS（RFC 8785）。接收方可密码学验证 Card 确实由该域名所有者签发。没有签名，攻击者可以伪造一张 Card 把对等 Agent 引到恶意端点，这是发现层的伪造漏洞。
  2. 多租户——一个端点承载多个逻辑 Agent（SaaS 提供商必需）。
  3. 多协议绑定——同一个逻辑 Agent 可同时暴露 JSON-RPC 2.0、gRPC、HTTP+JSON/REST，数据模型与传输解耦。
  4. 版本协商——承诺从 v0.3 向后兼容迁移。
如果你还在 v0.2，请本季度升级：v0.2 没有签名 Card，这是一个不该留在信任模型里的伪造入口。

现状

  • Google 于 2025-04-09 发布，2025 年 6 月捐给 Linux 基金会
  • IBM 的 ACP 于 2025 年 8 月合并进 A2A——避免了一场协议战争
  • 2026 年 8 月成为 AAIF 正式项目，与 MCP 同属一个中立治理机构
  • 生态：150+ 组织签署（AWS、Microsoft、Salesforce、SAP、ServiceNow、Cisco、Atlassian、麦肯锡等）；GitHub 约 2.2 万星，约为 MCP 的 40%
  • 生产落地：PayPal（配合 AP2 支付协议完成代理支付）、Google Cloud ADK / Agent Engine / Cloud Run / GKE、Microsoft Azure AI Foundry、AWS Bedrock AgentCore

场景

  • CRM Agent 把工单升级委派给 ServiceNow ITSM Agent，两边团队不写定制集成
  • 跨公司供应链对账：一个团队用 LangGraph，另一个团队用别的框架
  • 安全运营（SOC）：把一堆单点 Agent 串成一套"神经系统"
  • 代理支付：购物与商户 Agent 通过 A2A 完成发现、议价、下单
两个必须注意的点。（1）A2A 不做内容净化——prompt injection 会随任务负载一路传播，输入校验是应用层责任。（2）跨组织的信任模型比 MCP 难得多：MCP 是 client–server，A2A 是两端都有自主性的对等 Agent，信任建立、鉴权、审计都要重新设计。

04ANP — 面向开放互联网的那一版

ANP 开源社区 · 2024MIT生态早期

是什么

Agent Network Protocol，自我定位是"The HTTP of the Agentic Web"，由国内 ANP 开源技术社区主导。A2A 的隐含前提是可信环境（企业内部、合作方之间）；ANP 赌的是另一个未来：全球任意两个陌生 Agent，像人类访问网站一样，不需要中心平台撮合就能互相发现、验证身份、协商协作。

三层架构

第一层 · 身份与加密通信层

基于 W3C DID 标准，自创 did:wba（Web-Based Agent）方法：继承 did:web 的优点，补上跨平台身份认证流程与 Agent 描述服务。DID 的公私钥对同时承担身份验证和 ECDHE 端到端加密两件事。这带来一个很实际的效果：Agent 可以租用第三方平台的端口转发消息，而平台方无法解密内容。这是 ANP 最"互联网原教旨"的地方——身份不依赖任何中心平台。

第二层 · 元协议协商层（与 A2A 的根本差异）

  1. Agent A 用自然语言向 B 描述需求、输入、期望输出，并给出候选协议（传输层协议、数据格式、数据处理方式）
  2. B 用 AI 判断能否满足；不能则拒绝，或不接受候选协议并提出自己的方案，进入下一轮协商
  3. 双方达成一致后，各自生成并部署协议处理代码
  4. 协商测试数据，联合调试协议与 AI 生成的代码
  5. 正式通信，使用最终协商出的协议与生成代码
  6. 需求变更时重复上述过程，直到达成新一致

第三层 · 应用协议层

ADP（Agent Description Protocol）用 JSON-LD + schema.org 词汇描述能力，配合发现协议构成"AI 原生数据网络"——每个节点是可描述、可发现、可调用的 Agent，每条链接是有语义的协议连接，而不是给人看的超链接。传输基于 HTTP，数据格式用 JSON-LD。

定位

官方自己的说法最清楚：用 MCP 接工具，用 A2A 做企业内 Agent 协作，用 ANP 做开放互联网上的 Agent 连接。采用 P2P 架构，不依赖中心平台。

典型场景

个人助理用自己持有的 DID 直接与任意酒店 / 航司 / 商户 Agent 交互，无需在对方平台注册身份、无需模拟人类点击网页，也不依赖平台专属 API；助理可在本地处理信息，只把必要信息发给对方。

现状与不确定性。目前是 v1.1 白皮书加参考实现 AgentConnect（Python SDK），生态仍处早期。它最大的不确定性在于押注"开放互联网"这个前提会成立——如果 Agent 协作长期发生在可信企业边界内，A2A 就够了，ANP 的价值会被压缩。另外一个实际障碍：元协议层让 Agent 运行时生成并部署代码，在合规审计上很难解释"为什么这次通信用了这个格式"。

05Agora — 不是协议，是"生产协议的协议"

牛津大学 · 2024-10MIT概念验证

是什么

前三个协议都默认一个前提：通信协议在部署前就已经定好了。Agora 恰恰挑战这个前提。它由牛津大学工程科学系团队（Samuele Marro、Emanuele La Malfa、Jesse Wright、Guohao Li、Nigel Shadbolt、Michael Wooldridge、Philip Torr）在 2024 年 10 月提出，论文是《A Scalable Communication Protocol for Networks of Large Language Models》（arXiv:2410.11905）。

它是一个元协议（zero-layer protocol）——不规定任何具体通信格式，而是让 Agent 在运行时自己协商并生成协议。

核心洞察：Agent 通信三难困境

论文指出，不存在一种协议能同时最优地满足三个属性：

传统方案要么用固定结构化协议（牺牲通用性），要么纯自然语言（牺牲效率）。Agora 的解法是承认这个权衡存在，然后动态切换：

  • 罕见通信用自然语言——保通用性
  • 频繁通信用协商出的专用协议——保效率
  • LLM 驱动协商本身——保可移植性

协商三步

  1. 自然语言初步协商。两个陌生 Agent 初次交互，直接对话。不管对方基于 LangChain、Camel 还是 Swarm，都能先聊起来。
  2. 产出 Protocol Document（PD）。一份纯文本描述的协议规范，双方确认后用 PD 的 SHA1 哈希作为该协议的标识。PD 用去中心化方式存储与检索，因此两个从未交互过的 Agent 也能复用同一个协议——这就是它解决"可移植性"的方式。
  3. 按 PD 执行，不再经过 LLM。后续通信直接按 PD 走，保效率。如果通信频繁，Agent 还会自动把 PD 编译成代码例程（Python / JS），把开销再降一档。
现状与硬伤。仍属学术概念验证，MIT 许可；论文在 100 个 LLM Agent 构成的网络上验证了可扩展性，但没有主流开源框架实现。生产环境的硬伤是：让 Agent 自主协商通信规则，合规审计和确定性行为无法保证——"这次为什么用这个格式"给不出可解释的答案。

它的价值不在于被部署，而在于指出一个方向：未来的 Agent 基础设施可能不是一组固定协议，而是一个能按需生成协议的元层。ANP 的元协议协商层就是这个思路的工程化尝试（ANP 白皮书的参考文献里就引了 Agora 那篇论文）。

同名排雷

"Agora"这个词在这个领域至少指四样东西：

名字是什么
牛津 Agora本文所讲的元协议，arXiv:2410.11905，MIT
声网 Agora实时音视频 RTC 服务，与 Agent 协议无关
npm agora-protocol2026 年出现的多智能体投票 / 否决 / 法定人数 / 异议保留语义库，架在 MCP 和 A2A 之上，不改这两个规范
npm @rookdaemon/agora基于 Ed25519 签名信封的 Agent 协调网络，提供直连 HTTP、WebSocket 中继与本地信誉工具

其中 agora-protocol 值得单独说一句：2026 年 9 月一份协议分析报告《Governance Gaps in Agent Interoperability Protocols》检查了 MCP、A2A、ACP、ANP、ERC-8004，发现这五个协议全都没有定义投票、法定人数、偏好聚合，也没有记录"提案被否以及为什么被否"的机制。于是每个团队都在自己的编排代码里手写一遍，而且写法各不相同。这类"补缺层"很可能会长出一批。

06AG-UI — 智能体与用户之间的那条轴

CopilotKit · 2025-05MIT1.0 稳定版

是什么

Agent-User Interaction Protocol，由 CopilotKit 创建，2025 年 5 月发布，MIT 许可，仓库在 ag-ui-protocol/ag-ui。它标准化的是Agent 后端与用户界面之间的双向事件流。注意它的出身——它是从 CopilotKit 与 LangGraph、CrewAI 的真实合作实践里长出来的，不是先设计规范再找人用。

为什么需要它：Agent 打破了请求-响应模型

传统 HTTP 一次请求返回一个响应。但 Agent 不是这样：它逐 token 流式输出、中途调用工具、还会派生 subagent。于是前端的处境是：得自己解析流、跟踪 Agent 此刻在干什么、再把这堆东西映射成 UI。

问题在于每个 Agent 框架的流格式都不一样。LangGraph 一种、CrewAI 一种、OpenAI Agents SDK 又一种。换框架就要重写一遍胶水代码，而且前端和后端被死死绑在一起。

AG-UI 做的事很朴素：定义一条共享的双向事件流。Agent 后端按标准事件发，前端按标准事件渲染。结果是解耦——换框架不用改前端，换前端不用改 Agent，同一个 Agent 能同时跑在 Web、移动端、终端和 Slack 里。

三轴定位

原理：只有一个核心抽象

run(input: RunAgentInput) -> Observable<BaseEvent>

Agent 只要实现这一个方法，返回一个事件流即可。

每个事件的结构极简：type（必填）、timestamp?、rawEvent?（转换前的原始框架事件——这个字段保留了溯源能力）。协议里 type 用 SCREAMING_SNAKE_CASE，SDK 类名用 PascalCase。

传输无关：SSE、WebSocket、webhook 都支持。官方 HttpAgent 提供两种通道——HTTP SSE（好读好调试）和 HTTP 二进制协议（protobuf，生产环境更省带宽）。AG-UI 是这些传输之上的抽象层，不需要任何特殊基础设施。

中间件层降低接入成本：事件不要求和 AG-UI 格式完全一致，只要"AG-UI 兼容"即可，现有框架把自己的原生事件格式做点适配就能接上。

几条硬规则（规范明确定义，不是建议）

  • 每个 run 必须以 RUN_STARTED 开始，以 RUN_FINISHED 或 RUN_ERROR 结束
  • TEXT_MESSAGE_CONTENT.delta 不能为空
  • 工具调用事件靠 toolCallId 关联
  • STATE_DELTA 使用 RFC 6902 JSON Patch 格式
  • 多个 run 顺序执行，每个必须完成才能开始下一个；消息跨 run 累积
  • TEXT_MESSAGE_CHUNK 与 TOOL_CALL_CHUNK 是便利事件，客户端的 transformChunks 管道会自动展开成 Start / Content / End 三件套，后端实现可以简化

超出"流式文本"的能力

  1. 双向共享状态——STATE_SNAPSHOT 全量加 STATE_DELTA 增量（JSON Patch），前端可实时渲染 Agent 正在处理的结构化对象，而不只是等最终结果
  2. 人在环中中断——协议级一等公民，见下节
  3. 生成式 UI——Agent 输出可渲染成真实 UI 组件，而不只是文字
  4. 前端工具执行——Agent 可调用运行在用户浏览器里的工具，带类型化交接；这意味着 Agent 能拿到当前页面状态、用户本地数据这类只在客户端存在的东西
  5. Agent 引导（steering）——用户可在 run 执行中途改变方向
  6. 多模态——文件、图片、音频、转录文本随文本一起传
  7. 分支 / 时间旅行——parentRunId 把 run 组织成类似 git 的追加式日志
  8. 推理可见性——REASONING_* 事件族单独成组，含加密推理内容的处理

人在环中：协议级的中断与恢复

当 Agent 需要一个确认（比如"要不要真的删掉这个生产环境里的桶"），它不是挂在流上傻等，而是结束当前 run 并声明自己被打断了。RUN_FINISHED 的 outcome 是一个判别联合：

  • 省略——生产者还没采用中断感知生命周期，按正常完成处理
  • { type: "success" }——正常完成
  • { type: "interrupt", interrupts: [...] }——为了等人输入而暂停，未决中断放在 outcome 里

客户端恢复的方式是发起一个新的 run，在 RunAgentInput 里带 resume 数组，逐个回应每一个未决中断。

这个设计的好处是它没有破坏无状态性：中断期间服务端不需要挂着连接、不需要保存会话，只需要表达"我被打断了，这是我要问的问题"。人什么时候回来都行。这与 MCP 2026 版用 MRTR 替换长连接 elicitation 是同一个思路——两边独立演化到了同一个结论。

AG-UI 1.0：从"能用"到"稳定"

  • 发布完整规范加 JSON Schema，明确定义每个事件携带哪些字段；TypeScript、Python、.NET 三个 SDK 由 schema 生成，不再手工维护
  • 规范里每条规则都注明责任方：生产者（Agent）还是消费者（客户端）。schema 与规范冲突时以 schema 为准；实现违反规则时是实现的 bug，不用猜
  • 向后兼容，现有 Agent 和应用不受影响；1.0 规范不会再变
  • 1.0 新增：subagent 支持、向前端发送自定义数据的 metadata、多模态工具结果、人在环中断、token 用量统计
  • 规范先以草案发布、在 GitHub 公开讨论，Anthropic、Pydantic AI、TanStack 团队的反馈进入了最终版本

应用场景

  • "边想边看"的协作型产品——Cursor 那一类，用户在同一工作区和 AI 一起改文档、代码、表格。这类体验靠传统请求-响应做不出来
  • 需要工具审批的场景——Agent 执行敏感动作（发邮件、部署、退款）前暂停，等人点确认
  • 生成式 UI——Agent 返回直接变成可交互的表单、看板、图表
  • 多端复用同一个 Agent——Web、移动端、终端、Slack 共享一个后端
  • 前端工具——让 Agent 调用只在浏览器里存在的工具
局限与容易踩的坑。
  1. 它只管 Agent ↔ 用户这一段。工具接入还是 MCP，Agent 间协作还是 A2A。
  2. 取消语义还不完整。目前没有 cancelled 结果类型——一方主动取消时，适配器只发一个裸的 RUN_FINISHED，不会报 RUN_ERROR；而客户端断连会被服务端视为外部取消，不会触发取消回调。想实现"停止生成"手势，正确做法是保持流连接，通过独立的取消端点做一方取消。
  3. "人在环中"是协议级中断，不是业务级审批流。谁能批、批几级、怎么留痕，仍要自己实现。
  4. 治理结构与前两者不同。MCP 和 A2A 已在 Linux 基金会下的 AAIF 做中立治理；AG-UI 由 CopilotKit 主导、MIT 开源。采用方名单很长，但治理集中度确实更高——如果评审流程会问"供应商弃用风险"，这一条要单独评估。
  5. 与 MCP Apps 有重叠区。MCP Apps 是让 MCP Server 渲染 UI，AG-UI 是让 Agent 驱动任意前端。选择依据是 UI 的所有权在工具方还是应用方。

08怎么选：五个问题

  1. "我这个 Agent 能碰到什么？" 这是 MCP 问题。一个 Agent 要接 10 个工具，用 MCP，别自己写插件。
  2. "谁能把这个活接走？" 这是 A2A 问题。两个团队的 Agent 要互相委派，用 A2A，别写私有胶水代码。
  3. "公网上的陌生 Agent 怎么找到我？" 这是 ANP 问题。但如果协作永远在可信边界内，A2A 就够了。
  4. "用户怎么看见并干预这个过程？" 这是 AG-UI 问题。只要 Agent 是流式、会调工具、需要人确认，就该用它，别让每个前端自己解析各家框架的流。
  5. "协议能不能自己长出来？" 这是 Agora 问题。今天别上生产，但值得理解它的思路，因为它正在被工程化项目吸收。
一个自检方法。如果你已经写了一个"A 调 B"的接口，还顺带定义了 B 的能力描述、版本管理、超时与断连处理——那你其实在写一个没有文档化的私有 A2A。每个团队写出来的都不一样，这正是标准化要解决的问题。

10七个必须避开的误区

  1. 把五者当竞品比较。层次不同。MCP 和 A2A 甚至已经同属 AAIF，官方定位是"垂直 / 水平两条互补的轴"，不会被合并，只是让路线图不再相撞；AG-UI 又在第三个方向上，面向用户。
  2. 以为 MCP 能替代 A2A。MCP 管不了任务生命周期、能力发现、跨组织委派；它也不描述"对方是谁、凭什么信他"。
  3. 以为 A2A 能替代 MCP。A2A 不定义工具调用原语。一个 Agent 接受任务之后，它怎么访问自己的数据库，仍然是 MCP 的事。
  4. 把 AG-UI 和 A2UI 混为一谈。AG-UI 是事件流线协议（管道），A2UI 是声明式载荷格式（管道里流的东西）。名字只差一个字符，层次完全不同。
  5. 以为协议写好了就安全了。协议只解决"怎么连"，不解决"连上之后对方会不会骗你"。MCP 第一年 40+ CVE、A2A 的注入传播，都是现成的例子。
  6. 忽视治理归属。MCP 从 Anthropic、A2A 从 Google 都转到了 Linux 基金会下的 AAIF；AG-UI 仍由 CopilotKit 主导。做架构或采购评审时，"如果厂商弃用怎么办"这个问题，三者的答案并不一样。
  7. 忽略 IETF 的存在。见下一节。

11标准化动向：IETF 在做什么

IETF 第 126 次会议（2026 年 7 月，维也纳）组织了智能体相关的工作组组建讨论。目前的共识很清楚：聚焦可互操作的发现与通信协议，不覆盖语义层，坚持问题驱动，避免构建大而全的协议体系。

方向内容
agentprotoAgent 通信协议工作组。定义通用的 Agentic Dialog Management Protocol，处理对话标识、生命周期语义、对话上下文如何跨多方中介与信任边界传播；不替代应用层协议，也不定义新传输。里程碑：2026-12 用例草案、2027-02 架构草案、2027-03 协议草案、2028-03 提交 IESG
DAWN智能体发现方向的工作组组建讨论
DMSC多智能体动态安全交互方向
OAuth / WIMSE两个安全工作组均已修改章程，把智能体授权与智能体身份认证纳入标准范围。讨论覆盖十大典型智能体授权场景、动态细粒度令牌的申请 / 授予 / 委托 / 撤销

一个重要的概念转变：AI Agent 需要独立于所代表用户的、可验证的自身身份。这样才能独立撤销 Agent 的访问权、把 Agent 权限约束为用户权限的子集、并把 Agent 发起的动作与用户发起的动作在审计上区分开。
