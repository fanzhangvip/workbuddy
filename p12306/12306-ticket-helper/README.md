# 12306 抢票助手

> 基于 Python 的 12306 自动化购票工具，**独立实现**（非任何仓库的 fork），
> 协议行为参考开源项目 **pjialin/py12306** 与 **testerSunshine/12306**，
> 补齐了 **Web 可视化配置、Windows 桌面客户端、智能候补、数据持久化、异常自愈、
> 反检测限速** 六块能力。
>
> **定位：个人学习 + 自用工具。严禁商业牟利、代抢代购、黄牛倒票。**
> 商业/批量使用违反 12306 用户协议与相关法律法规。本工具**不保证买到票**，
> 也不做任何资金操作（出票后仅提醒 + 引导跳转到官方渠道支付）。

---

## 一、5 分钟上手

### 1. 安装依赖

```bash
# Python 3.9+（推荐 3.11/3.12）
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS / Linux

pip install -r requirements.txt

# 可选：桌面客户端（需要 .exe 时必装）
pip install PySide6
# 可选：打包
pip install pyinstaller pillow
```

### 2. 初始化并自检

```bash
python main.py init        # 创建数据目录与配置文件
python main.py doctor      # 逐项自检（配置/数据库/站点表/加密/依赖）
```

首次运行会在用户目录生成配置与随机后台密码：

```
C:\Users\<你>\.ticket-helper\        # Windows
~/.ticket-helper/                    # macOS / Linux
├── env.py                # 配置文件（含 Web 后台密码）
├── data\app.db           # SQLite（账号密文/任务/订单/日志索引）
├── data\station_name.txt # 站点表（首次联网自动缓存官方全量数据）
├── logs\12306.log        # 结构化 JSON 日志
└── runtime\secret.key    # 加密密钥（请自行备份，丢失则已存密码无法还原）
```

### 3. 导入账号

**方式一：扫码登录（推荐，不用存密码）**

命令行也可以直接扫（不用打开界面）：

```bash
python scripts/real_qr_login.py            # 生成二维码并等待扫码
python scripts/real_qr_login.py --timeout 300
```


启动后台或桌面客户端后，在「账号管理」页点 **扫码登录**，用手机 **12306 App**
（「我的」→ 右上角扫一扫）扫描弹出的二维码并确认即可。

- 扫码前不需要填账号名，程序会在扫码成功后自动按官方返回的账号建号；
- 这类账号**不保存密码**，账号列表里「登录方式」会显示为「扫码」，
  「测试登录」按钮会被禁用（它本来就没有密码可填）；
- **登录会话会被加密记住**（`data/sessions/`，与密码同一把本机密钥），
  所以正常情况下**重启程序不必重新扫码**；只有会话在 12306 侧过期时
  （或超过 3 天）才需要再扫一次。账号列表的「详情 → 账号信息」里能看到
  「免扫码登录：已保存 / 未保存」。

> 会话文件是**加密**存放的，等价于一份登录凭据：不要把它拷贝到别处，
> 泄露即可被用于登录你的 12306 账号。删除账号时会自动一并删除。

**方式二：账号密码（可长期免登录）**

```bash
python scripts/seed_account.py                      # 交互式（密码不回显）
python scripts/seed_account.py --from-file acc.txt  # 批量（格式：用户名|密码）
```

> 密码用本机密钥以 AES（Fernet）加密后写入 SQLite，**不落明文、不回显、不进日志**。
> 两种方式可以混用：同一个账号先扫码登录，之后再补上密码，扫码不会把已存的密码清掉。

### 4. 启动

**方式一：双击 exe（推荐，免环境）**

打包后的目录里有**两个** exe，用途不同：

| 文件 | 用途 |
|---|---|
| `TicketHelper.exe` | **双击即用**。不带参数直接打开桌面客户端窗口（会自动在后台拉起服务） |
| `TicketHelper-CLI.exe` | 命令行用。`web` / `desktop` / `doctor` / `init` / `qr` / `profile` / `grab` / `mock` 等子命令 |

> 为什么拆成两个：图形界面版不带控制台，双击时不会闪出一个黑色窗口；
> 命令行版保留控制台，才能看到日志与自检输出。

**方式二：源码运行**

```bash
python main.py              # 无参数 = 直接打开桌面客户端（等同双击 exe）
python main.py desktop      # 桌面客户端
python main.py web          # Web 后台 → http://127.0.0.1:8008
python main.py qr           # 扫码登录账号（手机 12306 App 扫一扫）
python main.py profile      # 查看账号信息 / 乘车人 / 我的订单（需账号已登录）
python main.py grab         # 纯命令行挂机（无界面，适合服务器）
python main.py -v           # 查看版本与命令概览
python main.py -h           # 查看完整帮助
```

登录后台用 `env.py` 里的 `web.auth_user` / `web.auth_pass`；
桌面客户端会自动读取该密码登录，无需手输。

### 界面怎么组织的

两端用**同一套信息架构**，换客户端不用重新找菜单：

| 分组 | 页面 | 干什么 |
|---|---|---|
| — | **总览** | 顶部一条「你现在该做什么 + 一个能点的按钮」，然后是三张主卡片（已抢到 / 运行中 / 账号在线） |
| 抢票 | **任务配置**、**余票看板** | 配任务、看实时余票 |
| 账号 | **账号管理**、**个人中心** | 登录账号、看账号信息/乘车人/订单 |
| 记录 | **订单记录**、**实时日志** | 抢到之后去哪儿付款、每轮查询查到了什么 |
| 系统 | **通知设置**（网页端另有**系统设置**） | 提醒渠道、限速与反检测 |
几处刻意的设计，改之前请先读：

- **状态写在看得见的地方**：网页端顶栏常驻「已抢到 / 运行中任务 / 账号在线 / 风控次数」，
  点一下直接跳到能处理它的页面 —— 不用为了「账号掉线了要重新扫码」在菜单里自己找。
  桌面端状态栏常驻同样的概览。
- **总览页永远给「下一步」**：没账号 → 去扫码；有账号没任务 → 去配任务；
  有任务没抢到 → 去看余票；已抢到 → 去订单记录付款。空列表也这么写，不写「暂无数据」。
- **席别优先级是一个有序列表**，不是勾选框：席别的顺序就是「有票时先要哪个」，
  用 ↑↓ 调整。车次类型同理用勾选，不用多选下拉（那玩意儿要按住 Ctrl 点，还得先知道这件事）。
- **任务表单分四组**，前三组填完就能存，「运行参数」默认折叠
  （以前十几个控件一次摊开，想找「乘车日期」得先滚动）。编辑已有任务时会自动摊开。
- **校验指名道姓**：缺哪项就说哪项，并把那一格标红滚到眼前；
  出错的提示**不自动消失**（一闪而过的错误等于没报）。
- **通知设置是「一渠道一张卡」**（桌面端）：卡片头一行是「启用」开关 + 说明 + 该渠道的
  **测试**按钮与结果，参数按两列排；**没启用的渠道参数区是灰的**，一眼看出哪些现在不用填。
  每个渠道可以**用界面上当前填的值直接测**，不必先保存 —— 保存一份错的配置本身就是污染。
- **任务表单 / 通知设置整页可滚动，而「保存」按钮固定在底部**，
  内容再长也不用手动滚到底去找它。
- **任务表单里，带按钮的自定义控件（日期 / 站点 / 车次）各占一整行**，
  字段名写在控件上方 —— 塞进两列表格的右列时，一行里要同时放下输入框和 2~3 个按钮，
  输入框会被压到几十像素，等于没法打字。

账号登录之后，可以查看**个人中心**（账号信息 / 乘车人 / 我的订单 / 待支付）：

| 入口 | 位置 |
|---|---|
| 网页端 | 左侧导航 → **「个人中心」**（顶部有账号下拉，切换即拉取） |
| 桌面端 | 左侧导航 → **「个人中心」**（同上） |
| 快捷方式 | 两端都可以在「账号管理」里点某一行的 **「详情」**，会直接跳到「个人中心」并选中该账号 |
| 命令行 | `python main.py profile [--user 账号名] [--where G\|H]` |

- 账号未登录时页面**照常显示**，顶部横幅会说明原因，并给出「扫码登录」按钮就地解决；
- 扫码账号的登录会话会被加密记住（见下面「扫码登录」一节），
  所以正常情况下**重启不必再扫码**。页面里「账号信息」会显示
  「免扫码登录：已保存 / 未保存」，可以直接确认这件事有没有生效。

抢到票之后到**「订单记录」**：每一条都有订单号和「去 12306 支付」按钮。
**本工具不代扣款** —— 超时未支付的订单会被官方自动取消，所以这一步别拖。

排查字段问题时用 `python scripts/diagnose_profile.py`（会把三个接口的原始 JSON 落盘）。

> **想知道「每个按钮到底有没有真的去调 12306」**：跑
> `python scripts/audit_callchain.py`。它把探针挂在协议层唯一的出网口上，
> 逐个 UI 入口实测并打印实际发出的 12306 路径；报告见
> [`docs/调用链审计.md`](docs/调用链审计.md)。

**配置任务时，基础信息也是「选」而不是「敲」**：

| 字段 | 怎么填 |
|---|---|
| 乘车日期 | 点日期控件弹出日历选一天 → 「添加日期」；「连加 3 天」一次加三天（抢票常连着抢几天）；标签可点 × 删除 |
| 出发站 / 到达站 | 输入关键字（如 `广州`）→ 「搜索站点」→ 点候选里的站名加入；数据来自 **12306 官方站点表**（启动时拉全量表并缓存，离线退回包内常用站表） |

- 关键字留空直接搜，会列出**常用大站**，不用先猜一个名字；
- 每个候选带**电报码**（如 `广州南 IZQ`），能确认选到的是官方那个站；
- 为什么非要选不能敲：站名必须与 12306 一字不差，把「广州南」敲成「广州」或「广州南站」，
  症状是「任务跑起来一条都查不到」，很难联想到是站名写错了。

**「车次白名单 / 车次黑名单」同样不用手敲车次号**：

| 入口 | 位置 |
|---|---|
| 网页端 | 任务配置 → 车次白名单右侧 **「从 12306 拉取车次」** → 勾选 → 「应用到车次框」 |
| 桌面端 | 任务配置 → 车次白名单右侧同名按钮 → 弹窗里勾选 → 「应用并关闭」 |

- 先填好**乘车日期 / 出发站 / 到达站**，再点拉取 —— 拉的就是这条线路当天真实存在的车次；
- **不需要登录**：余票查询接口不要求登录态。有在线账号就用账号的会话，没有就用匿名会话
  （真机实测：匿名会话预热一次余票页即可正常返回，广州→长沙一次 200+ 班车）；
  账号会话失效时会自动改用匿名会话，并在状态栏说明；
- 拉回来的表里有车次、类型、发车/到达时刻、历时、余票摘要，按发车时间排序；
- 白名单的顺序就是**抢票优先级**：已有车次保持原顺序，新勾选的追加在后面；
- 同一车次不能同时在两个名单里（保存会被判配置非法），所以加入其中一个时会自动从另一个移出，并在状态栏说明动了什么；
- 单次最多查 **12** 个「日期 × 起止站」组合，超出会明确告知（而不是悄悄少查几个）；
- 结果有 **60 秒缓存**，连点不会反复打 12306；要强制重查就点「重新拉取」。

> 拉车次不需要登录，但**抢票下单需要**（下单必须用登录会话）。
> 另外：真机上**密码登录走不通**（登录验证码接口已变更），扫码登录是唯一可靠路径。

排查「拉不到车次」用 `python scripts/diagnose_train_pull.py`
（把每一步的请求路径、HTTP 状态、返回是 JSON 还是 HTML、解析出几条按顺序打出来）。

对应接口：

| 用途 | 接口 |
|---|---|
| 站点检索 | `GET /api/stations?kw=广州&limit=60`（空 `kw` 返回常用站；返回 `items[{name,code}]`，`stations` 为兼容的纯站名列表） |
| 车次候选 | `GET /api/trains/options?dates=...&from=...&to=...&refresh=0|1`（`errors` 非空但 HTTP 200 是正常结果 —— 某个日期/线路没查到只影响它自己） |

> 端口被占用（例如上次的后台没退干净）时，程序会**自动换一个可用端口**继续启动，
> 而不是直接报错。

### 关于包名与上游参考（重要）

本项目的导入包名为 **`ticket_helper`**。

> 早期版本曾用 `py12306` 作为包名，已**修正**：该名字同时撞了上游项目目录名
> 与 PyPI 上的同名包，会导致「看起来像二次开发」以及潜在的 `import` 冲突。

**与上游的关系**：本项目是自己写的一套实现，**不依赖也不包含**上游代码
（`requirements.txt` 里没有它们）。但在**协议细节**上以上游为准，尤其是：

| 采纳自 | 内容 |
|---|---|
| pjialin/py12306 | 登录鉴权接口必须带 `Origin` + passport 跳转页 `Referer`；扫码收尾顺序 `userLogin → uamtk → uamauthclient`；`checkqr` 需带 `appid=otn`；二维码过期即换码 |
| testerSunshine/12306 | 扫码登录 / 本地打码的整体思路（其 TF1 模型改由 ONNX 方案替代，见下） |

**本地打码模型的说明**：`testerSunshine/12306` 使用的是
`12306.image.model.h5`（60MB）+ TensorFlow **1.14** / Keras 2.2.4，
而 TF1.14 只支持 Python ≤ 3.7，在本项目上**无法加载**。
因此 `codec.mode=local` 改为支持现代方案：现成的 `ddddocr`（`pip install ddddocr`）
或自备 ONNX 模型；不装也没关系，会走人工兜底（这是最稳的一条路）。

**关于识别效果的实测（不要高估本地模型）**：拿真实登录验证码样本跑
`ddddocr`，通用检测模型返回 10 个框，**其中 9 个是顶部那句提示文字**
（"点击下图中所有的…"被当成了待点击目标）。已加入「剔除顶部提示文字行」
的处理，把答案从"必然错"拉到"可能对"；但通用模型的字符集与 12306 点击型
验证码的题型并不一致，**命中率仍不可指望**。结论：
`ddddocr` 对**字符型**（下单）验证码有用，对**点击型**（登录）验证码作用有限，
识别链末尾的**人工兜底**才是可靠路径 —— 这是刻意保留的设计，请不要删。

**注意：打包版不含本地打码依赖。** `ddddocr` / `onnxruntime` / `cv2` 已写入
`TicketHelper.spec` 的 `excludes`。原因：一旦被 PyInstaller 顺着 `import ddddocr`
拉进来，产物会从 **~128MB 涨到 ~277MB**（实测 cv2 112MB + onnxruntime 36MB），
而这点能力对点击型验证码本就不可靠，不值得这个体积。
所以：

| 运行方式 | 本地打码 | 说明 |
|---|---|---|
| 源码运行（`python main.py ...`） | ✅ 可用（`pip install ddddocr`） | 想用本地识别就走这条路 |
| 打包 exe（双击即用） | ❌ 不含 | 走**人工兜底**（把验证码推给界面，你点一下） |

### 登录验证码接口已变更（真机实测）

2026 版登录页 `login_new_v20260207.js` 把**旧的 passport 验证码接口注释掉了**，
改用 `passcodeNew`：

| 接口 | 用途 | 真机现状 |
|---|---|---|
| `GET /otn/passcodeNew/getPassCodeNew?module=login&rand=sjrand` | 登录验证码（返回图片字节流） | ✅ 接口存在；缺设备指纹上下文时回 `{"status":false,"messages":["系统忙，请稍后重试"]}` |
| `GET /passport/captcha/captcha-image64` | 旧登录验证码（base64 JSON） | ❌ **已被 WAF 挡掉**，任何请求头组合都回 HTML 错误页 |

**这意味着密码登录在真机上目前走不通**（拿不到验证码）。程序已把两条路径都试过，
并在都失败时给出指明出路的提示：

```
登录验证码获取失败：官方接口当前不接受程序化请求。建议改用「扫码登录」（无需验证码）。
```

登录页现在还会加载阿里 `nc.js`（无痕验证），说明登录风控已迁移到第三方挑战。
**结论：扫码登录是当前唯一可靠的登录方式**（协议已按真机修正并验证）。

### 余票查询：查询前必须先「逛一次页面」（真机实测）

余票接口有一个隐蔽前提：**会话里必须先真实加载过一次页面**，否则 12306 会回
HTML 错误页（HTTP 200，不是 4xx）。同一时刻并排对照：

| 请求 | 结果 | Cookie |
|---|---|---|
| 新会话直接调 `leftTicket/query` | ❌ HTML 错误页 | （空）|
| 同一时刻，先加载一次 `/otn/leftTicket/init` 再调 | ✅ JSON | 有 `JSESSIONID` 等 |

浏览器天然满足这个条件（用户总是先打开页面），脚本必须自己补 ——
这一步由 `TicketApi.ensure_session_warm()` 完成（**会话级只做一次**）。

另外两条相关约束：

- **被拒 ≠ 路径下线**。`queryZ/queryA/query/queryO` 是灰度轮换路径，
  候选轮换是为「路径下线」准备的；而「被拒」是会话/风控层面的，
  把 4 条路径全打完只会把短暂限流变成持续限流。所以现在一旦识别到被拒，
  就**立即停止轮换**并抛 `RiskControlError`，交给上层降频（grab 引擎会
  `report_risk()` + 退避 + 通知使用者）。
- **看板读缓存**。`/api/tasks/<id>/remain` 用最近一次查询的候选回填，
  刻意不额外打接口，避免刷新看板时把风控踩响。

**真机验证记录**：北京南 → 上海虹桥（7 天后），命中 **47 个车次**、

```bash

```

├── TicketHelper-CLI.exe   ← 命令行用这个

**验收要求（干净 Windows、未装 Python）**：双击 `TicketHelper.exe` → **直接打开桌面客户端窗口**
（不是黑窗一闪而过）、能配置账号与任务、能看板与日志、关窗进托盘继续挂机、出票有弹窗；
配置/数据库/日志写入 `%USERPROFILE%\.ticket-helper`；关闭重开数据不丢。

**启动失败怎么排查**：任何未处理异常都会写进
`%USERPROFILE%\.ticket-helper\logs\crash\crash-*.log`（含完整堆栈、Python 版本、打包状态），

打包要点（已在 spec 中落实）：

| 项 | 做法 |
|---|---|
| 入口拆分 | 图形版 `console=False` + 命令行版 `console=True`，共用 `_internal`，只多几百 KB |
| 形态 | onedir 为主（启动快、杀软误报低），可另出 onefile |
| 写路径 | 全部走用户目录，绝不写 exe 目录 → 免管理员权限 |
| 资源 | 站点表 / 前端静态文件 / 图标 `--add-data` 随包 |
| 隐藏导入 | flask_sock / simple_websocket / PySide6 子模块显式声明 |
| 体积 | 排除 pytest、numpy、tensorflow、未用的 Qt 模块 |
| 误报 | 不启用 UPX、内嵌版本信息与文件说明、onedir 形态 |
| 重建 | 构建脚本用「改名让路」而非删除旧目录，避免受管控机器上批量删除被拦截 |

> 打包时若目标目录已存在，PyInstaller 会先 `rmtree` 它。在启用了删除防护的机器上这会被拦截，
> 表现为「打包到 99% 突然失败」。构建脚本已改为把旧目录改名（`TicketHelper.old-<时间戳>`），
> 可以放心反复构建；这些残留目录可随时手动删除。

## 八、安全与合规

1. **合规边界**：仅限个人学习与自用购票。**严禁**商业牟利、代抢代购、黄牛倒票。
2. **账号安全**：密码加密存储；密钥文件 `runtime/secret.key` 与数据库分离，
   请妥善保管（丢失后已存密码不可还原）。
3. **后台安全**：默认只监听 `127.0.0.1`；若改为对外监听，**务必**设置强密码，
   系统会在启动时对「空密码 / 监听公网 / 放开跨域」给出显式告警。
4. **风控风险**：自动抢票可能触发 12306 风控。请保持默认及以上的查询间隔
   （建议 ≥1s），程序内置自适应降频，但**不保证**绝对不被限制。
5. **成功率**：本工具只是加速购票流程，放票受官方调度与候补规则影响，**不承诺买到票**。
6. **版本漂移**：12306 接口与风控随时可能调整。所有接口路径与字段索引集中在
   `ticket_helper/inter/urls.py` 与 `ticket_helper/inter/parser.py`，便于快速适配。

## 九、常见问题

**Q：候补一直不提交，提示「账号未完成人证核验 / 未核验」怎么办？**

12306 规定：申请**候补购票**前，账号需完成**人证一致性核验**
（已通过核验的账号、以及已激活的「铁路畅行」会员自动满足）。核验要人脸识别，
**必须本人在手机上做**，程序不能代做。做法：

1. 手机上打开「铁路 12306」App（认准官方）
2. 登录账号 → 右下角「我的」
3. 名字下方找到「人证核验」，点进去
4. 勾选同意 → 「开始核验」→ 按提示做人脸识别
5. 回到本程序 →「账号管理」→ 点该账号的「**重测核验**」，状态会刷新

两端界面里都常驻了这个入口：桌面端顶部有「**人证核验怎么做？**」按钮，
网页端账号页有一块「人证核验怎么做？」的可展开说明（有账号被拦时自动展开）。

> ⚠️ 注意区分两种状态：**「未核验」**是真的会被候补拦住；
> **「无法判定」**只是官方接口没返回核验字段（真机实测这两个接口都不返回），
> **不影响候补**——程序会照常提交，官方若拒绝会给出真实原因。
> 排障用：`python scripts/diagnose_verify.py --restore`（把三个用户信息接口的原始响应落盘）。

**Q：候补一直不提交，日志写「响应不是合法 JSON (HTTP 405)」或「未找到可候补的车次」？**

两种原因完全不同，先分清：

- **HTTP 405**：说明候补接口的**路径**不对。12306 的候补接口在 `/otn/afterNate/` 下，
  不在 `/otn/confirmPassenger/` 下（详见 `ticket_helper/inter/urls.py` 里的注释）。
  这个坑已修，若再出现请把这段日志发出来。
- **未找到可候补的车次**：说明这一天**没有可候补的车次**。最常见的两种情况：
  ① 车次处于「列车运行图调整，暂停发售」或尚未起售 —— 这类车次连下单密钥都没有，
  官方根本不受理候补；② 该车次还有票（有票就不需要候补）。
  **换一个在售的日期**再试，或等车票开售之后再跑。

想自己确认链路通不通，用只读诊断（**不会创建候补订单**）：

```bash
python scripts/diagnose_standby.py --restore --task 1            # 看链路前 4 步
python scripts/diagnose_standby.py --restore --task 1 --until-confirm   # 走到「确认订单」之前
```

**Q：提示「账号未完成人证核验」（或状态显示「无法判定」）？**

先看状态是哪个：**「未核验」**才是真的会被候补拦住，需要去铁路 12306 App 里做核验
（App →「我的」→ 名字下方「人证核验」→ 人脸识别，必须本人），回来点「重测核验」刷新。
**「无法判定」**只是用户信息接口没返回核验字段，**不影响候补**；
程序会在候补链路第一步（`chechFace`）拿到官方的真实结论。

**Q：双击 exe 后黑窗一闪就没了 / 完全没反应？**
确认你双击的是 **`TicketHelper.exe`**（图形版）。如果仍然异常，去
`%USERPROFILE%\.ticket-helper\logs\crash\` 看有没有崩溃日志——里面有完整堆栈。
命令行版请用 `TicketHelper-CLI.exe`。若窗口没出现但进程在跑，检查系统托盘图标。

**Q：提示「端口被占用」？**
程序会自动改用下一个可用端口，一般无需处理。若想固定端口，用
`TicketHelper-CLI.exe desktop --port 8100`，或在 `env.py` 里改 `web.port`。

**Q：提示「所有账号登录失败」怎么办？**
先运行 `TicketHelper-CLI.exe doctor`（或 `python main.py doctor`）看自检结果。
常见原因：密码错误、验证码识别源不可用（把 `codec.mode` 改成 `manual`，
在 Web/桌面端弹窗里人工输入验证码即可）、网络不通。

**Q：验证码总是识别失败？**

先分清是哪一类，两者机制完全不同：

- **登录验证码（点击型）**：真机上官方接口已不接受程序化请求（见上文「登录验证码接口
  已变更」），**拿不到图**，所以不是识别源的问题 —— 请改用**扫码登录**。
- **下单验证码（字符型）**：`codec.mode=free` 需要一个可用的免费打码接口（默认未配置）；
  建议改用 `manual`（人工兜底，最稳）。
  本地也可 `pip install ddddocr` 走 ONNX 识别（对字符型有效）。

> ⚠️ **`codec.mode=cloud`（云打码）已于 2026-09-29 移除。**
> 原实现任何配置下都不可能成功 —— 请求里的账号是空串、且**从不真正上传验证码图片**
> （`HttpClient` 没有 multipart 文件上传能力），但 `available()` 只看"有没有填 Key"，
> 于是它会在识别链里"假装可用"，把失败吞成一句「验证码识别失败」。
> 现在配置里若还写着 `mode="cloud"`，启动时会**明确报错**并给出改法，而不是静默忽略。

**Q：扫码登录失败 / 二维码扫不了？**
- 二维码**只有约 21 秒**寿命（官方限制，实测结论，网传的"2 分钟"不准确）。
  程序会自动换码并在界面上跟着换图，不必手动刷新；
- 必须用 **12306 官方 App** 里的扫一扫（不是微信/支付宝的扫码）；
- 扫完要在手机上点「确认登录」，只扫码不确认会一直停在「已扫码」；
- 提示「会话不存在」通常是后台重启过，重新点一次扫码登录即可。

**Q：扫码登录的账号重启后显示异常？**
正常现象：扫码账号没有保存密码，重启后无法自动登录，需要在「账号管理」里
再扫一次。如果希望长期免登录，给该账号补一个密码即可（扫码不会覆盖已有密码）。

**Q：状态栏显示「实时通道：轮询模式（未安装 QtWebSockets）」，是什么问题？**

**不是故障，是环境缺件**：`QtWebSockets` **不在 `PySide6-Essentials` 里**，
它在 `PySide6-Addons` 里。缺它时实时日志与任务状态会自动降级为轮询 ——
功能不缺失，只是延迟约 2 秒。

装上即恢复 WebSocket 推送（版本要与 PySide6 严格一致）：

```bash
pip install PySide6-Addons==6.11.2
python main.py doctor     # 应显示：[√] 实时通道  WebSocket 推送可用（QtWebSockets 已就绪）
```

两条容易踩的坑（本项目已处理，改打包配置时注意）：

- QtWebSockets 依赖 `PySide6.QtNetwork`，打包时两者都要在 `hiddenimports` 里，
  且**不能**把 `PySide6.QtNetwork` 放进 `excludes` ——
  否则打包版会报 `libshiboken: could not import module 'PySide6.QtNetwork'`
  （源码运行正常，只有打包后才暴露）。
- Addons 整包约 500MB，但本项目只需 4 个文件（约 400KB）。
  离线环境可只解压到 `site-packages/PySide6/`：
  `Qt6WebSockets.dll`、`QtWebSockets.pyd`、`QtWebSockets.pyi`、
  `metatypes/qt6websockets_metatypes.json`。

**Q：后台密码忘了？**
打开 `<用户目录>/env.py` 查看 `web.auth_pass`，或直接改成新密码后重启。
删掉整个 `env.py` 再启动，程序会自动重新生成一份带随机密码的配置。

**Q：想要长时间挂机？**
用桌面端最小化到托盘（关窗即最小化，不退出），或
