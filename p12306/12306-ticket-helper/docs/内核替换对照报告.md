## 〇、一句话结论

**能换的不是「整个内核」，而是「候补链路的请求体构造」这一层 —— 而且恰恰是这一层有 5 处分歧，
全部集中在从未在真机跑通过的候补路径上。** 传输层（风控识别 / 会话 / 限速）**不能**换成上游的，
上游根本没有这些能力，换了会必坏。所以本轮做的是：**把可换的那层抽成可切换的门面，
默认仍走自研实现，用一条命令就能灰度切到上游实现并当场看见差异。**

## 二、能换什么：逐接口的请求体对照（本轮真正的产出）

### 2.1 一处细节：链路顺序与「成功率的返回值」上游是怎么用的

上游的链路（`inter/` 逐文件读出来的调用关系）：

```
ChechFace → GetSuccessRate → SubmitOrderRequest → PassengerInitApi → ConfirmHB → QueryOrderWaitTime
```

关键在上游 `GetSuccessRate.sendSuccessRate()` 这两行：

```python
flag = successRateRsp.get("data", {}).get("flag")[0]
train_no = flag.get("train_no")                       # ← ② 的返回值里取 train_no
...
submitOrderRequestByAfterNate(self.session, self.secretList, train_no)
```

也就是说：**上游的 `hbTrain` 用的 `train_no` 是 ② `getSuccessRate` 返回的官方内部号**，
然后一路传给 `PassengerInitApi` → `ConfirmHB`。

我们的实现（`inter/api.py::confirm_hb`）：

```python
rate = self.get_hb_success_rate(ticket, seat_label)     # ← 拿到了整个 flag[0]
...
train_no = ticket.train_no or ticket.train_code          # ← 却没用它，改用本地字段推算
...
"hbTrain": f"{train_no},{SEAT_CODE.get(seat_label, seat_label)}#",
```

**我们已经把权威值取到手了，然后把它扔掉、改用本地推算值。**
`ticket.train_code` 是明文车次（如 `G1772`），而官方要的是内部号
（上游 docstring 里写的是 `hbTrain  5l000G177230,O#`）。本地字段恰好也对时看不出问题，
**不对时就只能看到一句「系统忙，请稍后重试」** —— 参数无效的标准伪装。

> **F1｜`hbTrain` 的 `train_no` 来源分歧**
> 上游：`getSuccessRate.data.flag[0].train_no`（权威，我们已有）
> 我们：`ticket.train_no or ticket.train_code`（本地推算）
> 性质：**信息我们已经拿到却丢弃** → 可直接修，且上游是外部依据。
> 现状：**【假设·待真机验证】** 本地字段是否等于官方内部号，尚无真机证据。

### 2.2 第二处：`passengerInitApi` 的返回值，上游在用，我们完全丢弃

上游 `PassengerInitApi.sendPassengerInitApi()`：

```python
data = passengerInitApiRsp.get("data", {})
jzdhDateE = data.get("jzdhDateE")
jzdhHourE = data.get("jzdhHourE").replace(":", "#")
jzdhDate = f"{jzdhDateE}#{jzdhHourE}"                       # ← 形如 2019-08-31#19#00
...
confirm = confirmHB(self.secretList, self.session, self.tickerNo, jzdhDate)
```

上游 `ConfirmHB.data_apr()`：

```python
data["jzParam"] = self.jzdhDate                              # ← 真值
```

我们 `inter/api.py::init_hb_passengers()`：

```python
def init_hb_passengers(self) -> None:
    """..."""
    self._hb_post(urls.HB_PASSENGER_INIT, {"_json_att": ""}, tolerant=True)   # ← 返回值直接扔掉
```

然后 `confirm_hb` 里：

```python
"jzParam": "",
```

> **F2｜`jzParam` 分歧**
> 上游：`f"{jzdhDateE}#{jzdhHourE}"`（从 ④ 的响应里取）
> 我们：`""`（空串）
> 性质：**同一个「调了接口但不读返回值」的问题**。发空串能不能过、官方会不会给默认值，
> 我们**没有任何证据**。
> 现状：**【假设·待真机验证】**。
> 可修部分：把 ④ 的响应**捕获并落日志**（不改行为）—— 这样下一次真机跑就能直接看到
> 官方到底返不返 `jzdhDateE/jzdhHourE`，再由证据决定填什么。这一步无论如何都该做。

### 2.3 第三处：`passengerInfo` 的段数，我们比上游多一段

上游 `inter/GetPassengerDTOs.py`（候补分支，逐字）：

```python
tickers.append(f"1#{user['passenger_name']}#1#{user['passenger_id_no']}#{user['allEncStr']};")
```

按 `#` 切分 = **5 段**：`票种 / 姓名 / 证件类型 / 证件号 / allEncStr`。
上游自己的 docstring 也就是 5 段：`1#XXXX#1#***************77X#bf6ae40d…957;`

我们 `inter/api.py::build_hb_passenger_info` 拼的是 **6 段**，
末尾多一个「是否 60 岁以上」：

```
<票种>#<姓名>#<证件类型>#<证件号>#<allEncStr>#<是否60岁 0/1>;
```

> **F3｜`passengerInfo` 段数分歧（5 vs 6）**
> 性质：**两边的依据都不硬**。上游是 2019–2021 的代码，我们是自己写的；
> 谁对谁错**离线无法判定**。
> 现状：**【假设·待真机验证】**，**不得单方面改**。

### 2.4 这里必须点出一个元问题：我们的 mock 是自己出的卷子

`mock_server/server.py` 的 `confirmHB`：

```python
chunks = [c for c in info.split(";") if c.strip()]
if not chunks or any(len(c.split("#")) != 6 for c in chunks):
    return jsonify({"status": True, "data": {"flag": False, "msg": "乘车人信息格式不正确"}})
```

**mock 把「6 段」写成了硬校验 —— 而 mock 是照我们自己的实现写的。**
于是离线测试永远是绿的，它证明的只是「我和我自己一致」。

这与 2026-09-29 那次 405 是**同一个机制**：
> 当时 mock 按直觉把 `confirmHB` 挂在了 `/otn/confirmPassenger/` 下，
> 和真机实现同一个直觉 → 离线全绿，真机 405。

同一机制的第二次出现，只是这次还没被真机揭穿。
**这是本轮最该记住的一件事：mock 只能证明自洽，不能证明正确。**

### 2.5 第四处：我们比上游多发了 6 个字段

上游 `ConfirmHB.data_apr()` 的完整请求体 —— 只有 4 个键：

```python
data["passengerInfo"] = self.passengerTicketStrByAfterLate
data["jzParam"] = self.jzdhDate
data["hbTrain"] = f"{self.tickerNo},{ticker}#"
data["lkParam"] = ""
```

我们发了 10 个：

```python
"passengerInfo", "jzParam", "hbTrain", "lkParam",
"sessionId": "", "sig": "", "scene": "nc_login", "encryptedData": "",
"if_receive_wseat", "realize_limit_time_diff",
```

> **F4｜多出的 6 个字段**
> `sessionId` / `sig` / `scene` / `encryptedData`：**上游全仓库 0 处**。
> 其中 `scene = "nc_login"` 尤其可疑 —— 上游对阿里风控（nc.js）是**完全零实现**的
> （见第三节），这四个字段更像是从别处抄来/推测的。
> `if_receive_wseat` / `realize_limit_time_diff`：本项目历史上作为参数化配置引入。
> 现状：**【假设·待真机验证】**：多发字段是被忽略、还是被判参数错误，无证据。

### 2.6 小结：路径对，请求体有 5 处悬空

| 编号 | 分歧 | 上游有依据 | 我们有依据 | 能否离线判定 |
|---|---|---|---|---|
| F1 | `hbTrain` 的 `train_no` 来源 | ✅ 权威 | ⚠️ 本地推算 | 不能 |
| F2 | `jzParam` 空 vs 日期 | ✅ 权威 | ❌ 无 | 不能 |
| F3 | `passengerInfo` 5 段 vs 6 段 | ✅ 5 段 | ⚠️ 6 段（mock 自我确认） | 不能 |
| F4 | 多发的 6 个字段 | — 上游没有 | ❌ 无 | 不能 |
| F5 | 第 ⑤ 步 `getQueueNum` 无出处 | ❌ 上游没有 | ✅ 真机实测 | 已登记，可接受 |

**五处全部落在候补链路 —— 也就是唯一从未真机跑通的那条链路。**
这不是巧合：有真机反馈的地方（登录、余票、订单），分歧早就被真机逼掉了。

## 三、换了会坏什么：上游没有的能力清单

如果要「把内核换成上游」，先看清上游缺什么。以下全部是 grep 计数，不是评价：

| 能力 | 上游命中数 | 本项目对应实现 | 换了会怎样 |
|---|---|---|---|
| **WAF/风控 HTML 错误页识别** | **0** | `TicketApi._reject_html` + `RiskControlError` | 官方回一张 HTML 页时，上游按「业务响应」解析 → **静默失败或崩在类型上**。这正是本项目排障最难的一条（「返回 HTML 而不是 JSON = 请求不被接受」） |
| **阿里 nc.js / slide 风控** | **0** | 已知边界，不自行计算、走人工兜底 | 上游打码体系（`verify/`）已不适用于 2026 版登录页 |
| **扫码登录 `checkqr`** | **0** | `account/qrlogin.py`（21 秒换码、无密码登录） | 上游只有密码登录。而真机 **密码登录已走不通，扫码是唯一可靠路径** → 换上去等于不能登录 |
| **会话持久化到磁盘** | **0** | `account/session.py::SessionStore`（加密 Cookie、3 天、恢复后真调 `checkUser` 验活） | 每次重启都要重新登录 |
| **预售期 14 天判断** | **0** | `train_date.py`（区分「真风控」与「日期不可售」） | 同一张 HTML 页的两种含义分不开 → 「换个日期」被伪装成「被限流」 |
| Python 运行环境 | TF1.14 / keras2.2.4 / sklearn / opencv | Python 3.13 + Flask 3 + PySide6 6.11 | **装不上**（见 `reference/VENDOR.md`） |

**所以「整体换内核」不是一个可选项**：换上去会同时失去登录、风控识别与会话保持。
这不是「上游不好」，而是**上游停在 2021-01，而 12306 已经变了**。

想在运行时真的 import 上游 `inter/`，它的依赖闭包是：

## 四、结论：换成什么、怎么换

### 4.1 分层的换法（本轮落地）

| 层 | 上游有依据吗 | 决定 | 理由 |
|---|---|---|---|
| **候补请求体构造**（`chechFace`/`getSuccessRate`/`submitOrderRequest`/`confirmHB`/`passengerInfo`） | ✅ 有 | **抽成可切换门面，提供 `upstream` 实现** | 这是 F1–F4 所在层，也正好是唯一「上游比我们知道得多」的层 |
| **传输层**（风控识别、限速、重试、Referer、会话） | ❌ 没有 | **不换，保持自研** | 换了会同时失去登录与风控识别（第三节） |
| **业务层**（抢票引擎、候补引擎、订单、通知、UI） | ❌ 没有 | **不换** | 上游是单文件脚本，无此分层 |
| **打码** | ⚠️ 有但不可用 | **继续 ddddocr** | 上游模型无 LICENSE + TF1.14（`reference/VENDOR.md` 已记录，不再重复讨论） |

### 4.2 灰度开关（可一键回退）

```python
# env.py / 环境变量
kernel.standby_payload = "self"      # 默认 self = 现有行为，一字不变
                                     # 可选 "upstream" = 上游写法
```

**默认必须是 `self`**：本轮不改变任何现有行为。切换只影响请求体构造，
传输层与业务层不走这条开关 —— 所以切错了最多是「请求体不一样」，
不会连登录一起出问题。

### 4.3 验收标准（外部信号，不由我定义）

按本项目的验收纪律，这五处分歧**不能靠测试通过来判定**，只能靠外部信号：

| 级别 | 外部信号 | 谁来跑 |
|---|---|---|
| **A（可离线，本轮做）** | 切换开关后，两条实现产出的**请求体差异表**可打印、可断言，且差异**只有**文档里写明的那几项 | 本轮的 `scripts/kernel_diff.py` + 契约测试 |
| **B（需真机，一次）** | ④ `passengerInitApi` 的真实响应体（是否含 `jzdhDateE`/`jzdhHourE`）、② `getSuccessRate` 的 `train_no` 与本地 `ticket.train_no` 是否相等 | **使用者本人**跑一次诊断脚本（低频、只读优先） |
| **C（需真机，最终）** | 候补单能否真的提交成功 | 使用者本人，按需 |

**B 级信号是 F1–F4 的唯一裁判。** 在拿到 B 之前，把任何一条「改成上游写法」
当成「修好了」都是自欺 —— 这与当年 405 的成因是同一个。

## 八、P0–P4 执行状态（2026-09-30 更新）

**每一期都按同一套路交付**：规格（数据）+ 共享判定/组装纯函数 + 两套后端各给一份数据；
**差分表**（带预期差异断言）+ **契约测试**（撤掉实现必须变红）+ **一键回退开关**。

| 期 | 域 | 默认 | 切到上游意味着 | 证据 |
|---|---|---|---|---|
| P0 | vendor 整包 + 合规 + `registry` 骨架 | — | — | `--check` 退出码 0；sha256 逐文件 |
| P1 | `captcha`（打码） | **pjialin** | 用上游的「渠道 + 格子编号换算」；`self` 是自研链 | V5 生成物 + V4 `kernel_diff`；变异 6/6 |
| P2 | `station` / `query_route` / `login_check` / `qr_check` | self | 站点表是 2021 快照（**11 个错电报码**，永不切）；登录态判活字段互不认得；扫码多带设备指纹 | V5 三张基线 + V4 三张差分；变异 6/6 · 4/4 · 6/6 |
| P3 | `order_submit`（下单六步）/ `slide`（滑块） | self / **pjialin** | 六步**都不带 Referer**（很可能被 WAF 拒）+ 两处取值来源不同 + `cancel_flag` 类型不同；滑块上游有程序化解法 | V5 `test_order_baseline`(42) + V4 `order_diff`；变异 下单 11/11 · 滑块 9/9 |
| P4 | `pacing`（限速）/ `heartbeat`（心跳） | self | 查询 0.5~1.0s（比本项目密一倍以上）+ 超时 5s；心跳 120s **无地板** | V5 `test_pacing_baseline`(9) + V4 `pacing_diff`；变异 节奏 5/5 · 心跳 5/5 |

**没有换默认值的域（`self`）与原因**（都是「换默认值 = 换行为」，要真机证据）：

| 域 | 不换的原因 |
|---|---|
| `station` | 上游 11 个电报码与官方现状不同 → 「查不到车」，**极难联想** |
| `query_route` | 更省请求，但需要真机确认上游那条路径仍然可用 |
| `login_check` | 判活字段互不认得（换了端点必须连响应结构一起换）；上游那条**不带 Referer** |
| `qr_check` | 上游多带设备指纹属「双保险」；本项目不带也真机跑通了 |
| `order_submit` | 上游六步都不带 Referer（很可能被 WAF 拒）+ 3 处参数差异 |
| `pacing` | 上游那套**更激进**（请求密一倍以上）→ 更容易被限流 |
| `heartbeat` | 上游**没有地板** → 切过去等于去掉一层防护 |

**切到上游的两个域**：`captcha`（需求方明确要求打码必须用上游；未配置服务地址时
`available()=False`，自动让识别链继续往下走，不会打挂功能）与 `slide`
（本项目**根本没有**程序化解法 —— 「上游有的禁止自己实现」最直白的一例；
它 `available()` 为假时不报错、只留 WARNING 照旧走）。

⚠️ **仍未解决的是「谁对」**：上述全部是 V2–V5 证据，**没有一条来自真机**。
真机判据见 `docs/缺陷回流台账.md` 与 `verification_manifest.json` 里 5 条「未验证声明」。
