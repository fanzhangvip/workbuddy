| 位置 | 状态 |
|---|---|

| 第 1 步 `submitOrderRequest` | ✅ 真机已验证（修 #48 之后） |
| 第 2 步 `initDc`（token） | ✅ 真机已验证 |
| 第 3 步 下单验证码 | 🔴 **本次修**（#60：端点路径与 `rand` 都写错了，图片**永远拿不到**） |
| 第 4 步 `checkOrderInfo` | ⚠️ 真机曾被拒「余票不足！」→ 根因两条已修（#50 选车 / #51 参数），**待真机复验** |
| 第 5 步 `getQueueCount` | 🔴 **本次修**（#61：`leftTicket` 取错了字段） |

## 2. 七步主链

| 步 | 官方接口（`inter/urls.py`） | 方法 / Referer | 这一步的关键参数 | 成功长什么样 |
|---|---|---|---|---|
| 1 | `/otn/leftTicket/submitOrderRequest` | POST / 余票页 | `secretStr` `train_date` `back_train_date` `tour_flag=dc` | `{"status":true,"data":"N"}` = **锁票成功** |
| 2 | `/otn/confirmPassenger/initDc` | POST / 自身 | `_json_att` | HTML 里含 `globalRepeatSubmitToken` |
| 3 | `/otn/passcodeNew/getPassCodeNew` | GET / initDc | `module=passenger` `rand=randp` | **返回图片字节流** |
| 4 | `/otn/confirmPassenger/checkOrderInfo` | POST / initDc | `passengerTicketStr` `oldPassengerStr` `randCode` `REPEAT_SUBMIT_TOKEN` | `{"status":true,"data":{"submitStatus":true}}` |
| 5 | `/otn/confirmPassenger/getQueueCount` | POST / initDc | `leftTicket` `train_location` `seatType` `train_no` | `data.count` = 前方排队人数 |
| 6 | `/otn/confirmPassenger/confirmSingleForQueue` | POST / initDc | **同第 4 步** + `key_check_isChange` `leftTicketStr` `train_location` | `data.submitStatus=true` **（这一步才真的建单）** |
| 7 | `/otn/confirmPassenger/queryOrderWaitTime` | GET / initDc | `random` `tourFlag=dc` | `data.orderId` 出现 = 出票，去官方支付 |

> ★ **第 1 步成功 ≠ 有订单。** 它只是「锁票」（占一个位置），会自行过期。
> 真正产生待支付订单的是第 6 步。本项目曾把日志里的「锁票成功」当成
> 「已建单」去提醒使用者，是错的（已更正）。

## 3. 「取值来源」——本链路最容易错的一个维度

路径与返回值两边常常一样，**差别只在「同一个字段名，值从哪来」**。

| 参数 | 正确来源 | 曾经的错法（及其症状） |
|---|---|---|
| `secretStr` | 余票行下标 0，**必须是 URL 解码后的** | 原样发回 → `requests` 把 `%` 再编码成 `%25` → 官方只回「提交失败，请重试...」（**#48**） |
| `passengerTicketStr` | 每人 **9 段**，第 9 段 = 乘车人的 `allEncStr` | 只发 8 段 → `checkOrderInfo` 回含糊的**「余票不足！」**（**#51**） |
| `oldPassengerStr` | 每人 `姓名,证件类型,证件号,票种_`，拼完 `rstrip("_")` 再补 **`'__ _ _'`** | 少那 4 个字符 → 同上（**#51**） |
| `train_location` | 余票行下标 16 | —— |
| `leftTicket` / `leftTicketStr` | **`yp_info`，余票行下标 12** | ✗ 用了下标 15（`seat_types`，值是 `O9M3` 这种席别列表）→ 真机必被拒（**#61**，本次修） |
| `key_check_isChange` | `initDc` 页面的 `ticketInfoForPassengerForm` | ✗ 解析要求结尾分号且失败静默 → 页面上没有时会**静默发空串**（**#49**，本次加固） |
| `REPEAT_SUBMIT_TOKEN` | `initDc` 页面的 `globalRepeatSubmitToken` | —— |
| `randCode` | 第 3 步拿到的图 → 识别 → 坐标串 | ✗ 端点写成 `/otn/confirmPassenger/getPassCodeNew` + `rand=sjrand` → 永远只回 HTML 错误页（**#60**，本次修） |

**为什么这些错能一路混到真机**：mock 的对应端点以前**照着我们自己的形状实现**
（不校验或返回同样的错值）。这是同一个机制的多次复发 ——
「mock 按我们出的卷子改卷，只能证明我和我自己一致」。

## 4. 本次修了哪四处（都在同一根因族里）

| 回流 | 症状（真机/离线） | 根因 | 修法 | 判据落点 |
|---|---|---|---|---|
| **#60** | 下单验证码图片**永远**显示不出来，每次都退人工兜底 | 端点写成 `/otn/confirmPassenger/getPassCodeNew`（上游没有这条路径）+ `rand=sjrand`；上游是 `/otn/passcodeNew/getPassCodeNew?module=passenger&rand=randp` | 路径与 `rand` 都改对（字面量只留在 `urls.py`）；mock 把**错路径**如实复现成 HTML 错误页 | `test_order_chain_fixes.py`（线缆：路径+`rand`+真拿到 PNG） |
| **#61a** | 第 5 / 6 步的 `leftTicket(Str)` 是**席别列表** | 兜底用了 `seat_types_raw`（下标 15）而不是 `yp_info`（下标 12） | `TrainTicket` 增加 `yp_info`，两处兜底改过来；mock 两步都加校验 | `test_order_chain_fixes.py` + `test_order_params_on_the_wire.py` |
| **#61b** | 订单**已撤销**却被报成「排队超时，请到未完成订单查看」 | 只认 `queryOrderWaitTimeStatus=false`，不认 `waitTime=-2/-3` | 按上游判读把 `-2/-3` 判为失败；mock 新增 `queue_cancelled` 场景复现 | `test_order_chain_fixes.py`（走到 `OrderService`，断言 `retryable=False`） |
| **#49 加固** | `ticketInfoForPassengerForm` 取不到，且**不知道为什么** | 正则要求结尾分号 + 失败静默 | 改成多形态匹配（分号/无分号/`JSON.parse`）+ 整页抢救 + **匹配不到就 WARNING 说清后果** | `test_order_chain_fixes.py`（形状参数化 + caplog 断言） |

已在此前修完、这次一并复验的：**#48**（`secretStr` 解码）、**#51**（下单参数 9 段 + 后缀）、

## 5. 唯一剩下的未知量：`key_check_isChange`

第 6 步要它。它的来源只有一个：`initDc` 页面里的 `ticketInfoForPassengerForm`。
而台账 #49 记着「真机那个页面里根本没有这个词」——**但那条结论的证据其实不足**：
当时只证明了「我们的解析没匹配到」，而「页面里真没有」与「我们没匹配上」
在日志里**完全同形**。

三种可能，处置完全不同：

| 可能 | 现象 | 处置 |
|---|---|---|
| A. 页面里真有，只是写法变了 | 加固后的多形态匹配能拿到 | ✅ 已解决 |
| B. 页面里真没有 | 第 6 步只能发空串 | 需要真机试；若被拒，得找替代来源 |
| C. 现代 12306 已不需要它 | 发空串也能过第 6 步 | ✅ 无需处置 |

**不再猜了**：`scripts/diagnose_order.py` 现在会把 `initDc` 页面**存盘**到
`~/.ticket-helper/export/initdc-*.html`，并逐个报告 7 个候选关键字的存在性。
跑一次 `--until initdc`（**不建单**）就有答案。

## 6. 真机验收怎么做（按危险程度递增）

```bash
# ① 最安全：锁票 + 拿 token + 报告页面关键字（不产生待支付订单）
python scripts/diagnose_order.py --restore --until initdc

# ② 再往前一步：验第 4 步的参数（仍不建单）
python scripts/diagnose_order.py --restore --until check

# ③ 真下单（会建待支付订单，跑完必须去官方 App 支付或取消）
python scripts/diagnose_order.py --restore --until queue --yes-create-order
```

判据写在脚本输出里（每步一句「判据[通过/不通过]」）。
**不要在任务正在抢票时跑** —— 请求叠成突发会把短暂限流变成持续限流，
那时所有结论都不可信。

## 7. 使用上的实话

1. **打包版的下单验证码仍需要人工录入。** 识别链是
   「外部打码服务 → 本地模型 → **人工兜底**」，而 `ddddocr` 刻意不进包
   （对 12306 的点击型验证码实测命中率很低，且要多 200MB）。
   `free` 模式的本机打码服务要用源码目录的 venv 起：
   `python -m ticket_helper.verify.captcha_server`。
   #60 修好之后，**图片能正常显示、文案说的是「下单」不是「登录」**，
   人工这条路是通的。
2. **本工具不代扣款。** 第 7 步拿到 `orderId` 只表示「已出票待支付」，
   支付或取消都由你本人在 12306 官方 App/网站完成。
3. **第 2 步会锁票、第 6 步才建单。** 前者会自动过期，后者需要你去处理。
4. **机器上装了全局代理（`HTTP_PROXY`）也没关系了。** 回环地址（本机 mock 服务、
   桌面端的本地后端 `127.0.0.1:8008`）现在**显式直连**，不会再被系统代理劫走
   （之前的症状是 `ProxyError: Cannot connect to proxy` —— 完全看不出是系统代理干的）。
   显式配置的代理（`proxy_provider`）仍然优先，因为那是使用者的明确意图。

**取值来源修正**（本轮最重要的教训）：
- `leftTicket(Str)` 权威来源 = **initDc 页面下发的 `leftTicketStr`**（加密长串），
  与余票行的 `yp_info` **不是一个值**；`yp_info` 只是页面没下发时的兜底。
- `getQueueCount.train_date` = 官方浏览器同款 JS 日期串
  （`Tue Oct 13 2026 00:00:00 GMT+0800 (China Standard Time)`）。
- 同名字段、不同来源 —— 本链路第 5 个「取值来源」族缺陷。
