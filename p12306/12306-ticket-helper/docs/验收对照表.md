### AC-07 补充：人证核验改成「四态」，不再用姓名猜（2026-09-28 真机踩出来的）

**真机现象**：扫码登录成功后账号 `樊章` 显示「未核验」，但它其实是实名的。

**根因**：旧实现对没有明确核验字段的响应，用 ``user_name != self.username`` 去猜
「返回了真实姓名就说明已实名」。而扫码登录时官方 `uamauthclient` 返回的
`username` **本身就是真实姓名**，于是 `樊章 != 樊章` 为 False → 已实名账号被判成「未核验」。

**为什么这是有害的**：显示「未核验」会让人以为账号被 12306 限制了（未核验会被候补拦住），
把一个不存在的问题变成了用户要处理的问题。

**修法**：只在**拿到明确字段**时才置位 `is_checked`，并新增 `verify_known` 表示
「本次到底判没判出来」。两端展示改为四态：

| 展示 | 条件 | 含义 |
|---|---|---|
| 已核验 | `is_checked` | 拿到字段且通过 |
| 未核验 | `verified_checked` + `verify_known` | 拿到字段且**未通过**（真会被候补拦） |
| 无法判定 | `verified_checked` + `not verify_known` | 接口没给字段，如实说不猜 |
| 未检测 | `not verified_checked` | 还没登录成功，没检测过 |

**原则**：宁可如实说「无法判定」，也不要给一个看起来确切、实际是错的结论。

### AC-07 补充二：候补引擎把「判不出来」当成「未核验」拦掉（2026-09-29 真机实测）

**真机现象**：任务 `test`、账号 `樊章` 反复收到通知
「账号 樊章 未完成人证核验，无法提交候补（请先在 12306 完成核验）」，
而日志里 grep 得到的是 `账号 樊章 未核验，跳过候补`。

**排查**：新增 `scripts/diagnose_verify.py`，用磁盘会话探测真机这两个用户信息接口的**原始响应**：

| 接口 | 结果 |
|---|---|
| `GET /otn/modifyUser/initQueryUserInfoApi` | `data` 键 22 个，`userDTO` 里 40+ 个字段，**没有任何核验字段** |
| `POST /otn/modifyUser/initQueryUserInfoApi` | 同上 |
| `POST /otn/index/initMy12306Api` | `user_status='1'`、`_is_active='Y'`，**也没有核验字段** |

于是在真机上 `verify_known` 恒为 `False`。

**根因**：`StandbyEngine._create_order` 写的是

```python
if not user.is_checked:
    user.detect_verified()
if not user.is_checked:      # ← 把「判不出来」也当成「未核验」拦了
    ...跳过候补
```

界面（两端）已经按四态如实显示「无法判定」，**但引擎只看 `is_checked`** ——
同一个账号在界面上是「无法判定」、在引擎里被当成「未核验」拦掉，
而「未核验」在真机上又必然发生（官方不返回该字段），
所以正常账号会被**永久**挡在候补之外，提示还写着「未完成人证核验」。

**修法**：
- 判定收敛到 `ticket_helper/account/verify.py`，`should_block()` **只有「明确未核验」为真**；
  判不出来 → 放行，让官方去判，官方真拒了再把它翻成人话（`is_unverified_error`）。
- 「怎么核验」写成**可照做的步骤**（12306 App → 我的 → 人证核验 → 人脸识别），
  放进通知正文、桌面端「人证核验怎么做？」弹窗、网页端常驻折叠说明，三处同源。
- 新增 `POST /api/users/<id>/verify/refresh` + 两端「重测核验」按钮 ——
  扫码账号没有密码、`测试登录` 是禁用的，此前**没有任何途径**刷新核验状态。

**教训**：四态只在展示层实现是不够的；**任何消费这个状态的判断逻辑都必须用同一份语义**，
否则「界面说无法判定、后台按未核验处理」这种自相矛盾会一直存在，而且极难归因。

### HB 补充：候补接口族在 `/otn/afterNate/`，不在 `confirmPassenger`（2026-09-29 真机实测）

**现象**：日志反复出现

```
WARNING 任务[test]候补提交失败: 响应不是合法 JSON (HTTP 405)
```

**排查**：`scripts/diagnose_standby.py` 把候选路径的**原始响应**打出来对照：

| 路径 | 真机结果 |
|---|---|
| `POST /otn/confirmPassenger/confirmHB`（我们一直在用的） | **HTTP 405** |
| `POST /otn/afterNate/getQueueNum` | `{"status":true,"data":{"flag":true,…}}` |
| `POST /otn/afterNate/queryQueue` | `{"status":true,"data":{"flag":true,"isAsync":true,"status":2}}` |
| `POST /otn/afterNate/chechFace` | `{"status":true,"data":{"login_flag":true,"face_flag":true,"face_check_code":"12"}}` |
| `POST /otn/afterNate/getSuccessRate` | `{"data":{"flag":[{"level":"1","info":"候补人数较少"}]}}` |

**结论**：候补全流程在 `/otn/afterNate/` 下，且是**七步串行**（见 HB-01）。
原来的实现只有一个「猜出来的」路径，而且缺了 6 步。

**顺带解决了两件事**：

1. **核验的真信号找到了**：`chechFace.face_flag`。真机上 `face_flag=true` ——
   说明该账号**核验是通过的**，之前那条「未完成人证核验」100% 是程序误判。
   用户信息那两个接口永远不返回核验字段，在那里判断注定得不出结论。
2. **`secretStr` 为空的原因**：真机 83 条车次里有 73 条是「列车运行图调整,暂停发售」，
   这些行 `secretStr` 是空的。候补目标因此必须加「当前可网订」这一条过滤，
   否则整条链路会拿着一把空钥匙去跑，最后得到一句「系统忙」。

**mock 也跟着改了**：mock 以前把 `confirmHB` 挂在 `confirmPassenger` 下（按直觉猜的），
于是「路径写错」在离线环境**永远测不出来**。现在 mock 如实回 405，并实现了 `afterNate` 七步 ——
同类错误下次会在离线测试里立刻现形。

### QY 补充：余票查询前必须「逛一次页面」（2026-09-28 真机实测）

**现象**：查询整轮失败，错误为「`/otn/leftTicket/queryO` 返回非 JSON」。

**排查过程（连续两次误判后才定下真因）**：

| 阶段 | 判断 | 对错 |
|---|---|---|
| 1 | 冷启动拦截 → 退避重试一轮 | ❌ |
| 2 | 突发请求被限流 → 别轮换候选路径 | ⚠️ 部分对 |
| 3 | **会话必须先在真机加载过一次页面** | ✅ |

**为什么会误判两次**：对照实验是**分开时段**做的。这类站点的放行状态带「时间窗」——
一旦被某次页面加载打开，之后一段时间内连冷会话也能查通；窗口关了又全部失败。
**隔着几分钟做实验会得出相反结论；必须并排、同一时刻对照。**

决定性对照（同一时刻）：

| 请求 | 结果 | Cookie |
|---|---|---|
| 新会话直接调 `leftTicket/query` | ❌ HTML 错误页 | （空）|
| 同一时刻，先加载一次 `/otn/leftTicket/init` 再调 | ✅ JSON | 有 `JSESSIONID` 等 |
| （窗口打开后）新会话直接调 | ✅ JSON | （空）|

**改动**：

| 位置 | 改动 |
|---|---|
| `inter/urls.py` | 新增 `LEFT_TICKET_INIT = "/otn/leftTicket/init"` |
| `inter/api.py` | 新增 `ensure_session_warm(force=False)`；`query_left_ticket` 改为「预热 → 查 1 条路径 → 被拒则重新热身重试一次 → 仍被拒抛 `RiskControlError`」 |
| 同上 | 被拒时**停止候选路径轮换**（原先要打完 4 条），接入既有风控管道（`report_risk()` 降频 + 退避 + 通知） |
| `mock_server` | 新增 `session_warmed` 与 `/otn/leftTicket/init`；**未热身就查 → 回 HTML 错误页** |
| `tests/test_query.py` | 新增 4 例：预热顺序 / 只热一次 / force 重发 / 被拒时请求数有界（2 次而非 4+） |

**真机结果**：北京南 → 上海虹桥（7 天后）命中 **47 个车次**，其中 **36 个二等座可购**，
余票数字（`6`/`15`/`有`/`无`）解析正确，零错误。

**原则**：`queryZ/queryA/query/queryO` 候选轮换是给「**路径下线**」准备的；
「**请求被拒**」是会话/风控层面的问题，必须按会话级处理，不能靠轮换路径去试。

## 一之二、双击启动缺陷的修复记录（2026-09-28）

**现象**：双击 `TicketHelper.exe` 后黑窗一闪就没了，看起来像"打开就崩溃"。

**根因**：exe 打包为控制台程序，且无参数时的默认行为是「打印帮助文本后退出」。
控制台随进程退出立即关闭，用户完全看不到任何信息。此外还有若干
「看起来像崩溃」的连带问题一并修复：

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | 无参数启动 = 打印帮助后退出 | 双击闪退（本次故障主因） | 无参数改为启动图形界面（`main.cmd_default`） |
| 2 | exe 带控制台，双击会弹黑窗 | 观感差、易被杀软盯上 | 拆成图形版（`console=False`）+ 命令行版（`console=True`），共用依赖目录 |
| 3 | 窗口模式下 `sys.stdout` 为 `None` | 任何 `print` 抛 `AttributeError`，静默退出 | `make_console_safe` 兜底到 `os.devnull` |
| 4 | 异常直接冒到进程外 | 无任何错误信息，无法排查 | 全局异常兜底：崩溃日志（完整堆栈）+ 可读对话框；双击场景暂停等回车 |
| 5 | 端口被占用即启动失败 | 常见（上次后台没退干净），表现为"打不开" | 自动改用下一个可用端口 |
| 6 | 托盘不可用时关窗 → 僵尸进程 | 再双击毫无反应，端口被永久占用 | 无托盘时关窗即真正退出 |
| 7 | 首启凭据在后台生成前读取 | 被要求输入自己都不知道的随机密码 | 后台就绪后重新读取 `env.py` 再自动登录 |
| 8 | 桌面端日志只写 stderr | 窗口模式下日志全丢，崩溃无从查起 | 复用后端日志系统，桌面与后台统一写入 `logs/12306.log` |
| 9 | `get_app_paths()` 缓存忽略环境变化 | 数据可能写到非预期目录 | 缓存时校验解析结果，变化即重建 |

**回归防护**：`tests/test_cli.py` 与 `tests/test_desktop.py` 新增 12 个用例，
覆盖「无参数必须进图形界面」「窗口模式 None 流」「崩溃日志必写」「端口自愈」
「不弹裸堆栈」「托盘缺失即退出」等，防止问题复发。

## 一之三、扫码登录实现记录（AC-08，2026-09-28）

新增能力：用手机 12306 App 扫二维码登录，**无需在本地保存密码**。

### 协议与实现

| 环节 | 官方接口 | 实现位置 |
|---|---|---|
| 申请二维码 | `POST /passport/web/create-qr64`（appid=otn）→ uuid + 裸 base64 图片 | `api.py::create_qr_login` |
| 轮询状态 | `GET /passport/web/checkqr?uuid=` → result_code 0待扫/1已扫/2成功/3过期 | `api.py::check_qr_login` |
| 完成登录 | `passport/web/auth/uamtk` → `otn/uamauthclient` | `api.py::finish_qr_login` |

路径与状态码全部收敛在 `inter/urls.py` 与 `inter/parser.py`，与既有约定一致。

### 真机实测出来的 4 条硬约束（改协议前必读）

这些**全部是拿真实 `kyfw.12306.cn` 做对照实验得到的**，社区文章里的说法有多处不准确。
mock 已按这些行为逐条复现，写错会立刻测挂。

| # | 约束 | 违反后的症状 |
|---|---|---|
| 1 | `checkqr` **必须带 `appid=otn`** | 不报错，稳定返回 `{"result_message":"操作失败","result_code":9}` —— 用户「还没扫就提示失败」 |
| 2 | 二维码 **只有约 21 秒**寿命（非网传 2 分钟） | 用户来不及扫；必须自动换码。实测：1 秒/3 秒轮询、带不带设备指纹，结论一致 |
| 3 | 鉴权接口必须带 **`Origin` + `Referer=/otn/passport?redirect=/otn/login/userLogin`** | 不报 4xx，而是回 **HTML 错误页**（"网络可能存在问题，请您重试一下！"）→ 换票拿不到 `newapptk` → 报「uamtk票据内容为空」 |
| 4 | 扫码与密码流程的收尾顺序不同：扫码用 `GET /otn/login/userLogin`（带跳转）→ `uamtk` → `uamauthclient`；密码用 `POST userLogin` → `uamtk` → `uamauthclient` | 顺序/方法照参考实现来即可，见下方「一次误判的更正」 |

第 3 条是**根因**：之前一直用登录页 Referer，被 12306 的同源校验拦掉。
浏览器里 jQuery 会自动带这些头，所以「浏览器正常、脚本失败」。

**参考实现（权威依据）**：上游 `pjialin/py12306` 的 `user/job.py::auth_uamtk` 就带着这两个头，
`qr_login()` 的顺序是 `GET userLogin` → `uamtk` → `uamauthclient`。
**这个仓库本身就该是排查协议问题的第一参考**，比社区文章可信（我一开始只看了博客，绕了远路）。

#### 一次误判的更正（重要）

我一度写下「扫码流程不能调用 `userLogin`，它会新建 `JSESSIONID` 打断扫码上下文」，
并据此改了代码、mock 与文档。**这个结论是错的。**

原因：那次实验是在**鉴权请求头还没修好**的情况下做的 —— 无论调不调 `userLogin`，
换票接口都只会返回 HTML 错误页，两种原因混在一起，根本无法区分。
修正请求头后做了干净的对照实验：

| 前置动作 | `uamtk` 结果 |
|---|---|
| 不调 `userLogin` | ✅ 正常 JSON |
| 先 `POST userLogin` | ✅ 正常 JSON |
| 先 `GET userLogin` | ✅ 正常 JSON |
| （对照）头不正确 | ❌ HTML 错误页 |

→ 已按参考实现把 `userLogin`（GET 带跳转）放回扫码流程，并**从 mock 里删除了那条错误的破坏性模型**。

**教训：在多个变量都有问题时做实验，得到的结论往往是错的。**
修完一个变量后，必须回头复验先前依赖该变量的结论。

### 关键设计决策

| 决策 | 原因 |
|---|---|
| **非阻塞**：`start()` 只拿二维码，`poll()` 只查一次 | 轮询节奏交给前端定时器，用户关掉弹窗时请求立即停止，不留后台循环继续打接口 |
| **原地采纳临时 User**（`adopt_qr_user`） | 登录态（Cookie/tk）挂在发起扫码的 HttpClient 上；新建 User 会丢会话，表现为「扫码提示成功但账号仍离线」 |
| 账号在**扫码成功后**才创建 | 扫之前根本不知道是谁，无法预先绑定；服务端返回用户名后再建号 |
| 无密码账号用 `password_enc == ""` 表达 | 不改表结构（避免迁移风险）；「有没有密码」这个信息本身就足够决定登录方式 |
| 终态幂等 | 两个标签页同时轮询时不会重复完成登录 |
| 轮询撞风控**不终结会话** | 风控是暂时不通；若直接判失败，用户刚扫完码就被告知失败，会引发重复操作 |
| 空密码不覆盖已有密码 | 同一账号先扫码后补密码时，不能把密码清掉 |

### 排查过程中发现并修复的 3 个真实缺陷

| # | 问题 | 影响 | 修法 |
|---|---|---|---|
| 1 | `/api/users` 硬编码 `has_password: True` | 扫码账号被显示成「密码账号」，还放出必然失败的「测试登录」按钮 | 改为采用 `User.to_dict()` 的真实值 |
| 2 | `POST /users/qr/start` 用 `ttl or 默认值` 解析 | 传 `ttl=0` 被当成「没传」，静默返回 180 秒二维码 | 显式判 `None` |
| 3 | mock 的 `/otn/uamauthclient` 用 `next(iter(set))` 取账号 | 集合无序，多账号演练时返回上一个登录用户，导致集成测试**假失败** | 记录「当前会话账号」并据此返回；顺带提升 mock 保真度 |

另：桌面端槽函数收到 Qt 的 `checked(bool)` 参数时会把 `username_hint` 变成 `False`，

## 一之四、扫码登录线上故障修复（2026-09-28 下午）

**现象**（用户反馈）：点「扫码登录」后**还没扫就被提示「扫码登录失败：操作失败」**；
之后真的去扫码，界面再也没有任何变化，也看不到账号。

### 根因（两个问题叠加）

| # | 问题 | 说明 |
|---|---|---|
| 1 | **`checkqr` 用了 GET** | 官方该接口是 **POST 表单**（`uuid` + `_json_att`）。GET 拿不到正常响应，返回的是错误信封 |
| 2 | **不可识别的响应被判为终态失败** | `parse_qr_check` 把「无法识别的 result_code」直接归为 `failed`。会话当场终结 → 前端停止轮询 → 之后扫码当然不会有任何变化 |

第 2 点是设计过度激进：当时为了避免「协议变更后永远停在等待扫码」，
把未知一律判失败；但对**偶发异常信封**来说代价太大——二维码其实还有效。

### 修复

| 修复 | 位置 |
|---|---|
| `checkqr` 优先 POST，响应不可识别时回退 GET（不同部署/版本有差异） | `api.py::check_qr_login` |
| 新增 `QR_STATE_UNKNOWN`：不可识别 = **非终态**，保留会话继续轮询 | `parser.py`、`qrlogin.py::poll` |
| 连续异常达到 `MAX_UNKNOWN_RESPONSES`（6 次）才判失败，并给出「刷新二维码」的可操作提示 | `qrlogin.py` |
| 服务端原始说明透出到 `status.message` / `extra.server_message`，日志记录原始响应片段便于排查 | `parser.py`、`qrlogin.py` |
| 风控异常必须向上抛（`RiskControlError` 是 `InterError` 子类，被 `except InterError` 吞掉会同时丢失风控信号与真实原因） | `api.py` |
| 桌面/网页端把 `unknown` 显示为「正在重试…」（中性色），并保持轮询 | `qr_dialog.py`、`app.js` |
| mock 支持 POST 轮询与 `qr_bad_response` 场景（如实复现该故障） | `mock_server/server.py` |

### 回归防护

`test_qr_login.py` 新增 6 例专门锁死这个故障模式：
未知状态码必须归 `unknown` 而非 `failed`、异常响应期间会话存活、
异常过后能恢复并成功建号、连续异常才失败且提示可操作、
未知计数在正常响应后归零、POST 失败回退 GET 的请求序列。
`test_desktop.py` 新增 1 例验证对话框在 `unknown` 时继续轮询并能在恢复后成功。

### AC-06 补充：个人中心（账号信息 / 乘车人 / 我的订单）

**入口**：**两端左侧导航的「个人中心」页**（首选，顶部有账号下拉）、
「账号管理」里某行的「详情」（会跳到该页并选中账号）、命令行 `python main.py profile`。

> **为什么要有独立页面**：功能第一版只挂在账号表格最后一列的「详情」小按钮上，
> 使用者扫了一眼左侧导航就认定「功能没做」——连着反馈了两次。
> **功能存在但不被发现，等于不存在。** 所以现在它是一级入口。

**三条链路各自独立**，不要互相替代：

| 用途 | 接口 | 特点 |
|---|---|---|
| 账号信息 | `POST /otn/index/initMy12306Api` | 路径带 `init` 但真机收 POST；核验字段缺失时回退 `initQueryUserInfoApi` |
| 乘车人（查看） | `POST /otn/passengers/query` | 分页；**不需要先锁票**；证件号官方已打码 |
| 乘车人（下单） | `POST /otn/confirmPassenger/getPassengerDTOs` | 需要 `REPEAT_SUBMIT_TOKEN`；返回**完整**证件号 |
| 我的订单 | `POST /otn/queryOrder/queryMyOrder` | `query_where=G` 未出行 / `H` 历史；`queryType` 1 按订票日期 |

**几个必须记住的坑**：

1. **历史订单的结束日期必须是「昨天」**。传今天时官方把今天算进未出行范围，
   结果是「查历史订单什么都查不到」——静默空结果最难排查，已在协议层按死。
2. **不要拿个人中心链路去下单**：`/otn/passengers/query` 的证件号是打码的，
   拿去下单必然失败。抢票链路继续走 `getPassengerDTOs`。
3. **判不出来就说「无法判定」**：`verified` 为 `None` 表示接口没给明确字段，
   界面显示「无法判定」而不是「未核验」（后者会让人以为账号被限制）。
4. **单块失败不影响其它块**：三块数据分散在不同接口，失败概率差别很大。
   `AccountProfileService` 逐块取数、逐块记错，接口始终返回 200 并把原因放在
   各块的 `error` 里 —— 否则「订单查不到」会连账号信息一起变空白。
5. **`where` 非法报 400**（路由层参数校验），而不是 200 + `ok=false`：
   调用方传错参数与「12306 拒绝了查询」必须区分开。

**真机排查工具**：`python scripts/diagnose_profile.py` 会把三个接口的**原始 JSON**
落盘并打印键名，用于确认字段假设或定位「某一列整片空白」是不是官方改字段了。

## 三之三、P5 打包验收（2026-09-30）

这一节与前面几节的**性质不同**：前面是「真机才能判」，这一节是**离线就能自证**，
而且**必须每次都自证** —— 因为「源码能跑」与「产物能跑」在这里不共享任何证据。
上游内核（`vendor/pjialin`）对 PyInstaller 是**不可见的**（垫片把它挂到 sys.path
上，各后端在方法体内才 import），所以它的存在、它的依赖、它的落点，
全都得显式声明并**在产物上验一次**。

### ① 静态对账（秒级，应当进 CI / 每次提交前）

```bash
python scripts/check_packaging.py
```

它把 `TicketHelper.spec` **真的执行一遍**（stub 掉 PyInstaller 注入的
`Analysis`/`PYZ`/`EXE`/`COLLECT`），拿到实际的 `datas`/`hiddenimports`，
再从本项目源码找出「真正会去 import 上游」的入口，对 vendor 做**可达性分析**，
逐个对账。判据：

- `vendor/pjialin` 的包内落点必须**恰好**是 `vendor/pjialin`
  （垫片按 `_MEIPASS/vendor/pjialin` 找；落错地方的表现是**静默回退**，不是报错）；
- 可达路径上用到的第三方包必须有归属（进包，或在豁免清单里写明理由）；
- 豁免清单里的名字必须**真的可达**（否则清单在腐烂）。

### ② 产物自证（每次出包后）

```bash
dist/TicketHelper/TicketHelper-CLI.exe doctor
```

**必须看到这一行**（`doctor` 的第 12 项）：

```
  [√] 上游内核        py12306 已加载（打包产物；可写路径已重定向 6 项）
```

它比「vendor 目录在不在」更强：它真的执行了 `import py12306.config` 与
`import ticket_facts`。三层判据对应三种不同的处置：

| 输出 | 说明 | 怎么办 |
|---|---|---|

### ③ 反向对照（**建议至少做一次**）

把产物里的 `_internal/vendor` **改名**，再跑一次 ②：

### ④ 两种产物形态
