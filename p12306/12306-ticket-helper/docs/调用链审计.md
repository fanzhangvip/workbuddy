# UI 调用链审计（UI 入口 → 后台 → 服务层 → 协议层 → 12306）

> 目的：确认界面上**每一个入口**都真的走到了协议层（会发 HTTP 出网），
> 而不是靠猜、也不是被某处的假数据或 mock 糊弄过去。
>
> 复现方式：`python scripts/audit_callchain.py`（可重复运行，见文末「怎么复现」）。

---

## 一、判定方法（为什么这个结论可信）

### 审计的「锚点」：协议层唯一的出网口

```
HttpClient.request()          ticket_helper/inter/base.py:244
   └── requests.Session.request()   ← 全项目唯一与 12306 通信的实现
```

所有出网请求都必然经过 `HttpClient.request`。审计脚本在这里挂探针，
记录每一次请求的 `(UI 入口标签, method, path, status)`。于是：

- **有记录** → 这条链路真的通到了协议层；
- **无记录** → 要么它是「本来就该在本地完成」的（查库 / 配置 / 日志），
  要么就是真的没走内核。

### 「本地入口」必须显式声明，不搞模糊口径

不给「没出网就默认没问题」这种放过方式。每个不出网的入口都要写明**为什么**它
本来就不该出网（例如「任务配置只落本地 SQLite」）。审计脚本里用 `local=...`
声明，报告里单列一节，并统计「既没出网、也没声明」的**异常项**（本次为 0）。

### 反向证据

| 检查项 | 结果 |
|---|---|
| `AppConfig.api_base` 默认值 | `https://kyfw.12306.cn`（真机） |
| 运行期包（`ticket_helper/`、`desktop_ui/`）内 mock 引用 | **0 处** |
| `mock_server` 的唯一引用点 | `main.py:327` 的 `mock` 子命令（本地起 mock 服务，供离线验证用） |
| 客户端代码是否被替换 | **否** —— 审计只改 `api_base`（服务端地址），`HttpClient` / `TicketApi` / 服务层 / 两个 UI 一行未动 |

## 二、架构分层与「唯一入口」

```
网页端 app.js ─┐
桌面端 ApiClient ─┼─→ 本地后台 HTTP/WS (127.0.0.1:8008) ─→ web/api.py 路由
CLI main.py ─────┘                                              │
                                                                ▼
                                                    AppContext（依赖装配中心）
                                                                │
                ┌───────────────┬───────────────┬───────────────┤
                ▼               ▼               ▼               ▼
        AccountManager   AccountProfile   Query/TrainOptions  GrabEngine
        QrLoginSession      Service           Service        StandbyEngine
                └───────────────┴───────────────┴───────────────┘
                                        │
                                        ▼
                                  TicketApi（协议语义）   inter/api.py
                                        │
                             ┌──────────┴──────────┐
                             ▼                     ▼
                        urls.py（路径）     HttpClient（会话/重试/风控）
```

两条纪律（已落实，也是「不会猜」的原因）：

1. **桌面端不直连引擎**：`desktop_ui/api_client.py` 全部走本地后台 HTTP，
   与网页端**同一套接口**（`desktop_ui/api_client.py:1-11`）。所以两端不可能分叉。
2. **12306 的路径只出现在 `inter/urls.py`，字段下标只出现在 `inter/parser.py`**。
   业务层不拼 URL。

## 四、本次审计发现的问题

### 4.1 已修：`standby`（界面写着「仅候补」）实际会下直购单 ⚠️ 行为错误

- **现象**：`strategy="standby"` 时，`GrabEngine._main_loop` 仍无条件进入直购捡漏循环，
  只要有余票就会真的下直购单。
- **根因**：全项目只有**一处**读 `strategy`（`grab/engine.py:246`），
  且把 `"standby"` 与 `"dual"` 当成完全相同 —— 两者行为零差别。
  而两端 UI 的文案分别是 `standby · 仅候补` 与 `dual · 候补 + 捡漏双轨`
  （`desktop_ui/pages/tasks.py:51-52`、`web/static/index.html:355-356`）。
- **影响**：选「仅候补」的人往往正是不想产生直购订单（例如怕同一趟车重复占票），
  结果却真的下了单。这不是文案问题。
- **修复**：`grab/engine.py` 新增 `DIRECT_PURCHASE_STRATEGIES = ("direct", "dual")`
  与 `_run_standby_only()`：`standby` 只跑候补轨，并把候补轨终态同步回任务状态；
  配置成仅候补却没有候补轨时**明确报错**（不静默空转）。
- **回归测试**：`tests/test_grab.py::test_standby_strategy_never_enters_direct_loop`、
  `::test_standby_strategy_skips_direct_even_when_tickets_are_available`、
  `::test_dual_strategy_still_places_direct_order`、
  `::test_direct_strategy_does_not_start_standby_track`、
  `::test_standby_only_without_standby_engine_reports_error`。

### 4.2 已修：mock 把 `queue_fail` 归进「无票可候补」组，直购排队测试形同虚设

- `mock_server/server.py` 的 `default_tickets` 把 `queue_fail` / `queue_timeout`
  与候补场景合并，返回的是「无票、只能候补」的车次。
- 后果：直购路径连候选都选不出来，**永远走不到排队那一步**，
  `test_engine_switches_candidate_on_queue_failure` 以 `candidates_seen=0`
  这种与主题完全无关的方式失败（红着）。
- 修复：`queue_fail` / `queue_timeout` 描述的是**直购排队阶段**失败，
  必须给**可购**车次；已从候补组移出。

### 4.3 已修：候补端到端用例的断言已过时（误导性失败）

- `test_scenario_3_dual_track` 断言 `standby_engine.hb_order_id` 非空，
  但实现已明确「官方不再返回候补单号，不造假单号」（`TicketApi.confirm_hb` 注释）。
- 它红的原因与候补链路**毫无关系**，属于典型的误导性失败。
- 修复：改判 `status` 进入 `QUEUING`，并要求 `queue.status == 1`
  （即候补单生效必须有**官方排队结论**作依据）。

### 4.4 仍未真机核对（已知，保持诚实标注）

| 项 | 现状 | 需要什么 |
|---|---|---|
| `inter/parser.py` 余票 `result` 的 34 号位解读 | 仅 `_is_remain_text()` 挡掉了「席别编码串」误读，**字段含义未真机核对** | 一次真机查询的原始 `result` 比对 |
| `TicketApi.cancel_hb`（取消候补） | 路径 `CANCEL_HB` **真机未验证**，调用处已按「容忍失败」处理 | 真机验证取消入口 |
| 个人中心三个接口的**字段名** | 已按真机探针（未登录行为）与文档实现，**登录后字段名未逐项核对** | `python scripts/diagnose_profile.py` 落盘的原始 JSON |
| 登录验证码 | `getPassCodeNew` 可达但缺设备指纹时回「系统忙」→ **密码登录在真机不可用**，扫码是唯一可靠路径 | 无（已知结论） |

## 五、怎么复现

```bash
python scripts/audit_callchain.py            # 全部入口（约 1 分钟）
python scripts/audit_callchain.py --keep-home  # 保留临时数据目录，便于排查
```

脚本会：

1. 起本地 mock-12306，并在 `HttpClient.request` 挂探针；
2. 建账号 + 真登录，然后用 **Flask test client** 逐个驱动 UI 入口
   （桌面端与网页端打的就是这套接口）；
3. 打印三节报告：① 已证实打到协议层（含实测 12306 路径）
   ② 本地入口及其理由 ③ 异常项（应为 0）；
4. 打印反向证据（默认站点、运行期 mock 引用数）。

## 六、结论

- **18 个 UI 入口实测打到协议层**（共 68 次出网请求被探针记录），
  覆盖登录、扫码、个人中心、任务配置、直购全链路、候补全链路。
- **27 个本地入口**均有明确的本地数据源理由（SQLite / 配置 / 日志 / 内存状态）。
- **异常项 0 个**：没有任何入口是「既不出去、又说不清为什么」。
- 运行期**不含任何 mock 引用**，默认站点为真机 `https://kyfw.12306.cn`。
- 审计过程中发现并修复了 1 个**会真下单的行为错误**（`standby` 语义）
  和 2 个**让测试给出误导信号的缺陷**（mock 保真度、过时断言）。
- 全量测试 **499 项通过 / 0 失败**。
