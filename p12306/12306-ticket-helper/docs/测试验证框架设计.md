# 测试验证框架设计 · 闭环（Verification Framework v1）

> 目标：**约束并保证当前代码功能的正确性** —— 注意是「正确性」，不是「测试通过率」。
> 本文是设计，不含实现。落地分期见 §7。
> 依据：`docs/` 下既有方案 + 本项目两次真实事故 + 用户既定的「验收契约」纪律。

---

## 〇、为什么不能直接说「测试都过了」

本项目**两次**被同一个机制咬过，必须先写下来，否则框架会退化成仪式：

| 事故 | 表面现象 | 真实原因 |
|---|---|---|
| **405**（2026-09-29） | 候补提交一直失败，日志只有一句「响应不是合法 JSON (HTTP 405)」 | 候补路径**整族写错**（写在 `confirmPassenger/` 下）；`mock_server` 照**同一个错误直觉**实现 → **离线全绿** |
| **6 段**（2026-09-29 发现） | 离线测试断言「每乘客 6 段」，一直绿 | 那个 6 段是**照我们自己的实现**写的；上游是 5 段 → **mock 是我们自己出的卷子** |

⇒ **结论（框架地基）**：本地测试只能证明「代码与自己的假设一致」。
**要证明「正确」，必须有代码之外的东西当锚点**：官方真实行为、上游源码、人类定义的状态机。

因此框架的核心不是"更多测试"，而是**给每条正确性声明标注它靠什么证据**，
并**机器化地拒绝弱证据**。

## 一、框架总览

```
                     ┌──────────────────────────────────────────┐
                     │  证据强度递增 ↑    （越往下越"贵"、越可信）  │
                     └──────────────────────────────────────────┘

  V0  静态纪律门       分层依赖方向 / 单一真源 / 无 skip / 无弱断言 / 溯源合规
      ────────────────────────────────────────────────────────────────
  V1  冻结回归        单元 + 集成。**只证明自洽**，不作为正确性依据
      ────────────────────────────────────────────────────────────────
  V2  契约测试        命名一次全局引用 / 状态机终态不可转出 / 注释即测试
      ────────────────────────────────────────────────────────────────
  V3  变异检验        **撤掉实现必须变红** —— 让 V1/V2 可信的唯一手段
      ────────────────────────────────────────────────────────────────
  V4  差分验证        双实现对照（self / pjialin / testerSunshine）逐字段比对
      ────────────────────────────────────────────────────────────────
  V5  协议基线        每条路径/参数必须有**上游出处**或写明证据与日期
      ────────────────────────────────────────────────────────────────
  V6  mock 端到端     流程连通性。**效度有界**：只证明"流程能走通"
      ────────────────────────────────────────────────────────────────
  V7  真机探针        ★ 唯一能判定「对不对」的一层（人工、低频、只读优先、可回放）

                     ┌──────────────────────────────────────────┐
                     │  三个闭环：缺陷回流 / 信号采集 / 证据门禁   │
                     └──────────────────────────────────────────┘
```

**一句话读法**：V0–V3 保证「我们没骗自己」；V4–V5 保证「协议有外部出处」；
V6 保证「流程能跑」；**V7 才决定「对不对」**。

## 二、逐层定义

### V0 静态纪律门（零成本、先跑、可机器判）

**判定标准**：不通过就直接失败，不进入后续层。

| 检查 | 防的故障 | 现状 |
|---|---|---|
| `kernel/` 不得 import `inter/` | 门面与实现绑死 → 切换失效 | ✅ 已有（C1） |
| 业务层不得 import `kernel/`、`vendor/` | 灰度泄漏进业务语义 | ✅ 已有（C2） |
| 适配层**不得出现 12306 协议细节**（路径/参数/解析正则） | 「只管搬运」这条被违反 | 🆕 **待加**（决策 §10-16） |
| 状态/文案常量**唯一处定义**，别处引用 | 两处各写一遍靠字面量耦合 | ⚠️ 部分（`test_contracts` 覆盖一部分） |
| **无 `pytest.skip`** | skip 是隐藏问题 | 🆕 待加 |
| **无弱断言**（`assert x is not None` / `assert x`） | 等于没断言 | 🆕 待加 |
| 运行期包内 `mock` 引用数 **恒为 0** | 测试代码泄漏进产品 | ✅ 已有（`audit_callchain`） |
| `vendor/**` sha256 与溯源清单一致、合规文件齐全 | 「用了上游代码」变成假话 | ✅ 已有（`test_vendor_pjialin`） |
| 行尾统一（`.py` 一律 CRLF，`.bat` 纯 ASCII） | Windows 下多行替换静默失败 | 🆕 待加 |

> **设计原则**：V0 全部是「一眼能判、且与业务无关」的机械规则。
> 它便宜到应该每次提交都跑 —— 所以它是**第一道闸**。

### V1 冻结回归（证明自洽，**不证明正确**）

**判定标准**：通过 = 「改动没有破坏既有行为」。

- 覆盖：单元、集成、两端 UI（Web / 桌面离屏渲染）。
- **硬约束（写进测试文件头）**：本层的绿色**不得**被引用为「功能正确」的证据。
- 本机限制：全量 pytest 约 40s 会被回收 → **必须分层入口 + 分批跑 + junitxml 汇总**（§5）。

### V2 契约测试（防静默失效）

**判定标准**：一条契约测试必须能说出「它防的是哪一种**真实会发生且静默**的故障」。

| 契约类型 | 例子（本项目真实出现过的） |
|---|---|
| 跨模块字符串/状态一致 | 任务状态、订单状态文案、引擎状态翻译表 |
| 状态机完整性 | 终态不可转出；每个状态都有退出路径（`STANDBY_SUBMITTED` 僵尸状态就是反例） |
| 「判不出来 ≠ 否」 | 人证核验四态：判不出来必须放行（曾把正常账号永久拦住） |
| 「空串 vs 未设置」语义 | `password_enc == ""`；脱敏占位符永不回填输入框 |
| 失败必须显式 | 云打码 `available()` 只看「有没有 key」→ 填了就必然失败且被吞 |

### V3 变异检验（**让 V1/V2 可信的唯一手段**）

**判定标准**：脚本注入一次「真实违规」→ 对应测试**必须变红** → 还原。

现状：`scripts/contract_mutation_check.py` 已覆盖订单/日期/限速/内核门面（4 条）等。
**要补的纪律**：

1. **每个 V2 契约测试都必须有对应变异**（没有变异 = 不知道它是否有效）；
2. 变异必须是「**曾经真发生过**或极易发生」的改动，不是语法错误；
3. 变异脚本本身要有**自检**：注入后若测试仍绿 → 报告「假测试」，**退出码非 0**。

### V4 差分验证（外部锚点之一）

**判定标准**：同一组输入跑两条实现，**逐字段差异必须只有文档写明的那几项**；多一项、少一项都算失败。

- 现状：`scripts/kernel_diff.py`（候补请求体，4 项差异与文档一致，退出码 0）。
- 扩展方向：每个新切换的功能域都要有一张**该域的差分表**（余票解析 / 端点路径 / 通知载荷 / 站点表映射）。
- **关键**：差分表只说明「差在哪」，**不说明谁对** —— 这一句必须打印在报告里，防止被误读为验收。

### V5 协议基线（外部权威）

**判定标准**：`inter/urls.py` 里**每一条路径**必须满足其一：上游基线里有 / 在 `JUSTIFIED` 里写明证据类型与日期 / 否则失败。

- 现状：✅ 已落地（`tests/test_protocol_baseline.py`，46 条基线 + 7 条断言 + 证据类型白名单）。
- **要补的**：参数级基线（不只路径）。当前 F1–F4 那类**参数**分歧还没有基线机制，
  只有差分表 —— 差额正是「谁对」没证据的地方。

### V6 mock 端到端（流程连通，**效度有界**）

**判定标准**：流程能走通、状态机能推进到终态。

**必须写在报告里的免责句**（不是客套，是防止误读）：

> 本层只证明「流程与状态机自洽」。mock 由本项目编写，
> **它的字段名与格式来自我们的假设**；它无法证明 12306 真的接受这些请求。
> 历史上两次事故（405、6 段）都发生在这一层全绿的情况下。

**要求**：mock 的每个字段都要标注来源（`device`真机实测 / `upstream`上游 /
**`guess`我们猜的**）。任何标 `guess` 的字段，**mock 不得把它当硬校验**（这次已修掉一处）。

### V7 真机探针（★ 唯一能判「对不对」）

**判定标准**：把官方**真实行为**采集下来，落成可比对的结构化证据。

| 设计要点 | 说明 |
|---|---|
| 只读优先 | `diagnose_*` 脚本默认走到**写操作之前**停（`--until-confirm`） |
| 低频 | 对照实验必须**并排 + 同一时刻**；分时段做会得出相反结论（误判过两次） |
| 结构化落盘 | 每次探针产出 `data/evidence/<日期>-<主题>.json`，含：请求摘要、响应摘要、结论、**观察时间** |
| 可回放 | 证据文件可被测试读入 → **一旦成为契约，就能长期回归** |
| 人工触发 | 本机不承诺自动跑真机（沙箱限制 + 风控） |

**现有的 B 级探针**（已就位）：`TicketApi._log_hb_evidence` 每次候补尝试把
「官方车次号 vs 本地 / `jzParam` / `passengerInitApi` 返回键」打到 INFO。

## 三、三个闭环机制（**这才是「闭环」二字**）

### 闭环① 缺陷回流（Defect → Test）

> **一条故障在被"记住"之前不算修完。**

规则：任何**真机故障 / 用户报告 / 线上异常**，修完必须产出三样，缺一不算完成：

| 产出 | 落到哪 | 缺了的后果 |
|---|---|---|
| ① 一条**能复现**的测试（先红后绿） | `tests/` | 下次同样故障会再犯，且没人知道修过 |
| ② 一条**对应变异**（撤掉修复必须变红） | `contract_mutation_check.py` | 测试可能是假的 |
| ③ 一条**文字记录**（症状 → 真因 → 为什么以前没抓到） | `docs/缺陷回流台账.md` | 只记得"修好了"，不记得"为什么没早点发现" |

台账格式（一条一行，含「为什么以前没抓到」——这一栏最关键）：

```
| 日期 | 症状 | 真因 | 为什么以前没抓到 | 回流测试 | 回流变异 |
```

### 闭环② 外部信号采集（Evidence → Contract）

```
真机探针  →  data/evidence/*.json  →  人工判读  →  升级为**断言**（写进测试）
                                              ↓
                                    与既有契约冲突？ → **先改契约**，再改实现
```

要点：**证据一旦到手，必须变成测试**，否则它只是一次性观察，会随时间腐烂。
例：F1–F4 真机结果回来后 → 立刻把「官方 `train_no` 与本地是否相等」写成断言。

### 闭环③ 证据等级门禁（Claim → Evidence）

> 每条「正确性声明」都要能回答：**你凭什么这么说？**

机器可读台账 `verification_manifest.json`：

```json
{
  "subject": "候补 confirmHB 请求体",
  "claims": [
    {
      "claim": "请求体与上游 testerSunshine/12306 一致",
      "evidence": ["V5:vendor sha256 --check", "V4:kernel_diff 4 项一致", "V3:mutation 4/4"],
      "level": "V5",
      "open_questions": []
    },
    {
      "claim": "官方接受这个请求体",
      "evidence": [],
      "level": "none",
      "open_questions": ["F1 train_no 来源", "F2 jzParam", "F3 段数", "F4 字段集合"],
      "deadline_signal": "V7 真机一次候补"
    }
  ]
}
```

**门禁规则（脚本自动判）**：

- 一条 claim 的 `level` 若只有 V1/V6 → **标记为「未验证」**，
  并且**禁止**在文档/UI/通知里把它写成「已正确」；
- `open_questions` 非空 → 报告里必须出现在「**未决问题**」区块顶部；
- 新增功能域时**必须**先写 claim（否则门禁拒绝合并）。

## 四、机器可执行的关键设计

| 机制 | 形态 | 为什么这么选 |
|---|---|---|
| V0 纪律门 | 单个 pytest 文件 + AST 静态分析 | 纯静态、快、不需要起服务 |
| 弱断言检测 | AST 扫描 `assert <Name>` / `is not None` | 用文本正则会被字符串误伤 |
| 无 skip 检测 | AST 扫描 `pytest.mark.skip` / `pytest.skip()` | 同上的理由 |
| 变异检验 | 已有脚本 + **自检**（注入后仍绿 → 非 0 退出） | 变异脚本自己也可能失效 |
| 差分表 | 已有 `kernel_diff.py`，按功能域扩展 | 输出必须稳定可比对 |
| 真机证据 | JSON 落盘 + `data/evidence/` | 可比对、可回放、可审计 |
| 能力可用性 | **本地回声服务器**（记真实请求体） | 见下，专治「假实现」 |

### 4.1 能力可用性证明（**专治「假实现」**）

这一条值得单列，因为本项目正深受其害：云打码曾经「填了 key 就去调、请求根本发不出去、
失败被 `log.warning` 吞掉」，使用者永远只看到「识别失败」。

**规则**：任何**对外部系统的能力**（打码 / 通知渠道 / CDN / 代理 / 上游托管服务的替代品）
必须有**一条测试证明它真的发出了请求、并真的处理了响应**。
做法：起一个**本地回声服务**（不依赖外网），断言：

1. 请求**真的到达**（否则 `available()` 不得返回 True）；
2. 请求体**包含必需的字段**（例：超级鹰要 multipart `file`，而我们当时只有 `data`）；
3. 响应被**真的解析**（例：云码返回了坐标但没解析）；
4. 失败路径**不被吞**（失败必须可观测——日志 / 返回值 / 状态）。

> 这条测试的判据是「**请求长什么样**」，不是「返回什么」——
> 因为假实现的本质是**请求没发对**。

## 五、总入口与报告形态

```
python scripts/verify.py                 # 全部层（V7 默认跳过，需 --device）

python scripts/verify.py --profile fast  # V0+V2+V3（提交前用）
```

## 七、落地分期（建议）

| 期 | 内容 | 交付物 | 成本 |
|---|---|---|---|
| **F1** | V0 纪律门补全（弱断言/skip/适配层无协议细节/行尾）+ `verify.py` 总入口 | 1 个测试文件 + 1 个脚本 | 低 |

### 9.3 V5 参数级基线的做法（F5，已落地）

**锚点不是「我写的期望值」，而是从上游原件逐字切出的协议事实**
（`vendor/pjialin/ticket_facts.py`，`--check` 会重新生成一遍再比对）：

1. 把上游的**字段下标 / 端点路径 / 响应字段点号路径**切出来；
2. 逐项对自家常量做参数化断言 —— **「一致」也要断言**，
   否则改了一边没人发现（而且改了还能跑，因为另一边才是真在用的）；
3. 差异**显式留档**，并配一张差分表说明「差在哪、差多少请求」。

**这套做法当场逮到一个静默缺口**：上游读用户信息用
`data.userDTO.loginUserDTO`（**两层**），而本项目只剥一层 ——
三种嵌套结构字段名完全一样，少剥一层不报错，只是解析出**一片空白**
（见 `docs/缺陷回流台账.md` #20）。

⇒ 价值不在「证明我们对了」，而在**让「没写出来的那一层」进入视野** ——
读自己的代码推理时，它根本不存在。

### 9.1 F1 落地细节

`tests/test_discipline.py`（6 条）+ `scripts/verify.py`：

| 检查 | 机制 | 变异检验 |
|---|---|---|
| 无 skip / xfail | AST 扫 `pytest.mark.skip|skipif|importorskip|xfail` + `pytest.skip()`；豁免要写理由且会被打印 | ✅ 注入 skip → 变红 |
| 弱断言只减不增 | **棘轮**：AST 扫 `assert <裸名>` / `is[/is not] None`，冻结基线 92 条；新增即失败，修掉也要收窄基线 | ✅ 注入 `assert x` → 变红 |
| 行尾一律 CRLF | `vendor/` 与 `reference/` 除外（上游原件必须逐字节原样） | ✅ 改成 LF → 变红 |
| 适配层无协议细节 | 扫 `kernel/pjialin/**` 的字符串常量（不查注释） | ✅（P1 建目录后生效） |
| `.bat` 纯 ASCII | 解码检查 | — |
| 豁免清单不腐烂 | 豁免的 skip 必须仍存在且有理由 | — |

**变异检验替我们揪出了门本身的三个漏洞**（这就是为什么 V3 不是装饰）：
1. 行尾检查最初**漏扫 `tests/`** —— 而本项目的行尾事故恰恰发生在 test 文件上；
2. 「no-mixed」规则不够 —— 纯 LF 文件同样会让 CRLF 锚点找不到，改为「一律 CRLF」；
3. `verify.py` 的报告目录没清空 → 读到上一批的 junitxml，出现「批次失败但统计 0 失败」的自相矛盾报告。

### 9.2 F2 的判据（可机器执行）

`scripts/verify.py` 会把「证据里没有 V4/V5/V7」的声明列出来。
当前 **5 条**，每条都带 V7 判据（`deadline_signal`）：

| 未验证声明 | 判据（V7） |
|---|---|
| 官方接受候补请求体（confirmHB / passengerInfo） | 真机跑一次候补，读 `_log_hb_evidence` 的 INFO |
| 候补的兑现结果 | 真机提交候补后观察「我的订单」 |
| 官方接受我们的下单表单（本项目形态与上游形态） | `python scripts/diagnose_order.py --restore --task N` |
| 上游 pyppeteer 滑块在真机上真的能过风控 | 同上（initDc 那步会打印滑块判读与结果） |
| 上游那套节奏在真机上会不会触发限流 | 真机把 `pacing` 切到 pjialin 跑一轮查询 |

**它们出现在报告最显眼的位置**，而不是藏在「全部通过」后面。

另：`verify.py` 自身也有测试（`tests/test_verify_tool.py`）——
本机 `test_desktop.py` 带 `--junitxml` 会原生崩溃，那一批的 xml 写不出来；
现在会自动**重跑一遍不带 junitxml**、从 stdout 摘要取计数，
而「两次都拿不到摘要」记成**错误**而不是「0 通过」（后者会把崩溃伪装成全绿）。

## 十、F4 能力可用性证明：交付与实测战果

`tests/test_capability_witness.py`（14 条）+ `mock_server/echo.py`（本地回声服务，不依赖外网）。

### 10.1 它抓出来的 4 个真缺陷（全部已修）

| # | 缺陷 | 性质 |
|---|---|---|
| 1 | `Channel.send` 的两条 early return（未启用 / 非重大事件）**只回 False、不写 `last_error`** | 「因为没到触发条件所以跳过」和「真的发失败了」在调用方眼里长得一模一样 |
| 2 | Telegram 在 `ok` 为假时**直接 return，丢掉 `description`** | 失败原因丢失 |
| 3 | `FreeSolver` 把异常吞在 `log.debug` 里 | 默认日志级别下**完全看不见**，与当年云打码「请求没发出去只说识别失败」同源 |
| 4 | 语音 / Telegram 的 URL **硬编码、没有接缝** | **不可测 = 无法证明它真的工作了** → 已加 `endpoint` 配置项（留空=官方地址） |

### 10.2 我自己的测试也错了两次（记录在案）

1. 语音渠道用 `params=` 传参（参数在 **query string** 里），我的 `_fields()` 只读 body
   → 得出**「请求缺字段」的错误结论**。
   **这类「验错地方」的测试比没有测试更糟**：它会让人去改本来正确的代码。
2. 校验器锚点又忘了 CRLF（第 N 次）—— 变异脚本报「找不到待变异片段」。

### 10.3 判据（写死在测试里）

1. **请求真的到达**（回声服务里必须有记录）—— 否则 `available()` 说的「可用」是假的；
2. **必需字段在**（JSON / form / **query string** 都要读）；
3. **响应真的被解析**（内容真的被带进了请求）；
4. **失败不被吞**（`last_error` 必须非空）。

判据是「**请求长什么样**」，不是「函数返回了什么」—— 因为假实现的本质就是**请求没发对**。
