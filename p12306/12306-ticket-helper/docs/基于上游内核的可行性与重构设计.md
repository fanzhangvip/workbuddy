> testerSunshine/12306model 这三个项目的代码」。

## 一、先回答「是不是」：**不是**

当前项目与这三个上游**没有任何代码关系**。三条独立证据链：

| 核查项 | 命令 | 结果 |
|---|---|---|
| 有没有 import 上游 | `grep -rn "import py12306" --include=*.py .` | **0 处** |
| 有没有内嵌上游源码 | `ls -d vendor third_party libs extern` / `cat .gitmodules` | **都不存在** |
| 有没有打码模型 | `find . -name "*.h5" -o -name "*.onnx"` | **0 个** |
| 依赖声明 | `requirements.txt` | 只有 requests / Flask / flask-cors / flask-sock / cryptography |
| 协议层基于什么 | `ticket_helper/inter/base.py` | 直接基于 `requests` + `urllib3.Retry` 自写 |
| 项目自己的说法 | `README.md:233` | 「本项目是自己写的一套实现，**不依赖也不包含**上游代码」 |

补充一条历史：项目**早期确实用过 `py12306` 作为包名**，后来主动改成 `ticket_helper`，
理由写在 README：该名字撞了上游目录名与 PyPI 同名包，「会导致看起来像二次开发」。
也就是说，项目是有意走向**独立实现**的。

**「只是在 UI 上层封装」这个理解与事实不符。** 核心链路的自研规模：

```
ticket_helper/inter/     协议（URL 表 / 解析 / 接口封装）
ticket_helper/account/   登录 / 会话 / 扫码 / 核验
ticket_helper/standby/   候补引擎
ticket_helper/grab/      抢票引擎
ticket_helper/query/     余票查询 / 车次选项
                         ——————————————
                         合计约 7,700 行
```

UI（Web + 桌面）是这些之上的一层。所以**不存在「壳留下、内核换掉」这种低成本替换**。

## 二、⚠️ 纠正：我先前说「两个上游都没有候补」，**这句话错了一半**

建基线的时候，这份错误结论**当场被自己的工具推翻了**（这就是建基线的价值）。
逐仓库核对后的真实情况：

| 上游 | 许可证 | 形态 | **候补能力** | 能跑在 Python 3.13 上吗 | 最后实质更新 |
|---|---|---|---|---|---|
| `pjialin/py12306` | Apache-2.0 | 配置驱动的**独立应用**（无 `setup.py`） | ❌ **没有**（`helpers/api.py`、`order/order.py`、`query/query.py` 里都没有 `afterNate`） | 纯 Python 部分可以 | 核心逻辑 **2019** |
| `testerSunshine/12306` | **MIT** | 顶层脚本 + `TickerConfig.py` | ✅ **完整实现** | `inter/` 是纯 `requests`，可单独迁移；`verify/` 要 TF1.14（本项目不用） | 2021-01 |
| `testerSunshine/12306model` | **无 LICENSE** | 两个 `.h5` 权重 | — | ❌ TF1.14 / Python ≤3.7 | 2019-09 |

`testerSunshine/12306` 的候补实现，文件级证据：

```
inter/ChechFace.py            ← 人脸/登录标志检查（核验的真信号）
inter/GetSuccessRate.py       ← 候补成功率
inter/SubmitOrderRequest.py   ← 提交需求
inter/PassengerInitApi.py     ← 乘车人初始化
inter/ConfirmHB.py            ← 确认候补订单
inter/GetQueueCount.py        ← 排队前置
inter/QueryOrderWaitTime.py   ← 排队轮询
```

它的 `config/urlConf.py` 里也完整定义了 6 个 `afterNate` 端点，且 **Referer 明确写着
`https://kyfw.12306.cn/otn/leftTicket/init`**。

### 这个纠正为什么重要

**我们当初写错的那条路径，上游里恰好有正确的。**

| | 我们当初写的 | 上游 `urlConf.py` 里的 |
|---|---|---|
| 候补确认订单 | `/otn/confirmPassenger/confirmHB` → 真机 **HTTP 405** | `/otn/afterNate/confirmHB` ✅ |

也就是说：**只要当时有这么一份上游基线，那次 405 当场就能发现**，
不必等到真机跑出「响应不是合法 JSON (HTTP 405)」再靠人工排查。
**你的判断是对的**：这类协议细节本来就该以上游为准，而不是凭直觉写。

（附带说明：候补七步里的 `afterNate/getQueueNum` 上游没有列，它来自另一处参考 +
真机实测；这条已经登记在 `tests/test_protocol_baseline.py` 的归类表里。）

## 三、已经落地的第一步（本次完成）

选择的是「**两者都做**」里的第一阶段：**先把基线建起来**。
这不只是准备动作 —— 它本身就是那次事故的直接对策。

| 新增 | 作用 |
|---|---|
| `reference/upstream/py12306_helpers_api.py` | 上游地址表原件（Apache-2.0，只读参照） |
| `reference/upstream/testerSunshine_urlConf.py` | 上游地址表原件（MIT，只读参照） |
| `reference/VENDOR.md` | 出处 + 来源 commit + 许可证 + 合规说明 |
| `reference/baseline/upstream_endpoints.json` | **协议基线快照**：46 条路径 + 2 个模板 |
| `scripts/build_upstream_baseline.py` | 从上游原件重建快照；`--check` 可校验是否过期 |
| `tests/test_protocol_baseline.py` | **7 条断言**（见下） |

基线测试的核心规则：`inter/urls.py` 里的**每一条路径**必须满足三者之一 ——

1. **上游基线里有**（有出处）；
2. 在归类表 `JUSTIFIED` 里写明理由，且证据类型**必须可机器检查**：
   `device`（真机实测，必须带 `YYYY-MM-DD`）/ `referer` / `static` /
   `degraded`（不在主流程且已降级 —— **必须确实被引用**，否则该标 `unused`）/
   `unused`（**必须确实 0 引用**）/ `upstream_templated`（该模板必须在基线里）；
3. 否则 **测试失败**。

第一次跑就把**17 条「上游没有、也没写理由」的路径**全部列了出来，现已逐条归类
（真机实测 5 条、降级 6 条、Referer/静态资源 3 条、死常量 1 条、灰度候选 3 条）。

### 变异检验（证明它不是橡皮图章）

写完立刻做了三次「撤掉实现必须变红」：

| 变异 | 结果 |
|---|---|
| 把候选补路径改回 `/otn/confirmPassenger/confirmHB` | **变红 ✓** |
| 往 `urls.py` 里塞一条编造的路径 `/otn/totally/madeUpPath` | **变红 ✓** |
| 让那个「死常量」`CHECK_TRAIN_AVAILABILITY` 真的被引用一次 | **变红 ✓**（`unused` 检查生效） |

三次都正确报错，之后已还原源码。

### 顺带修掉的一个真问题

`urls.py` 里的 `CHECK_TRAIN_AVAILABILITY = "/otn/leftTicket/queryTrainStop"`
**全仓库 0 引用** —— 真正在用的经停站接口是 `/otn/czxx/queryByTrainNo`。
留着它只会让人误以为「有道能查余票的接口」。当前标记为 `unused`，
一旦有人真的开始用，基线测试会立刻变红要求补证据。

## 四、第二阶段（待开工）：内核门面 + 灰度换内核

### 4.1 目录结构

```
ticket_helper/
├── kernel/                     # 【新增】内核门面
│   ├── base.py                 #   TicketKernel 协议（Protocol）
│   ├── self_kernel.py          #   现有 inter/ 的封装
│   └── upstream_kernel.py      #   vendor 进来的上游实现的适配层
├── inter/                      # 现有自研协议层（降级为「自研 backend」）
├── standby/                    # 候补（**有上游出处了，第二阶段可切到上游实现**）
└── ...
vendor/testerSunshine/          # 【新增】真正被 import 的上游代码（MIT）
```

### 4.2 关键设计：可逐个接口灰度、可一键回退

```python
class TicketKernel(Protocol):
    def login(...) -> LoginResult: ...
    def qr_login(...) -> QrSession: ...
    def query_left_ticket(...) -> list[TrainTicket]: ...
    def get_passengers(...) -> list[Passenger]: ...
    def submit_order(...) -> OrderResult: ...
    def submit_standby(...) -> StandbyResult: ...
```

配置 `kernel.backend = "self" | "upstream"`，**按接口逐个切**。
好处：能灰度、能回退，而且**能做 A/B 比对** —— 比对结果就是「上游内核真的在用」的证据。

### 4.3 差分校验

`scripts/contract_diff.py`：对同一组录制参数，分别跑上游实现与本项目实现，
比对 **URL / 方法 / 请求头 / 表单字段 / 解析结果**。差异必须「解释或修复」。

**注意**：上游 `testerSunshine/12306` 整体依赖 Python 3.6/3.7 + TF1.14，
但它的 `inter/` 那批协议模块是**纯 `requests`**，不含 TF 依赖 —— 迁移时要逐个核对
`import`，把 `verify/`（打码）那部分排除掉，本项目的打码继续走 `ddddocr`。

## 五、第三阶段：打码模型 —— **已决定不引入**

两个独立障碍都不是我能绕过的：

1. **法律**：`testerSunshine/12306model` **没有 LICENSE 文件** → 默认「保留所有权利」。
   把权重打进 `TicketHelper.exe` 再分发属于再分发无许可作品。
2. **技术**：TF 1.14 只支持 Python ≤3.7，本项目跑在 **Python 3.13**。
   要强上就得把整个项目降到 Python 3.7 + TF1.14 —— 放弃 Flask 3 / PySide6 6.11 /
   cryptography 42，不可逆的降级。

**决定（2026-09-29）**：继续用 `ddddocr`（onnxruntime，Python 3.13 原生可用），
识别不了走人工兜底。评估记录见 `reference/VENDOR.md`，以免以后重复讨论。
