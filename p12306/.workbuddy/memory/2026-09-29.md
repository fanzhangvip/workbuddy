## 「我的订单」查不到 —— 已定位并修好（两个真 bug）

使用者回「还是查询不到订单」。用他 14:47 的会话真机复现 + 抓官方页面 JS，查出**两个**真因：

### 真因 1：`pageIndex` 差 1（主因）

官方订单页 `/otn/view/train_order.html` 引入的
`personalJS/dist/train_order/main_v30108.js` 里写得很清楚：

```js
data: { come_from_flag:"my_order", pageIndex:"0", pageSize:"8", query_where:"G", ... }
// 分页回调：n.pageIndex = t.getCurrent() - 1
```

**官方 pageIndex 是 0-based**，我们传的是 1（= 官方语义的「第 2 页」）。
订单不足一页时 → 返回**空数组**，而 HTTP 200、`OrderDTODataList: []` 的样子
与「真的没订单」一模一样 —— 所以查了半天以为是账号没订单。

### 真因 2：订单记录字段名全错（次因）

修完 1 之后订单**能取到了**（G 2 条 / H 1 条），但**每一列都是空的**。
把原始记录打出来才看到真机字段：

| 真机字段 | 含义 |
|---|---|
| `train_code_page` | 车次 |
| `from_station_name_page` / `to_station_name_page` | 车站，**是数组** `["长沙南"]` |
| `start_train_date_page` | 乘车日期+时间 `"2026-09-30 23:42"` |
| `start_time_page` / `arrive_time_page` | 发/到时间 |
| `ticket_total_price_page` | 金额 |
| `array_passser_name_page` | 乘客姓名（官方拼写就是 `passser`） |
| `tickets[]` | 票的明细：席别/座位/票种/状态，车次在 `stationTrainDTO.trainDTO.train_code` |

（我们原来猜的是 `train_code` / `from_station_name` / `passengerDTOs` —— 全不在。）

### 顺带发现的两个隐患

- **订单接口对连续请求很敏感**：连打 4 次就被 WAF 拦（空 `data` 或 HTML）。
  而我们的兜底一次要打 4 个组合 → 「查不到」会被自己放大成「一直被拒」。
  已改为 3 档 + 档间延时 + 记住成功档位。
- **mock 的字段名是假的**：`MOCK_ORDER_HISTORY` 按「直觉」写的字段名，
  所以「真机有订单但每列全空」在离线测试里**永远测不出来**。
  已把 mock 数据重写成真机结构（`*_page` 数组 + `tickets[]` + `order_total_number`），
  并把 mock 的 `pageIndex` 也改成 0-based —— 现在只要有人把 1-based 传进去，
  mock 立刻返回空列表 + `order_total_number=2`，界面上会直接提示「官方称名下共 2 单」。

## UI 与操作流程整体优化（网页端 + 桌面端）

需求：「仔细看下 UI 设计，从用户优化使用的角度思考，优化 UI 和操作流程。」

### 先发现的「真问题」（不是审美）

1. **席别优先级控件根本表达不了顺序**。网页端是 `<select multiple>`，桌面端是十个 `QCheckBox`
   且标题写着「从下往上勾选，勾选顺序即优先级」—— 这句话与实现不符：
   `_payload()` 是 `[box.text() for box in self.seat_boxes if box.isChecked()]`，永远按**布局顺序**取。
   也就是说「把二等座排在硬座前面」这件事在界面上做不到，而它直接决定有票时先要哪个席别。
2. **车次类型也是多选下拉** —— 要求使用者知道「按住 Ctrl 才能多选」这个隐藏知识。
3. **任务表单 15+ 个控件平铺**，一屏看不完，想找「乘车日期」得先滚动。
4. **黑名单只有输入框没有拉取入口**，白/黑名单都得在逗号串里手动增删。
5. **导航 9 项平铺**，核心的「任务配置」排第 4，看不出重点。
6. **没有任何引导**：空仪表盘只知道数字，不知道该干什么；空列表只写「还没有任务」。
7. **校验只弹一句 toast**，而表单要滚两屏 —— 不知道说的是哪一格。
8. **桌面端没有「订单记录」页**：抢到票只在托盘弹一句，人不知道去哪儿看订单号、怎么付款。

## 通知设置 / 任务配置：控件挤在一起（承接 UI 改造）

需求：「通知设置，任务配置 很多控件都挤到一起了 先给我把这些优化好。」

### 桌面端通知设置：为什么看起来是「一堵墙」

原来是 3 个 `QGroupBox` 里塞 **19 行 `QFormLayout`**：
「启用 Server酱」「钉钉 Webhook」「企业微信 Webhook」全在同一列，
开关和它的参数混排，`addRow("", checkbox)` 的空标签行还让对齐更乱。

**更严重的是这一页当时根本没有 `QScrollArea`** —— 内容超出窗口高度就是
**被直接裁掉**（QTabWidget 不会给你滚动条）。我实测过：内容 1216px、
可视 718px。也就是说「挤」的表象底下是「下面的控件根本够不到」。

改法：
- 新 `ChannelCard`（`QGroupBox` 子类）：首行 = `[启用]` + 说明 + 测试结果 + `[测试]`；
  参数按 2 列网格，`add_field()` 把**小标题放在控件上方**（标签放左边会让长短字段起点参差不齐）；
- 未启用 → `body.setEnabled(False)` 整块置灰；用普通 `QGroupBox` 而**不是**
  `checkable=True`（后者会把「测试」按钮一起禁用，而「先测再启用」是常见顺序）；
- 整页塞进 `QScrollArea`，操作条（保存 / 测试全部）放在滚动区**外面**固定住；
- 「系统设置」tab 同样处理（内容 741px / 视口 718px）。

实测核对（offscreen + 程序化量尺寸）：卡片 149~317px 高、无重叠、无零尺寸控件、
输入框 914px 宽、**无横向滚动条**、纵条有、保存按钮常驻可见。

### 顺手抓到的真 bug：定时器覆盖正在输入的内容

`refresh_history()` 末尾调 `_load_channels()`，而它挂在 **8 秒定时器**上 →
输入 Webhook 时输入框每 8 秒被静默还原成已保存的值。
已拆开：定时器**只刷记录表**。加了回归测试

### 又抓到一个会丢数据的 bug：脱敏值被回填进输入框

`AppConfig.to_dict(mask_secrets=True)` 会把
`password` / `key` / `webhook` / `appcode` / `bot_token` / `chat_id` / `phone`
**全部**替换成 `********`，而 `loader.update_section` 是「有则覆盖」、**不做任何过滤**。

原代码把读回来的 `webhook` / `chat_id` / `phone` / `appcode` 直接 `setText()` 进输入框 →
界面上显示 `********`；用户以为那就是当前值，改别的字段一点保存，
**真实凭据就被 `********` 顶掉了** —— 通知从此静默失效，界面上看不出任何异常。
（`serverchan` 那条有过一段防护，但写的是 `!= "***"`，常量压根不对。）

修法（三个小函数，语义清晰）：
- `visible_secret(v)`：占位符 → `""`，**永不进输入框**；
- `secret_to_send(t)`：空串或占位符 → 返回 `""`，调用方**不放进 payload**（服务端保留原值）；
- `_fill_secret(widget, stored, hint)`：有明文就填；是占位符就把 placeholder 改成
  「已保存（留空表示不修改）」，让它知道「存过」但看不到值。

网页端 `loadSettings` 对 `#cd-key` 是直接置空的，本来就对 —— 所以这个 bug 只在桌面端。
新增 2 例回归测试（不写回占位符 / 填了新值照常发）。

## 22:20 追问「verify/service.py 的云打码稳不稳」→ 实证：渠道是坏的

用**本地回声服务**（把 `CloudSolver.ENDPOINTS` 指向 `127.0.0.1` 的 HTTPServer）抓真实请求体，

```
chaojiying → user=&pass2=&softid=0&codetype=9004
yunma      → username=&password=MY-REAL-KEY-123&image=RkFLRV9DQVBUQ0hBX0JZVEVT
```

- 超级鹰：账号空串、**`cloud_api_key` 没用上**、**图片没上传**
  （`HttpClient.request` 只有 `data`/`json_body`，**没有 multipart 文件上传能力**）。
- 云码：图片传了但 `username` 空、缺 `type`、返回坐标未解析。
- `available()` 只看「有没有 key」，不看配置完整性 → 填了 key 选 cloud 必然失败，
  而失败被 warning/None 吞掉 → 用户只看到「识别失败」，看不出云打码没发出去。
- 测试只断言配置管道（`api_key=="k"`、`mode=="cloud"`），**从未调用 `solve()`** → 一直是绿的。
- 用户当前 `env.py`：`codec.mode="free"`、`cloud_provider="chaojiying"`、`cloud_api_key=""`
  → 目前未启用，不会误导。

**结论**：登录链路不需要云打码（扫码才是唯一可靠路径）；唯一可能的用武之地是下单时的
