### ★ 收尾时踩到「静默死循环」（回流 #23）——本轮最值得记的一件事

**根因链**（每环都静默）：

2. `query_order_history` 每次抛 `AttributeError`；
3. 被 `engine._check_fulfilled_by_order` 的 `log.debug` **吞掉**（默认级别看不见）；
4. 监控**永远等不到「已兑现」也不报错** → 同步 `_monitor_loop()` 死循环。

**定位手段（值得复用）**：`faulthandler.dump_traceback_later(25, exit=True)` ——
栈显示主线程正常停在 `self._stop_event.wait(delay)` → **排除死锁**，

**修法**：属性移回 `__init__`；`log.debug` → `log.warning`；两条守卫

## 补丁脚本幂等守卫的一个漏洞（今天踩到）

本环境会把同一个脚本**偶发执行两次**（§一 规则 13）。我原来的守卫是：

```python
if old not in text:            # 锚点没了 → 认为已经打过
    ...
```

这对**替换型**补丁成立，但对**「插在锚点之前」**的补丁**不成立** ——
因为插完之后那个锚点**仍然存在**，第二次执行会**再插一遍**。
今天就撞上了：MEMORY.md 里两条新规则被写了**两份**（grep 计数 2 才发现）。

正确的守卫要**检查新内容是否已在**，而不是只看锚点还在不在：

```python
MARK = "<新内容里的一个特征串>"
if MARK in text:               # ← 判据放在**新内容**上
    return
assert text.count(old) == 1
```

对「插在锚点前」这类补丁，判据必须落在**新内容**上。

### 二、#51 定稿：真机「余票不足！」的根因是**参数少了一段**

三方独立证据（不再是猜想）：
1. 上游 `make_passenger_ticket_str`（`vendor/pjialin/py12306/order/order.py:595-613`）每人是 **9 段**，
   第 9 段是**官方加密串** `enc_str`，取自 `getPassengerDTOs` 的 **`allEncStr`**；`oldPassengerStr` 拼完还要补 `'__ _ _'`。
2. 上游候补 + `testerSunshine` 的 `passengerInfo` 也一律带 `allEncStr`，
   而**本项目候补链路（`kernel/self_builder.py`）早就写着「缺 allEncStr 官方必拒」** —— 同一个坑，直购这条没跟上。
3. 数据源里**本来就有**：`api.get_passengers` 是**原样透传**整个 `normal_passengers`，我们只是从没取过那个字段。

**为什么一直没抓到**：mock 的 `checkOrderInfo` **完全不校验参数**（只看 token）——
「真机必被拒的形状」在离线永远全绿。**与 #48 是同一个机制的第二次复发**：
mock 按我们自己的形状出卷子，只能证明「我和我自己一致」。
⇒ 这次给 mock 加校验时**照上游源码写**，并且**让它回真机那句含糊话术**（「余票不足！」）——
复现症状才防得住下一次。

**改动**（`docs/缺陷回流台账.md` §二十）：
`parser.build_passenger_ticket_str` 补第 9 段（空则**仍发空段** + WARNING，不静默退回旧形状）；
`build_old_passenger_str` 补 `'__ _ _'`；mock 加校验；新增 `tests/test_order_params_on_the_wire.py`（7 条，判据**全在线缆上**，含两条反向判据）；既有测试数据同步补 `allEncStr`。

### 三、新缺陷 #60：人工验证码超时后**白等 N 个 120 秒**

`verify/service.py` 里人工兜底**已经**做到「超时就不再重试」（注释原话：三倍下来就是 6 分钟白等，而且他不会得到任何新信息），
但那条判断只修在**识别链内部**；上层 `OrderService.submit` 的 `max_retry` 对 `VerifyCodeError` **照样重来**。

根子在类型上：`VerifyCodeError` 是 `InterError` 子类，被 `except (InterError, ResponseParseError)` 一并接住并**统一标成可重试**；
而「识别失败」与「官方说验证码错误」**完全同形** —— 只有看**是谁抛的**才分得开。

**改法**：`order/service.py::_submit_once` 只把**识别环节**包住，失败就地收成 `retryable=False` 并 `return`；
`checkOrderInfo` 抛的「官方说验证码错误」**仍走上层重试**（换一张新图再试是有意义的，两者不能混为一谈）。
新增 `test_order.py::test_captcha_failure_does_not_retry`，判据是**尝试次数**（`max_retry=3` 也只允许调一次识别）。
