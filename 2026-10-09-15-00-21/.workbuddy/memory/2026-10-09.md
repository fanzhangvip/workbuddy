## Docker Desktop 无法启动的排查与修复

**问题**
`docker compose up -d postgres` 先报 `npipe:////./pipe/dockerDesktopLinuxEngine` 不存在，启动 Docker Desktop 后变为
`Error response from daemon: Docker Desktop is unable to start`。

**本机环境实测结论**
- Docker Desktop 4.94.0（要求 WSL >= 2.1.5）
- Windows 11 23H2，build 22631.5335
- `C:\Program Files\WSL\` 不存在，`%LOCALAPPDATA%\Microsoft\WindowsApps\wsl.exe` 不存在
  → 只装了老式 inbox WSL，从未安装微软商店版 WSL
- 根因日志：`%LOCALAPPDATA%\Docker\log\host\com.docker.backend.exe.log`
  - `[wslexec][E] c:\windows\system32\wsl.exe --version failed: exit status 0xffffffff`
  - `[engines][W] engine linux/wsl failed to start: checking preconditions: WSL update required`
  - `wsl --version` 实际返回 "Invalid command line option: --version" → 旧版 WSL 不认识该参数
- 虚拟化正常（vmmem 在运行），磁盘 797G 可用，均非瓶颈

**目标项目**
`postgres` 服务位于 `C:\zero\learningAssistant\learning-assistant\docker-compose.yml`
（image: pgvector/pgvector:pg16，container: learning-assistant-postgres，端口 5432）

**交付**
`fix-wsl-for-docker.ps1`（工作区根目录）：需管理员运行，步骤为
校验虚拟化 → 启用 WSL/VirtualMachinePlatform 功能 → 停 Docker Desktop →
`wsl --update`（失败依次回退 `--web-download`、`--install --no-distribution`）→
`wsl --shutdown` 并校验 `wsl --version` → 重启 Docker Desktop 并轮询 `docker info` 最多 4 分钟。

**约束记录**
本机沙箱把 `wsl.exe`、`sc.exe` 列入程序黑名单，无法代为执行；`PowerShell` 工具在本会话中不回传 stdout。

## 15 个预置中间件实测行为（20:30）

**分类**：安全合规（PII / HumanInTheLoop / ShellTool）、上下文与成本（Summarization /
ContextEditing / ModelCallLimit / ToolCallLimit）、稳定性容错（ModelRetry / ToolRetry /
ModelFallback / ToolError）、能力增强（LLMToolSelector / TodoList /
FilesystemFileSearch / ProviderToolSearch）。

**实测确认的关键行为（假模型 + 真实中间件）**

1. `PIIMiddleware("email", strategy="redact", apply_to_input=True)`
   → 入库的 user 消息被改写为 `我的邮箱是 [REDACTED_EMAIL]`（是**原地替换 state**，不是只脱敏发给模型）。
   strategy 取值：`block`（抛 `PIIDetectionError`）/ `redact` / `mask` / `hash`。
   内置类型：email / credit_card(Luhn 校验) / ip / mac_address / url；也可传自定义正则。

2. `ModelCallLimitMiddleware(run_limit=4)` → Agent 从"无限循环"变为**优雅结束**
   （实测：5 条 AI 消息、4 次工具执行、10 条消息后正常返回）。
   `exit_behavior="error"` → 抛 `ModelCallLimitExceededError`；默认 `'end'`。

3. ⚠️ **`ToolCallLimitMiddleware` 默认行为是个陷阱**：`exit_behavior` 默认 `"continue"`，
   它只**拦截超限的那次工具调用**，模型会继续请求同一个工具 → 死锁到
   `GraphRecursionError`。实测对比（都设 run_limit=3）：
   - `"continue"`（默认）→ GraphRecursionError（recursion_limit=200 时照样撞）
   - `"end"`    → 正常结束，10 条消息
   - `"error"`  → 抛 `ToolCallLimitExceededError`
   **结论：ToolCallLimit 必须显式写 `exit_behavior="end"`，否则等于没设。**

4. `ToolErrorMiddleware(on_error=lambda exc, req: "...")`
   → 签名是 `Callable[[Exception, ToolCallRequest], str | list | None]`（**两个参数**）。
   返回字符串则把异常转成 `ToolMessage(status="error")` 交给模型自愈（实测 Agent 正常收尾）；
   返回 None 则异常继续上抛终止运行（默认行为）。

5. `TodoListMiddleware()` → 自动注入 `write_todos` 工具（实测工具列表变为
   `['write_todos', 'broken']`），并附带一段引导规划的系统提示。

6. `HumanInTheLoopMiddleware(interrupt_on={...})` → `True` 简写与
   `{"allowed_decisions": ["approve","edit","reject"]}` 完整写法均可用。

7. `SummaryMiddleware` 默认 `trigger=("tokens", 4000)` / `keep=("messages", 20)`；
   `ContextEditingMiddleware` 的 `ClearToolUsesEdit(trigger=100000, keep=3,
   exclude_tools=(), placeholder="[cleared]")`，对齐 Anthropic `clear_tool_uses_20250919`。

8. `ShellToolMiddleware` 需搭配执行策略：`HostExecutionPolicy`（全权限，仅限已隔离环境）/
   `DockerExecutionPolicy`（默认镜像 `python:3.12-alpine3.19`，默认禁网）/
   `CodexSandboxExecutionPolicy`。**不要在宿主机上裸用 HostExecutionPolicy。**
