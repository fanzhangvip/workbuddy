## 〇、使用说明

### 0.1 本稿的定位

本稿把「业务系统交接四步」拆成**可执行动作**与**可判定条件**两部分。

核心原则：**每一步必须有输出，输出必须被认可，认可才能进下一步。** 没有输出的步骤等于没做。

### 0.2 通用验收规则

以下四条规则适用于全部四步，任何一条不满足则该步不予通过。

| 规则号 | 规则内容 | 判定方式 |
|--------|---------|---------|
| G1 | **有输出**：每步结束时须有书面产出物，口头汇报不算 | 产出物文档存在且可查 |
| G2 | **有评审**：产出物须经老板（或指定人）确认后方可进入下一步 | 老板明确表态「可以进入下一步」 |
| G3 | **有边界**：每步开始前书面明确本步不做什么 | 范围清单书面确认 |
| G4 | **可回退**：任一步发现重大风险，立即上报并暂停，不硬推 | 上报记录 + 暂停决定 |

### 0.3 关键前提：三条硬约束

以下三点是本项目区别于普通技术任务的特殊性，必须在执行标准中体现：

| 编号 | 约束 | 对执行标准的影响 |
|------|------|-----------------|
| C1 | **系统是公司运转基本盘**，一丝风险都不能出 | 所有步骤以「不影响生产」为前置条件 |
| C2 | **代码质量历史欠账**：系统由应届生接手、无架构师带、长期堆叠而成 | 允许「摸清现状」优先于「立即重构」 |
| C3 | **数据部门是缓冲地带**：业务部门只找数据部门要数据 | 交接过渡期必须与数据部门同步推进，不可单线推进 |

## 一、总体节奏与阶段门禁

### 1.1 阶段门禁图

| 步骤 | 核心产出 | 门禁条件 | 预估周期 |
|------|---------|---------|---------|
| 第一步 | 系统分析报告 | 报告获认可 | 3–4 周 |
| 第二步 | 需求台账 + 优先级判断 | 优先级获认可 | 2–3 周 |

> ⚠️ **第一、二步存在交叉**，可部分并行。老板原话是「第二步有可能跟第一步同时做，有交叉的地方」。因此第一步摸底到 70% 时即可启动第二步，不必等报告完全定稿。

### 1.2 阶段间的硬门禁

**未通过的门禁不得跨越。** 具体判定：

- 第一步报告未获认可 → 不得进入第三步（因为工作量评估依赖系统理解）
- 第二步优先级未获认可 → 不得进入第三步（工作量评估的前提是优先级确定）
- 第四步出现重大事故 → 全流程回退至第三步，重新评估

## 二、第一步：资料交接与系统全面摸底

### 2.1 目标

把系统从「别人做的东西」变成「我能独立判断的东西」。

### 2.2 交付物清单

| 编号 | 交付物 | 格式 | 责任人 |
|------|--------|------|--------|
| D1.1 | 系统分析报告 | 文档 | 本人 |
| D1.2 | 本地可运行环境 | 环境 | 本人 |
| D1.3 | 脱敏测试数据包 | 数据包 | 数据部门（陈强）配合 |
| D1.4 | 技术难点清单 | 文档 | 本人 |

### 2.3 执行动作

#### 动作 1：接收资料并本地跑通

| 项 | 要求 |
|----|------|
| 接收内容 | 需求文档、源代码、数据库结构、部署配置、第三方对接说明 |
| 环境部署 | 本地跑通；服务器要求可能不低，需提前评估 |
| 云端方案 | 可布一套云环境用于测试（本人已有云资源） |
| 关键约束 | **真实数据不得上云**；测试环境与生产环境必须分离 |
| 数据要求 | 由数据部门提供脱敏数据或分批数据，用于跑通流程；不需全量全表，能跑起来即可 |

**达标条件**：
- [ ] 本地环境成功运行，系统可正常访问
- [ ] 核心业务流程完整走通一遍（至少覆盖一条端到端主流程）
- [ ] 测试环境与生产环境物理或逻辑隔离，验证无数据串用

#### 动作 2：全面摸底并输出报告

系统分析报告须包含以下**七个板块**，缺一不可：

| 板块 | 内容 | 最低要求 |
|------|------|---------|
| 1. 架构总览 | 技术栈、模块划分、数据流、部署形态 | 能画出完整架构图 |
| 2. 系统完备性 | 哪些功能已实现、哪些是半成品、哪些是设计但未落地 | 逐模块列出，无遗漏 |
| 3. 缺陷清单 | 已知问题与新发现问题，含严重度分级 | 每项含复现路径 |
| 4. 技术难点清单 | 搞不定的技术问题、准确率不足的业务问题 | 见2.4 判定标准 |
| 5. 安全状况 | 端口暴露、账号权限、历史入侵痕迹 | 见 2.5 专项要求 |
| 6. 迭代方向 | 技术层面的完善建议与优先级 | 区分「必须改」与「可延后」 |
| 7. 遗留问题 | 无法自行解决、需外部支持的问题 | 标注所需支持方 |

### 2.4 技术难点的判定标准（重点）

这是本步最容易流于形式的环节。老板明确要求：**「有些大家觉得 OK 的，实际上可能还是欠缺一点；你们能发现的就交给他，发现不了的他能发现。」**

因此技术难点清单必须区分**三个层级**，不可只报明显问题：

| 层级 | 定义 | 判定方法 |
|------|------|---------|
| L1 显性缺陷 | 功能不正常、报错、体验明显不对 | 正常测试即可发现 |
| L2 隐性质量问题 | 功能能用但准确率/性能不达标，业务方未察觉 | **需主动构造测试用例验证** |
| L3 架构性隐患 | 当前可用，但业务增长后必然出问题 | 需从架构与容量角度判断 |

**硬性要求**：
- L2 隐性质量问题**必须主动排查**，不得等业务方反馈。重点方向为 AI 识别类功能的准确率。
- L3 架构性隐患**必须列出容量水位判断**，即「并发量到什么程度会出问题」。

**L2 的量化要求（无阈值即无法判定）**：

每个 AI 识别类功能，须书面记录三项数据：

| 记录项 | 要求 |
|--------|------|
| 当前实测准确率 | 在脱敏测试集上实测得出，写明测试集规模 |
| 业务方期望值 | 由业务方明确给出 |
| 差距 | 两者之差，并判断是否构成「大家觉得 OK、实际欠缺」 |

**无实测数据的项，一律直接标为 L2 待测**，不得因「看起来能用」而放行。已知的图片识别有效通话判定问题即属此类——已更换多个 AI 工具未见改善，属典型 L2。

### 2.5 安全状况专项（不可跳过）

该系统曾因**MySQL root 密码未设置 + 端口暴露公网**被入侵，数据被删除。虽事后请网安团队加固过，但**是否已彻底修复目前不确定**。

因此第一步必须包含：

| 检查项 | 达标条件 |
|--------|---------|
| 数据库弱口令 | root 及所有业务账号均无弱口令，密码策略可验证 |
| 端口暴露 | 数据库、后台管理端口不对公网暴露，验证方式为外部扫描结果 |
| 后台暴露面 | 已知后台地址全部修改默认口令 |
| 备份有效性 | 备份策略明确，且**至少验证过一次可恢复** |
| 加固复核 | 邀请网安团队复核历史加固项，出具结论 |

**一票否决项**：若安全状况无法确认，**第一步不予通过**。理由：交接后若因安全问题导致业务中断，将直接冲击公司基本盘。

### 2.6 第一步达标条件（汇总）

**全部满足**方可通过：

| 编号 | 达标条件 | 验证方式 |
|------|---------|---------|
| S1-1 | 系统在本地/测试环境稳定运行，端到端主流程可走通 | 实机演示 |
| S1-2 | 系统分析报告七个板块齐全，无空缺 | 报告评审 |
| S1-3 | 技术难点清单含 L1/L2/L3 三层，L2 已主动排查 | 报告评审 + 用例清单 |
| S1-4 | 安全状况五项检查全部通过，含备份可恢复验证 | 报告评审 + 网安复核 |
| S1-5 | 遗留问题已列明并标注所需支持方 | 报告评审 |
| S1-6 | 老板明确认可报告，并同意进入下一步 | 书面或会议确认 |

## 三、第二步：现有需求摸排与优先级判断

### 3.1 目标

把「十几个需求」从口头台账变成**可判断、可排序的清单**，并回答一个关键问题：**他们现在排的优先级，对不对？**

### 3.2 交付物清单

| 编号 | 交付物 | 格式 |
|------|--------|------|
| D2.1 | 需求台账 | 表格 |
| D2.2 | 优先级评估意见 | 文档 |
| D2.3 | 10 月优先级调整建议 | 文档（供 10 月会议使用） |

### 3.3 执行动作

#### 动作 1：需求台账（必备字段）

每个需求必须记录以下字段，**缺项即为台账不合格**：

| 字段 | 说明 |
|------|------|
| 需求名称 | — |
| 提出部门 | 财务 / 运营 / 销售 / 售后 / 其他 |
| 提出时间 | 用于判断紧急程度是否已过期 |
| 业务背景 | 为什么提这个需求 |
| 归属层级 | 已对接 / 未对接 |
| 业务方期望优先级 | 对方自己排的位置 |
| 技术评估复杂度 | 本人独立判断 |
| 建议优先级 | 本人判断 |
| 是否与现有需求冲突 | 关键项 |

#### 动作 2：优先级判断

**第一步：先认可，再调整。**

老板与梅梅给出的判断依据是：优先级由业务情况决定，**财务优先**（涉及提成、奖金、各项指标，一动全盘数据都要改），然后运营与销售业务线，售后排最后。

**因此执行标准是**：
- 默认沿用现有优先级排序，**不做无依据的推翻**；
- 仅在有明确技术依据时提出调整建议，且必须书面写明理由；
- 若认为某项优先级不当，先记录为「建议调整」，交 10 月会议由业务方与老板共同决定。

**第二步：技术视角必须给结论。**

不能只写「排期不合理」，需给出具体判断：

| 判断类型 | 达标写法 |
|---------|---------|
| 优先级是否合理 | 合理 / 建议调整至X 位，理由为…… |
| 排期是否合理 | 合理 / 偏长 / 偏短，建议调整为 X 天 |
| 技术阻塞点 | 无 / 有，阻塞原因为…… |

### 3.4 第二步达标条件（汇总）

| 编号 | 达标条件 | 验证方式 |
|------|---------|---------|
| S2-1 | 十几个需求**全部**进入台账，无遗漏 | 台账与业务方核对一致 |
| S2-2 | 每条需求九个字段齐全 | 台账检查 |
| S2-3 | 每条需求都有「技术评估复杂度」结论，无「待定」 | 台账检查 |
| S2-4 | 每条需求都有建议优先级，或明确说明「沿用原优先级」 | 台账检查 |
| S2-5 | 建议调整的项均写明技术理由 | 文档评审 |
| S2-6 | 老板认可优先级结论，并同意进入下一步 | 会议确认 |

## 四、第三步：工作量重排与进度对齐

### 4.1 目标

**把进度计划的主导权从下面的人手里拿过来。**

老板的原话很直接：「他们会给自己放很多水，明明只需要做一天，他评估了 5 天，你不知道；但是你现在不知道。」

因此本步的核心是：**用技术视角把每个需求的真实工作量算清楚，形成统一的、饱和的时间计划表。**

### 4.2 交付物清单

| 编号 | 交付物 | 格式 |
|------|--------|------|
| D3.1 | 需求工作量评估表 | 表格 |
| D3.2 | 统一时间计划表 | 表格 |
| D3.3 | 重构优先级建议 | 文档 |

### 4.3 执行动作

#### 动作 1：逐项技术评估

对第二步台账中的**每一条需求**，独立评估其真实技术工作量。

评估必须满足：

| 要求 | 说明 |
|------|------|
| 拆到任务粒度 | 一个需求拆为若干子任务，各子任务单独估时 |
| 区分工作量与排期 | **工作量**＝纯开发时间；**排期**＝含等待、沟通、测试的日历时间 |
| 标注不确定性 | 高不确定性项单独列出并预留缓冲 |
| 依赖关系明确 | 标出哪些需求依赖其他需求完成 |

**关键区分**：老板指出的问题正是把工作量与排期混为一谈。若技术活 2 天但因业务方确认流程耗时 5 天，**排期可以标 5 天，但工作量必须标 2 天**。混着算就看不出虚高在哪。

#### 动作 2：形成饱和的时间计划表

| 要求 | 说明 |
|------|------|
| 按优先级排布 | 依据第二步确认的优先级 |
| 排满可用产能 | 计入日常事务、沟通、会议占用的时间，不按满负荷排 |
| 留出机动 | 整体保留 20% 机动余量 |
| 明确交付节点 | 每个需求有明确的验收日期 |

**产能基线参考**：老板指出「开发不加班就说不过去」，说明当前产能未被充分使用。但**不作为排期依据**——排期按实际可投入时间算，不按理论上限算。

#### 动作 3：重构优先级判断

系统重构的工作量很大，优先级应排在需求之后。

**判定依据（老板原话）**：并发量不大，代码写得烂一点暂时没问题；**先保证服务跑得起来**。只有并发量上去之后，代码不合理才会出问题。

因此重构优先级判定标准：

| 条件 | 重构优先级 |
|------|-----------|
| 当前并发量远低于容量上限 | 靠后，不占用本阶段资源 |
| 并发量接近容量上限或已有增长趋势 | 提前，与需求并行推进 |
| 出现明确性能瓶颈 | 立即启动 |

**建议**：本阶段重构**不排入主计划**，仅在计划表中预留「架构优化」条目并标注触发条件，待后续按实际业务增长情况决定何时启动。

### 4.4 第三步达标条件（汇总）

| 编号 | 达标条件 | 验证方式 |
|------|---------|---------|
| S3-1 | 每条需求均有独立的技术工作量评估，无「待评估」 | 评估表检查 |
| S3-2 | 工作量与排期分列，不混算 | 评估表结构检查 |
| S3-3 | 高不确定性项已标注并预留缓冲 | 评估表检查 |
| S3-4 | 时间计划表覆盖全部需求，无遗漏 | 计划表与台账核对 |
| S3-5 | 计划表含 20% 机动余量 | 计划表检查 |
| S3-6 | 重构已明确不进入本阶段主计划，并写明触发条件 | 文档检查 |
| S3-7 | 老板认可计划表 | 会议确认 |

## 五、第四步：突发需求试交接

### 5.1 目标

**验证我是否真的接得住。**

前三步是「我懂了」，第四步是「我能干」。这一步的核心不是交接动作本身，而是**在实际压力下验证前三步的成果是否扎实**。

### 5.2 执行动作

#### 动作 1：让对方先接

| 要求 | 说明 |
|------|------|
| 突发需求 | 由对方（数据部门侧）先对接，先行处理 |
| 本部门需求 | 逐步开始与对方对接 |
| 我的角色 | 二线把关，不直接抢做 |

**验证重点**：当需求真正落到对方手上时，暴露的问题是否都在我的可控范围内。

#### 动作 2：周例会机制

**最低要求：以周为单位召开周例会。**

| 项 | 要求 |
|----|------|
| 周期 | 每周固定 |
| 议题 | 围绕系统所有工作事项的**分析总结**与**计划安排** |
| 主持 | 本人 |
| 范围 | 系统相关的全部工作，不限于本周新增 |
| 输出 | 会议纪要 + 下周计划 |

#### 动作 3：日常沟通机制

- 研发与数据部门两人先打通，两人不通则任何一边都交不了；
- 需求对接未来逐步转由本人承接，但数据部门仍专注数据本身；
- 日常沟通保持透明，任何风险及时同步。

### 5.3 第四步达标条件（汇总）

| 编号 | 达标条件 | 验证方式 |
|------|---------|---------|
| S4-1 | 至少完成 3 次突发需求试交接 | 交接记录 |
| S4-2 | 试交接期间无生产事故 | 事故记录 |
| S4-3 | 周例会机制已建立并连续运行 4 周以上 | 会议纪要 |
| S4-4 | 对方可独立完成需求对接，我仅做把关 | 交接记录 |
| S4-5 | 我对系统的判断被验证正确（无「问三不知」情况） | 试交接反馈 |

**一票否决**：试交接期间出现生产事故，**立即回退至第三步**，重新评估后再继续。
