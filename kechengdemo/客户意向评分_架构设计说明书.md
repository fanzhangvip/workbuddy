# 0. 速览

| 项 | 事实 |
|---|---|
| 系统做什么 | 把企微会话存档的聊天记录，变成**可执行的客户意向结论**：分数、等级、画像、话术建议，并把分数与等级**写回微伴**，负分交人工复核，全链路可评估、可追溯 |
| 技术栈 | Python 3.13 + FastAPI（单进程：API + APScheduler + 托管前端 `dist`）· PostgreSQL 16（pgvector 镜像）· Vue 3 + Vite（图表 echarts，按需引入）· Docker Compose（可选 Caddy HTTPS + 定时备份） |
| 代码规模 | 后端 49 个模块 + 根目录 13 个共用模块 + 前端 8 个视图；**31 张表 / 471 个字段**；**106 个 API 操作**（97 条路径） |
| 判定链路 | 候选筛选 → 事实 → 上下文装配 → 大模型判定 → 契约校验 → 规则引擎算分 → 置信度 → 策略三档 → 落库（同事务入待办）→ 回写/标签/复核 → 检查点 |
| 第二条链 | 兴趣点提取（第十四章）：会话 → 受控一级分类 + 自由二级标签 + 证据原话 → 总览页「兴趣点分布图」。**只读消息、不写回任何外部系统**，与评分共用上下文装配与契约机制，但各自独立增量 |
| 三条硬规则 | ① **取什么给模型看**只在一个地方决定（`scoring_context`）；② **分数由本地规则算**，模型只产出结构化判定；③ **写外部系统**（微伴分数/标签）必须可确认、可审计、不可逆动作先问人 |
| 状态 | 15 条规则（8 正 / 7 负）· 72 项运行时配置 · 13 个定时任务 · 52 个测试文件（默认跑 t0+t1 共 51 个） |

# 1. 业务问题与定位

## 1.1 要解决什么

销售与客户的会话沉淀在企微会话存档里，人工读不完、读不齐、口径不一。系统把这件事变成**确定性流水线**：
同一份会话、同一版规则、同一套口径，产出同一份结论；结论能写回微伴被销售看到，能被人工复核纠偏，能被评估集量化"判得准不准"。

## 1.2 三个核心问题与对策（这几条决定了整体形态）

| 问题 | 后果 | 对策 |
|---|---|---|
| 模型输出**不可信**（自由文本、漏项、极性写反、证据编号瞎编） | 结论无法落库、无法对账 | 双层契约 `contracts.py`：结构合法 + 业务合法（极性、档位一致性、证据编号必须在给定行内）。不合法重试，连续失败转人工（`session_failure`） |
| 模型**算不准数**（把加减法交给 LLM） | 同一份会话两次跑出两个分 | **分数不进模型**：模型只输出"命中了哪条规则的哪个档 + 证据行 + 理由"，分数由 `rules.py` 按本地规则表算 |
| 模型**看得不全**（长会话早期关键事实被窗口挤掉） | 漏判"预算/需求/岗位"这类最早出现的信号 | 上下文装配按**价值**取数而非按位置（第四章），并把"取了什么、砍了什么"记账可观测 |

## 1.3 质量属性优先级（第一约束）

**稳定性 > 可靠性 > 可评估 > 可观测 > 性能。**

理由：本系统的写操作会**改变外部业务系统**（微伴分数累加、标签增删），且客户数据不可重放。因此宁可慢、宁可转人工，也不能写错或静默丢。所有"看起来更聪明"的设计（自动调参、自动改规则、让模型决定回写）都被这条优先级否决。

## 1.4 范围边界

- **做**：会话存档 → 评分 → 回写/标签/复核 → 评估闭环 → 观测与运维。
- **不做**：客户画像推荐系统、销售 CRM、消息实时流处理（本系统是**批处理**，不是实时管道）。
- **单实例**：同一时刻只允许一轮评分或一轮同步（见 9.4 互斥），不做多实例与高可用。

# 2. 分层架构

## 2.1 八层

| 层 | 职责 | 落点 |
|---|---|---|
| 入口层 | 页面 / API / 角色守卫 / 幂等 / 互斥 | `frontend/`、`api_*.py`、`api_guard.py`、`idempotency.py` |
| 编排层 | 一轮批量的生命周期：候选、进度、停止、超时、检查点、续跑 | `scoring_service.py`、`sync_service.py`、`job_service.py`、`task_runtime.py` |
| 上下文工程层 | **唯一**决定"取哪些消息、怎么渲染给模型" | `scoring_context.py`、`ctx_preprocess.py` |
| Harness（模型之外的控制） | 五个显式判定点，把散落的护栏收敛成统一口径 | `hooks.py` |
| 判定层 | 大模型判定 + 契约 + 规则引擎算分 + 置信度 | `analyze.py`、`contracts.py`、`rules.py`、`confidence.py` |
| 行动层 | 策略三档 → 分数回写 / 等级标签 / 负分复核 / 审批 | `policy.py`、`outbox.py`、`writeback_repo.py`、`grade_tag.py`、`review_repo.py` |
| 状态存储层 | PostgreSQL：结论、账本、队列、检查点、审计 | `schema.sql`、`*_repo.py`、`db.py` |
| 可观测与安全层 | 指标 / 追踪 / 保留期 / 审计双层 / 鉴权与脱敏 | `metrics`、`trace.py`、`audit.py`、`retention.py`、`security.py` |

**分层的第一原则：同一件事只有一个落点。**
会话对象只在 `_SESSION_COLS` 里定义；"消息→文本"只在 `ctx_preprocess`；写 `customer_intent_assessment` 只经 `assessment_repo`；
写 `eval_case` 只经 `eval_case_repo`；回写的记账与水位只经 `writeback_repo`。改一次需求只动一个文件。

## 2.2 三层循环

```
业务闭环（L3）  采集 → 判定 → 行动 → 验证 → 学习
                 ↑                                    ↓
任务循环（L2）  一次批量：候选 → 逐个会话 → 检查点 → 恢复/续跑     （task / task_step）
                 ↑
内循环（L1）    单个会话：装配 → 模型 → 契约 → 算分 → 置信度 → 策略  （11 步，见第三章）
```

- **L1 可重放**：同一份输入 + 同一版规则 + 同一锚点 → 同一结论（评估集就靠这条成立）。
- **L2 可恢复**：每个会话是一个检查点步骤；进程挂掉后 `recover_stale()` 标失败并给出可续跑清单，续跑**新建任务**（历史不可变）。
- **L3 可学习**：人工复核的改判回流成评估样本，成为以后发布规则的门禁依据。

# 3. 判定链路（十一步）

**同一个会话的 11 步**（`graph_session.py` 的节点顺序即权威顺序；`scoring_service._score_one` 是等价的串行实现，开关 `use_graph_session` 默认关，两者有 parity 测试逐字段比对）：

| # | 步骤 | 输入 | 判定 / 动作 | 产出 | 失败处置 |
|---|---|---|---|---|---|
| 1 | `prepare` | `staff_id`+`session_id` | 取消息 → `ctx_preprocess` 规范化 → 内容量闸（保留条数 / 客户开口数 / 文本长度） | `ctx` | 不足 → `skipped`（不计入失败） |
| 2 | `ctx_stats` | `ctx` | 记账：保留/裁剪了多少条、命中哪些规则标签 | `ctx_stats` | — |
| 3 | `facts` | 会话 + 时间锚点 | `compute_facts(as_of)`：48h 未回复、到课/完课标签、消息计数 | `facts` | — |
| 4 | `judge` | 系统提示词 + 三段上下文 | **大模型判定**（只输出命中项与证据，不输出分数） | 原始 JSON | 超时/网络 → 退避重试；认证/契约类致命错误直接抛 |
| 5 | `items` | 原始 JSON | **双层契约**：结构合法 + 业务合法（极性、档位、证据编号必须在给定行内） | 合法 items | 不合法 → 重试（带错误回灌）；连续失败 → `session_failure` 转人工 |
| 6 | `local_score` | items + `facts` | **规则引擎**：同维度取最高档、跨维度累加、按上下限截断；引擎规则（如 48h 未回复）由代码直接算 | `raw_score` / `grade` / `score` 明细 | — |
| 7 | 置信度 | items + facts + 上下文统计 | 三层合成（第六章）：证据质量 + 覆盖/漏检 + 结构风险 | `session_confidence` + `review_reasons` | 低于阈值 → 进人工复核队列 |
| 8 | 策略 | `confidence` + 风险 | `policy.decide()` → `auto` / `confirm` / `human` | `action` + `action_reasons` + 阈值快照 | `confirm`/`human` 在 **live** 下拦回写（第七章） |
| 9 | `persist` | 结论 + 行动判定 | `hooks.before_persist` → **同一事务**写结论 + 入回写待办 + 标记旧结论被取代 | `assessment_id` | 事务失败 → 整条回滚重试 |
| 10 | `tag` / `writeback` / `review` | 结论 | 三条**独立**行动链：等级标签（`grade_tag_mode`）· 分数回写（`writeback_mode`）· 负分复核（有负分才入队） | 账本 / 队列 / 复核行 | 各自记账，互不影响 |
| 11 | `progress` | 本步结果 | 检查点落 `task_step`、累计进度、单会话耗时入分布 | 进度 / 指标 | — |

**为什么要有"图化"这条路**：11 步里有 5 个判定点、3 条行动链、1 个检查点，串行实现里它们的顺序只是"代码读下来的顺序"。图化后顺序是**显式声明**的（`add_node`/`add_edge`），可以逐节点追踪耗时与输入输出指纹，改动顺序会被 parity 测试立刻发现。

**两条不可越过的原则**：
1. **模型不参与计分**：模型只做"有没有命中、证据是哪一行"，分数、等级、阈值全部本地确定性计算。
2. **行动与判定解耦**：判定先落库（结论 + 待办同事务），行动由 `outbox`/`grade_tag_outbox` 独立推进，失败可重试、绝不影响判定结果。

# 4. 上下文装配

## 4.1 为什么要按价值取数

实测：中位会话没有超窗口，问题只在长尾（`msg_count` p99≈171、max≈320）。但"岗位/需求/预算"这类**最早出现且最重要**的事实，恰恰会被"最近 N 条"挤掉；而窗口之外的重要片段（报价、邀约、到课、拒绝）**没有任何检索键**可取。结论：**短会话零成本按原样走，长会话才启用检索与裁剪**。

## 4.2 事实先行（`compute_facts`）

事实是**代码算的确定量**，与模型无关，且可复现：

- `no_reply_2d`：客户最后一条消息距今 ≥ `no_reply_window_days`（**默认 14 天**）；
- 到课类标签命中情况；
- 消息计数（总数 / 客户条数 / 有正文条数）。

**必须带时间锚点 `as_of`**：判定结果与 `assessment.data_as_of` 用同一个值落库。否则同一批样本换一天跑，"48h 未回复"会自己出现或消失，指标无法比较（评估样本因此固定 `anchor_ts`，见 8.3）。

## 4.3 五段上下文（两段记忆 + 三段消息）

| 段 | 内容 | 为什么需要 |
|---|---|---|
| ① 客户状态档案 | **上一次评估**的等级 / 总分 / 消息数 / 规则版本 + 画像摘要 + 销售策略（后两者各截 400 字） | 让模型知道"上次看到了什么、判成了什么"，不必每轮从零开始 |
| ② 上次评分明细 | 上次命中的 `rule_id(+3)` / `rule_id(-2)`（各列前 12 条 + 合计） | 同一事实不该因为"这轮没复述"被当成新信号或漏掉 |
| ③ 增量 | 上次评估水位（`assessment.last_msg_time`）之后的新消息 | 只看"没见过的话"，避免重复判断 |
| ④ 关键历史 | 按**本次相关规则集**检索出的、窗口外的关键行（载体 `chat_message.rule_tags` + GIN） | 把"早期被挤掉的关键事实"捞回来 |
| ⑤ 兜底窗口 | 最近 N 条（默认 60） | 保底：短会话与冷启动全靠它 |

**①② 是"记忆"不是证据**：用 `【】` 段标、**不带 `#编号`**，故不进 `index` —— 模型无法把它们当
`evidence_ids` 回链（决议 M-C：记忆能影响理解，改不了分数）；超预算时**永不裁剪**（只砍 ③⑤）。

① 段的数据源是 `customer_memory`（跨次稳定事实，`memory_repo.active_rows`）：每次评估落库时，
把模型产出的 8 个结构化槽位（`profile_struct`）**在同一事务里**归并进去 —— 同值只刷新
`last_seen`，变值把旧行标 `superseded` 再插新行，"未提及"**不删**（只在 ① 里标注
"上次会话未提及"），人工改判的值模型覆盖不了。默认 180 天到期（`memory_ttl_days`）。
开关 `ctx_memory`（总闸）与 `ctx_memory_source`（`table` = 读记忆；`assessment` = 退回只读上次
评估，**零代码回滚**）。

⚠️ 兴趣点链走 `delta=False`（只给"最近 N 条客户发言"），**不装配记忆** —— 它要回答的是
"客户在关心什么"，不是"这个客户值不值得跟"，历史结论会污染选题。

三段**合并去重**（④ 优先，保住 `_pinned`）后**统一编号**（`#001 [时间] 角色: 内容`，编号即契约里 `evidence_ids` 的引用键，渲染与校验共用一份实现）。

## 4.4 预算与裁剪

上下文有**硬预算**。超预算时按固定顺序裁：先砍 ⑤ 兜底窗口 → 再收缩 ③ → ④ 只"保留最新、按维度收缩"，**永远不整体砍掉 ④**（它的存在意义就是捞回被窗口挤掉的事实）。

**不引入权重**：`rules.json` 里没有 `weight` 字段，裁剪不按"规则权重"排序 —— 权重会引入一套无人能用数据校准的直觉参数。

## 4.5 唯一入口

"消息 → 文本"的逻辑只存在于 `ctx_preprocess.py`（`render_lines` / `type_label` / `role_of` / `build_llm_context`）。任何页面、任何导出工具、任何提示词都从这里取，不允许第二份实现 —— 否则"编号规则"一变，契约校验与渲染立刻错位。

# 5. 评分规则与版本

## 5.1 `rules.json` 结构

```jsonc
{
  "rule_version": "v1.1",
  "score_bounds": { "min": -12, "max": 13 },
  "scoring_policy": {
    "positive": "同一维度命中多个档位时只取最高分；不同维度可累加；总分上限 +13。",
    "negative": "扣分维度可叠加；总分下限 -12。",
    "final":    "raw_score = 加分合计 + 扣分合计，并按上下限截断。"
  },
  "grade_thresholds": [ { "min": 6, "grade": "S", ... }, ... ],
  "positive_rules": [ { "rule_id": "...", "dimension": "...", "options": [
      { "score": 2, "criteria": "...", "examples": { "positive": [...], "negative": [...], "ambiguous": [...] } } ] } ],
  "negative_rules": [ ... ]
}
```

- **`polarity` 由分组决定**（在 `positive_rules` 里就是正向），规则体里不写极性 —— 少一个能写反的地方。
- **`options[]` 是档位**：同一规则的不同强度各占一档，`score` 互不相同（加载期校验）。`examples` 三档（positive / negative / ambiguous）会被注入提示词，用来钉住边界。

## 5.2 规则清单（15 条）

正向 8 条：`positive_coder_profile`（程序员/转型画像）· `positive_clear_work_need`（明确职业需求）· `positive_cooperative`（配合度高）· `positive_urgency`（紧迫感）· `positive_learning`（学习意愿）· `positive_attended_class`（到课/完课）· `positive_high_tier_city`（高线城市）· `positive_ask_course`（主动问课程）

负向 7 条：`negative_price_haggling`（追着问价格）· `negative_bad_attitude`（态度差）· `negative_low_cooperation`（配合度低）· `negative_low_recognition`（认可度低）· `negative_self_study`（要自学）· `negative_no_reply_2d`（**引擎规则**：48h 未回复，由代码算）· `negative_refuse`（明确拒绝）

## 5.3 等级阈值与建议

| 分数 | 等级 | 优先级 | 建议动作（写进结论，供销售执行） |
|---|---|---|---|
| ≥6 | S | 最高 | 每日重点跟进；课后 30 分钟内跟进并推动关单 |
| ≥4 | A | 高 | 每日 1 次有效跟进，重点推动到课与预定 |
| ≥2 | B | 中 | 隔日有效跟进，以价值内容与公开课邀约培育 |
| ≥0 | C | 低 | 每周 1–2 次低打扰触达，等主动咨询信号 |
| <0 | D | 暂停 | 停止一对一深度跟进，进长期激活池 |

阈值区间**覆盖 (-∞,+∞) 且 `min` 严格递减**，由加载期校验强制 —— 一条规则改坏档位，单测很难发现，必须在加载期拦下。

## 5.4 版本化与发布

- 规则按 `rule_version` 版本化：库里 `scoring_rule` 保存**当前版本快照**（含 `effective_at`），结论行记下当时用的是哪一版。
- **版本变化会让已评会话重新进入候选**：增量条件里本来就有"规则版本不同"这一条，所以发布新规则不需要全量重跑命令。
- **换规则不需要重建镜像**：`rules.json` / `interests.json` 以**只读卷**挂进容器（`docker-compose.yml`），而 `rules.load_rules()` / `interest.load_taxonomy()` 每次调用都读文件（后者按 mtime 缓存）—— 所以流程是「改文件 → 校验预览 → 发布 → 下一轮生效」，不重启、不打断跑批。
- **发布前先预览**：`POST /api/scoring/rules/validate`（评分中心「规则草稿预览」）吃一份完整草稿，跑加载期校验并返回**新增/删除/改档/改阈值**的差异，**不落盘**。它回答"我改了什么"；闸6 回答"指标有没有降"。两者都不通过就不该发布。
- **版本号必须升**：不升 `rule_version` 时闸6 不触发、旧结论也不会重评 —— 表现是"规则悄悄变了、分数没变"。预览接口对这种情况会明确警告。
- **发布通道**：`POST /api/scoring/rules/publish`（评分中心也有按钮）→ 先过**闸6 门禁**（第八章）→ 通过才生效；确有理由强推用 `force=true`（写审计）。
- **不发布就等于没改**：门禁会挡住日常评分（且调度器只打一行日志），所以改完 `rules.json` 必须走发布。

# 6. 置信度与策略

## 6.1 三层合成

| 层 | 含义 | 权重 |
|---|---|---|
| 证据质量 | 引擎规则 1.0 · 精确引用 1.0 · 多处呼应 0.8 · 模糊匹配 0.7 | 取最优项 |
| 覆盖 / 漏检 | 有规则被漏检 → 罚 0.5；无正向项 0.5；无文本 0.5 | 下调 |
| 结构风险 | 与上次等级翻转 → 罚 0.1；与上次判断一致 → 奖 0.1；引擎项 → 奖 0.05 | 微调 |

最终 `session_confidence` ∈ [0,1]，并记录 `review_reasons`（机器可读）与中文文案分离。

## 6.2 触发人工复核的原因（由规则判定，不听模型自报）

`has_negative`（有语义负分项）· `engine_negative_only`（仅引擎硬指标）· `unchecked_rules`（有规则漏检）· `low_confidence`（< 阈值 0.5）· `grade_boundary`（分数卡在等级分界）· `weak_evidence`（高权重项但证据不硬）· `grade_flip`（与上次等级明显翻转，≥2 档）

## 6.3 三档动作

| 动作 | 条件 | 含义 |
|---|---|---|
| `auto` | 置信度 ≥ 0.95 且无阻断性原因 | 允许自动执行（回写 / 打标签） |
| `confirm` | 0.80 ≤ 置信度 < 0.95，或等级处于边界 | **人工二次确认后**才写 |
| `human` | 置信度 < 0.80（**优先判**），或命中高风险规则 | 只进人工复核，不进自动链路 |

**判定顺序即语义**：① 无置信度 → `human`；② **置信度 < `confirm_min` → `human`（优先于高风险/阻断原因）**；③ 有高风险动作或阻断性复核原因 → `confirm`；④ 按阈值给 `auto` / `confirm`。
第 ② 条先判很关键：否则 "0.1 置信度 + 高风险" 会被判成 `confirm`，等于"有人点一下批准就能把一条几乎不可信的结论写进微伴"。

阈值与动作原因随判定一起落 `policy_decision`（含阈值快照）—— 回答"当时为什么这么判"必须有当时的阈值，而不是今天的。

## 6.4 为什么策略门只拦 `live`

`dry_run` 不写外部系统、没有副作用，拦它只会改变默认配置下的行为、打乱既有运维习惯。**策略门只拦真有副作用的动作** —— 这是"闸门开在该开的地方"的具体体现。

# 7. 行动层（回写 · 标签 · 复核）

## 7.1 分数回写的核心结论：只能累加，所以只能写差值

微伴「添加客户评分」是**累计行为分，没有覆盖接口**。因此：

- 写进去的必须是**增量**：`本次 positive_total − 客户已回写水位`；
- 整值回写在累加语义下会让分数虚高（同一次评估被反复累加）；
- 水位 `writeback_ledger.written_total` **只增不减**，且**只有真投递成功**才推进（dry_run 不推进、失败不推进 —— 否则差值被吃掉，重试时无分可写）。

**入队时差值就固化了**：出队重试时不再重算（水位会被别的任务推进，重算会得到不同的数）。

**写回前的身份自检**：两条写回都只靠 `staff_id + external_user_id` 定位客户，而"库里的
`target_id` 就是微伴的 `external_user_id`"曾经只是假设。`GET /api/scoring/writeback/identity-check`
（评分中心治理卡里的「写回身份自检」按钮）拿同一员工的客户列表逐一对账，返回
命中/缺失清单 —— **只读、不写任何数据**。实测（2026-10-19，3 个员工 385 个客户）命中率 100%；
缺失项意味着"关系已解除/换员工"，这类客户写回必然失败，应先处理关系而不是让它反复重试。

## 7.2 待办与重试

`writeback_outbox`（`UNIQUE(assessment_id)`）：与结论**同事务**入队 → 失败按指数退避重试（含 ±30% 抖动，避免同时重试冲击微伴）→ 超上限转 `dead` 终态待人工。`score_writeback` 记每次投递的结果，`UNIQUE(assessment_id)` 保证"一定只落一行"。

### 7.2.1 结果未知的行**绝不自动重投**

失败分两类，处置**刻意不同**：

| 失败形态 | 判据 | 处置 |
|---|---|---|
| **明确失败** | 对端回了 HTTP 状态码，或回了业务 `errcode != 0` | 按退避重试（可重投） |
| **结果未知** | 超时 / 连接被重置 / 进程被杀（请求可能已经送达） | **停投**：置 `dead` + `needs_reconcile=true`，等人工对账 |

为什么必须分开：微伴「客户评分」是**累加、无覆盖接口**，重投就会**多加一次分且无法撤销**。
进程被杀时卡在 `sending` 的行同样按"结果未知"处理（`reclaim_stuck_sending(unknown_outcome=True)`）——
标签队列不适用这条（标签是覆盖语义，重投无害）。

**对账入口**：`GET/POST /api/scoring/writeback/reconcile`（评分中心「待对账的回写」卡片）。
判据是**读回客户当前累计分**（`weiban.list_external_users`）与水位比对；
`written=true` → 补记账 + 推进水位（不推的话下次差值会把这笔分再写一遍）；
`written=false` → 恢复待投递。两者都写审计。

配额与幂等（`hooks.before_writeback`）：单轮上限、单客户每日上限、同一评估只写一次、模式开关（`off` / `dry_run` / `live`）。

## 7.3 回写审批队列

**只有 `confirm` 进审批队列**（`human` 见下）。登记 `approval_request` 时挂 `assessment_id`、**不阻塞批次**，在「评分中心 → 回写审批队列」人工签字：

| 决定 | 系统行为 |
|---|---|
| 批准 | 放行该条待办（`next_attempt_at` 拉回当下），下一轮排空投递；仍要求 `writeback_mode=live` |
| 驳回 | 待办置 `dead` 终态，不再投递（微伴那边不会有任何变化） |
| 过期 | 就地标 `expired` 并拒绝再签（分数/会话/阈值都可能已变，隔夜签字没有意义）；有效期 `writeback_approval_expires_minutes`（0 = 不过期） |

只有 `live` 模式才登记审批：dry_run 本就不打算写，拦它没有意义。

**`human`（低置信度）不进审批队列**：它的待办被直接停投（`dead`）并写明"先完成复核/改判并重评该客户"。
若 `human` 也能走审批，审批队列就成了绕过复核的旁路 —— 低置信度的结论只要有人点一下批准就能写进微伴，与 `human` 的定义（只进人工复核）自相矛盾。

## 7.4 等级标签（与分数回写**完全独立**）

- 为什么独立：微伴「客户评分」只能累加，表达不了**降级**；标签有增有删 → `tag/batch_update` 一次 `add` 新等级 + `remove` 旧等级 = 天然的**覆盖语义**。
- 三个独立开关：`grade_tag_mode`（off / dry_run / live，**默认 off**）· `grade_tag_group`（标签组名）· 标签 id 缓存（`tag_id` 未就绪时**延后**而不是失败，避免"没同步标签就把流水打成一堆 failed"）。
- 入队时把**旧等级标签 id 固化**进待办：出队重试不能再算一次（水位已变）。
- 人工干预入口：同步标签（拿 `tag_id`）· 创建缺失标签（真实建，需确认）· 对齐预演 / **执行对齐（真写微伴，需确认，最多 200 位）** · 立即投递队列。

## 7.5 负分复核队列

有负分项 → 入 `negative_review`（**一次评估只建一条**复核单：`ON CONFLICT(assessment_id) DO NOTHING`）→ 人工填"实际扣了多少、为什么" →
**同一个事务**里三件事一起落：队列落人工结论、结论行落 `verification_status`（`verified` / `corrected` / `rejected`）、**并按人工负分重算该结论的总分与等级** → 改判同时**回流成评估样本**（`meta_loop.backflow_reviews`）。

**改判必须真的修正这个客户**（2026-10-16 修正）：此前只写队列与 `verification_status`，结论行的 `raw_score`/`grade` 一个字都不改 ——
于是"人工改判"只对以后的规则有用，客户在微伴上的分数与等级标签仍是 AI 的错判。
重算是**纯本地确定性**的（`raw = positive_total + 人工负分`，按上下限截断 + 阈值定级）：不重跑模型、
不动 `last_msg_time`/`rule_version`（否则会触发增量重评）、不动回写水位与账本（`positive_total` 未变 → 下次差值不变 → 不会重复累加）。
**已写进微伴的分数不会被撤回**（微伴无覆盖接口），修正后由下一轮同步/标签对齐收敛。

**AI 原始扣分与人工结论分字段存**（`ai_negative_items` / `human_negative_items`）：互相覆盖就再也回答不了「AI 判错了什么」，而误报率与误报排行（`meta_loop`）正是靠这个差值算的。

只有**改判过**的才回流：与 AI 一致的复核只是确认、不带来新信息，回流只会稀释评估集。

# 8. 评估集与回归门禁

## 8.1 三层样本

| 层 | 用途 | 来源 |
|---|---|---|
| `golden` 金标准 | 盯"判得准不准"的基准 | 抽样 + 人工标注 |
| `regression` 回归集 | 盯"改坏了没有" | 人工改判回流 |
| `edge` 边界集 | 盯"最容易判错的样本" | 人工挑边界样本 |

抽样从"达标会话"里**分层抽**：按「等级 × 是否有负分」分组，组内再按消息数分档轮转 —— 分层维度直接决定样本能覆盖到什么。

## 8.2 标注口径

只标**命中了哪些 `rule_id` + 哪个档位**，不标总分（总分是算出来的，标总分等于把规则抄一遍）。

**AI 预标注 = 草稿（`prefilled`），默认不计入指标**：草稿是 AI 自己的答案，用它算指标就是「AI 批改自己」，F1 必然虚高。草稿要经人工「判对」或「保存修改」才转成金标准。

## 8.3 固定锚点与失效检测

- 样本记 `anchor_ts`（抽样时那次评估的时刻），跑分时用它当 `as_of`，**同一批样本换天跑结果一致**；
- 样本记 `messages_hash`，跑分前比对：会话内容变了 → 该样本漂移失效、跳过（`drift`），不拿脏样本算指标。

## 8.4 指标

`rule_f1`（命中项 F1，可选排除引擎项 → `rule_f1_llm`）· `precision` / `recall` · `grade_acc`（等级一致率）· `fp_case_rate`（误报率）· `engine_drift_rate`（引擎项与人标不一致率）·
`case_total` / `case_valid`（有效样本数）/ **`case_skipped`（内容不足被跳过）/ `case_error`（模型、契约异常没跑成）**。

**「跳过」与「没跑成」必须分开**：`skipped` 是内容不足（生产链路本来也会跳过，合理排除）；
`error` 是模型/契约异常 —— 它**不进指标分母**，所以**必须单独计数并披露**。
否则「模型抽风」会静默变成"这轮样本少了几条"：有效样本变少 → 容差 `max(2%, 1/有效样本数)` 变宽 → 保护被悄悄放松。

## 8.5 基线

基线 = 一次跑分结果的冻结快照，是门禁的对比参照。**库内持久**（`app_setting.eval_baseline_run_id` → `eval_run` 行），`eval/baseline.json` 只作兜底与人工留档（文件丢过，所以不能只靠文件）。每轮跑分把"对比的是哪条基线"写进 `eval_run.baseline_id`。

基线缺失的指标会被门禁**明说"本次不受保护"**，而不是安静地当通过。

## 8.6 门禁三结果与两步发布

| 情况 | `blocked` | 说明 |
|---|---|---|
| 门禁关闭 / 无基线 / 无已标注样本 | false | **放行但 `decidable=false`** —— 无法判定 ≠ 通过，界面与日志都要看到 |
| 有基线且指标未下降 | false | 正常通过 |
| 有基线且指标下降（超容差） | **true** | 拦截，附逐指标 diff |
| 有基线、但有样本未跑成 | 视占比 | `reason` **必须写明**「N 条未跑成、指标不完整」；占比 ≥20%（`CASE_ERROR_UNDECIDABLE_RATIO`）→ `decidable=false`（放行但不代表通过），请重跑一轮 |

**容差随样本量**：样本 30 条时 1 条翻转就是 3.3pp，固定 2% 的门槛会被单条抖动击穿 —— 所以容差取 `max(2%, 1/有效样本数)`。

**两步发布**（`eval_publish_requires_run=true`）：先 `POST /api/eval/start` 后台跑一轮（十几分钟，**不要用同步的 `/api/eval/run`**，浏览器 120 秒就断），再带 `eval_run_id` 发布；该跑分必须**对版**（规则版本 + 提示词版本一致）且**新鲜**（`eval_gate_fresh_minutes` 内），否则算"无法判定"。

## 8.7 覆盖度与定期回归

- **覆盖度**（`/api/eval/coverage`）：哪些规则**一条样本都没有** —— 那些规则"改坏了也测不出来"，评估集页直接显示；
- **定期回归**：`eval_regression_cron`（默认每周一 09:00）跑一轮，指标回退写审计 `eval_regression_failed`；
- **整轮异常也要留痕**：后台跑评估若中途抛异常，落一条 `eval_run(status='failed', error=…)` + `eval_run_failed` 审计（此前只写进程内状态 —— 重启即失、库里零记录）；
- **告警聚合**（`/api/eval/alerts`）：门禁回退 · **未跑成的样本数**（`eval_case_errors`）· 单规则误报率 · 复核积压 · 凭据/同步新鲜度 —— 评估集页顶部直接展示。

# 9. 同步与存档

## 9.1 取数窗口（三条规则缺一不可）

1. `start_time = 水位 − sync_overlap_minutes`（默认 15 分钟）：微伴消息会**乱序/迟到**入库，不重叠就会永久跳过它（重复由 `PRIMARY KEY(staff_id, session_id, message_id)` 幂等吸收，代价只是少量重复请求）；
2. `end_time = 本轮开始 − 60 秒`：本轮**固定上界**。接口是"按时间逆序 + offset 分页"，不固定上界时翻页途中的新消息会把整页往后挤，边界那条被跳过；
3. 水位 = `sync_cursor.last_msg_time`（会话级）；首次同步（水位 0）取全量。

## 9.2 两条硬上限

- **每员工会话数 `max_sessions_per_staff` 上限 200**：它直接决定外部调用量（每个会话还要再拉消息 + 调企微解密）。不封顶时"全量 + 不选员工"就是全部员工 × 上千会话。收敛在服务层**单点**完成，API / 调度器 / 脚本三条路都绕不过。
  **这道上限在翻页时就生效**（够 200 条即停止翻页），不是"翻完再截"——否则为 200 条付十几二十页的请求，而调用方随后就把多余的丢掉。
- **会话列表翻页上限 `sync_session_page_cap`（默认 20000）**：撞到就停，并把 `truncated_count` / `truncated_staff` 写进任务详情、在「同步中心」显示 —— 截断必须可见，不能静默。

## 9.3 凭据

微伴后台**只有企微授权登录**（没有账号密码），所以凭据链路必然带浏览器：`wb_bootstrap` 在**宿主机**扫码产出 `.cache/ww_bootstrap.json`，容器通过 volume 读同一份。登录态**滑动过期**（约 7 天），且企微正文通道的 `open_sid` **更短命**（会先死）。

续期要**打开浏览器重建会话**，因此：

- **容器里的 `credential-keepalive` job 必然失败**（没有 Chrome，`keepalive_last.code=4`）—— 它只负责把失败如实写进状态，不负责续期；
- 真正的保活必须在**宿主机**跑 `python wb_keepalive.py`（`ensure_credentials` 会先验 cookie 年龄 + 正文通道，只在需要时才开浏览器）。**项目没有自带这个宿主机计划任务**：不配的话，大约每 3~7 天同步就会因凭据过期断一次（2026-10-19 就是这样断的：`createOpenChatSession … missing session`）。

结果落 `app_setting.keepalive_last`（`GET /api/sync/keepalive` 可查，`source` 会写清是谁触发的）。

## 9.4 互斥与失败处置

- **互斥是"各自有指向的"，不是"全局只许一个批"**（唯一判定出处 `job_service.running_kinds`）：
  - **同步 ⊥ 评分**：只要有一条 `status='running'` 的 `sync_job`，评分启动会被拒绝 —— 评分读到半截会话会得出错误结论；
  - **评分 ⊥ 兴趣点提取**：两者都调大模型（同一份配额、同样的排队时长），同时跑只会互相拖慢；
  - **同步 ∥ 兴趣点提取**：兴趣分析**只读**消息、不写回任何外部系统，不必阻塞 20:00 的日常同步。
- 取不到正文的会话落 `session_failure`，由 `failure_worker` 按退避重投，超上限转人工；
- 正文解密走企微接口（纯 HTTP），由 `ww_chatdata` 负责，抓取失败不影响元数据落库。

# 10. 数据模型

**31 张表按职责分七域**，每域都有明确写入口（"谁能写这张表"是硬约束）：

| 域 | 表 | 唯一写入口 |
|---|---|---|
| 存档 | `staff` · `chat_session` · `chat_message` · `sync_cursor` · `sync_job` | `sync_service` |
| 结论 | `customer_intent_assessment` | `assessment_repo` |
| 记忆 | `customer_memory`（每客户每槽位一条 active；历史值留 `superseded`） | `memory_repo` |
| 规则 | `scoring_rule`（版本快照） | `scoring_service.sync_rules` |
| 行动 | `writeback_outbox` · `score_writeback` · `writeback_ledger` · `grade_tag_outbox` · `grade_tag_ledger` · `negative_review` | `outbox` / `writeback_repo` / `grade_tag` / `review_repo` |
| 评估 | `eval_case` · `eval_run` | `eval_case_repo` / `eval_runner` |
| 兴趣点 | `interest_scan`（每会话一行的提取结果 + 增量水位） · `interest_run`（运行行） | `interest_repo` / `interest_service` |
| 任务与观测 | `task` · `task_step` · `approval_request` · `scoring_run` · `session_failure` · `trace_span` · `policy_decision` · `audit_log` · `tool_audit` | `task_runtime` / `job_service` / `failure_worker` / `trace` / `policy` / `audit` |
| 基础设施 | `app_setting` · `request_guard` · `login_session` · `credential` | `db.setting*` / `idempotency` / `security` / `auth_service` |

**几条必须知道的口径**

| 口径 | 结论 |
|---|---|
| `relationship_key` | `staff_id:target_id`，是**一个客户在一个员工名下**的稳定主键；同一键下只有一条 `is_current=true` 的结论（同事务替换旧行并记 `superseded_by`） |
| `is_current` | 列表/门禁只看当前有效行；历史行保留，用于回答"这个客户是怎么一路变过来的" |
| `content_state` | 消息正文是否取到（`ok` / 其他）；"正文未解密"的红标与"已解码 %"都由此而来 |
| `data_as_of` | 这条结论用的时间锚点（与 `compute_facts` 同一个值），可复现性的落点 |
| `policy_action` | 当时策略判到哪一档 —— 回写与异步排空都读它（避免"同步一套、异步另一套"） |
| `writeback_outbox.needs_reconcile` | 该行的投递**结果未知**（超时/断连/进程被杀）：已停投、等人工对账，**不参与自动重投** |
| `msg_time` + `message_id` | 消息翻页用**复合游标**（秒级时间戳会重号，只按秒翻页会丢同秒消息） |
| `interest_scan.last_msg_time` | 兴趣分析的**独立水位**（与评分的 `assessment.last_msg_time` 互不影响）：候选 = "有正文 且 (没分析过 或 水位落后)"，因此增量、幂等、可续跑 |
| 兴趣点的计数口径 | 一律 `count(DISTINCT relationship_key)` = **多少客户**关心；`mentions`（兴趣点条数）只作第二指标 —— 同一客户反复问同一件事不该被算成多个客户 |
| `customer_memory` 的来源与优先级 | 每次评估的 `profile_struct` 归并进记忆；`source='human'`（人工改判）**不会被模型覆盖**；"未提及"**不删除**已有事实；默认 180 天到期（`memory_ttl_days`），过期不进上下文 |
| 记忆不是证据 | ① 段用 `【】` 段标、**不带 `#编号`**、不进 `index` —— 模型不能把记忆当 `evidence_ids` 回链（决议 M-C 的延续） |
| 表结构治理 | 不用迁移框架：`schema.sql` 是唯一定义，`schema_check` 检测漂移（缺表/缺列/多列） |

# 11. 安全与权限

## 11.1 三道边界

1. **信任边界**（模型侧）：聊天记录是**完全由外部写入的文本**，与"规则/系统指令"同段进提示词时可能被当作指令。对策是**结构隔离**（外部内容放进显式标记的不可信区块 + 清洗正文里出现的标记 + 系统提示声明信任规则），不是"再叮嘱模型一句"。后果很实在：本系统会**真改微伴客户数据**。
2. **权限边界**（接口侧）：四档角色，危险动作按角色守卫（`api_guard.require(...)`）；`viewer` 只读。
3. **写外部系统的边界**（动作侧）：真写微伴的路径都必须显式开启模式 + 二次确认 + 审计留痕（回写模式、标签模式、规则发布 `force`、保留期清理、对齐执行、创建缺失标签、审批批准）。

## 11.2 登录双通道

- 浏览器：走应用自己的**登录页**（用户名 + 口令 + 「记住我」30 天），服务端下发 HttpOnly 会话 cookie；口令不进浏览器存储。
- 脚本 / curl：HTTP Basic 并存可用。
- 口令在部署机 `.env` 的 `API_PASSWORD`（首次为空自动生成并打印在启动日志）；多账号用 `API_USERS=用户:口令:角色,...`（格式错的条目**跳过**，不会静默提权成 admin）。

| 角色 | 能做什么 |
|---|---|
| `viewer` | 只读 |
| `reviewer` | 提交人工复核、标注评估集 |
| `operator` | 发起任务、改运行时设置、执行需确认的回写/发布 |
| `admin` | 全部 + 审计导出 / 数据清理 / 规则发布 / 建标签 |

**所有写接口都挂角色守卫**，唯二例外是 `POST/DELETE /api/auth/session`（登录/登出，必须匿名可达）。

## 11.3 审计双层

PostgreSQL（可查、可关联） + JSONL（按天轮转、可离线留存、可校验）。工具调用按**五问**记账：谁 / 什么 / 何时 / 为何 / 结果，参数**脱敏后**落库（token、cookie、口令等一律替换）。导出**不删除** —— 删除属于保留期策略，两者解耦（避免"导出失败却已删库"）。

# 12. 可观测与运维

## 12.1 任务运行时

统一 `task` / `task_step`：状态机 + 检查点 + 心跳 + 僵尸回收 + 续跑（约束见第十三章的不变式表）。三条业务批（评分 / 同步 / 兴趣点）与任务行关联（`scoring_run.task_id` / `sync_job.task_id` / `interest_run.task_id`），"这一批走到哪、下一步做什么"从库里可查，不靠日志猜。

## 12.2 指标

评分中心一屏可见：已评客户 / 待复核 / 已完成复核 / 回写成功与演练 / 平均分 / **人工与 AI 一致率** / 等级分布；另有每轮运行记录（会话数、新增评分、转复核数、回写成败、**整轮用时**、停止原因）。

| 审计（audit） | `audit_log` / `tool_audit` | 0 = 不清理 |
| 任务（task） | `task` / `task_step` | 0 = 不清理 |

**业务结论表（评估结论 / 复核 / 回写账本 / 评估集 / 规则快照）永不按天数清理** —— 保留多久是业务决策，代码不替业务拍板；清理必须二次确认且可预演。

## 12.5 部署与运维要点

| 容器 | 作用 | 宿主端口 |
|---|---|---|
| `weiban-chat-pg` | PostgreSQL 16（pgvector 镜像） | 127.0.0.1:5433（排障） |
| `weiban-scoring-app` | FastAPI + APScheduler + 前端 `dist` | 127.0.0.1:8848 |
| `weiban-scoring-proxy` | Caddy TLS（`--profile https`） | 127.0.0.1:8443 |
| `weiban-scoring-backup` | 定时 `pg_dump` + 校验（`--profile ops`） | — |

- **默认只绑 127.0.0.1**；要给多人用必须起 `https` profile（否则口令在明文 HTTP 上裸奔）。
- **代码与前端 `dist` 都打进镜像**：改了代码只 `restart` 不生效，必须 `up -d --build`；重建会重启 app 并打断正在跑的批（数据安全：水位增量 + 僵尸回收）。
- **凭据链路在宿主机**（9.3）：容器里没有 Chrome，扫码与保活必须 `python wb_bootstrap.py` / `wb_keepalive.py`。
- 重建前建议先 `POST /api/sync/stop` 并避开 20:00 / 03:30；`.\scripts\verify_image_matches_worktree.ps1` 可校验容器跑的是不是工作区这份代码。

### 12.5.1 两种部署形态（全栈容器 / 仅数据库用容器）

| 形态 | 适用 | 应用进程 | 数据库 |
|---|---|---|---|
| **A 全栈 Docker**（默认） | 服务器、长期无人值守 | 镜像内 uvicorn + APScheduler + `dist` | compose 的 `postgres` |
| **B 仅 PG 用 Docker** | 开发机 / 单台 Windows / 需要本机浏览器 | 原生 `start_backend.bat` | 同一个 compose 的 `postgres` |

两种形态**代码与 schema 完全一致**，差别只在"谁托管进程"。形态 B 的步骤：

1. `docker compose up -d postgres`（只起库；宿主端口 127.0.0.1:5433）；
2. `py -3.13 -m venv .venv` → `.venv\Scripts\python.exe -m pip install -r requirements.lock.txt`；
3. `.env`：`DATABASE_URL` 的口令与 `POSTGRES_PASSWORD` 一致；**不要**设 `BROWSER_ENABLED=0`（那是容器专用）；
4. 前端：`cd frontend && npm ci && npm run build`（或把别处构建好的 `dist/` 复制过来）；
5. `start_backend.bat`（127.0.0.1:8848）；局域网用 `start_backend_lan.bat`（0.0.0.0，**必须先配口令 + HTTPS**）。

形态 B **更好**的三点：

- `credential-keepalive` 能真正工作（本机有 Chrome；容器里必然失败）——不必再挂宿主机保活任务；
- `rules.json` / `interests.json` 就地改、即时生效（不需要卷挂载，也没有"重建镜像"这一步）；
- 改代码重启进程即可，前端改完只需重新 `npm run build`。

形态 B 的**硬约束**（违反会出问题）：

- **单实例**：调度器、互斥判定、内存进度都假设单进程 —— 不要 `--workers 2`，也不要同时起两份；
- **不要用 Windows 服务（Session 0）**：扫码/保活要弹 Chrome，必须在有桌面的登录会话里跑（任务计划程序"登录时启动"）；
- **`POSTGRES_PASSWORD` 只在首次初始化数据卷时生效**：改 `.env` 不会改已有口令，只有 `DATABASE_URL` 变 → 连不上；
- **没有 backup 容器**：自己加计划任务 `pg_dump`（结论与回写账本不可逆，必须备份）。

## 12.6 配置面

72 项运行时配置注册在 `settings_registry.py`（键 / 类型 / 默认值 / 说明的**唯一来源**），分 13 组：
`ctx` 15 · `eval` 10 · `scoring` 9 · `llm` 8 · `schedule` 7 · `confidence` 5 · `interest` 6 · `memory` 2 · `writeback` 3 · `grade_tag` 3 · `pipeline` 2 · `observability` 1 · `retention` 1。

取值优先级：`app_setting`（库内，可在界面改） > `.env` > 注册表默认值。

非法值**拒绝落库并说明原因**，合法键照常保存（一处实现，所有键受益）。**保护类配置**（默认开启的安全/正确性开关）与观测类默认值有清单自检（`defaults_manifest`），被关掉会在启动日志里吵。

# 13. 运行时不变式

系统在**任意时刻**都必须成立；违反即为缺陷。落地方式以代码为准：

| # | 不变量 | 强制方式 |
|---|---|---|
| INV-1 | 每个 `relationship_key` 恰有 1 条 `is_current=true` 的结论 | 同事务替换 + 启动自愈 |
| INV-2 | 每个 `assessment_id` 在 `score_writeback` 至多 1 行 | `UNIQUE(assessment_id)` |
| INV-3 | `writeback_ledger.written_total` 只增不减；`delta ≥ 1` 才入队 | `writeback_repo` 单入口 |
| INV-4 | 每个 `relationship_key` 在 `grade_tag_ledger` 至多 1 行 | `PRIMARY KEY(relationship_key)` |
| INV-5 | `task.status` 处于终态时不得再迁出 | `task_runtime.TERMINAL` + 状态机守卫 |
| INV-6 | 同一 `task_id` 的 `task_step.seq` 严格递增；`last_step_seq` = 最后一个 succeeded | `step_begin()` 取 `max+1`、`GREATEST` 维护 + **`UNIQUE(task_id, seq)`**（schema.sql 已声明，多实例并发也不会重号） |
| INV-7 | 提示词中「外部内容段」与「指令段」结构分离，外部内容不得被当作指令解析 | 结构隔离 + 专项测试 |
| INV-8 | 同一幂等键至多产生一次外部副作用 | `request_guard` 唯一键（手工端点）；工具级随网关未做 |
| INV-9 | `rule_f1` 等指标只在**同一时间锚点**下可比 | 样本固定 `anchor_ts` |
| INV-10 | `grade_thresholds` 单调递减且覆盖 `(-∞,+∞)`；`score_bounds.min < max` | **加载期校验** `validate_rules()` |
| INV-11 | 同一规则各档 `options[].score` 互不相同；`polarity` 由分组决定；`engine='rule'` 不进 LLM 规则集 | 加载期校验 + 遍历断言 |
| INV-12 | 任何有副作用的工具调用必有审计记录 | 已覆盖"真写微伴分数"；其余随网关未做 |
| INV-13 | 结论与回写待办**同事务**落库（否则"结论有了、回写丢了"） | `persist` 单事务 |
| INV-14 | 人工复核的结论必须能回流成评估样本 | `meta_loop.backflow_reviews` |
| INV-15 | 同步与评分不得并发（同库只允许一条 running 的业务批） | 启动前互斥检查 |
| INV-16 | 规则版本变化后，已评会话必须重新进入候选 | 候选增量条件含"规则版本不同" |
| INV-17 | **结果未知**的回写**不得自动重投**（累加语义下重投 = 多加一次分且不可撤销） | `_unknown_outcome()` 分类 + `needs_reconcile` 停投 + 人工对账 |
| INV-18 | 人工改判（`corrected`/`rejected`）必须**修正结论**的总分与等级 | 复核提交同一事务内 `apply_human_correction()`（本地重算，不重跑模型） |
| INV-19 | 评估里「没跑成」的样本必须**单独计数并披露**（不得与「跳过」合并、不得静默退出指标） | `metrics.case_error` + 门禁 `reason` + `alerts.eval_case_errors` + 评估集页标红 |
| INV-20 | 批量的**整轮失败**必须有落库载体（不只写进程内状态/日志） | 评估：`eval_run(status='failed')` + `eval_run_failed` 审计；同步/评分：`sync_job`/`scoring_run`；单会话：`session_failure` |
| INV-21 | 每个 `(staff_id, session_id)` 至多 1 行 `interest_scan`，且水位只增不减 | `PRIMARY KEY(staff_id, session_id)` + `upsert_scan` 的 `GREATEST` |
| INV-22 | 兴趣点**必须带能回链到具体消息的证据**；回链不上的条目不得入库（只计数） | `interest.to_rows()` 丢弃 + `interest_run.dropped_points` 落库 |
| INV-23 | 兴趣链**只读**消息，不产生任何外部副作用（不写微伴、不回写分数/标签） | 该链无写外部系统的代码路径；写操作只有 `interest_scan` / `interest_run` 两张自有表 |
| INV-24 | 每个 `(relationship_key, slot)` 至多 1 条 `active` 记忆；历史值只以 `superseded` 存在 | 部分唯一索引 `uq_memory_active` + `memory_repo` 单入口 |
| INV-25 | 记忆与结论**同一事务**写入；记忆永不出现在 `index` 里（不是证据） | `_persist_assessment` 内调 `memory_repo.apply_in(conn, …)`；① 段渲染不带编号 |

# 14. 兴趣点提取链（第二条模型链）

## 14.1 它回答什么（为什么与评分**并列**而不是它的一个字段）

推广要"从聊天记录里找选题"：**客户在关心什么** —— 而评分回答的是"这个客户值不值得跟"。
两者口径不同（关注点 vs 转化力）、更新理由不同（兴趣随对话变、分数随规则变）、失败处置
不同（一个失败不该拖累另一个）。分开之后各自增量、各自重跑、各自可观测，代价只是每会话
多一次模型调用。

| 维度 | 评分链 | 兴趣点链 |
|---|---|---|
| 问题 | 这个客户值不值得跟 | 客户在关心什么（选题） |
| 输入 | 消息 + 事实 + 关键历史 + 记忆块 | 最近 N 条**客户发言**（`delta=False` + `customer_only=True`，员工的发言整体剔除） |
| 产出 | 分数 / 等级 / 画像 / 话术（写回微伴） | 一级分类 + 二级标签 + 证据原话（只进库与站内展示） |
| 单位 | 客户（`relationship_key`） | 会话（每会话一行），**计数时按客户去重** |
| 增量 | 水位 = 结论的 `last_msg_time`；规则版本变了也重跑 | 水位 = `interest_scan.last_msg_time`；只有新消息才重跑 |
| 外部副作用 | 有（分数回写、等级标签） | **无**（INV-23） |

## 14.2 技术路线：受控分类 + 证据回链

一级分类由 `interests.json` **受控**（模型选别的会被契约拒绝并触发回灌重试），二级标签
自由生成 —— 选题要用客户自己的说法；每个兴趣点必须给出 `#编号`，经
`ctx_preprocess.resolve_evidence` 回链成 `message_id`，并把**原话片段**一起存下来。

另外三条路都不选，理由是确定的：

- **关键词 / 正则**：漏判严重（"想转行"有几百种说法），也不懂否定（"我不打算考证"）；
- **embedding + 聚类**：要新引向量服务与依赖，而几百条会话的簇数极不稳定、跨月不可比 —— 而"可对比的分布"正是本功能的目的；
- **微调分类器**：没有标注数据，且需求是"发现新兴趣"，不是"把已知类别分类"。

复用而非另造：`contracts.prompt_schema`（注入 schema）· `analyze.judge_with_repair`（回灌修复）·
`llm.chat`（json_mode / 超时 / 截断自救）· `ctx_preprocess`（渲染与回链）· `build_context`（装配）·
`job_service` + `task_runtime`（跑批骨架与检查点）。**新写的只有"兴趣"这件事本身**：词表、
提示词、聚合 SQL、三件套图。

## 14.2.1 只喂客户自己说的话（`customer_only=True`）

输入**只有客户本人的发言**，员工的发言在装配阶段就整体剔除。理由不是"省 token"，是**口径**：
员工话术里塞满课程卖点（"现在报名有优惠""名额不多了""我们这门课……"），整段丢给模型，
模型很容易把**销售的主张**读成"客户的兴趣"—— 图上就会出现一批客户从没提过的点，而且点开
证据还是销售自己说的原话。实测数据也支持这个做法：685 个有正文的会话里员工写了 28,727 条、
客户只回了 5,731 条（中位 4 条），**83% 的语料其实是销售在说话**。

落点与两条配套纪律：

- 过滤在 `scoring_context.build_context(customer_only=True)` 里做（"取什么给模型看"仍然只有
  一个落点），"谁说的"复用 `ctx_preprocess.role_of`，**不另写一份判定**；
- 该参数**只允许与 `delta=False` 组合**（增量/关键历史/记忆块那几段混着档案与上次结论，
  按方向筛只会得到半截上下文）→ 组合错**直接报错**，不静默降级；
- 候选与覆盖度的分母同步改成**客户发言条数**（`interest_min_customer_msgs`，默认 2，
  见 14.4）：员工单方面刷屏的会话（实测 42 个）不进队列 —— 它们既提不出兴趣，又因为
  没有语料会被永远判为"待分析"。

## 14.3 数据与接口

- `interest_scan`：每会话一行（`PK(staff_id, session_id)`），`interests` = `[{primary, secondary,
  confidence, evidence_message_ids, evidence[:原话]}]`；并随行落 `taxonomy_version` / `prompt_version`
  / `model_name`，用来回答"这张图是哪版词表跑出来的"。唯一写入口 `interest_repo`。
- `interest_run`：运行行（进度 / 预算 / 心跳 / 停止 / 检查点任务），与 `scoring_run` 同形。
- 接口：`GET /distribution`（分布 + 覆盖度）· `GET /customers`（下钻：客户 + 二级标签 + 证据原话）·
  `GET /status` · `POST /start` · `POST /stop`。读接口登录即可；写接口要 `operator/admin`
  （它会真调模型、真花钱），并与其它批量一样带 `request_key` 幂等。

## 14.4 增量、预算与终态

- **候选**：**客户说过话**（可读的客户发言 ≥ `interest_min_customer_msgs`，默认 2）且总会话
  消息数达标，且"没分析过 **或** 水位落后"（`interest_repo.candidates`，与覆盖度共用同一段
  SQL）→ 天然增量、重跑幂等、中断后接着跑。这个门槛是活的：实测门槛 1/2/3/5/8 分别覆盖
  642/550/467/319/210 个会话 —— 想省调用就调高，代价是话少的客户整条被跳过；
- **可复现**：固定 `build_context(delta=False, key_history=False, limit=interest_ctx_limit)`
  并固定 `customer_only=True` —— 同一会话任何时候重跑得到同样的兴趣点，不受"上次跑到哪"
  与员工话术多少的影响；
- **两道护栏**：单轮墙钟（复用 `scoring_deadline_minutes`）与模型调用预算
  `interest_max_llm_calls`（撞上落 `partial` 并写明原因，下一轮从水位接着跑）；
- **单会话失败不拖垮整轮**：落 `session_failure`（`stage='interest_extract'`、`status='dead'`
  —— 重试由下一轮增量天然完成，不交给 `failure_worker`），且**不吞异常**：契约连续不满足会
  抛错并记账，而不是静默返回"这个客户没兴趣"（那是两件完全不同的事）。

## 14.5 呈现与合规

总览页首屏正中的「兴趣点分布图」= **树图（面积 = 客户数）+ Top-8 条形 + 二级标签气泡云**，
三张图都用 **echarts**（`treemap` / `bar` / `graph(force)`）绘制。等级切片读客户**当前有效**
的评估结论，所以"排选题优先级"能直接看 S/A 客户在关心什么。

**切片是"整张卡一起切"**：等级 / 员工一变，树图、条形、气泡云、**头部覆盖度与等级分布**
全部跟着变 —— 头部的"已分析 N/M 会话"如果仍是全局数字，读者会以为某个员工名下真有 M 个会话。
树图用 `primaries_all`（全部一级分类），条形只画 Top-8（长度可精确比较的那个视图足够）；
百分比的分母用全量客户数，不是"可见块之和"。

**为什么是 echarts**：初版是零依赖手写 SVG/CSS（squarified 布局 + 条形 + 圆环排布），当时
的理由只是"不想为一个图多引一个依赖"。但手写的代价持续存在 —— 提示框、自适应、标签避让、
无障碍都得自己补，而且同一类图一旦别处也要用就得再抄一份。改用 echarts 后那 40 行布局代码
被删除（**不是并存**），只保留了业务差异：颜色按一级 key 固定、悬浮显示"客户数 · 提及次数"、
点击开抽屉。

- **按需注册**：唯一注册点 `frontend/src/echarts.js`（`echarts/core` + `use([...])`，只装树图/条形/
  关系图 + 提示框 + 网格 + 标签避让 + Canvas 渲染器）。漏注册的表现是"图是空白的"，所以
  "本项目用了 echarts 的哪几块"必须有确切清单且只有一处。
- **代价（明说）**：前端多一个运行时依赖（2.4MB 未压缩 / 打包后主包 ~890KB、gzip ~280KB，
  之前 ~308KB）。首屏因此变重，但只影响总览页，且是本地部署、不跨网络。
- **接口**：`InterestDistribution.vue` 负责取数与抽屉，`echarts.js` 负责注册；等级切片、
  失败说明与重试仍复用 `PartialLoadBanner.vue` + `useLoadFailures`。

⚠️ **证据原话只存库与站内展示，不提供导出接口**，界面常驻一行"仅限内部选题参考，不得直接对外发布"。

**本期不做**：embedding/聚类式话题发现 · 按城市画的地理地图 · 跨周趋势线（当前样本量下曲线没有
统计意义）· 自动建词表（二级标签先人工在看板里筛，稳定后再升为一级）。

# 15. 边界：明确不做与尚未落地

## 15.1 明确不做（连同理由）

| 不做 | 理由 |
|---|---|
| 语义检索 / embedding 重排 / RAG / 向量库 / GraphRAG | 取数是**主键定位**（按规则标签取消息），不是相似度问题；引入向量库解决不了"哪些消息该进上下文" |
| 微服务化 / 消息队列 | 单机单实例的批处理，拆开只增加一致性与运维成本 |
| 迁移框架（Alembic 等） | DDL 收敛在 `schema.sql` + `schema_check` 漂移检测，够用且少一层依赖 |
| 让模型算分 / 自动调参 / 自动改规则 | 违反 1.3 的优先级：分数必须可复现、可对账 |
| SSE / WebSocket 实时推送 | 批处理场景，轮询足够（且轮询已做可见性停摆与空闲降频） |
| 多实例高可用 | 无分布式锁与任务抢占；多实例会抢同一批任务 |
| 非 Windows 宿主 | `.bat` 启动脚本、`taskkill`、`%USERPROFILE%` 是 Windows 语义 |

## 15.2 设计已定、代码未落地（现状边界，不是承诺）

- **工具网关**（统一注册表 → 权限判定 → 建审批 → 幂等 → 调用 → 审计）：没有注册表，也没有"所有工具必须经过它"的入口。当前唯一的外部工具调用是**真写微伴分数**（`weiban.add_customer_score`）：直接 HTTP + `audit.tool_call(...)` 单点审计（`tool_audit` 的 `decision` / `approval_source` / `result_status` 等字段都已建模）；`approval_request` 是**回写待办**的审批队列，不是通用工具审批。
- **记忆的"团队/全局"层**：`customer_memory` 只有**单客户**粒度（一个 `relationship_key` 一组 8 槽）。跨客户的共性（"这一批客户都在问分期"）由兴趣点分布图回答，不做"团队记忆"。
- **记忆的自动衰减**：只有 TTL 到期失效（默认 180 天）；不做"越久越不可信"的置信度衰减，也不做"长期没被提及就自动降权"。
- **`api_token` 表**：不存在；程序化访问用 HTTP Basic 即可。
- **任务级预算闸**：`task.budget_calls` / `budget_tokens` / `deadline_at` 只是**记录与展示**（建任务时写入、任务页展示、resume 复制），**没有强制点**。真正生效的是服务级的 `hooks.guard_reason`：评分与兴趣点各有一道"整轮墙钟 + 单轮模型调用上限"；`budget_tokens` 连服务级也没接。**消耗已真实累计**（`cost_calls` / `cost_tokens` 由评分/兴趣点在每次模型尝试后累加，任务页能核对）。
- **无前端入口的运维端点**（**有意如此**，走 curl；新增此类端点请登记到 `AGENTS.md`）：`/api/scoring/schema-check`、`/api/scoring/defaults-manifest`、`/api/scoring/repair-current`、`/api/scoring/audit/export`。**其余原先"只能 curl"的已经有界面**：`/eval/alerts`、`/eval/coverage`、`/eval/run-detail`、`/eval/delete`、`/review/batch-status`、`/scoring/audit/stats|tool`、批次任务 `/scoring/tasks*`、回写审批、规则发布、保留期清理、标签队列投递、单会话重评。
