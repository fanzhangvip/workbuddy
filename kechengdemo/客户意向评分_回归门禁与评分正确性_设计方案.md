# 客户意向评分 · 回归门禁与「持续正确」治理设计方案

> 状态：**待评审（尚未实施）** ｜ 日期：2026-10-15 ｜ 依据：本轮代码通读 + 生产库实测
> 范围：只治理「判定正确性的验证与发布」这条链路（评估集 / 指标 / 门禁 / 基线 / 定期回归 / 告警）。
> 不改评分规则的分值口径 —— 唯一例外是 P3 的引擎规则窗口语义，**需业务确认**（见 §8）。
> 关联：`ARCHITECTURE.md` ADR-002（三层循环）、ADR-014（链条式定时）、`客户意向评分_优化建议.md` G3~G8。

## 0. 一句话结论

评估集、指标、门禁、误报回流、人工复核这套骨架**已经建成且设计是对的**（尤其"预标注不当金标准""无法判定 ≠ 通过"这两条判断很到位）。
问题是**闸门没有通电**：基线没冻结、门禁认可的样本为 0、发布门禁是 16 分钟同步长请求、主指标被时间漂移污染。
本方案把这条链路从「有代码」变成「可信且可持续」。

## 3. 设计

### 3.1 目标与非目标

**目标**：① 门禁可判定、可拦截、可解释、可审计；② 同一批样本在任何一天跑出同样的指标；③ 模型 / 数据 / 规则任一变化能在 N 天内被发现；④ 发布不再依赖 16 分钟同步请求。
**非目标**：不做工作流引擎、不引入新中间件、不重写评估集、不把 LLM 判定改成多 Agent。

---

### 3.2 D1 · 时间锚点（修 P2）

**契约**

```python
# scoring_context.py
def compute_facts(staff_id, session_id, fetch_tags=False, as_of=None) -> dict:
    as_of = int(as_of) if as_of else int(time.time())
    ...
    hours = round((as_of - int(last["msg_time"])) / 3600, 1)
```

**改动点**

| 位置 | 改动 |
|---|---|
| `scoring_context.compute_facts` | 新增 `as_of` 参数，默认 `now()`（**生产行为不变**） |
| `eval_runner.run_case` | 传 `as_of=case.get("anchor_ts") or int(time.time())` |
| `eval_case` 新列 | `anchor_ts BIGINT` —— **取 `baseline_at`（该样本"改动前基线"那次评估的时刻）**，无则退化为抽样时刻；`prefill` 不改它（理由见 §3.2.1） |
| `messages_hash` 语义 | 保持不变（只防内容漂移）；"锚点漂移"由 `anchor_ts` 天然免疫 |
| `customer_intent_assessment` 新列 | `data_as_of BIGINT` —— 记录这次判定用的锚点，供事后解释"为什么当时判成 D" |

**验收**：同一样本、同一 `anchor_ts`，连续两天跑两次 → `metrics` 完全一致；把 `anchor_ts` 前移 3 天 → 48h 项按预期出现 / 消失。

#### 3.2.1 锚点为什么必须取 `baseline_at`（本轮实测修正）

不能取"抽样时刻"，也不能取"当前的 `last_msg_time`"，否则 D2 的窗口会变成一把随机刀：

| case | 距最后消息（今天） | 距最后消息（`baseline_at` 时刻） | 结论 |
|---|---|---|---|
| 2 / 6 / 7 / 13 / 15 / 25 / 28 | **15.2~15.5 天**（超 14 天窗口） | **13.2~13.5 天**（窗口内） | 锚点取 `baseline_at` → 这 7 条判定稳定；取"今天"→ 它们会因为过了 24 小时而集体翻转 |
| 16 / 17 / 22 / 23 / 24 / 30 | 84~99 天 | 83~98 天 | 两种口径下都超窗，属于**真正该改语义**的那批（7 条） |

实测印证：`eval_case.baseline_items` 里含 48h 引擎项的是 **17 条**，而当前草稿里是 **21 条**——同一批样本在两个时刻跑，结果不一样，这就是 P2 在评估集内部的直接证据。
取 `baseline_at` 的语义是"**在系统当时判定那一刻的输入下，判得对吗**"，这才是评估集要回答的问题。

### 3.3 D2 · 引擎规则窗口（修 P3，**需业务确认**）

**语义收紧**：从「最后一条是员工、距今 ≥48h」改为「**活跃会话**中断 48h ~ N 天」：

```python
# scoring_context.compute_facts
gap = as_of - int(last["msg_time"])
no_reply = (last.get("direction") == "send"
            and 48 * 3600 <= gap <= window_days * 86400)
```

`window_days` 取 `db.setting_int("no_reply_window_days", "NO_REPLY_WINDOW_DAYS", 14)`。

**同步改动**：`rules.json` 的 `criteria` 由"连续 48 小时未回复"改为"连续 48 小时未回复，且距最后互动不超过 N 天"；`hint` 同步说明窗口可配。

**为什么必须改**：窗口相对 `as_of` 计算 → 锚点固定则结论固定（与 D1 协同，指标不再自己跑）；同时消掉"规则变更 → 全量重评 → 半年前结束的会话平白 -2、等级掉到 D"。

**副作用（显式承认）**：超过窗口的客户不再被扣分 → 这些会话等级会**上调**，需要一次全量重评 + 备份 + 业务知悉。

**验收**：47.9h 命中 / 48.0h 命中 / N 天命中 / N+1h 不命中；老会话不再命中。

### 3.4 D3 · 基线持久化与版本绑定（修 P7）

**复用既有预留**，不建新表：

| 用途 | 载体 |
|---|---|
| 当前基线指向 | `app_setting["eval_baseline_run_id"]` → `eval_run.id` |
| 基线指标本体 | `eval_run`（已有 `metrics` / `rule_version` / `prompt_version` / `case_total` / `finished_at`） |

| 谁在何时冻结 | `audit.record_action(actor, "eval_baseline_set", "run:<id>", {...})` |

**契约变更**

```python
def load_baseline() -> dict:      # 先 app_setting → eval_run；读不到再回退 eval/baseline.json
```

`/api/eval/baseline` 的 GET / POST 保持路由不变，POST 增加 `run_id` 参数（缺省 = 最近一次成功 run）。

**验收**：冻结基线 → 重启容器 → `gate_decision().has_baseline` 仍为 true；`eval_run.baseline_id` 被填上。

### 3.5 D4 · 门禁指纹与新鲜度（修 P5）

`gate_decision()` 复用 `_STATE["result"]` 前必须核对：

```python
fresh = (cached.get("rule_version") == rules_mod.load_rules().get("rule_version")
         and cached.get("prompt_version") == analyze.PROMPT_VERSION
         and (time.time() - cached.get("finished_at", 0)) <= 30 * 60)
```

不满足 → 不复用，按 `run_if_possible` 决定现跑或返回 `decidable=false`。
`run_sync()` 的返回与 `_STATE` 需补 `rule_version` / `prompt_version` / `case_ids` / `finished_at` 四个字段（当前 `out` 里没有）。

**验收**：跑一次评估 → 改 `rules.json` 版本号 → 再发布：门禁必须拒绝复用旧结果（`stale=true`）。

### 3.6 D5 · 发布两步化（修 P4）

| 接口 | 行为 |
|---|---|
| `POST /api/eval/gate/start` | 后台线程跑评估（走已有的 `eval_runner.start()`），返回 `run_id`，前端轮询 `/api/eval/status` |
| `POST /api/scoring/rules/publish` | 新增 `eval_run_id`；校验该 run **指纹一致且新鲜**，直接用它的 `metrics` 比基线，**不再同步跑分** |
| `force=true` | 保留逃生口：跳过校验、写 `rule_publish_blocked` / `forced:true` 审计 |

**开关**：`eval_publish_requires_run`（默认 `false`）。默认关 → 行为与现在完全一致（零风险上线）；确认流程跑顺后再打开，届时前端按钮改成「跑分 → 看 diff → 发布」两步。

**前端**（`frontend/src/views/EvalView.vue`）：已有 `gate` 面板与 `<span v-for="d in gate.gate_diffs">` 逐指标 diff，只需加"跑分中…（预计 N 分钟）"进度与"用这次结果发布"按钮；`axios` 超时只作用于新的短请求。

**验收**：`eval_publish_requires_run=true` 时，不带 `eval_run_id` 的发布被拒并给出可读原因；带陈旧 run 也被拒；`force` 能过且审计可见 `forced:true`。

### 3.7 D6 · 容差与覆盖率（修 P6 / P9 前半）

1. **容差随样本量**：`tol = max(GATE_TOL, 1 / max(case_valid, 1))` —— 30 条样本时等价于"允许 1 条翻转"，200 条时回到 2pp 口径；`tol` 与实际 `case_valid` 一起写进 `eval_run.gate_diffs`，可复现。
2. **覆盖率报告**（新增 `eval_runner.coverage()`）：
   ```json
   {"rule_id": "positive_urgency", "cases": 4, "negative_cases": 0, "last_seen": "..."}
   ```
   来源：扫 `eval_case.expected_items` 的 rule_id。暴露为 `GET /api/eval/coverage`，评估页单列一块。
3. **发布时的覆盖提示**：把"本次规则变更涉及的 rule_id"（新增 rule_id + `rule_version` 变更）与覆盖率对比，任一 rule_id 样本数 < `eval_min_cases_per_rule`（默认 3）→ `decidable=false` 并在 reason 里列出具体 rule_id（**不硬拦**：硬拦会让新规则永远发不出去；先如实告知，风险由人决定）。

**验收**：新增一条规则 → 覆盖率报告新增一行 `cases=0`；发布接口在 reason 中列出它。

### 3.8 D7 · 指标口径拆分（修 P9 后半）

`metrics()` 增加两组数（**不改** `rule_f1` 现有算法，只加键，避免历史 `eval_run` 不可比）：

| 指标 | 口径 |
|---|---|
| `rule_f1`（**语义不变**） | 命中项级 F1，**含**引擎项 —— 保持与历史 `eval_run`（#100 等）可比 |
| `rule_f1_llm`（新增） | 同上，但**排除引擎项**（`engine_rule_ids`）→ 回答"判得准不准"；门禁主指标切到它 |
| `engine_drift_rate`（新增） | 引擎项的命中与人工标注的差异率 → 回答"这条硬指标稳不稳" |

`eval_run.metrics` 是 JSONB，直接加键即可，无需 DDL。

> ⚠️ **一个自己给自己挖的坑（已修正）**：本方案的早期版本写作"`rule_f1` 不变，但口径改为排除引擎项"，自相矛盾。真正的风险在于：`gate()` 对基线里**缺失的键是静默 `continue`**（`if base is None or cur is None: continue`），所以如果先冻结基线、后启用 `rule_f1_llm`，这一项会**安静地失去保护**而不报错。因此顺序必须是 **P0 先加键 → P4 再冻结基线**（与 §4.2 的顺序一致）。

**验收**：构造"人标无该项、引擎命中"的样本 → `rule_f1` 不受影响、`engine_drift_rate` > 0。

### 3.13 评估集写入门禁（修 P13 / P14 / P15）

#### 现状

`eval_case_repo` 已经是唯一写入口，但**留痕分散在调用方**、且**覆盖没有分级保护**。三个 bug 合起来构成一条完整的数据丢失链：能写（无保护）→ 写不留痕（审计带条件）→ 写完不可见（`prefilled` 被排除出指标）。

#### 设计：把"谁能写、写成什么、从什么改成什么"收进写入口

| # | 措施 | 修哪个问题 |
|---|---|---|
| W1 | `eval_case_repo` 内部统一走 `_write_with_audit(cid, changes, actor, action)`：**同一事务**内 ① `SELECT ... FOR UPDATE` 取旧值 → ② UPDATE → ③ 写 `audit_log`（detail 含 `before/after` 的 `{rule_id, score}` 集合 + grade + `prefilled`，**不含正文**）。任一步失败整体回滚 —— 从机制上消灭"写了但没留痕" | P15 |
| W2 | 删除 `eval_runner.prefill()` 里的 `if total <= 30` 审计条件；审计改由 W1 强制 | P15 |
| W3 | `set_prefill` 分级覆盖：`overwrite=False` → 只填 `expected_items IS NULL`（现状不变）；`overwrite=True` → **只覆盖 `prefilled=true` 的行**；要覆盖 `prefilled=false`（已人工确认）必须显式 `overwrite_annotated=True`，接口层用 `force_overwrite_annotated` 暴露、仅 `admin` 可用，并在审计里记 `overwrote_annotated=N` | P14 |
| W4 | `prefill` 补看 `frozen`：`frozen=true` 的样本**任何情况下**不接受预标注（现状只有 `/save` 拦冻结，`prefill` 完全没看） | P14 |
| W5 | `set_annotation` 的 `prefilled=false` 已经是正确实现（本轮已落盘），但要**加一条回归测试**钉住它，防止再次漂移 | P13 |
| W6 | 让"保存了但没生效"可见：`/api/eval/stats` 增 `prefilled_with_content`（`prefilled AND expected_items IS NOT NULL`）；`gate_decision()` 在 `decidable=false` 时把这个数写进 reason（"有 30 条已保存但仍是草稿态，重存一次即可生效"）；`EvalView.vue` 的「AI 草稿」页签显示计数徽标 | P13 的观测面 |
| W7 | 数据修复工具 `backend/eval_restore.py`：从 `audit_log` 的 `eval_annotate` payload 取出"当时保存的版本"，与**当前行内容**并排输出成对照表（每条的 `{rule_id, score}` 差异 + 建议），默认 dry-run，`--apply` 才写；写入统一走 `set_annotation`（因此会正确清 `prefilled`） | P13 的数据面 |

> ⚠️ **W7 不是"一键恢复"，这里必须纠正我早期的说法**：审计里那版标注**很可能本身就是脚本生成的稀疏集合**（30 条 × 4.5 秒一条；而且 run#100 用 `fp_case_rate=0.5385` 说明它比 AI 输出少了很多项）。**无脑恢复 = 把一个可疑标准提升为金标准**，那样比没有门禁更糟：它会拦住正确的改动、放过错误的改动。所以 W7 的定位是**"给出可核对的对照表，由人逐条定稿"**，不是自动写回。
>
> 另外 W7 的唯一数据源是 `audit_log`，而 `audit_log` **正是 `retention.py` 会定期清理的表**（`eval_case` / `eval_run` 反而明确不删）。所以这次恢复要在清理窗口之前跑完；长期方案不应把"标注版本"寄托在审计日志上。

> W7 是**工具**不是脚本洪流：仓库根目录不新增一次性脚本，工具放 `backend/`、与 `backfill.py` 同级（后者已是同类先例：离线重算、写前备份、`--apply` 才落库）。

| 下游 | `facts["text"]` → `_llm_analyze()` → **进 prompt**；`facts` → `engine_negative_items()`（`scoring_service.py:1072` / `graph_session.py:145` / `eval_runner.py:291`）；`facts["tool_failure"]` → `_note_facts()` | D2 改 `text` 文案 = **改 prompt 输入** → LLM 输出可能变化。属于行为变更，只能用评估集量，不能凭直觉 |

#### R3 · 规则版本号（D2 的 `v1.0 → v1.1`）

上下游：`load_rules()` → `current_rule_version()` → `scoring_run.rule_version` / `scoring_rule` 表 / `assessment.rule_version` / `eval_case.baseline_rule_version`。已核对：**没有任何逻辑依赖 `'v1.0'` 这个字面值**（只出现在 fallback 默认值与测试里）→ 改版本号本身不会打断逻辑；唯一副作用是 `_candidates` 把 723 条纳入重评（预期内）。

#### R4 · 写入门禁（W1–W6）

- 调用方已核清：`eval_runner`（sample / prefill）、`api_eval`（save / dispute / freeze / active / delete）、`meta_loop`（`insert_from_review`，只插不改）。
- **前端 prefill 不带 `overwrite`**（`EvalView.vue:232` 只传 `kind`）→ W3 的分级覆盖**不影响现有 UI 行为**。
- ⚠️ **W1 承诺的「同一事务内写审计」目前做不到**：`audit.record_action()` 走的是自己的连接（`db.execute`），而且该模块的设计原则明确写着"**失败绝不抛出** —— 审计是旁路观测，不能因为它把主流程带崩"。**处置（必须二选一，不能含糊）**：① 给 audit 加 `record_action_in(conn, ...)`，让"改金标准"这条路径用事务内审计、写失败即回滚（这是对上述原则的**有意例外**，要写进 ADR）；② 退回"尽力而为"，但那样仍存在静默覆盖的可能。

#### R5 · 定时回归（D8）与既有互斥闸

`guard_can_start(owner)` 只认 `sync` / `scoring` 两个 owner，`job_service.JOB_TABLES = {"scoring":..., "sync":...}`，而 `eval_run` 没有心跳列 → **不能直接把 eval 接成第三种 kind**。但 eval 回归要读 `chat_message`，与同步并发会读到半截会话（与评分必须互斥同一个理由）。**处置**：eval 任务启动前检查 `running_kinds()`，**非空就跳过**（不新增 kind、不引入心跳）。

#### R6 · 基线入库（D3）的一个权限细节

`load_baseline()` 的读方是 `eval_runner`（run_sync / gate_decision / status）、`api_eval.stats`、`api_eval.baseline GET`；`retention.py:21` 明确**不删** `eval_run`（比现在的文件更持久）。⚠️ 但 `eval_baseline_run_id` **不能注册进 `settings_registry.py`** —— 注册即出现在设置页并可由前端写入，等于谁都能把基线指向任意 run。**处置**：作为内部 key（`db.setting()` 仍可读、不写入白名单），只允许经 `POST /api/eval/baseline` 变更。

#### R7 · 发布链（D5）的幂等语义

`/rules/publish` 目前**没有任何前端页面调用**（只在 `frontend/src/api.js:76` 有封装），实际靠 curl / 外部脚本；它走 `idempotency.run_once(key, "rules.publish", _do)`。⚠️ 同一 `request_key` 配不同 `eval_run_id` 重放时会返回**首次结果**，容易让人误以为"换了 run 已经重新判定过"。**处置**：把 `eval_run_id` 纳入幂等键，或在返回里显式标注 `_replayed`。
