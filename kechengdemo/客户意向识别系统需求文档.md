# 客户意向识别系统需求文档

**版本：** v1.0  
**目标读者：** 业务负责人、产品经理、研发与测试人员  
**首期范围：** 企业微信员工与外部联系人的单聊；不含客户群聊天。

## 1. 项目目标

本系统从微伴助手 OpenAPI 同步企业微信员工与客户的聊天记录，使用 OpenAI 大模型按既定评分规则评估客户意向，并自动识别、输出需要销售重点跟进的客户。

业务目标：

- 用可追溯的客观规则替代“聊得不错就高意向”等主观判断。
- 让销售优先处理转化潜力高、意向刚升高的客户。
- 保留每次评分的依据，便于销售交接、人工复核和后续优化。

## 2. 首期范围与边界

### 2.1 包含

- 从微伴助手获取已授权员工与外部联系人的**单聊**会话及消息。
- 同步员工发送和客户发送的消息。
- 处理可获取的文本、图片说明、语音转写文本、文件说明、链接、小程序及撤回消息等。
- 使用 OpenAI 对客户意向评分、生成客户画像总结及建议销售策略。
- 生成重点跟进人群，并支持 Excel 导出、写入飞书文档及对外 API 查询。

### 2.2 不包含

- 客户群聊天、群成员映射和群内单客户意向判断。
- 自动向客户发送消息、自动修改聊天内容或自动改写销售话术。
- 未开通企业微信会话存档、未购买会话席位或未授权获取的聊天记录。

客户群聊天作为二期能力扩展；届时需额外设计群成员身份映射、群消息归属和群内客户级评分。

自动向客户发送消息将作为二期能力拓展；届时需额外设计AI生成与客户沟通发送消息的业务流程。

## 3. 数据来源与唯一标识

### 3.1 微伴助手 OpenAPI

系统使用以下接口：

- 会话列表：`GET /open-api/chat/session/list`
- 会话消息：`GET /open-api/chat/message/list/v2`

微伴权限、会话存档及会话席位已具备。部署时由服务端安全配置微伴访问凭据；不得将 Token 写入前端、日志或导出文件；为了确保信息安全，需将调用OpenAI或者DeepSeek的api-key写入环境变量配置中。

### 3.2 客户关系唯一标识

首期以如下字段标识一个“员工—客户关系”：

```text
relationship_key = staff_id + ":" + target_id
```

- `staff_id`：企业微信员工 ID。
- `target_id`：微伴会话返回的外部联系人 ID。
- `name`：微伴返回的客户名称，作为首期展示名称。
- `session_id`：会话追溯及同步游标字段，不作为员工—客户关系主键。

若同一个客户由多个员工服务，应按不同 `staff_id + target_id` 分别评分、输出及跟进。

## 4. 聊天记录同步需求

### 4.1 首次全量同步

首次接入时，系统应：

1. 获取所有已授权员工的会话列表。
2. 建立本地单聊会话清单。
3. 分页获取每个会话的历史可用消息。
4. 幂等写入消息并建立会话同步水位。
5. 对有足够信息的客户进行首次意向分析。

首次导入的高分客户标记为“基线高意向客户”；默认不当作日常“新增重点跟进”重复推送。

### 4.2 日常任务

| 执行时间 | 任务 | 目的 |
|---|---|---|
| 每晚 20:00–20:20 | 主增量同步与分析 | 覆盖约 19:30 的销售主动发送及其后的客户互动。 |
| 每日 03:30 | 48 小时补偿同步与分析 | 修复接口入库延迟、网络失败、任务中断及漏处理。 |

销售主动发送但客户未回复时，消息也必须进入本地消息库。它可以更新对话上下文，但不应仅因销售单方面群发而大幅提高客户分数。

### 4.3 增量与去重

每个 `staff_id + session_id` 保存独立同步水位。

```text
start_time = 上次成功水位 - 15 分钟
end_time   = 本轮任务开始时间 - 1 分钟
```

- 每轮任务开始时固定 `end_time`，分页中不得改变，避免新增消息造成分页漂移。
- 成功写入该会话的全部页面后才推进水位；失败时保留原水位，供下一次自动补齐。
- 消息使用下列唯一约束幂等写入：

```text
UNIQUE(staff_id, session_id, message_id)
```

## 5. 评分规则

### 5.1 评分原则

- 最终原始分值范围为 `-12` 至 `+13`。
- 同一加分维度命中多个档位时，只取最高分；不同加分维度可累加，上限 `+13`。
- 扣分维度可叠加，下限 `-12`。
- 每一次有效互动后应重新评分；公开课前一天、公开课后及每日早会前应复核 S/A 客户。
- 每一项得分或扣分必须返回证据消息及简短理由。
- **规则是可以随着时间变化的，由人来修改**

### 5.2 加分规则

**要结合标签来打分，需要加入微伴中拿标签的动作**

| 维度 | 关键判定依据 | 分值 |
|---|---|---:|
| 程序员或转型画像 | 在职编程技术岗计 +2；非编程岗但明确转型 AI/大模型，或相关专业在校生计 +1。 | +2 / +1 |
| 明确的工作具体需求 | 有可落地的业务痛点、AI 项目或明确场景计 +2；仅有学习方向但需求不具体计 +1。 | +2 / +1 |
| 配合度、认可度高 | 积极回复、配合画像收集，且认可课程、师资或平台。 | +1 |
| 紧迫性高 | 1 个月内的刚性需求计 +2；1–3 个月的中期计划计 +1。 | +2 / +1 |
| 已学习一段时间 | 已接触或自学大模型 1 个月以上，含实操、API、RAG、Agent 等。 | +1 |
| 邀课成功 | 已实际到课计 +2；已确认参加但尚未到课计 +1。 | +2 / +1 |
| 高转地区 | 一线或指定新一线城市。 | +1 |
| 主动问课 | 客户主动询问课程、价格、师资、就业、方式等计 +2；经销售引导后表示想了解计 +1。 | +2 / +1 |

### 5.3 扣分规则

| 维度 | 分值 | 关键判定依据 |
|---|---:|---|
| 追着问价格 | -1 | 未了解课程价值和服务、反复只比价。 |
| 态度差 | -2 | 不耐烦、粗鲁、挑衅或无理指责。 |
| 配合度低 | -1 | 敷衍回复、拒绝提供基础信息、长期不配合沟通。 |
| 认可度低 | -1 | 明确否定在线教育、课程、公司或品牌。 |
| 要自学 | -2 | 明确选择免费自学并拒绝付费课程。 |
| 连续 2 天不回复 | -2 | 销售正常跟进后，客户连续 48 小时未回复；客户已说明“忙、晚点聊”等情形不计。 |
| 明确拒绝报课 | -3 | 明确表示不报、不学、暂不考虑、没有需求等。 |

### 5.4 等级与行动建议

| 原始分值 | 等级 | 跟进优先级 | 系统建议 |
|---:|---|---|---|
| ≥6 | S | 最高 | 每日重点跟进；课后 30 分钟内跟进并推动关单。 |
| 4–5 | A | 高 | 每日 1 次有效跟进，重点推动到课和预定。 |
| 2–3 | B | 中 | 隔日有效跟进，以价值内容和公开课邀约培育。 |
| 0–1 | C | 低 | 每周 1–2 次低打扰触达，等待主动咨询信号。 |
| <0 | D | 暂停 | 停止一对一深度跟进，进入长期激活池。 |

### 5.5 自动计算与 AI 判断的分工

- **后台规则引擎负责：**连续 48 小时不回复、评分时间节点、前后分数比较、重点跟进触发及重复通知控制。
- **AI 负责：**从聊天语义中识别其他加减分项、提取证据、生成画像和销售建议。
- **外部事件优先：**“实际到课 +2”最好接入直播/课程平台到课事件；只有聊天记录但无法确认到课时，不得直接给 +2。目前展示无法和直播平台直接衔接，但是在客户标签里面会在微伴平台有到课和完课的标签，如果能够获取到就可以按照标签来给学员打分。
- **冲突规则：**客户在具备学习或业务需求时主动问价格，按“主动问课”判断；在未了解价值的前提下反复只比价，才计“追着问价格 -1”。

## 6. OpenAI 意向分析需求

### 6.1 分析输入

每次分析应包含：

1. 当前评分规则版本与规则表。
2. 员工 ID、客户 ID、客户名称。
3. 上一次有效评分、等级、画像总结及已通知等级。
4. 自上次分析后新增的消息和必要的近期上下文。
5. 相关历史关键消息，例如需求、报价、邀约、到课、拒绝等。
6. 后台计算的事实，例如连续未回复时长、已确认到课事件。

不得无限量发送全部历史聊天记录；应保留长期画像摘要，并按需加入近期与关键历史消息。

### 6.2 分析触发

应触发分析：

- 客户有新的有效回复；
- 销售发送了报价、方案、邀约、课程说明等可能影响决策的关键信息；
- 首次导入、补偿重算、评分规则版本变更或人工要求重算。

不应因重复同步或无意义系统消息重复调用模型。

### 6.3 结构化输出

通过 OpenAI Responses API 的 Structured Outputs，以 JSON Schema 约束返回，确保结果可被系统稳定解析。官方说明见：[OpenAI Platform Structured Outputs](https://platform.openai.com/overview)。

```json
{
  "raw_score": 5,
  "grade": "A",
  "positive_items": [
    {
      "rule_id": "positive_clear_work_need",
      "score": 2,
      "evidence_message_ids": ["msg_001"],
      "reason": "客户描述公司需要搭建知识库。"
    }
  ],
  "negative_items": [],
  "customer_profile_summary": "客户背景、需求、紧迫性、顾虑与当前阶段摘要。",
  "sales_strategy": "下一步行动、沟通重点与建议跟进时间。",
  "confidence": 0.86,
  "needs_human_review": false
}
```

约束：

- `raw_score` 必须由命中的加分项与扣分项计算，不允许凭感觉直接给总分。
- 每个命中项必须列出至少一条证据消息；证据不足时不命中或标记人工复核。
- `grade` 必须由总分映射产生，不能独立判断。
- 模型不得捏造客户信息、到课事实、预算、职位、时间节点或聊天内容。
- `customer_profile_summary` 和 `sales_strategy` 使用中文。

## 7. 重点跟进人群规则

系统输出“重点跟进人群”，而不是仅输出全部高分客户。

### 7.1 触发条件

```text
条件 A：新增达到 5 分及以上
  - 无上一次有效评分，且本次 raw_score ≥ 5；或
  - 上次 raw_score < 5，且本次 raw_score ≥ 5。

条件 B：意向等级发生变化，且当前分数大于 5
  - 上次有效分数存在；
  - 本次 raw_score ≠ 上次 raw_score；
  - 本次 raw_score > 5。
```

示例：

| 上次分数 | 本次分数 | 是否输出 | 原因 |
|---:|---:|---|---|
| 无 | 5 | 是 | 新增达到 5 分。 |
| 4 | 5 | 是 | 首次跨越 5 分阈值。 |
| 5 | 6 | 是 | 分数变化且当前大于 5。 |
| 6 | 8 | 是 | 分数变化且当前大于 5。 |
| 6 | 5 | 否 | 当前不大于 5。 |
| 5 | 5 | 否 | 分数未变化。 |

### 7.2 去重与审计

同一客户关系在同一评分结果上只能生成一次重点跟进记录。应保存：

```text
relationship_key
assessment_id
old_raw_score
new_raw_score
trigger_type
generated_at
export_status
```

`trigger_type` 至少包括：`new_reach_5`、`level_changed_above_5`、`manual_reassessment`。

## 8. 输出需求

### 8.1 核心字段

重点跟进列表必须包含：

1. 企业微信员工 ID
2. 聊天对象 ID
3. 聊天对象名称
4. 意向级别/原始意向得分
5. 聊天对象画像总结
6. 建议客户的销售策略

### 8.2 保留字段

系统同时保留并可选导出：

```text
S/A/B/C/D 等级
上一次有效分数
本次分数
触发类型
评分规则版本
分析时间
置信度
评分理由
关键意向信号
证据消息 ID 列表
是否需要人工复核
最后消息时间
上次通知等级
```

### 8.3 Excel 导出

- 支持按日期、员工、分数、等级和触发类型筛选。
- 导出 `.xlsx`，默认包含核心字段及上述保留字段。
- 导出行为需写入审计日志。

### 8.4 飞书文档

系统每天生成或更新“重点跟进人群日报”，包含：

- 日期；
- 新增达到 5 分及以上的人数；
- 分数变化且当前大于 5 的人数；
- S/A/B 级数量汇总；
- 重点跟进客户明细表。

首期支持按日期向指定飞书文档追加内容；部署时需配置飞书应用凭据、目标文档或文件夹及编辑权限。

### 8.5 对外 API

提供版本化只读接口，供未来 CRM、数据看板和自动化触达系统调用：

```text
GET /api/v1/high-intent-customers
```

支持参数：

```text
date_from, date_to, staff_id, min_score, grade,
trigger_type, page, page_size
```

接口返回重点跟进记录、分页信息及评分规则版本。接口必须采用服务端鉴权，例如 API Key 或 OAuth。

## 9. 核心数据模型

### 9.1 chat_session

```text
staff_id, session_id, target_id, target_name, last_msg_time,
session_type, is_active, last_discovered_at
```

唯一键：`(staff_id, session_id)`。

### 9.2 chat_message

```text
staff_id, session_id, message_id, message_time, direction,
from_id, to_id, message_type, text_content, content_json,
file_url, synced_at
```

唯一键：`(staff_id, session_id, message_id)`。

### 9.3 scoring_rule

```text
rule_id, rule_version, polarity, dimension, score,
criteria, examples, conflict_priority, source_type,
effective_at, status
```

`polarity` 为 `positive` 或 `negative`；评分规则由提供的 Excel 加分表与扣分表初始化，并支持后续版本化修改。

### 9.4 customer_intent_assessment

```text
assessment_id, relationship_key, staff_id, target_id, target_name,
raw_score, grade, positive_items_json, negative_items_json,
profile_summary, sales_strategy, confidence,
needs_human_review, rule_version, analyzed_at
```

### 9.5 high_intent_notification

```text
id, relationship_key, assessment_id, old_raw_score, new_raw_score,
trigger_type, generated_at, export_status
```

## 10. 任务可靠性、权限与安全

- 同一会话同一时间只允许一个同步任务执行。
- 单页或单会话失败不得阻塞其他会话；失败会话保留水位并自动重试。
- 网络、限流和临时接口错误采用指数退避重试。
- 微伴 Token、OpenAI API Key、飞书应用密钥只能由服务端密钥管理机制保存。
- 普通日志不得记录完整聊天正文、访问凭据或完整模型请求。
- 原始聊天记录、评分结果、导出与人工复评操作均需审计。
- 仅具备相应角色与数据范围权限的用户可查看或导出聊天内容及评分结果。

## 11. 验收标准

1. 已授权的员工—客户单聊可被完整同步，重复拉取不产生重复消息。
2. 销售主动发送、客户未回复的消息仍可同步并作为上下文保存。
3. 每次有效分析都输出可追溯的逐项加减分、总分、等级、画像及销售建议。
4. 相同加分维度仅取最高档；扣分项按规则叠加；总分及等级映射正确。
5. 客户达到 5 分，或分数变化且当前大于 5 分时，生成一条重点跟进记录；重复任务不重复生成。
6. 重点跟进记录可筛选、导出 Excel、写入飞书日报，并通过 API 查询。
7. 任务失败、接口延迟或服务中断后，48 小时补偿任务可自动补齐数据。
8. 每一条评分均保留评分规则版本、证据消息和分析时间，支持人工复核。

## 12. 上线前待确认事项

1. **展示口径：**原始分数范围为 `-12` 至 `+13`。建议保留 `raw_score` 原值；若界面必须显示 `0–13`，负分显示为 0，但仍保留原始负分和 D 级。
2. **到课数据：**是否可提供直播/课程平台的实际到课事件，以准确计算“邀课成功 +2”。
3. **飞书目标：**确定日报写入固定文档还是按天创建新文档，并提供目标位置与应用权限。
4. **OpenAI 接入：**配置服务端 OpenAI API 项目与密钥；上线前用脱敏样本验证评分准确率。
5. **人工复核：**确认哪些角色可以查看、修改或确认 AI 评分，以及人工修改后是否覆盖 AI 当前结果。
