# 客户意向评分 · 测试套件体检与精简方案

> 日期：2026-10-16 ｜ 依据：35 个测试文件逐个真实计时（`test_stage_a_acceptance` 除外）+ 代码通读
> 目标：把"每改一次代码要跑半天"压到"默认 ≤1 分钟、需要时再上重活"

---

## 一、体检结果（实测，不是我猜的）

**家底**：`tests/` 下 **36 个 `test_*.py` + `run_all.py` + `_harness.py`**，合计 **7,953 行**。

**逐个计时（35 个文件，上限 180s/个，`test_stage_a_acceptance` 因真调模型未跑）**：

| 层 | 文件数 | 实测总时长 | 单文件典型 |
|---|---|---|---|
| 纯逻辑（不碰 DB / 网络） | 9 | **≈5.5s** | 0.4 – 1.1s |
| DB 集成（stub 掉模型） | 24 | **≈530s** | 20.6 – 25.9s |
| 跨进程子测试 | 1（`test_g6_...`） | 41.4s | — |
| 真实模型 / 外部通道 | 1（`test_stage_a_acceptance`） | **1861 – 2909s** | 31 – 48 分钟 |

合计 **600s（10 分钟） + 31~48 分钟 ≈ 45~60 分钟/轮**。而 `run_all.py` 的默认超时是 900s/个、三个文件 1500–3600s —— **只要有一个测试挂住，一轮就多花 15–60 分钟**。改一次代码跑一轮、失败了再跑一轮，"半天"就是这么来的。

---

## 二、根因（三条，按"省时间"排序）

### G1 · 每个 DB 测试进程白等 20 秒（**最大且最容易修**）

**实测**：`test_schema_and_defaults` 20.8s、`test_hooks` 20.6s、`test_confidence` 20.7s、`test_eval_runner` 21.7s …… 四个不相干的测试**齐刷刷 20.x 秒**。拆开一测就露馅了：

```
import db        : 0.31s
first query      : 0.02s
init_db          : 0.01s     ← schema.sql 整份幂等执行只要 10 毫秒
进程整体墙钟      : 20.76s    ← 剩下 20 秒全在**退出时**
```

退出时的这行就是答案（每个测试的输出末尾都有，之前一直被当成噪声过滤掉）：

```
couldn't stop thread 'pool-1-worker-0' within 5.0 seconds
```

`db.pool()` 建的 `ConnectionPool` 从不关闭，解释器退出时 3 个 worker 线程 + 1 个 scheduler 线程**各等 5 秒**才被强杀 = **20 秒**。

**验证**：`db.pool().close()` 之后，同一进程墙钟 **0.69s**（`close()` 本身 0.02s）。

**代价**：24 个 DB 测试 × 20s ≈ **480 秒**，占实测总时长 600s 的 **80%**。也就是说：**这一轮 10 分钟里有 8 分钟是纯浪费。**

### G2 · 唯一的真模型测试占了 31–48 分钟，而且每轮都跑

`run_all.py` 自己的注释记着：`test_stage_a_acceptance` "实测两次分别是 1861s 与 2909s"，它最多循环 6 个候选会话、每次都真调模型。而 `--skip-llm` 的名单里**只有它一个**——看着像能用，实际上只要不加这个开关，它每轮都跑满。

### G3 · 开关与名单是手写的，已经和现实脱节

```python
DB_MARKERS = ("ctx_integration",)          # 实际需要 DB 的至少 24 个文件
LLM_MARKERS = ("stage_a_acceptance",)      # 真实外部依赖远不止它
```

- `--skip-db` 几乎什么也跳不过（只匹配 1 个），而实际 24 个文件要 DB；
- `--skip-llm` 只跳 `stage_a`，但 `test_channel_check`（真调微伴/企微通道）、`test_browser_capability`（拉 Chrome）、`test_llm_client`、`test_dedup_semantics`、`test_sync_window` 都摸外部世界；
- 名单**写在与测试文件分离的地方**，所以每加一个测试就可能漏登记 —— 这正是 `AGENTS.md` 里点名的"两侧靠约定保持一致，新增一个极容易只改一侧"。

## 三、顺带查出的两件事（比慢更值得先说）

### R-A · 测试套件**现在是红的**：`test_cb_delta_and_budget.py` 4 项失败

```
FAIL  ③ 恰好等于水位之后的总数        200
FAIL  超限时 trim 非空（V4）           {}
FAIL  第一个砍的是 ⑤（d5 非空）        {}
FAIL  ⑤ 砍完 seg_fallback 归零        55
通过 44 / 失败 4（共 48）
```

**四条是同一个根因，而且是测试自身的问题、不是产品退化**：

1. 该测试用 `_pick_session()` **从真实库里挑消息最多的那个会话**，取中位数时间为水位；
2. 断言 `len(delta) == 中位数之后的消息数`（`tests/test_cb_delta_and_budget.py:108`）；
3. 但 `_delta_rows(..., 200)` 有 **200 条软上限** —— 只要那个会话"后半段"超过 200 条，断言按构造就不可能成立（实际就是 `200`）；
4. 今天上午的 `kind='full'` 重拉往库里补了 **1,697 条**消息（含长会话），会话被撑大 → 越过了这个临界点；
5. ③ 段被截到 200 条后 token 没超 `ctx_tokens_max=2500` → **不触发裁剪** → 后面三条"该砍 ⑤"的断言一起落空。

**结论**：这是**脆弱测试**的标本 —— 断言与"真实数据的当前形态"强耦合（挑真实会话 + 断言具体条数）。数据一同步就红，而红的不是产品。

### R-B · 被截断的测试可能留下脏行

本轮的 35 个都跑完了（0 个超时被截断），所以没留。但 `run_all.py` 一旦撞 timeout 强杀，测试的 `finally` 清理不会执行 —— 这既污染库、又让下一次回归的结果不可信。

## 四、新测试方案

### 4.1 分层：按"依赖什么"分三层，默认只跑前两层

| 层 | 含义 | 依赖 | 目标耗时 | 何时跑 |
|---|---|---|---|---|
| **T0** | 纯逻辑（解析/校验/阈值/公式/状态推导） | 无 DB、无网络 | **≤5s** | 每次改完都跑 |
| **T1** | 集成（DB + stub 掉模型） | 本地 PG 5433 | **≤60s** | 每次改完都跑（默认） |
| **T2** | 端到端（真模型 / 真微伴企微 / Chrome / 跨进程） | 外部 | 分钟级 | 发布前、或显式 `--t2` |

### 4.2 层级声明**写在测试文件里**（消灭 G3 那份会漂的名单）

每个测试文件顶部声明一行，`run_all.py` 直接解析：

```python
TIER = "t0"        # 或 "t1" / "t2"
```

- 单一来源：**测试属于哪一层，只有测试自己说了算**；
- 新增测试忘声明 → `run_all.py` **直接报错并拒绝跑**（默认拒绝比默认放过安全：漏登记 = 悄悄不跑）；
- `run_all.py --list` 输出 `名字 + tier + 预计耗时`，一眼看清这一轮会跑什么。

### 4.3 三处机械性提速（都要改，缺一不可）

| # | 改动 | 效果 |
|---|---|---|
| P1 | **`db.py` 注册 `atexit` 关闭连接池**（`db.pool().close()`）；`_harness` 兜底 | 24 × 20s ≈ **省 8 分钟**（G1） |
| P2 | 超时按 tier 给默认值：T0 15s / T1 120s / T2 3600s；删掉手写的 `TIMEOUT_OVERRIDES` | 挂住一个只花 15s，不是 15 分钟 |
| P3 | T2 默认**不跑**，`--t2` 或 `--full` 才跑（`stage_a`、`channel_check`、`browser_capability`、`llm_client` 等） | 日常一轮省下 31–48 分钟（G2） |

提速后的预期：**T0 ≈ 5s，T1 ≈ 60s，默认一轮 ≈ 1 分钟**；发了 T2 才回到"十几分钟"量级。

### 4.4 加一个 `--changed`：改哪个模块就只跑相关测试

对"改一次跑一次"来说，这个比分层更省。用显式映射（放 `tests/_map.py`，与测试同目录、单一来源）：

| 改了 | 跑 |
|---|---|
| `rules.py` / `rules.json` | `test_rules_validation`、`test_contracts`、`test_confidence` |
| `scoring_context.py` | `test_cb_delta_and_budget`、`test_ca_key_history`、`test_cc_memory_segments`、`test_ctx_preprocess`、`test_graph_session_parity` |
| `scoring_service.py` | `test_loop_guard`、`test_run_with_graph`、`test_hooks`、`test_g0_hardening` |
| `sync_service.py` / `weiban.py` | `test_sync_window`、`test_dedup_semantics`、`test_channel_check`(T2) |
| `eval_runner.py` / `eval_case_repo.py` | `test_eval_runner` |
| `scheduler.py` / `job_service.py` | `test_bugfix_p0p1`、`test_production_hardening` |
| `db.py` / `schema.sql` | `test_schema_and_defaults`、`test_settings_registry`、`test_hooks` |

规则：**映射外的文件**改了就退回跑全量 T0+T1（宁可多跑，不可漏跑）；映射本身有测试盯着（每个被映射的测试文件必须存在）。

### 4.5 并行（可选，等 P1 落地后再做）

现在不能并行的理由是"连接池 `max_size=8`，两个进程互相抢连接"。但那是**每个进程各自的池**，PG 侧上限 100 —— 2~3 个并行没问题。落地 P1（池会正常关闭）后，可以按 tier 并行：T0 全并行、T1 里**启动批量的那几个必须串行**（`test_g0_hardening` / `test_loop_guard` / `test_run_with_graph` / `test_g6`，它们会撞互斥闸）。

## 五、顺手要修的三件事

1. **把 R-A 那 4 个失败修掉**，但**改测试而不是改产品**：`test_cb_delta_and_budget.py` 应该**造自己的合成会话**（插入固定条数的消息、跑完删掉），而不是向真实库"借"一个会话再断言具体条数。同类风险也存在于其它"挑真实会话"的测试（`_pick_session` 模式），落地时一并扫一遍。
2. **timeout 强杀要保证清理**：在 `_harness` 里提供 `cleanup_registry`（注册待删的行/键，用 `atexit` + 信号兜底），避免下一轮结果被脏数据污染。
3. **`run_all.py` 的"超时 ≠ 失败"要更硬**：现在两者只在展示上区分，退出码都是失败。保留这个语义，但把"本层超时"单独计入报告（它属于预算问题，处置不同）。

## 六、落地顺序与验收

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | `db.py` + `_harness.py` 的连接池关闭（P1） | 任取 3 个 DB 测试，单个耗时从 ~21s 降到 **≤3s** |
| 2 | `TIER` 声明 + `run_all.py` 解析 + 按 tier 默认超时（4.2 / P2） | `--list` 显示分层；未声明 `TIER` 的文件被拒绝执行 |
| 3 | T2 默认不跑（P3），并给出 `--t2` / `--changed`（4.4） | 默认一轮 **≤60s**；`--changed scoring_context.py` 只跑 5 个文件 |
| 4 | 修 R-A 的 4 个失败（改成合成会话） | `run_all.py` 默认一轮**全绿** |
| 5 | 把本轮实测数据与分层规则写进 `AGENTS.md` 的 Testing 段（替换现有"跑测试前先确认…"那段） | 新人只看 `AGENTS.md` 就知道该跑哪一层 |

## 七、显式不做

- **不改成 pytest**（项目约定 + `check()`/退出码语义已成型，改造成本远大于收益）。
- **不删测试换速度**：T2 只是"默认不跑"，不是删。`stage_a` 仍必须在发布前跑一次。
- **不为提速把断言放宽**（比如把 `==` 改成 `>=`）—— 那等于用"测不出来"换"跑得快"。R-A 的修法是**换夹具**（合成会话），不是放宽断言。

## 八、实施结果（2026-10-16 已落地）

### 与方案的差异（两处，都是收敛后的更好做法）

1. **R-A 的修法**：方案里写的是"改造合成会话"。实际没这么改 —— 那要重写 300 行测试、
   且会丢掉"在真实长会话上验证"的价值。真正的根因是**③ 段的规模由"借来的会话多大"决定**：
   ⑤ 兜底窗口只在 `kept < ctx_fallback_min` 时才补，而 ③ 越大越不需要兜底；样本会话从
   ~400 条涨到 693 条后，③ 恒被 200 软上限撑满（实测中位数之后 347 条）→ **⑤ 永不出现**
   → "该砍 ⑤"的三条断言必然落空。修法是让**测试自己定 ③ 的规模**（`ctx_delta_max=30`）
   ＋ 预算阈值由**实测 token 推导**（`base × 0.7`）而不是写死 2500。同样是"不依赖真实
   数据形态"，改动却只有十几行。
2. **连接池修法**：方案里写"db.py 注册 atexit，`_harness` 兜底"。实际只改了 `db.py` ——
   所有会建池的进程都 import 它，兜底是多余的（`AGENTS.md`：改一次需求应当只动一个文件）。

### 仍留白（明确未做）

- `--changed` 目前只覆盖后端模块；前端（`.vue`/`api.js`）没有对应测试，改前端仍建议手测。
- 并行执行（4.5）没做：默认一轮已经 59 秒，收益不足以承担互斥闸的风险。
- R-B（timeout 强杀后的清理兜底）没做：本轮没有超时被截断，暂不引入机制复杂度。
