## 〇、先对齐问题：这套系统在"评测学"上是个什么问题

先把任务类型说清楚，否则会选错方法。

| 维度 | 本项目的实际情况 |
|---|---|
| 输入 | 一段会话（多轮文本） |
| 输出 | **一组命中的规则项**（15 个 rule_id 中，哪些命中、各得几分） |
| 任务类型 | **多标签分类（Multi-label Classification）** |
| 标签数 | 15（8 加分 + 7 扣分） |
| 标签分布 | **极度不均衡**——多数会话命中 0~2 项，某些维度极少命中 |
| 最终决策 | 5 级等级（S/A/B/C/D）→ 决定销售跟进优先级 |
| 误判代价 | **严重不对称**——漏掉高意向客户（"藏客"）的代价 >> 误判低意向 |

**这个定义带来三个直接推论：**

1. **评估单位必须是"命中项"，不能是"总分"** —— 你设计稿里这一点是对的，且和学术界对多标签分类的通行做法一致。
2. **主指标必须包含 Macro-F1** —— 因为标签不均衡，Micro-F1 会被高频维度（如"主动问课"）主导，而低频维度（如"明确拒绝"）准不准才是业务真正关心的。
3. **这是一个"宁可多标、不可漏标"的任务** —— 所以评估要单独看**召回率**，不能只看准确率。这正是后面要引入共形预测（弃权/覆盖率）的原因。

## 二、调研结果

## 2.1 评估集（Golden Set）怎么做

### 2.1.1 规模：不是越大越好，**标注质量决定一切**

业界最一致的一条结论，也是与你现有设计差距最大的一条：

> **"300 条、kappa 0.8 的集合，在每一个下游指标上都胜过 3000 条、kappa 0.4 的集合。"**

- 起步规模共识是 **50~200 条高信号样本**，而不是几千条近重复样本
- 但你设计稿提的"100~200 条"只够算**全局指标**，**不够做切片分析**。而切片恰恰是发现问题的关键。

### 2.1.2 统计样本量：有公式，不是拍脑袋

业界给的经验公式（Maxim AI / Lenny 等一致口径）：

```
期望通过率 80%，允许误差 5%，置信度 95%  →  每个切片约需 246 条
```

**这意味着：要先想清楚"要按什么切片做决策"，再决定总量。**

对本项目，至少要能切片回答：
- 按**等级**切（S/A/B/C/D 各 20~40 条）
- 按**员工**切（不同销售的客户群体差异极大）
- 按**规则**切（每条 rule_id 的正例要够算 P/R/F1，低频维度要专门补样本）

> 结论：**不要追求一个 100 条的"总集"，要做"分片配额"**。
> 高频维度（主动问课、态度差）每维 30+ 条；低频但高价值的维度（明确拒绝、要自学）单独补到 15~20 条。

### 2.1.3 来源要多源，不能只从生产日志里捞

| 来源 | 贡献 | 注意 |
|---|---|---|
| 生产真实会话 | 真实用户措辞、脏上下文 | 你的数据已经脱敏？需确认 |
| **复核改判记录** | 已知的系统性错误 | 零成本、持续增长 ← 你设计稿的 L1 是对的 |
| 专家编写 | 清晰的业务规则边界 | 容易"太干净、太简单" |
| 边界/对抗构造 | 冲突规则、临界值 | 你设计稿的 L2 是对的 |

业界建议的构成比例：**常态 60% + 边界 30% + 对抗 10%**。

### 2.1.4 ⭐ 标注者间一致性（Inter-Annotator Agreement）—— 你最大的缺口

**这一条在你的设计稿里完全没有。** 而业界把它当成**唯一的质量闸门**，是"放量前必须过的一关"。

标准做法（"the cheap version"，成本极低）：

```
1. 两名标注员，独立标注同一批 50 条，不许商量
2. 每个评估维度（rubric）单独算 Cohen's kappa
3. 任一维度 kappa < 0.7  →  冻结该维度的标注
4. 按两人分歧的那些样本，重写标注指南（补正例/反例）
5. 重新标注这 50 条
6. 重复直到每个维度都过 0.7，才允许放量到全量
```

**kappa 阈值参考（Landis & Koch 分级，业界通用）**：

| kappa | 含义 | 处置 |
|---|---|---|
| < 0.00 | 还不如瞎猜 | rubric 或标注员坏了 |
| 0.00–0.20 | 轻微 | 任何数字都不可信 |
| 0.21–0.40 | 一般 | 重写 rubric，通常是标准含糊 |
| 0.41–0.60 | 中等 | 只能看粗趋势，**不能用来卡发布门禁** |
| **0.61–0.80** | **显著** | **生产门禁的最低门槛** |
| 0.81–1.00 | 几乎完全一致 | 可以当人工替身用 |

> 国内口径略有差异：有的厂商要求 **≥ 0.75**，有的要求 **≥ 0.80 才允许入库**。
> 一个真实的国内生产案例（瞬维 AI）用的是"**标注员之间一致性达到 85% 才开始正式标注**"（百分比口径）。

**为什么这条最重要**：如果两个人类看着同一段对话连"这条规则命中没有"都判不一致，那这条规则的 `criteria` 就是写得不够清楚。**标注不一致不是标注员的问题，是规则的问题**——它直接告诉你该改哪条规则。

```python
from sklearn.metrics import cohen_kappa_score

for rule_id in ALL_RULE_IDS:
    a = [c["annotator_a"][rule_id] for c in pilot_50]
    b = [c["annotator_b"][rule_id] for c in pilot_50]
    kappa = cohen_kappa_score(a, b)
    if kappa < 0.7:
        print(f"{rule_id}: kappa={kappa:.2f} → 冻结，重写 criteria/examples 后再标")
```

**分歧样本要单独存**：它们不是"废数据"，而是**"这条规则写得不清楚"的直接证据**，正好喂给你设计稿里的"闸 1 补 examples"。

### 2.1.5 ⭐ 结果锚定（Outcome Anchoring）—— 你第二大的缺口

业界有一条很硬的实践经验：

> **"标注员的观点会漂移，用户的行为不会。有下游信号的地方，就应该把标签锚定到那个信号上。"**

对本项目，可用的下游信号其实**你手里就有**：

| 下游信号 | 来源 | 用途 |
|---|---|---|
| **到课 / 完课** | 微伴到课/完课标签（`scoring_fetch_tags`） | 直接验证"邀课成功 +2"这条规则 |
| **成交 / 报名** | 订单系统（若有） | 验证高等级（S/A）是否真的转化更高 |
| **分数回写后的实际变化** | 微伴客户详情 `score` | 业务级一致率 |
| **人工复核改判** | `negative_review` | 验证负分维度 |

**为什么关键**：如果只用"标注员说这条命中"当作金标准，你得到的只是"AI 是否和标注员想的一样"；
而**锚定到成交/到课后**，你才能回答"AI 的高分客户是不是真的更容易成交"——这才是业务问题。

> 强烈建议：**金标准集里为每条样本带上一个 `outcome` 字段**（到课/成交/最终等级），
> 即使现在填不全，也要先把字段和采集路径留出来。

### 2.1.6 版本化与漂移刷新

业界三档节奏（可裁剪，但要固定下来）：

| 节奏 | 动作 |
|---|---|
| 月度 | 从新生产数据里采样补桶；**抽 20 条复检 kappa**；淘汰不再触发的旧用例 |
| 季度 | 补新的对抗/边界样本 |
| 年度 | 用刷新后的指南**重新标注全量**（防止标注员口径随时间漂移） |

配套要求：
- **dev / test 分离**：用来调 prompt 的样本，不能同时用来做发布判定（否则就是自己给自己出题）
- **版本号固定**：每次跑评估记录当时的 `rule_version` + `prompt_version` + `golden_set_version`
- **provenance**：每条样本记录"谁标的 / 何时 / 用的哪版指南 / 来自哪条会话"
- 你的设计稿里 `messages_hash` 的想法是对的（会话增长后标注失效），但**只解决了"输入变了"这一种过期**，没解决"指南变了""标注员变了"这两种

### 2.1.7 国内实践：三个直接可借鉴的案例

**案例 A｜中海地产 AI 客户意向分级（最相关，强烈建议细读）**

- 样本：83 组来访客户 + 78 组成交追踪
- 分级：从 13 类标准化置业目的标签出发
- **最关键的发现**：
  > **五级分级下，顾问与 AI 的评级一致率只有 29.5%；简化成"可跟进 / 直接放弃"二分类后，一致率飙升到 93.6%。**
- 藏客检测：顾问标 D/E 但 AI 判 B/C → 预警；**藏客召回率 100%、报警精确率 87%**，捞出 20 组藏客
- 代价数据：**35.9% 的客户被顾问刻意打低，"每 4 个客户就有 1 个被错杀"**
- 业务收益：按 6%–8% 转化率测算，多带 3 笔成交，省佣金约 108 万

**这条对你的直接意义（很重要）**：
你的系统是 **5 级（S/A/B/C/D）**。如果你把"等级一致率"当主指标，几乎注定会得到一个很难看的数字
（参考中海：29.5%）。**这不是你的系统差，而是"细粒度等级"本身在人类之间就不可靠。**
→ 对策：**主指标用命中项级 Macro-F1；等级一致率只作参考；同时必须额外报一个"二分类（值得跟进 / 不值得）"的一致率**。

**案例 B｜瞬维 AI 双层漏斗（线索分级）**

- **"标注员之间的一致性达到 85% 以上才开始正式标注"**
- **"每个等级配 5 个正例 + 5 个反例"** ← 和你设计稿"闸 1 补 examples"完全同构
- "标注最大的坑是标准不统一，不同人对'中意向'的理解差异很大"
- **每月把模型判断错误的案例加入训练集，重新迭代**
- 一个反直觉发现：**只给最后一条消息 vs 给完整对话历史，准确率差 8 个百分点**

**案例 C｜某医疗器械企业线索打分**

- 意向判断准确率：AI 模型 86.3% vs 纯表单填写 42%
- 响应时效：< 90 秒 vs 人工平均 4.6 小时
- **踩的坑（最值得警惕）**：A/B 测试发现"**销售对 AI 分级结果信任度低，常忽略 B 组建议**"，
  导致响应时间缩短 63% 但签约率只提升 2.1%

**这条指向一个非技术结论**：**系统准不准是一回事，销售信不信是另一回事。**
上线时"为什么这个客户是 S 级"的**证据展示**，和模型准确率同等重要——
好在你已经有 `evidence` 字段和复核页，这是你的优势，要继续强化。

### 2.1.8 评测集工具与交付物清单

国内厂商总结的"合格评测集"交付物（可直接当验收清单）：

- 数据表 + **配置说明** + **Rubric 手册** + **评分自动化校验脚本**
- 标准答案必须包含"**不能包含的内容**"（负向约束）

- 每月替换 15% 的边缘样本

开源/商业工具（可选，不必须）：
- **Label Studio**（开源，支持多人标注 + 一致性统计 + LLM 评估工作流）

- 现阶段你的规模，**用 JSONL + 一个 `run_eval.py` 脚本就够**，不必上平台

## 2.2 置信度怎么做

### 2.2.1 第一共识：**语言化置信度（让模型自报）不可信**

这是学术界和工业界罕见的完全一致的一条结论。数据很硬：

| 来源 | 结论 |
|---|---|
| Future AGI（2026） | 前沿模型在**答对率只有 60–70%** 的题上，**自报置信度 0.85–0.95**，系统性高估 |
| TianPan（2026） | RLHF/DPO 训练**结构性放大过度自信**；让模型自我评估确定性，其自报分数与准确率的相关性**并不更好** |
| arXiv 2604.05306 | 提示式自评（P(True)）把"过度自信的错误"从 88.5% 降到 39.7%，但 **ECE 几乎没动（0.357→0.340）** —— 说明自评只是**重新分配了置信度，没有对齐到正确性** |
| 一项 2025 研究 | 类比邓宁-克鲁格效应：**模型最自信的时候最不准确**，真正知道答案时反而更多犹豫 |

> **所以你的 E4 判断是对的，而且比你想的更严重**：
> 现在落库的那个 `confidence`，不是"不准"，而是**"和准确率几乎无关"**。它现在被展示在复核页上，可能误导复核人员。

### 2.2.2 四条技术路线（按你的条件排序）

| # | 方法 | 成本 | 适用条件 | 你的适配度 |
|---|---|---|---|---|
| **①** | **logprob 聚合**（取承载判断的 token 的 logprob） | **零额外成本**（同一次调用） | API 返回 token 概率 | ⭐⭐⭐ **已实测可行** |
| ② | **自洽性采样**（采样 N 次看一致率） | N 倍 token | 无 logprobs；或作为交叉验证 | ⭐⭐ 贵，用于抽查 |
| ③ | 语义熵（采样后语义聚类再算熵） | N 倍 + 聚类 | 开放式生成 | ⭐ 不必要（你的输出是结构化 JSON） |
| ④ | 训练小型校准器（用 `(输入, 是否正确)` 对） | 需 500–2000 条标注 | 有足够标注数据后最稳 | ⭐⭐ 二期再说 |

**⭐ 已实测（2026-10-14）：DeepSeek 支持 `logprobs` + `top_logprobs`**

```python
body = {..., "temperature": 0, "logprobs": True, "top_logprobs": 8}
```

实测结果（同一个规则 `positive_coder_profile`，4 个不同会话）：

| 场景 | 模型输出 | true/false 的 logprob 差 | 折算概率 P(命中) |
|---|---|---|---|
| 明显命中（"我是 Java 后端"） | true | **+8.78** | **0.9998** |
| 明显未命中（"我是 HR"） | false | **−9.43** | **0.0001** |
| 模糊-测试岗（"做测试的，不怎么写代码"） | false | **+1.04** | **0.7392** |
| 模糊-运维（"搞运维，也写点脚本"） | false | −13.71 | 0.0000 |

**结论：信号有明确的动态范围，且恰好把"模糊案例"标在了 0.74 这个"该有人看一眼"的位置。**

> 顺带一个副产品发现：第 4 例里模型高置信度判了"未命中"，
> 但你自己在调研中设想的规则是"运维写脚本算 +2"。**这就是"规则没写清楚"的典型案例** ——
> 恰好印证 2.1.4 说的：分歧/异常样本必须回流去改规则，而不是去改模型。

### 2.2.3 光有 logprob 还不够：必须做**校准**和**度量**

logprob 是模型的**内部**概率，**不等于**"实际正确的概率"。业界要求三个指标：

| 指标 | 含义 | 业界阈值 |
|---|---|---|
| **可靠性图**（reliability diagram） | 横轴预测置信度、纵轴实际准确率，完美校准沿对角线 | 目视检查 |
| **ECE**（Expected Calibration Error） | 各置信度分箱内 \|准确率−置信度\| 的加权平均 | **< 0.05 是可接受的生产目标**；**> 0.10 不可信**；**> 0.15 则"用置信度做路由还不如用固定阈值"** |
| **Brier score** | 预测概率与二值正确标签的均方误差 | 越低越好，可与 ECE 并列 |

**校准数据集要求：500–2000 条**（你的 100~200 条金标准集不够算 ECE，这是又一个"集合要更大"的理由）。

**后校准方法（三选一，从简到繁）**：

| 方法 | 做法 | 何时用 |
|---|---|---|
| **温度缩放（Temperature Scaling）** | 在留出集上学一个标量 T，把 logits 除以 T | **首选**，一参数，最简 |
| Platt scaling | 在 `(raw_confidence, was_correct)` 上拟合单参数逻辑回归 | 误校准呈单调且近似线性时 |
| 等渗回归 | 非参数单调映射 | 误校准曲线较怪；需 1000+ 条才稳定 |

**必须记住的一条**：**换模型、换 prompt、换规则版本、数据分布漂移，都要重新校准。**
所以校准参数（T 值）要落库并绑定 `prompt_version`。

### 2.2.4 ⭐ 共形预测（Conformal Prediction）—— 学术前沿，且完美匹配你的任务

这是本次调研里**最有新意、也最值得你采纳**的一条。

**是什么**：一种分布无关、模型无关的不确定性量化框架，能给出**有统计保证**的预测集。

**为什么特别适合你**：

1. 你的任务本质是**多标签分类**（15 个 rule_id 各判一次），而"**多标签共形预测**"正是它的一个成熟分支
   （Chalmers 2025 年硕士论文专门做了这个方向）——为每个标签生成带覆盖保证的预测集，并**对模糊输入弃权**。
2. **共形弃权（Conformal Abstention）** 直接对应你的 `needs_human_review`：
   它能给出这样的保证——"**在未被弃权（自动放行）的样本里，错误率不超过 α**"，
   并在此约束下**最小化弃权率**。
3. 你现在准备拍脑袋定一个 `session_confidence < 0.6` 的阈值 —— 共形预测的答案是：
   **不要拍脑袋，用标注集校准出一个阈值，使得"自动放行部分的漏判率 ≤ 5%"**，并告诉你"这样必须弃权多少比例"。

**落地方式（不需要重训模型）**：

```
1. 拿金标准集（≥300 条），用当前置信度分数排序
2. 设定容忍度 α（例如"自动放行的部分，错误率 ≤ 5%"）
3. 在留出集上算分位数阈值 → 得到弃权边界
4. 效果指标：弃权率（要越低越好）+ 放行部分的实际准确率（要 ≥ 1−α）
```

**注意其局限（论文也明确写了）**：
- 对**稀有标签**和**标签不均衡**较敏感 → 你正好有低频维度（明确拒绝、要自学），要单独看
- **有效性保证依赖标注质量**，标注一差，保证就失效 → **又回到 2.1：标注质量是所有东西的地基**
- 共形预测给的是**覆盖率保证，不是正确性保证**——它保证"我没漏掉太多"，不保证"我判对了"

### 2.2.5 LLM-as-Judge 的定位：**辅助标注，不作主判**

| 结论 | 数据/依据 |
|---|---|
| 强 judge（GPT-4）在成对偏好任务上 ~80% 与人类一致 | Zheng et al. 2023（MT-Bench）——**但仅限成对对话偏好，不可外推到其他任务** |
| 规则评分场景相关性低得多 | G-Eval：Spearman **0.514**（摘要任务） |
| 13 个 judge 模型里只有最大的勉强对齐，且**仍低于人类间一致率** | Thakur et al. |
| **高百分比一致率会掩盖分数差异** → 必须用 chance-corrected 指标（kappa） | 同上 |

**四种已知偏差（如果要用 judge，必须处理）**：

| 偏差 | 表现 | 缓解 |
|---|---|---|
| 位置偏差 | 成对比较时偏好第一个，可被"只调顺序"刷分到 66/80 | 交换顺序各跑一次，只有两次一致才算赢 |
| 冗长偏差 | 更长的答案得分更高 | 提示里明说"长度不加分"，或做长度归一 |
| 自我偏好 | 给自己家族的输出打分高 10%–25% | **用不同家族的模型当 judge** |
| 格式偏差 / 宽松 | Markdown 表格、列表白得分；倾向判"对" | 提示里要求忽略格式；用 kappa 而非原始准确率 |

**最关键的一条原则（直接支持你的现有设计）**：

> **"能用确定性逻辑判的，绝不要用 LLM judge。"**
> （schema 对不对、URL 能不能解析、类型对不对、值在不在范围内 → 用代码判：更便宜、更可靠、不需要校准）

这正是你 `rules.py` 本地计分 + `engine=rule` 预筛的依据。**这条设计有明确的外部支撑，继续保持。**

**如果要用 judge（比如辅助生成银标、加速冷启动标注）**：
- 与人工在 **30 条**上校准，相关系数 **> 0.7** 才可用
- 换 judge 模型、改 rubric、换输出类型 → **都要重新校准**
- judge 的结论只能当**分诊信号**（决定哪些样本优先给人看），**不能当金标准**

## 四、结论与建议

### 4.1 三条最重要的结论

**结论 1：你的设计主干是对的，缺的是"质量闸门"和"校准"两块。**

三层评估集、命中项为评估单位、置信度"算出来不猜出来"、确定性预筛——
这四条都与业界/学界主流一致，可以放心推进。**不用推翻重来。**

**结论 2：评估集的成败不在"数量"，在"两个标注员能不能对上"。**

先花半天做 50 条双人校准、算一遍 per-rule kappa，比你标 300 条标得糊里糊涂有用得多。
**kappa 低于 0.7 的规则，先去改规则的 `criteria` / `examples`，而不是去调 prompt。**

**结论 3：置信度现在落库的那个数不能用，必须换掉；换法已有实测支撑。**

实测确认 DeepSeek 返回 token logprobs，且区分度良好 → **走 logprob 路线，同一次调用零额外成本**，
然后在金标准集上做温度缩放校准、用 ECE 验证。**没有 ECE 的置信度只是又一个"模型自报"。**

### 4.2 评估集：在现有方案上补 6 件事

| # | 补什么 | 怎么做 | 成本 |
|---|---|---|---|
| E-a | **双人校准 + kappa 门禁** | 2 人独立标 50 条 → 每规则算 kappa → <0.7 冻结改指南 → 重标 → 过线才放量 | 半天 |
| E-b | **结果锚定** | 每条金标准样本加 `outcome` 字段（到课/成交/最终等级），先用微伴标签填 | 字段改造 |
| E-c | **分片配额 + 样本量依据** | 高频维度每维 ≥30 条，低频高价值维度 ≥15 条，总量按切片数×需求反推 | 设计工作量 |
| E-d | **主指标定为 Macro-F1** | 标签不均衡，Micro-F1 会被高频维度主导；同时单独看**召回率**（藏客代价高） | 指标改造 |
| E-e | **等级一致率降级 + 加二分类口径** | 5 级一致率作参考；另报"值得跟进/不值得"的二分类一致率（参考中海 93.6%） | 指标改造 |
| E-f | **版本化 + 刷新节奏 + 角色分离** | 集合版本号/指南版本号；月度 20 条复检 kappa；标注者与调 prompt 者不同人 | 流程 |

**主指标建议表**：

| 层级 | 指标 | 说明 |
|---|---|---|
| 规则级 | **per-rule Precision / Recall / F1** | 最重要，定位到具体哪条规则不准 |
| 规则级 | per-rule **Macro-F1**（跨规则平均） | 主指标，不被高频维度主导 |
| 规则级 | **Cohen's kappa（人工 vs AI）** | 比原始一致率可靠，避免"多数类都对"的假象 |
| 会话级 | 命中项集合完全一致率、`raw_score` 一致率 | 端到端 |
| 会话级 | **二分类一致率**（值得跟进 / 不值得） | 业务可解释，细粒度不可靠时的兜底 |
| 过程级 | `unchecked_rules`、证据回链通过率、`invalid_items` | 检验各道闸 |
| 校准级 | **ECE / Brier / 可靠性图** | 检验置信度是否可信 |
| 业务级 | 回写后微伴端一致率、人工改判率、**藏客召回率** | 最终业务状态 |

### 4.3 置信度：具体技术方案（按可行性排序，建议三步走）

**第 1 步｜用 logprob 替换模型自报（零成本，先做）**

```python
# llm.py 增加参数
def chat(..., logprobs=False, top_logprobs=None): ...

# analyze.py 里逐维度表态后，从 logprobs 提取 true/false 的 logprob
def rule_hit_confidence(logprobs_content, rule_id) -> float:
    """从 token 概率算 P(命中)。"""
    pt = pf = None
    for t in logprobs_content or []:
        if t["token"].strip() in ("true", "false"):
            for alt in (t.get("top_logprobs") or []):
                s = alt["token"].strip()
                if s == "true":  pt = alt["logprob"]
                if s == "false": pf = alt["logprob"]
    if pt is None or pf is None:
        return None                       # 拿不到 → 标记为缺失，不假装有
    import math
    return math.exp(pt) / (math.exp(pt) + math.exp(pf))
```

**第 2 步｜在金标准集上做校准与验证**

```
raw_confidence（logprob 折算） → 温度缩放（学一个 T）→ calibrated_confidence
在金标准集上算 ECE / Brier / 画可靠性图
目标：ECE < 0.05；若 > 0.10 则先别用置信度做任何自动决策
```

**第 3 步｜用共形预测定复核阈值（替代拍脑袋的 0.6）**

```
输入：金标准集 + 校准后的置信度
设定：α = 5%（自动放行部分的错误率上限）
输出：弃权阈值 + 弃权率 + 放行部分的实测准确率
收益：阈值有统计保证，能回答"为了保证不漏判，我必须让人看多少比例"
```

**会话级置信度（合成公式，沿用你设计稿的三层，但每项都改成可算的）**

```
session_confidence = f(
    mean(每条命中项的 calibrated_confidence),   # logprob + 校准
    维度覆盖率 = 1 - len(unchecked_rules)/规则总数,
    无效项比例 = len(invalid_items)/总表态数,
    与上次评估的一致性                            # 需先修 E1（读回上次结论）
)
```

**两条硬要求**：
1. **改名**：`confidence` → `model_confidence`（或 `raw_confidence`），与"人工验证状态"分开，
   免得复核人员把"模型说有 0.9 把握"误读成"这条已验证"。
2. **换模型 / 换 prompt / 换规则版本 → 必须重新校准**，并把 T 值与 `prompt_version` 绑定落库。

### 4.4 落地顺序（最小可行动作，按性价比排序）

| 阶段 | 动作 | 产出 | 为什么这个顺序 |
|---|---|---|---|
| **A｜先建地基**（1–2 天） | 跑一遍系统 → 抽 50 条 → **2 人独立标注** → 算 per-rule kappa | 一张"哪条规则人自己都判不准"的清单 | 不过这关，后面全是空中楼阁 |
| **B｜定指标**（半天） | 写 `eval/run_eval.py`，输出 per-rule P/R/F1 + Macro-F1 + kappa | 第一份基线 `baseline.json` | 有了基线才能谈"变好还是变坏" |
| **C｜修置信度**（1–2 天） | logprob 接入 + 温度缩放 + ECE 验证 | 可信的 `model_confidence` + 一张可靠性图 | 已实测可行，成本最低 |
| **D｜扩样本**（按需） | 按分片配额补到能切片分析；补 `outcome` 锚定字段 | 能按等级/员工切片看指标 | 地基稳了再放量 |
| **E｜定阈值**（1 天） | 共形预测算复核阈值，替换 `needs_human_review` 的模型自报 | 有统计保证的弃权策略 | 有校准后的置信度才能做 |
| **F｜流程化**（持续） | 版本化 + 月度 20 条 kappa 复检 + 复核反馈回流成回归集 | 自动增长的评估集 | 让整套东西长期活着 |

> **如果只做三件**：**A（50 条双人 kappa）→ C（logprob 置信度 + ECE）→ B（指标基线）**。
> 这三件做完，你的系统就从"我觉得它挺准"变成"我知道它哪条规则准、哪里不准、置信度可不可信"。

### 4.5 两个要提前想清楚的业务问题

1. **切片维度**：你最终要按什么维度做决策（等级？员工？客户来源？）→ 决定评估集的配额怎么分。
2. **可接受的漏判率 α**：为了保证不漏掉高意向客户，你愿意让多少比例的会话走人工复核？
   → 这是**业务决策**，不是技术决策。共形预测只是把这个 trade-off 显式化，答案得业务方给。
