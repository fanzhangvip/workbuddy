# 企业微信官方「会话内容存档」方案 · 可行性调研

> 目的：微伴 OpenAPI 返回的聊天正文（`content`）为 null，第 ② ③ 步（规则打分 / 回写评分）被卡住。
> 本文调研「绕开微伴、直连企业微信官方会话存档接口」这条备选路线的可行性、成本与改造量。
> 调研时间：2026-10-12

---

## 一、结论速览

| 判断项 | 结论 |
|---|---|
| 技术上能否实现 | ✅ 能。官方明确提供 SDK + 双重解密机制，Python 有成熟封装 |
| 能否拿到聊天正文 | ✅ 能，前提是**企业自己持有 RSA 私钥** |
| 是否依赖微伴 | ✅ 完全不依赖微伴，但**回写评分仍走微伴接口** |
| 主要门槛 | ⚠️ 企业认证 + 付费席位 + 自持私钥 + 可信 IP（不是技术门槛，是资质和配置门槛） |
| 最大的不确定性 | ❓ **现在企业微信后台配置的公钥，对应私钥在谁手里**（在微伴手里 = 你们要重新生成密钥对） |
| 是否推荐 | 推荐作为**主路线推进**（相比等微伴修复，自主可控） |

**一句话**：这条路本身是通的，卡点不在技术，在「私钥归属」和「是否已开通官方存档权限」这两件事上——需要你去企业微信管理后台核实。

## 二、两方案对比

| 维度 | 方案 A：微伴 OpenAPI（现状） | 方案 B：企业微信官方 SDK |
|---|---|---|
| 数据来源 | 微伴转发 | 企业微信直出 |
| 消息正文 | ❌ null | ✅ 明文 JSON |
| 依赖方 | 微伴（要他们修复存档配置） | 无第三方 |
| 是否需付费 | 已含在微伴席位里 | 需单独购买企微「会话存档」席位 |
| 需自持私钥 | 否 | ✅ 必须 |
| 可信 IP | 否 | ✅ 必须 |
| 拉取方式 | 按 staff_id + session_id 分页 | 按 seq 游标流水式增量拉取 |
| 单次上限 | limit ≤ 20 / 1000（视接口） | limit ≤ 1000，频率 ≤ 4000 次/分钟 |
| 消息去重键 | message_id | msgid（`_external` 结尾 = 外部消息） |
| 媒体文件 | 15 分钟有效链接 | 用 sdkfileid 调 GetMediaData |
| 开发量 | 已写完（`weiban.py`） | 新增一个模块 + 原生库 |

> **重点提醒**：企业微信现在还有个新产品叫「**数据与智能专区**」，走「会话记录」接口。
> 官方技术支持的原话是：**「数据与智能专区只能获取会话记录，不支持获取会话内容」**。
> 如果你走那条路，会**再次掉进和微伴一模一样的坑**（拿得到记录、拿不到正文）。**必须走经典的 SDK 路线。**

## 三、官方机制：双重解密

企业微信会话存档的核心是一套「密钥分离」设计：消息用**对称密钥**加密，而这个对称密钥又用**企业在管理后台配置的公钥（RSA 2048）**加密。

```
企业微信服务器
  ├─ encrypt_random_key  = RSA(企业公钥) 加密后的「对称密钥」   ← Base64 字符串
  └─ encrypt_chat_msg    = 用该对称密钥 AES 加密的「消息体」     ← Base64 字符串
                │
                ▼  企业用自己手里的 RSA 私钥
  ① Base64 decode(encrypt_random_key)
  ② RSA 私钥解密（PKCS1）→ 得到对称密钥 str2
  ③ DecryptData(str2, encrypt_chat_msg) → 明文 JSON
```

**关键结论：只有持有私钥的一方才能解密。** 谁配置的公钥，谁就能解密——这就是为什么微伴能给你 `secret_key`（加密密钥）却给不了正文：正文密文它没给你，或者它自己也没法解。

### 三个核心 SDK 接口

| 接口 | 作用 | 关键点 |
|---|---|---|
| `Init(sdk, corpid, secret)` | 初始化 | `secret` 是「**会话内容存档**」专用 Secret，**不是**普通应用 Secret |
| `GetChatData(sdk, seq, limit, proxy, passwd, timeout, &out)` | 拉取密文 | seq 游标增量；limit ≤ 1000；返回 `chatdata` 数组 |
| `DecryptData(encrypt_key, encrypt_msg, &out)` | 解密 | 一行封装，**强烈建议直接用它**，不要自己写 AES |
| `GetMediaData(sdk, sdkfileid, ...)` | 拉媒体 | 图片 / 语音 / 视频 / 文件，分片下载 |
| `NewSlice` / `FreeSlice` | 内存管理 | ctypes 调用时需要配对释放 |

### 返回字段

```json
{"errcode":0,"errmsg":"ok","chatdata":[
  {"seq":196,
   "msgid":"CAQQ2fbb4QUY0On2rYSAgAMgip/yzgs=",
   "publickey_ver":3,
   "encrypt_random_key":"ftJ+uz3n/z1DsxlkwxNgE+mL38H4...",
   "encrypt_chat_msg":"898WSfGMnIeytTsea7Rc0WsOocs0..."}
]}
```

- `seq`：消息序号，**下次拉取带上本次最大 seq**（不连续，跳号正常）
- `msgid`：唯一标识，用于**去重**
- `publickey_ver`：公钥版本号，多版本私钥时按它选私钥
- ⚠️ **`encrypt_random_key` 就是你之前看到的微伴 `secret_key` 的同源字段**——但官方这里**同时给了密文 `encrypt_chat_msg`**，微伴没给。

### 明文消息格式（解密后）

```json
{"msgid":"...","action":"send","from":"XuJinSheng","tolist":["icefog"],
 "roomid":"","msgtime":1547087894783,"msgtype":"text","text":{"content":"..."}}
```

- `action`：send / recall（撤回，**含撤回原文**）/ switch
- `from` / `tolist`：内部为 userid，外部为 external_userid（`wo`/`wm` 开头；机器人 `wb` 开头）
- `roomid`：群聊 id，单聊为空
- `msgtype`：text / image / voice / video / file / link / emotion / location / card / revoke / agree / disagree …
- `msgtime`：**毫秒**级 UTC 时间戳（注意：微伴那边是**秒**）

## 四、开通与配置前提（这部分是真正的门槛）

### 4.1 硬前提清单

| # | 前提 | 说明 |
|---|---|---|
| 1 | **企业已完成企业微信认证** | 未认证无法开通 |
| 2 | **超管权限** | 超级管理员或授权分级管理员 |
| 3 | **购买付费席位** | 会话存档是**付费功能**，按账号数购买，**最低 5 个账号** |
| 4 | **提交确认函** | 盖章上传，官方审核 1–3 个工作日 |
| 5 | **生成并上传 RSA 公钥** | 2048 位，公钥传到企微后台，**私钥自己保管** |
| 6 | **配置可信 IP** | 拉取服务器的**公网出口 IP**，不配则拉不到数据 |
| 7 | **获取存档 Secret** | 管理后台「会话内容存档」页查看即得 |
| 8 | **设置存档成员范围** | 指定部门/员工，建议先小范围 |
| 9 | **员工与客户知情同意** | 客户拒绝则无法继续聊天；员工端会有存档提示 |

### 4.2 开通路径

```
企业微信管理后台 → 应用管理 / 安全与管理 → 管理工具 → 会话内容存档
  → 申请开通 → 阅读协议 → 填资质 + 上传盖章确认函 → 提交审核（1–3 工作日）
  → 审核通过 → 配置可信 IP / 公钥 / Secret → 勾选存档成员范围 → 生效
```

### 4.3 费用参考（需以官方最新公告为准）

| 版本 | 参考价格 |
|---|---|
| 服务版 | 约 **450 元 / 账号 / 年** |
| 企业版 | 约 **900 元 / 账号 / 年**（含语音通话录音等能力） |

> 注意：**2026-01-22 有功能升级与价格调整公告**，采购前请核对最新报价与消息类型覆盖范围。
> 最低购买 5 个账号，实际费用 = 单价 × 账号数。

### 4.4 几条容易踩的坑

1. **开通前的历史记录追不回来** —— 只能从「授权那一刻」开始存。（注：微伴侧存档链路**当前仍在实时写入**，2026-10-12 实测最新消息精确到秒；只是正文为空。所以"数据旧"只是部分休眠员工的表象，不是全局停滞。）
2. **官方只给接口，不给界面** —— 必须二次开发（这正是我们要做的）。
3. **数据保留期 2 年**。
4. **旧版 HTTP API 已不推荐**，新接入一律用 SDK。
5. **要定期拉取** —— 官方文档提示会话记录获取有窗口限制（原文：「获取会话记录内容不能超过 5 天，如果企业需要全量数据，则企业需要定期拉取聊天消息」），因此**增量水位机制是必需的，不是可选项**。

## 五、Python 落地方式

官方只提供 **C++ / Java** SDK。Python 有两类现成封装，也可以自己用 `ctypes` 包一层。

### 5.1 现成开源封装

| 方案 | 说明 | 平台支持 |
|---|---|---|
| **PyWeWorkFinance**（`pip install pyweworkfinance`） | 官方 SDK 的 Python 封装，接口最贴近官方 | Windows x86_64 ✅ / Linux x86_64 ✅ / ARM64 ✅ / **macOS ❌** |
| Shunlly/we_work_sdk | 纯 `ctypes` + `pycryptodome` 实现 | Linux 为主 |
| wecom-msg-audit-mcp | 已封装成 MCP 服务 | Linux 为主 |

### 5.2 自封装骨架（ctypes）

官方 SDK 提供了 `libWeWorkFinanceSdk_C.so`（Linux x86/ARM）与 `WeWorkFinanceSdk.dll`（Windows）。核心就是用 ctypes 声明各函数的参数与返回类型：

```python
from ctypes import CDLL, c_void_p, c_ulonglong, c_uint, c_char_p, c_int

lib = CDLL("libWeWorkFinanceSdk_C.so")   # 把官方 SDK 库放到项目里
sdk = lib.NewSdk()                        # 必须在调用前声明 arity/restype

lib.Init.argtypes = [c_void_p, c_char_p, c_char_p]
lib.Init.restype  = c_int
assert lib.Init(sdk, corp_id.encode(), archive_secret.encode()) == 0

chatdata = lib.NewSlice()
lib.GetChatData.argtypes = [c_void_p, c_ulonglong, c_uint, c_char_p, c_char_p, c_int, c_void_p]
lib.GetChatData.restype  = c_int
assert lib.GetChatData(sdk, seq, 1000, None, None, 30, chatdata) == 0

lib.DecryptData.argtypes = [c_char_p, c_char_p, c_void_p]
lib.DecryptData.restype  = c_int
```

> ⚠️ 常见错误码：**10008 = 加密密钥解析失败**（多因 `encrypt_random_key` 的 RSA padding 不匹配），**10007 = 未找到私钥**。
> 建议**直接用 SDK 的 `DecryptData`**，不要自己实现 AES——社区里失败案例大多栽在 AES 位数（128 vs 256）和 IV 取值上。

### 5.3 平台注意事项

- **macOS 官方不支持**，需 Docker（Linux）或部署到 Linux 服务器。
- Windows 拉取方向可以，但**可信 IP 是服务器公网出口 IP** —— 本机跑意味着要暴露并固定本机公网 IP（家庭/办公宽带一般是动态 IP，不现实）。**建议部署到有固定公网 IP 的云服务器。**

## 六、对现有项目的改造点

### 6.1 影响面

| 现有文件 | 是否受影响 | 说明 |
|---|---|---|
| `config.py` | 🔸 小改 | 增加 `WECOM_CORP_ID`、`WECOM_ARCHIVE_SECRET`、`WECOM_PRIVATE_KEY_PATH`、`SDK_LIB_PATH` |
| `llm.py` | ✅ 不动 | 与数据源无关 |
| `rules.json` / `rules.py` | ✅ 不动 | 与数据源无关 |
| `analyze.py` | 🔸 小改 | 数据源从 `weiban.list_messages` 换成新的取数模块 |
| `weiban.py` | ✅ 保留 | **回写评分还要用**，会话/标签/客户详情也还用 |
| 新增 `wecom_archive.py` | 🆕 | 初始化 SDK → 增量拉取 → 解密 → 落地消息 |

### 6.2 需要一个「会话归集」步骤（新问题）

这是方案 B 相比方案 A 多出来的工作量：

- **方案 A**：微伴已经帮你把消息按「员工 + 客户」组织成 `session`，直接调 `session_id` 就行。
- **方案 B**：官方是**按 seq 的流水**，不带会话概念。你要自己用 `from` / `tolist` / `roomid` 把消息归集成「会话」：
  - 单聊：`roomid == ""`，会话键 = `(员工 userid, 客户 external_userid)`
  - 群聊：`roomid != ""`，会话键 = `roomid`

### 6.3 身份映射问题（需验证）

| 对象 | 官方侧 | 微伴侧 | 是否一致 |
|---|---|---|---|
| 客户 | `external_userid`（wo/wm 开头） | `external_user_id` | ❓ 大概率一致，需实测 |
| 员工 | 企微 `userid` | `staff_id` | ❓ 需实测（微伴的 id 形如 32 位 base64，不确定是否等同企微 userid） |

**回写评分时用的是微伴的 `external_user_id`（或 unionid）**，所以两边 ID 能不能对上，是方案 B 能否闭环的**关键验证点**。

## 七、⚠️ 最关键的决策点：私钥在谁手里

这是整条路线唯一的"拦路虎"，也是你现在唯一需要去查证的事。

**请登录企业微信管理后台 → 管理工具 → 会话内容存档，确认三件事：**

1. **「公钥」页显示的当前公钥版本（如 ver 3）是什么？**
2. **对应的 RSA 私钥文件（`.pem`）在你们自己手里吗？**
3. **「密钥」区能否看到 CorpId 和会话存档 Secret？**

### 三种情况对应的结论

| 情况 | 结论 | 处理方式 |
|---|---|---|
| ✅ 公钥是你们自己生成的，私钥在手 | 方案 B **立刻可做** | 直接配置 Secret + 可信 IP，写代码拉取即可 |
| ⚠️ 公钥是微伴生成的（微伴持私钥） | 方案 B **需重置密钥对** | 自己生成新密钥对 → 上传**新版本公钥** → 之后的新消息可解；**旧消息永久不可解**；同时要确认会不会影响微伴的存档展示 |
| ❌ 会话存档根本没开通 | 需先走完整开通流程 | 认证 → 购买席位（≥5 账号）→ 确认函 → 审核 → 配置 |

> **关键机制提示**：企业微信的公钥是**按版本号配置**的（`publickey_ver`），私钥也可以**按版本多把并存**。
> 所以理论上「自己生成新公钥 + 微伴继续用旧版本」**有可能并存**，但这需要和微伴确认他们是否支持多版本，不要默认可行。

## 八、建议的推进顺序

```
第 1 步（你来做，5 分钟）
  登录企业微信管理后台 → 会话内容存档 → 查公钥版本 / 私钥归属 / Secret
        │
        ├─ 情况✅ 私钥在手 → 直接进第 2 步
        ├─ 情况⚠️ 微伴持私钥 → 先生成新密钥对、上传新版本公钥，再进第 2 步
        └─ 情况❌ 未开通 → 先走开通流程（1–3 工作日审核）
        │
第 2 步（我来做）
  新增 wecom_archive.py：SDK 初始化 + 增量拉取 + 解密 + 会话归集
  先用 seq=0 拉一小段验证「能不能解出明文」，这是最小验证闭环
        │
第 3 步（我来做）
  接上 analyze.py，用真实聊天正文跑规则打分 → 验证打分准不准
        │
第 4 步（我来做）
  验证 external_userid ↔ 微伴 external_user_id 映射 → 打通评分回写
```
