# 第一章　判断：本项目要不要记忆系统

## 1.1 先回答"要不要"

**要。但不是要一个"通用 Agent 记忆平台"。**

先把"记忆"这个词分清楚。文章里三句话讲透了：

| 概念     | 解决什么                      | 本项目有没有                      |
| ------ | ------------------------- | --------------------------- |
| 上下文窗口  | 这次推理能放多少字                 | ✅ 有（`build_conversation`）   |
| 聊天记录   | 过去发生过什么                   | ✅ 有（`chat_message`，500 万条级） |
| **记忆** | **哪些信息该留下来、什么时候该找回来、怎么用** | ❌ **基本没有**                  |

本项目有海量聊天记录，但**没有记忆**。证据：`build_conversation` 每次只取最近 60 条，  
上次评估的结论（等级、画像、命中项）**只写不读**——每次重评都是从零开始看这 60 条。  
这正是文章开头那个"AI 每次都像第一次见面"的场景，只不过换成了"每次评估都像第一次评估"。

## 1.2 但也不能照搬

本项目与文章的目标场景有**三处结构性差异**，决定了不能照搬 Mem0 / Letta / Zep 那一套：

| 维度   | 文章的目标场景（对话型 Agent） | 本项目（批处理判定流水线）                      |
| ---- | ------------------ | ---------------------------------- |
| 交互形态 | 多轮对话，用户在线等         | 无人值守的定时批处理，无对话                     |
| 记忆主体 | 用户（人）的偏好与历史        | **客户（业务对象）的状态与事实**                 |
| 取数方式 | 语义相似度检索（不知道关键词）    | **结构化主键取数**（`relationship_key` 已知） |
| 时长   | 秒级，用户能感知延迟         | 分钟级，延迟不敏感                          |
| 成本   | 每轮都要检索             | 每会话一次，可接受更多预处理                     |

**结论**：

- 不要 Mem0 / Letta / Zep / Cognee（引入外部依赖 + 向量库 + 图数据库，收益不抵成本）；
- 不要向量检索（规模与语义都不需要，见 §4.6）；
- 不要"短期记忆缓冲"（没有多轮会话）；
- **要的是：把"客户当前有效的状态"单独沉淀一层，在评分前读回来。**  
  这就是文章七模块里的「长期记忆 + 记忆管理器」，但按本项目的形态重写。

## 1.3 一句话给这个设计定性

> 本项目的记忆系统 = **客户状态档案（Customer State Profile）**
>
> - **记忆管理器（写入校验 / 时效 / 冲突消解 / 取代）**
> - **反馈闭环（复核改判回流到规则）**。
>
> 不新增表以外的东西——一张 `customer_memory` 表 + 一处 `build_context()` 改造。

# 第二章　需求原点与现状缺口

## 2.1 需求文档其实已经要求了记忆

`客户意向识别系统需求文档.md` §6.1「分析输入」原文要求**每次分析必须包含**：

> 1. 当前评分规则版本与规则表
> 2. 员工 ID、客户 ID、客户名称
> 3. **上一次有效评分、等级、画像总结及已通知等级**
> 4. 自上次分析后新增的消息和必要的近期上下文
> 5. **相关历史关键消息（需求、报价、邀约、到课、拒绝等）**

并明确写了：

> **不得无限量发送全部历史聊天记录；应保留长期画像摘要，并按需加入近期与关键历史消息。**

**这五条就是一份记忆系统的需求书。** 第 3、5 条是纯记忆能力，第 4 条是"增量 + 兜底"。  
现状只做到了第 1、2 条，第 4 条做成了"硬切最近 60 条"（不等于"增量 + 必要上下文"），  
第 3、5 条**完全未实现**。

→ 所以本设计不是"锦上添花"，是**补需求缺口**（对应优化建议里的 E1 / F1 / F6）。

## 2.2 现状：本项目已有的"记忆零件"

好消息是，本项目已经是"有记忆层"的，缺的是**管理器**：

| 文章七模块                 | 本项目对应物                        | 现状判定                 |
| --------------------- | ----------------------------- | -------------------- |
| 用户（User）              | 客户（`chat_session.target_id`）  | ✅                    |
| 智能体（Agent）            | `scoring_service._score_one`  | ✅                    |
| 记忆触发器（Memory Trigger） | `_candidates` 水位筛选            | ⚠️ 只会被"有新消息/规则变更"触发  |
| 短期记忆（Short-term）      | `build_conversation(60)`      | ⚠️ 硬切，非"增量+关键历史"     |
| 长期记忆（Long-term）       | `customer_intent_assessment`  | ❌ **只写不读**           |
| 记忆管理器（Memory Manager） | —                             | ❌ **完全缺失**           |
| 知识库（Knowledge Base）   | `rules.json` + `scoring_rule` | ⚠️ 有版本化，缺 `examples` |

对照文章建议的**六阶段建设顺序**：

| # | 阶段          | 本项目                                 |
| - | ----------- | ----------------------------------- |
| ① | 当前任务状态管理    | ✅ `sync_cursor` / `scoring_run` 已具备 |
| ② | 持久化记忆       | ⚠️ 有存储，**没有读回**                     |
| ③ | 记忆提取与分类     | ❌ 缺（画像与命中项混在一张流水表里）                 |
| ④ | **多路检索与融合** | ❌ **完全缺失（最缺的一环）**                   |
| ⑤ | 安全与治理       | ⚠️ 连 `.gitignore` 都没有（E6）           |
| ⑥ | 评估体系        | ❌ 缺（E5 / 评估集未建）                     |

**一句话：①②部分具备，③④⑤⑥缺。而 ③④ 就是本文要补的。**

# 第三章　国内外方案调研

## 3.1 国外主流：三种范式

| 系统                  | 核心抽象                                                                | 存储                    | 生命周期管理                | 最适合            |
| ------------------- | ------------------------------------------------------------------- | --------------------- | --------------------- | -------------- |
| **Mem0**            | 抽取式事实（LLM 抽 salient facts）                                          | 向量库（可选图）              | 基本 CRUD，**不含自动合并/衰减** | 个性化、聊天历史压缩     |
| **Letta**（原 MemGPT） | OS 式分层：core（常驻上下文）/ recall / archival                               | PostgreSQL + pgvector | **由 Agent 自己决定**（自编辑） | 长时间自主运行的 Agent |
| **Zep / Graphiti**  | **双时态知识图谱**（每条边带 `valid_at / invalid_at / created_at / expired_at`） | Neo4j / FalkorDB      | **自动失效旧事实**           | CRM、客服、事实随时间变化 |
| Cognee              | 图原生 ECL（Extract-Cognify-Load）                                       | 混合图-向量-关系             | —                     | 多文档知识库         |
| LangMem             | 可配置 memory manager                                                  | 用户自选                  | 由 LangGraph 编排决定      | LangChain 生态   |

**Zep / Graphiti 的双时态模型，是本次调研里对本项目最有价值的一条**：

> 事实变更时**不覆盖、不删除**，而是给旧事实打上 `invalid_at`，新增一条新事实。  
> 于是「当前是什么」和「当时是什么」两个问题都有答案，且每条答案都能回指来源。

这恰好解决了本项目一个具体痛点：**等级会翻转（S→C），分数会回落**。  
如果只记"最后一次"，就无法解释"为什么这个客户从 S 掉到 C"，也无法实现需求里的"前后分比较"。

## 3.2 学术前沿：三条可借鉴的机制

**① Generative Agents（Stanford, 2023）——三因子检索评分**

```
score = α·Recency(指数衰减) + β·Importance(LLM 打分 1-10) + γ·Relevance(embedding 相似度)
```

这是"检索时该想什么"的量化方案，已成为后续几乎所有记忆系统的参考设计。  
**对本项目的启示**：取回的每条记忆也应带权重——不是"取最新一条"，而是"取**相关 × 重要 × 新鲜**"的组合。

**② A-MEM（2025, arXiv:2502.12110）——Zettelkasten 式自组织**

新记忆写入时生成结构化属性（上下文描述、关键词、标签），并**自动与历史记忆建立链接**；  
新记忆还会**反向更新**既有记忆的表示。Multi-Hop 任务比 LoCoMo 提升近 6 倍，token 用量仅 1,200–2,500。

**对本项目的启示**：「链接」比「存储」值钱。本项目天然有链接可用——**`rule_id`**。  
把"证据消息"按 `rule_id` 索引起来，未来就能回答"关于'主动问课'这个维度，历史上出现过哪些证据"。

**③ 认知科学侧：ACT-R 激活 / Ebbinghaus 遗忘曲线**

```
freshness = exp(-λ · Δt)      # 距上次访问越久，衰减越狠
```

被检索命中的记忆**重置衰减时钟**，即"用得越多越清醒"。

## 3.3 工程共识：写在多篇实践文里的八条

| # | 共识                                                | 对本项目的映射                          |
| - | ------------------------------------------------- | -------------------------------- |
| 1 | **写入不是 append，是四决策：ADD / UPDATE / DELETE / SKIP** | 现在只会 INSERT，需要补 UPDATE / SKIP    |
| 2 | **模型推断不得未经验证变成长期事实**                              | 现在 `profile_summary` 零校验直接落库（E3） |
| 3 | **记忆要带来源与信任度**（用户明说 > 系统直读 > 模型推断）                | 现在没有来源字段                         |
| 4 | **冲突要按时间和权威来源解决，不能靠相似度**                          | 现在连"当前有效"标记都没有（E2）               |
| 5 | **遗忘是被低估的一环**，不删就会用旧信息污染判断                        | 现在无过期机制                          |
| 6 | **合并（consolidation）**：同一主题的碎片要归并                  | 现在同一客户几十条评估并列（E2）                |
| 7 | **记忆投毒**是把一次性注入变成永久注入                             | 本项目模型无工具权（H4），天然免疫大半             |
| 8 | **抽取与写入要脱离主链路**（异步），别拖慢响应                         | 本项目批处理，无此顾虑                      |

第 2、3、4、5 条是本项目的主要缺口。

## 3.4 评测基准与一个反直觉发现

| 基准              | 测什么                                     | 关键指标                       |
| --------------- | --------------------------------------- | -------------------------- |
| **LoCoMo**      | 长多会话对话记忆（单跳/多跳/时序/开放域）                  | Exact Match、F1、Recall@k    |
| **LongMemEval** | 五能力：**信息抽取 / 多会话推理 / 时序推理 / 知识更新 / 弃权** | LLM Judge Accuracy、ROUGE-L |
| FAMA            | 知识更新（惩罚依赖过时信息）                          | Forgetting-Aware Accuracy  |
| MemoryArena     | 记忆是否**真的改善了任务完成**                       | Task Success Rate          |

**⚠️ 一个必须知道的发现**：独立评测（Bench'd, 2026-05）显示，  
**GPT-4o-mini 裸模型把整段对话塞进上下文，LongMemEval 得分 57.6%，  
反而打败了多数专门的记忆系统**（Mem0 OSS 32.4%、CrewAI 46.0%、AutoGPT 47.4%）。

> 原因：记忆系统的**压缩与摘要速度，快于它组织信息的速度**——把有用细节丢掉了。

**这对本项目是直接的决策依据**：记忆系统**不是越复杂越好**。  
如果"读回上次结论"的收益还没被验证，就先不要做摘要、合并、衰减那一整套。  
**先做最小可验证的一步：把上次结论读回来，然后测它有没有让结果变好。**

## 3.5 国内方案

**阿里云百炼「记忆库」**（2026-04 上线）——标准四段管道：

```
提取(Extraction) → 存储(Storage) → 检索(Retrieval) → 注入(Injection)
```

- **记忆片段（MemoryNode）**：自动从对话提取（"用户喜辣"）
- **记忆变量（KV）**：手工定义字段，**权重高于片段**，用来校准片段的即时偏差  
  → 官方原话："记忆片段**易受临时性信息干扰**（如用户临时提及'尝试素食'），需通过记忆变量校准"
- 动态治理：自动更新、**过滤记忆冲突**、**模拟遗忘曲线**对低频/过时信息衰减或归档
- 官方宣称（对"记忆库"的优化）：检索 RT 降 50%、日期相关性 +66%、内容相关性 +39%

**阿里云 RDS PostgreSQL 长期记忆**：一个实例内整合 `pgvector` + `Apache AGE`（图）+ 原生关系存储，  
完全兼容 Mem0 SDK。**这条对本项目最有参考价值——因为它说明"PG 里就能做记忆"，不需要独立记忆服务。**

**PolarDB Mem0 / Polar Agent Memory**：向量 + 知识图谱双模，支持事件关系推理（时序/因果/假设）。

**场景侧（CRM 客户档案类）**：悟空 CRM / 珍客 CRM / 纷享销客 / 铠盒 AIBOX 都指向同一个模式——  
**统一客户档案（360° 画像）+ 行为标签 + 时间线事件流**。  
铠盒那个案例的表述最贴本项目："客户信息从散落在微信聊天记录里，变成结构化数据"。

## 3.6 调研结论：借什么、不借什么

| 借                       | 来源                | 理由                 |
| ----------------------- | ----------------- | ------------------ |
| **双时态「当前有效 + 历史版本」**    | Zep / Graphiti    | 解决等级翻转、前后分比较、审计    |
| **三因子取用（相关 × 重要 × 新鲜）** | Generative Agents | 决定"该把哪几条记忆塞进上下文"   |
| **写入四决策 + 来源信任度**       | Mem0 / 工程共识       | 防模型推断污染长期事实（E3）    |
| **「记忆变量」校准「记忆片段」**      | 百炼                | 模型抽的画像不可信，键值槽位优先   |
| **"先在 PG 里做"**          | 阿里云 RDS 长期记忆      | 不引入新组件             |
| **遗忘与合并**               | 工程共识              | 但**延后做**，先验证读回收益   |
| **五能力评测口径**             | LongMemEval       | 用来给本项目的记忆做验收（见第五章） |

| 不借                             | 理由                             |
| ------------------------------ | ------------------------------ |
| Mem0 / Letta / Zep / Cognee 框架 | 引入外部依赖；本项目取数是主键而非相似度           |
| 向量数据库 / embedding 检索           | 记忆条目是结构化槽位，不是自由文本（§4.6）        |
| 图数据库（Neo4j / AGE）              | 本项目的关系只有"客户↔员工↔证据消息"，PG 外键足够   |
| 短期记忆缓冲                         | 没有多轮对话                         |
| 自动摘要 / 自动合并（第一期）               | 先验证读回收益，避免"压缩丢信息"（§3.4 的反直觉发现） |

# 第四章　设计：客户状态档案

## 4.1 记忆分层映射

文章七模块 → 本项目八层的落点：

```
┌─ 知识库（Procedural）──────────────────────────────────────┐
│  rules.json + scoring_rule + examples            [已有·补 examples]
└────────────────────────────────────────────────────────────┘
┌─ 长期记忆（Semantic + State）—— 本文新增 ────────────────────┐
│  customer_memory  ← 客户状态档案（当前有效的事实与状态）      │
│  customer_memory_event ← 记忆事件流（append-only，可回溯）    │
│  customer_intent_assessment ← 评分流水（保持不变）           │
└────────────────────────────────────────────────────────────┘
┌─ 短期记忆（Working）───────────────────────────────────────┐
│  build_context()  四段装配（替换 build_conversation）        │
└────────────────────────────────────────────────────────────┘
┌─ 记忆管理器（★ 新增逻辑，不新增组件）─────────────────────────┐
│  写入校验 · 来源标记 · 时效 · 冲突消解 · 取代 · 反馈回流       │
└────────────────────────────────────────────────────────────┘
```

## 4.2 三类记忆（先分类，再决定存哪、活多久）

文章里"判断进入哪一类记忆"的四个问题，落到本项目：

| 类型       | 内容举例                        | 变化速度 | 存放                               | 生命周期           |
| -------- | --------------------------- | ---- | -------------------------------- | -------------- |
| **事实记忆** | 岗位、公司、地域、需求、预算、时间节点、顾虑      | 慢    | `customer_memory` 槽位             | 长存，评估时刷新       |
| **状态记忆** | 当前等级、当前总分、当前阶段、已通知等级、已回写累计分 | 快    | `customer_memory` 槽位             | 每次评估覆盖 + 旧值留版本 |
| **规则记忆** | 15 个维度定义、examples、冲突优先级     | 极慢   | `rules.json` / `scoring_rule`    | 版本化            |
| **过程记忆** | 每次评估的命中项、证据、画像原文            | —    | `customer_intent_assessment`（流水） | 按保留期           |
| **元记忆**  | 每条规则的误报率排行                  | 慢    | `rule_metric_daily`（视图）          | 长期             |

**关键区分**：

- `customer_memory` = **客户现在是谁、处于什么状态**（一个客户一行）
- `customer_intent_assessment` = **某次评估做过什么**（一个客户多行）

现在的问题正是**把这两者混成了一张表**——导致每次评估都只能重看最近 60 条，而读不到"这个客户现在是什么状态"。

## 4.3 新增表 `customer_memory`

```sql
-- 决议 M-A：一客户一行（覆盖式）。relationship_key 为主键，天然满足「当前有效唯一」；
--           历史不覆盖不删除，全部记入 customer_memory_event（双时态语义见 §4.4 / §4.7）
CREATE TABLE IF NOT EXISTS customer_memory (
    relationship_key   TEXT PRIMARY KEY,        -- staff_id:target_id（需求 §3.2）
    staff_id           TEXT NOT NULL,
    target_id          TEXT NOT NULL,
    target_name        TEXT,

    -- ── 事实槽位（慢变化，键值化，模型不得凭空填）────────────────
    -- 决议 M-B：固定 8 个槽位（清单见本节表 4.3-2），缺值一律填字符串 "未提及"；
    --           不允许 null、不允许新增未定义键；增删槽位须同步改抽取 prompt 与校验白名单
    facts              JSONB DEFAULT '{}'::jsonb,
    -- {"position":"Java后端","company":"某互联网公司","city":"杭州",
    --  "need":"2个月内独立落地AI客服","budget":"未提及","timeline":"下季度",
    --  "concerns":["价格","时间"],"competitor":"未提及"}

    -- ── 状态槽位（快变化，每次评估覆盖 + 留版本）──────────────
    stage              TEXT,      -- 初询/比价/已邀课/已到课/已报价/已关单/流失
    grade              TEXT,      -- S/A/B/C/D（当前有效）
    raw_score          INT,
    last_notified_grade TEXT,     -- 上次已通知等级（F6）
    writeback_accumulated INT DEFAULT 0,  -- 客户级回写水位（D2-1）

    -- ── 画像（模型生成，但必须可校验、带来源）──────────────────
    profile_summary    TEXT,      -- 画像摘要
    sales_strategy     TEXT,      -- 销售策略

    -- ── 记忆元数据（文章建议的"一条可维护的记忆"字段）──────────
    source             TEXT NOT NULL DEFAULT 'ai',   -- ai / review / rule / system
    trust_level        TEXT NOT NULL DEFAULT 'inferred', -- stated/reviewed/derived/inferred
    confidence         REAL,      -- 系统算出的会话级置信度（E4）
    verification_status TEXT NOT NULL DEFAULT 'na',  -- na/verified/rejected

    -- ── 时效与取代（对齐 Graphiti 双时态）──────────────────────
    is_current         BOOL NOT NULL DEFAULT true,   -- 当前有效（E2）
    valid_from         TIMESTAMPTZ NOT NULL DEFAULT now(),
    valid_until        TIMESTAMPTZ,                  -- 留空=仍然有效
    superseded_by      TEXT,                         -- 被哪条记忆取代
    version            INT NOT NULL DEFAULT 1,

    last_assessment_id BIGINT,    -- 最近一次评估
    last_msg_time      BIGINT,    -- 参与更新的最后消息时间
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_mem_staff  ON customer_memory (staff_id);
CREATE INDEX IF NOT EXISTS idx_mem_grade  ON customer_memory (grade, is_current);
CREATE INDEX IF NOT EXISTS idx_mem_stage  ON customer_memory (stage);
CREATE INDEX IF NOT EXISTS idx_mem_current ON customer_memory (is_current, updated_at DESC);
```


**表 4.3-2　事实槽位清单（决议 M-B：固定 8 项，不再扩）**

| # | 槽位键          | 含义      | 典型值                | 变化速度 | 是否进评分                              |
| - | ------------ | ------- | ------------------ | ---- | ---------------------------------- |
| 1 | `position`   | 岗位/职能   | "Java后端"、"测试"、"HR" | 慢    | ✅ 直接影响 `positive_coder_profile` 等  |
| 2 | `company`    | 公司/行业   | "某互联网公司"、"教培"      | 慢    | ✅ 影响画像与报价合理性                       |
| 3 | `city`       | 地域      | "杭州"               | 慢    | ⚠️ 仅画像（影响线下课/服务半径）                 |
| 4 | `need`       | 明确的需求   | "2个月内独立落地AI客服"     | 中    | ✅ 高权重正信号                           |
| 5 | `budget`     | 预算信息    | "未提及"、"1万以内"       | 中    | ✅ 影响 `negative_price_haggling` 的判定 |
| 6 | `timeline`   | 时间节点    | "下季度"、"本月"         | 中    | ✅ 影响紧迫度与重点跟进                       |
| 7 | `concerns`   | 顾虑（数组）  | `["价格","时间不够"]`    | 中    | ✅ 负信号来源                            |
| 8 | `competitor` | 竞品/比价对象 | "未提及"、"某机构"        | 慢    | ⚠️ 仅画像（影响谈判策略）                     |

**槽位纪律**：

- 缺值统一写字符串 `"未提及"`（**不用 null**）——避免"没抽到"和"客户确实没说"两种语义混淆；
- 数组型槽位（`concerns`）缺值写 `[]`；
- **只允许这 8 个键**，多余键由校验层丢弃并记 `invalid_items`；增删槽位必须同时改本表 + 抽取 prompt + 校验白名单（三处同步）；
- `position` / `need` / `timeline` / `budget` / `concerns` 这 5 项是**高价值槽位**，读回时优先展示（见 §4.5）。

**记忆事件流（append-only，回答"怎么变成现在这样的"）**：

```sql
CREATE TABLE IF NOT EXISTS customer_memory_event (
    id              BIGSERIAL PRIMARY KEY,
    relationship_key TEXT NOT NULL,
    assessment_id   BIGINT,                  -- 由哪次评估产生
    op              TEXT NOT NULL,           -- add / update / supersede / verify / reject
    slot            TEXT,                    -- facts.position / stage / grade / profile ...
    old_value       TEXT,
    new_value       TEXT,
    source          TEXT NOT NULL,           -- ai / review / rule / system
    trust_level     TEXT NOT NULL,
    evidence_msg_ids JSONB,                  -- 证据消息 id（可回链）
    actor           TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_memev_rel ON customer_memory_event (relationship_key, id DESC);
```

> 这张表是文章说的"保留必要的历史版本"+"来源追踪"的载体。  
> 它让「为什么这个客户从 S 掉到 C」成为一个**可回答的问题**（查事件流即可）。

**关键历史消息索引（对齐需求 §6.1 第 5 条 + A-MEM 的"链接"思想）**：

在 `chat_message` 上加一列（或建一张轻索引表）：

```sql
ALTER TABLE chat_message ADD COLUMN IF NOT EXISTS rule_tags TEXT[];  -- 该消息作为证据命中的 rule_id
CREATE INDEX IF NOT EXISTS idx_msg_ruletags ON chat_message USING gin (rule_tags);
```

证据回链（A1）通过的消息，打上它命中的 `rule_id`。  
于是"相关历史关键消息"的检索变成一条 SQL：

```sql
SELECT ... FROM chat_message
 WHERE staff_id=%s AND session_id=%s AND rule_tags && %s   -- 与本次规则相关
 ORDER BY msg_time ASC;
```

**比 embedding 检索更准、更可解释、零额外成本**——因为"哪些消息算关键"这件事，  
规则表里已经定义好了（15 个维度），不需要靠语义猜测。

## 4.4 写入：四态 + 校验 + 来源

对齐文章"写入不能只考虑新增"，`_score_one` 落库后追加一步 `update_memory()`：

| 操作            | 触发条件                                   | 处理                                                                              |
| ------------- | -------------------------------------- | ------------------------------------------------------------------------------- |
| **ADD**       | 客户首次评估，或出现新的 `rule_id` 命中              | 新建槽位 + 写 `add` 事件                                                               |
| **UPDATE**    | 同一槽位的新值（如 `grade` S→C、`stage` 已邀课→已到课） | 覆盖当前值 + 旧值写 `update` 事件                                                         |
| **SUPERSEDE** | 新值与原值**矛盾**（如"有预算"→"不打算买"）             | 旧记录 `valid_until=now(), is_current=false, superseded_by=new` + 写 `supersede` 事件 |
| **SKIP**      | 与现有值等价，或来源可信度不高于现有值                    | 不写                                                                              |

**写入校验（修 E3，这是防幻觉的核心）**：

```
模型输出 profile_summary / facts
        ↓
① 证据回链（A1）：每条断言能否在原文定位？定位不到 → 不得进"事实槽位"
        ↓
② 来源分级：
   · engine=rule 算出来的（48h、到课标签）        → trust_level = derived（可直接生效）
   · 人工复核确认的                              → trust_level = reviewed（最高）
   · 模型明说的（客户原话"我是做Java的"）         → trust_level = stated
   · 模型推断的（"客户可能对价格敏感"）           → trust_level = inferred（不进事实槽位，只进画像文本）
        ↓
③ 槽位写入：只允许 stated/reviewed/derived 进 facts 槽位
             inferred 只能进 profile_summary 文本 + 标 source=ai
```

**关键原则**（对齐百炼的"记忆变量权重高于记忆片段"）：  
**结构化槽位 > 模型自由文本。** 因为槽位可校验、可比较、可覆盖；自由文本不能。

## 4.5 读回：`build_context()` 四段装配

这是本设计的核心动作——**用 `build_context` 替换 `build_conversation`**，对齐需求 §6.1。

```
┌─ ① 客户档案（长期记忆读回）★ 修 E1/F1 ─────────────────────┐
│  「该客户当前状态（截至上次评估）：等级 B（-1 分）；阶段=已邀课；│
│    岗位=Java后端；需求=2个月内落地AI客服；顾虑=价格；            │
│    上次画像摘要：……；上次销售策略：……                          │
│    已通知等级：B」                                             │
└───────────────────────────────────────────────────────────┘
┌─ ② 上次评分明细（供前后分比较）──────────────────────────────┐
│  「上次命中的加分项：positive_coder_profile(+2) 等 3 项，合计 +4│
│    上次命中的扣分项：negative_price_haggling(-1)，合计 -1」      │
└───────────────────────────────────────────────────────────┘
┌─ ③ 增量消息（自上次分析后新增）★ 对齐 §6.1 第 4 条 ───────────┐
│  WHERE msg_time > memory.last_msg_time 的全部可读消息          │
└───────────────────────────────────────────────────────────┘
┌─ ④ 关键历史消息（按 rule_id 拉取）★ 对齐 §6.1 第 5 条 ────────┐
│  WHERE rule_tags && 本次相关规则 → 全局上限 30 条，             │
│  每个 rule_id 最多 3 条（取最近的证据消息），组内按时间升序      │
└───────────────────────────────────────────────────────────┘
┌─ ⑤ 兜底窗口（沿用现状）─────────────────────────────────────┐
│  若 ③+④ 有效信息量不足（B4 口径），补最近 60 条可读消息         │
└───────────────────────────────────────────────────────────┘
```

**上下文预算与条数上限（决议 M-D）**：

| 段        | 上限                           | 理由                                               |
| -------- | ---------------------------- | ------------------------------------------------ |
| ① 客户档案   | ≈ 400 token（固定长度，不裁剪）        | 8 个槽位 + 上次摘要，体积可预测                               |
| ② 上次评分明细 | ≈ 300 token（固定长度，不裁剪）        | 只列命中项与分值                                         |
| ③ 增量消息   | **200 条软上限**                 | 单会话增量通常远低于此；防"沉寂 3 个月后一次涌入上千条"                   |
| ④ 关键历史消息 | **30 条**（每个 `rule_id` ≤ 3 条） | 15 维度 × 3 = 45 为理论上限，实际单会话通常命中 3–6 维度 → 约 9–18 条 |
| ⑤ 兜底窗口   | 60 条（沿用现状）                   | 仅在 ③+④ 信息量不足时启用                                  |
| **合计**   | **≈ 12k token / 会话**（硬预算）    | 与现状"硬切 60 条"的总量同量级，不增加成本                         |

超预算时的**裁剪顺序**：先砍 ⑤（兜底）→ 再把 ④ 中低权重 `rule_id` 组收缩为每组 1 条 → 最后从**最早**开始砍 ③ 的增量消息。  
**① 客户档案与 ② 上次评分明细永不裁剪**——它们是 §6.1 第 3 条的硬要求，也是"记忆"区别于"聊天记录"的全部价值所在。

**决议 M-C：记忆参与提示词，但不得改写分数。**

- 记忆以**自然语言上下文**形式进入提示词第 ① 段（"该客户当前状态（截至上次评估）：等级 B…"）；
- **记忆表里的 `grade` / `raw_score` 不得作为本次计分的输入参数**——本次分数 100% 由本次证据经 `rules.py` 计算；
- 记忆的合法作用只有两种：**(a)** 让模型知道"上次是什么状态"，从而识别**态度变化**（S→C 的正确解读，见 §4.7 的例子）；**(b)** 提供"上次命中的扣分项"，避免同一证据被重复计分。
- 这样既拿到了记忆的收益，又保持了"分数永远可追溯、可解释"的不变量（对齐需求 §6.3）。

**四段合并的取用规则**（借 Generative Agents 三因子）：

```
优先级 = 与本次规则的关联度 × 重要度(该 rule 的权重) × 新鲜度(exp(-λΔt))
```

具体到本项目：**engine=rule 的硬事实（48h/标签）永远排在前面**（重要度最高且不可辩驳），  
其次是增量消息（新鲜度最高），最后才是兜底窗口。

**与现状的差别**：现在 60 条硬切 = 会话一旦超过 60 条，早期信息（往往是"需求/预算/岗位"这类最重要的事实）  
就被挤掉了；而读回客户档案，等于把早期信息**以摘要形式永久保留**。

## 4.6 检索：为什么不用向量库

结论：**本项目的记忆取用是主键取数，不是语义检索。**

| 问题   | 传统 Agent 记忆    | 本项目                              |
| ---- | -------------- | -------------------------------- |
| 检索什么 | "哪段记忆与当前问题相似？" | "这个客户现在什么状态？"                    |
| 用什么键 | 语义相似度（不知道会问什么） | `relationship_key`（已知）           |
| 备选键  | —              | `rule_id`（关键历史消息）、`msg_time`（增量） |
| 条目数  | 数千~数百万         | 单客户几十条                           |
| 精度   | 相似度必然有噪声、有冲突   | 主键查询**无噪声、无冲突**                  |

**用户若问"那相似度检索什么时候用得上？"** —— 唯一可能的场景是"跨客户的相似案例检索"  
（"跟这个客户情况类似的客户，上次是怎么谈成的"），这属于**二期**，且那本质是知识库检索而非记忆检索。

## 4.7 时效与冲突消解

**时效（修 E2）**：

| 记忆             | 时效策略                                     |
| -------------- | ---------------------------------------- |
| 事实槽位（岗位/需求/地域） | 长存；每次评估可刷新；若与原文矛盾则 SUPERSEDE             |
| 状态槽位（等级/分数/阶段） | 每次评估覆盖；旧值进事件流；`is_current` 唯一            |
| 硬事实（48h 未回复）   | **不落记忆**——每次由规则引擎实时算（因为它是"此刻"的状态，不是历史事实） |
| 标签（到课/完课）      | 随客户标签变化刷新；标签消失即代表失效                      |

**冲突消解优先级（参考 AGM 信念修正 + 来源信任度）**：

```
人工复核（reviewed） > 规则引擎（derived） > 客户原话（stated） > 模型推断（inferred）
```

同优先级冲突时：**新证据覆盖旧证据**（时间优先），但旧证据保留在事件流里。

**一个具体例子**：

```
T1  评估：客户"在职、有明确项目需求"  → grade=S
T2  评估：客户"算了，我自己学"        → grade=C
```

错误做法：T2 的评估只看到最近 60 条 → 可能漏掉 T1 里那些正分证据，也可能把"自学"这条旧证据重复计分。  
正确做法：T2 读回"上次 grade=S、上次命中 6 项、已通知 B"→ 模型明确知道"客户**在 T1→T2 之间**态度转变了"  
→ 输出时会正确地把"态度转变"识别为负信号，而不是把 T1 的正信号再算一遍。

**这就是"记忆"相对"聊天记录"的价值：它让变化可被看见。**

## 4.8 遗忘与治理

**第一期不做自动遗忘**（理由见 §3.4：压缩丢信息的风险 > 收益）。只做三件确定的：

1. **取代而非删除**：`is_current=false` + `valid_until`，历史永不物理删除（审计要求）。
2. **列表去重（修 E2）**：`api_scoring.py` 的列表查询加 `WHERE is_current = true`，  
   同一客户只显示一条"当前有效"；历史版本在详情页按需展开。
3. **保留期**：`data_retention_days` 控制 `chat_message` / `customer_intent_assessment` 的保留  
   （记忆表 `customer_memory` 不删——它是聚合结果，体积小）。

**第二期（验证读回收益后）再考虑**：

- 槽位衰减：长期未更新的 `facts` 槽位降权，在上下文里标注"（N 天前）"
- 画像合并：同一客户多次评估的画像碎片归并为一条（聚类阈值 0.85，参考工程共识）

## 4.9 反馈闭环：meta-loop

对齐文章"真正决定记忆系统质量的是反馈闭环" + 本项目 E5/G8：

```
negative_review 复核改判（人工确认的扣分项）
        ↓
① 回流记忆：人工确认的事实 → trust_level=reviewed → 写入 customer_memory（人工最高优先级）
        ↓
② 回流统计：按 rule_id 聚合「AI 判了但被人推翻」→ rule_metric_daily（误报率排行榜）
        ↓
③ 回流规则：误报率高的规则 → 改 rules.json 的 criteria / examples
        ↓
④ 门禁：改规则后跑评估集（金标准 + 回归集）→ 指标不降才允许发布
        ↓
   下一轮评分用新规则 + 新记忆
```

**这条闭环是"越用越有用的记忆"与"越积越乱的存储"的分界线。**  
没有 ② ③ ④，记忆库只会越攒越大、误报照旧。

# 第五章　记忆系统的评测

对齐 LongMemEval 的五能力，逐条给本项目可执行的验证方法（不需要新框架，用 SQL + 脚本即可）：

| LongMemEval 能力 | 本项目对应验证                                               | 通过标准                                    |
| -------------- | ----------------------------------------------------- | --------------------------------------- |
| **信息抽取**       | 记忆写入的事实槽位是否与原文一致（抽 20 条人工核对）                          | 抽取准确率 ≥ 90%                             |
| **多会话推理**      | `msg_count > 60` 的会话，连跑两次 `force`，比较 `positive_items` | 两次结果一致（E1 的原始验证法）                       |
| **时序推理**       | 48h/时间节点类规则的判定是否由规则引擎算出、不被模型覆盖                        | `engine=rule` 项 100% 来自 `compute_facts` |
| **知识更新**       | 等级翻转（S→C）后，新评估是否读到了旧等级并正确识别"态度转变"                     | 记忆读回前后，`negative_items` 变化方向正确          |
| **弃权**         | 客户已明确拒绝后，是否仍用旧的"高意向"画像                                | 不出现"客户拒绝 + 仍输出高意向策略"                    |

**最关键的三个数字**（对齐架构说明书 G2 组的验收锚点）：

1. **一致性**：`msg_count>60` 的会话连跑两次 `force`，结果一致率
2. **读回有效性**：同一批会话，开/关记忆读回，`positive_items` 与等级一致率的变化
3. **画像可信度**：`customer_memory.profile_summary` 中能被证据支撑的比例

**并且必须对照测试**（呼应 §3.4 的反直觉发现）：  
**"不加记忆，直接把全部消息塞进上下文"** 作为基线。  
如果记忆读回的得分**打不过**"全塞"基线，就说明我们的摘要/抽取在丢信息——那时该修的是抽取质量，而不是继续加记忆机制。

# 第七章　落地阶段

| 阶段     | 做什么                                                                    | 依赖           | 验收                                  |
| ------ | ---------------------------------------------------------------------- | ------------ | ----------------------------------- |
| **M0** | 建 `customer_memory` 表 + 写入 `_score_one` 后的 `update_memory()`（**只写不读**） | 无            | 表被正确填充；同一客户多次评估后 `is_current` 唯一    |
| **M1** | `build_context()` 替换 `build_conversation()`（**开始读回**）                  | M0 + A1 证据回链 | `msg_count>60` 的会话连跑两次 `force` 结果一致 |
| **M2** | 写入校验 + 来源分级 + `customer_memory_event` 事件流                              | M1           | 画像中可被证据支撑的比例 ≥ 90%                  |
| **M3** | `rule_tags` 关键历史消息索引（需求 §6.1 第 5 条）                                    | A1           | 早期需求/报价消息能被正确召回                     |
| **M4** | 列表去重（`is_current`）+ 记忆详情页（前端）                                          | M0           | 评分中心每个客户只显示一条当前有效                   |
| **M5** | meta-loop 反馈回流（E5/G8）                                                  | M2 + 评估集     | 误报率排行榜可查；规则改动有门禁                    |

**如果只做两件**：**M0 + M1**。  
因为 M0+M1 就能回答那个最关键的问题——**"读回上次结论，到底有没有让评分更准？"**  
在它被验证之前，M2–M5 都是投机。

# 第八章　明确不做

| 不做                             | 理由                                                   |
| ------------------------------ | ---------------------------------------------------- |
| 引入 Mem0 / Letta / Zep / Cognee | 外部依赖；取数是主键，不是语义相似（§4.6）                              |
| 向量数据库 / embedding 检索           | 记忆条目是结构化槽位；关键消息用 `rule_id` 索引更准                      |
| 图数据库（Neo4j / Apache AGE）       | 关系仅"客户↔员工↔证据"，PG 外键足够                                |
| 短期记忆缓冲 / 多轮会话记忆                | 本系统无对话交互                                             |
| 模型自省式 Reflection（让模型生成"洞察"）    | 与 H4（模型无工具权）冲突，且产出的推断不可校验；改为**规则驱动的统计聚合**（meta-loop） |
| 第一期做自动摘要 / 自动合并 / 衰减           | 先验证读回收益（§3.4 反直觉发现）                                  |
| 加 Agent / 沙箱 / ReAct           | 沿用架构说明书第八章                                           |

# 第九章　待拍板

| #       | 事项                                                                                                    | 影响                |
| ------- | ----------------------------------------------------------------------------------------------------- | ----------------- |
| **M-A** | `customer_memory` 是**一客户一行（覆盖式）**&#x8FD8;是**一客户多版本（双时态）**？<br />本文默认：主表一客户一行（当前有效）+ 事件流存历史，兼顾查询性能与可回溯 | 决定表结构复杂度          |
| **M-B** | 事实槽位的字段清单（`facts` JSONB 的 schema）—— 需要业务确认"哪些信息必须记住"<br />（岗位/公司/地域/需求/预算/时间节点/顾虑/竞品这 8 项是否为全部？）      | 决定抽取 prompt 与槽位校验 |
| **M-C** | 记忆读回是否**参与评分**，还是只作为提示词的**参考上下文**？<br />本文默认：参与（作为提示词第 ① 段），但**不直接改写分数**——分数仍由本次证据算                   | 决定"记忆能否影响结论"      |
| **M-D** | 关键历史消息的**条数上限**（防止早期消息把上下文塞满）                                                                         | 影响 token 成本       |

**技术侧把记忆补上，业务侧把 M-A/M-B 定清楚，这套记忆系统就落地。**
