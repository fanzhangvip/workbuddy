## 0. 结论摘要

**这份代码的业务设计水准明显高于它的工程化水准。**

业务侧有三件做得相当扎实的事：把「模型只判断、代码算分」用类型契约钉死；
把「置信度必须算出来」从模型手里收回；把「回写与评分解耦」做成同事务入队 + 独立 outbox。
这些不是口号，`contracts.py` / `confidence.py` / `outbox.py` 里有可指认的实现，
并且有测试盯着「改造前后行为逐字一致」。

但工程化层面还停留在「能在这台机器上跑起来」：
**没有应用鉴权、没有 CI、没有锁文件、没有迁移框架、没有 lint、测试不是 pytest、
路径写死了某台机器的 Chrome 与 Python**。此外有真实客户数据进了版本库。

按严重度分布：**P0 4 项 · P1 5 项 · P2 14 项**。

| 维度 | 评级 | 说明 |
|---|---|---|
| 业务逻辑与领域建模 | 优秀 | 三条铁律落到实处，护栏有论证、有对照测试 |
| 可观测性 | 优秀 | 分段计数、裁剪明细、token、耗时分布、拒绝原因分布都落了 |
| 数据一致性 | 良好 | 同事务入队很扎实，但互斥与幂等回收只做了一半 |
| 安全与权限 | 欠缺 | 无应用鉴权、审计主体客户端自报、PII 入库 |
| 可移植与可复现 | 欠缺 | 硬编码路径、无锁文件、无容器运行路径 |
| 工程化与自动化 | 欠缺 | 无 CI / lint / 统一测试入口 / 覆盖率 |

## 1. P0 问题（建议优先处理）

### P0-1 真实客户数据已进版本库

**位置**：`analyze_result_real.json`（被 `git ls-files` 跟踪）

**证据**：

```text

analyze_result.json
analyze_result_low.json
analyze_result_real.json
```

文件名里的 `real` 说明它不是样例数据。该文件是 `analyze.py` 的完整输出，
含真实会话正文、客户画像摘要、销售策略、逐条命中项与证据原文行 —— 属于客户 PII。

**顺带发现**：仓库根 `C:\zero\workbuddy` 的 git 历史里还有一个 1.5 GB 的
`2026-10-07-17-13-39/training-deai.zip`（在 `e556daa feat: 删除zip` 中被删除，
但对象仍在历史里），本地对象占 **1.40 GiB**。

**影响**：PII 已随仓库分发，删除当前文件无法从历史中抹去；仓库体积异常。

**建议**：

1. 立刻把 `analyze_result_real.json` 从跟踪中移除并加进 `.gitignore`（`analyze_result*.json`）。
2. 用 `git filter-repo`（或 BFG）重写历史清掉该文件与 zip 对象，然后强推并通知协作者重新克隆。

### P0-2 全部 `/api/*` 端点没有应用层鉴权

**位置**：`backend/main.py`（`app.include_router(...)` 6 个 router，无任何依赖注入的鉴权）

**证据**：`backend/api_auth.py` 的 `auth_service` 管的是**微伴登录态**（cookie / open_sid），
与「谁能调用本系统」无关。`backend/api_review.py` 里 `reviewer` 全部取自请求体字符串：

```python
reviewer = (payload.get("reviewer") or "工作人员").strip()
```

**影响**：任何能访问 8848 端口的人都能：发起全量重评、真实回写微伴客户分数/标签、
提交或篡改人工复核结论、执行数据清理。`audit_log` 的 `actor` 可被随意伪造，
**审计无法作为追责依据**。

**缓解事实**：服务绑定 `127.0.0.1`，CORS 只放行 `localhost:5173`，外网不可达。
同一台机器上的其他用户或进程仍然可以调用。

**建议**：加一层最小鉴权（静态 Token 或反向代理 Basic Auth 均可），
并把 `actor` 从服务端身份推导而非请求体；对写外部系统的端点
（`grade-tags/align`、`retention/purge`、`rules/publish`、`auth/login`）额外要求显式确认。

### P0-3 `taskkill /F /IM chrome.exe` 无差别杀进程

**位置**（3 处）：

- `backend/auth_service.py:104`
- `wb_keepalive.py:277`

**建议**：改为只结束本项目专用 profile 启动的实例 —— 记录自己 `Popen` 的 PID，

### P0-4 借真实客户当「载体」创建微伴标签

**位置**：`backend/grade_tag.py:117-119`（配合 `_probe_staff()` / `_probe_customer()`，同文件 139 / 148 行）

### P1-1 机器路径硬编码，项目无法换机部署

| 位置 | 内容 |

### P1-2 「精确可复现版本」的承诺落空

`requirements.txt` 开头写着「精确可复现版本见 `requirements.lock.txt`（pip freeze 产物）」，
但 `.gitignore` 第 3 行正是 `requirements.lock.txt` —— **锁文件从未进仓库**。

**影响**：依赖只声明下限（`fastapi>=0.143.0` 等），不同时间安装会得到不同版本。

**建议**：要么提交锁文件，要么改用 `pyproject.toml` + `uv.lock` / `poetry.lock` 并提交。

### P1-3 DDL 存在三个来源

| 来源 | 内容 |
|---|---|
| `backend/schema.sql` | 22 张表的权威定义 |
| `backend/failure_worker.py` 的 `ensure_columns()` | 又给 `session_failure` 加了 4 列 + 1 个索引 |
| `backend/idempotency.py` 的 `_ensure_table()` | 又定义了 `request_guard` 表 |

**影响**：`session_failure`、`request_guard` 两处重复定义，改一处忘另一处会静默漂移；
散落在代码里的 DDL 也无法被评审。（`backend/main.py` 的 `db.init_db()` 只执行 `schema.sql`。）

**建议**：把 `ensure_columns()` / `_ensure_table()` 的全部语句合并回 `schema.sql`，
或引入 Alembic，让「schema 只有一个来源」重新成立。

### P1-4 同步的跨进程互斥只做了一半

```python
# scoring_service.py:784 —— 有跨进程检查（查 DB 里 status='running'），并带僵尸 run 回收
def is_running(self) -> bool: ...

# sync_service.py:90 —— 只看本进程线程
def is_running(self) -> bool:
    return self._thread is not None and self._thread.is_alive()
```

`scheduler.guard_can_start()` 与 `sync_service.start()` 都会调 `scoring.is_running()`，
但**没有任何地方**能让评分感知到「另一个进程正在同步」。

**影响**：脚本或调度器进程在同步时，后端仍可启动评分 → 评分读到
`msg_count` / `last_msg_time` 正在变化的「半截会话」，结论不可复现。
这正是设计文档里 H1 想解决的问题，实现只覆盖了单向。

**建议**：给同步也加一张 `job_lock` 表（或直接用 `pg_advisory_lock`），
让同步 / 评分 / 评估三类长任务共用同一套跨进程互斥。

### P1-5 明文口令进版本库

```yaml

POSTGRES_PASSWORD: <REDACTED>
```

```python
# backend/db.py:22
```

## 3. P2 问题

### P2-1 幂等表写了回收函数，但没有任何调用方

`backend/idempotency.py:110` 定义了 `reap()`，但全仓库搜索**只有定义处这一条匹配**，
`scheduler.py` 的 8 个 job 里也没有它。

叠加 `data_retention_days` 默认为 `0`（不清理），`request_guard` **默认永不清理**。
`audit_log` / `scoring_run` / `trace_span` / `session_failure` 同理。

这类问题比「没写」更值得注意：防御措施已经存在，会让人以为已经生效。

### P2-2 测试在默认 Windows 控制台下直接崩溃

实测（未做任何设置的默认控制台）：

```text
$ .venv\Scripts\python.exe tests\test_confidence.py
UnicodeEncodeError: 'gbk' codec can't encode character '\u2194' in position 18
  File "tests/test_confidence.py", line 90, in test_item
    check("大小写不敏感（rag ↔ RAG）", ...)
```

崩溃点在**测试断言名**里的 `↔`，而不是被测代码。加上编码设置后：

```text
$ $env:PYTHONIOENCODING='utf-8'
$ .venv\Scripts\python.exe tests\test_contracts.py        → 35 passed / 0 failed
$ .venv\Scripts\python.exe tests\test_ctx_preprocess.py   → 25/25 通过
```

**建议**：在 `tests/` 里统一设置输出编码（或在各脚本头部把 `sys.stdout` reconfigure 为 UTF-8），
避免「环境问题伪装成测试失败」。

### P2-3 无统一测试入口、无 CI、无覆盖率

23 个 `tests/test_*.py` 是脚本式测试（各自 `main()` + `sys.exit()`），需人工逐个执行；
没有 pytest、没有 `conftest.py`、没有 CI 配置、没有覆盖率统计。
`tests/_run_batch.py` 只是「续跑长会话批量评分」的运维脚本，不是 runner。

**另**：依赖 PostgreSQL 的测试在 DB 不可用时是 30 秒 `PoolTimeout` 硬失败（实测），
没有「检测到无 DB 就跳过并明确说明」的路径。

### P2-4 无 lint / format / 类型检查

根目录没有 `pyproject.toml` / ruff / black / mypy / flake8 / pre-commit 任何配置；
前端没有 ESLint / Prettier，也没用 TypeScript。风格目前靠「写的人自觉」，
1784 行的 `scoring_service.py` 里已经能看到换行与注释密度不一致。

### P2-5 写放大：每个会话都整行重写 `scoring_run.detail`

`_bump()` 每次调用都执行一次完整的 `UPDATE scoring_run SET ...`，
而 `detail` 是包含 `ctx_*` 分段计数、裁剪明细、`hook_denials` 分布、
以及最多 5000 个 `session_secs` 的 JSONB。

**影响**：长批量（170 会话量级）下每会话一次全量重写，detail 越大越慢。

**建议**：进度计数与最终 detail 分开 —— 计数走轻量单行 UPDATE，
详细 detail 只在收尾写一次；`session_secs` 改落独立表或只保留分位数。

### P2-6 token 预算是粗略估算

`_estimate_tokens()` = `ceil(len(text) / 1.5)`，注释也承认「宁可高估」。
预算阈值 12000 因此是近似量，中英混排时偏差方向不稳定。

**建议**：接入真实 tokenizer，或至少把估算值与 API 返回的实际 `prompt_tokens`
一起落库，用于事后校正系数。

### P2-7 回写路径绕过了统一 HTTP 层

`weiban.py:120-127`（`use_header_token=True` 分支）与 `_post_tag()`（同文件约 184 行）
都是裸 `urllib.request.urlopen`，没有超时分类重试、没有 metrics 计数 ——
而 `backend/http_client.py` 存在的全部理由就是统一这些。

注释解释了「重试交给 outbox，避免两层重试」，这个理由对 `_post_tag` 成立；
但 `add_customer_score` 在**同一个函数**里，`use_header_token=False` 时走 `request_retry`、
`True` 时走裸 urlopen —— 同一函数两种行为，容易踩坑。

### P2-8 规则档位在代码里硬编码

```python
# backend/scoring_service.py:1175
items.append({"rule_id": "negative_no_reply_2d", "score": -2, ...})
```

分值 `-2` 与 rule_id 都是字面量，而非从 `rules.json` 读档位。
若业务把该规则改成 `-3`，代码仍写 `-2` → `validate_items()` 会把它判为非法项**静默丢弃**，
表现为「该扣的分没扣」，而日志里只有一条 `invalid_items`。

### P2-9 前端两个巨型单文件组件

`ScoreView.vue` 623 行、`EvalView.vue` 485 行、`ChatView.vue` 414 行；
无状态管理（无 Pinia / Vuex）、无组件拆分、无前端测试、无类型约束。
`api.js` 把 60+ 个端点集中在 118 行里，改一处容易波及别处。

### P2-10 配置项没有注册表

约 50 个 `app_setting` 键硬编码在 `backend/api_scoring.py:519` 起的白名单元组里，
键名、类型、默认值全靠约定；而 `get_settings` 里又逐个人工地重新读一遍 ——
同一份清单存在读侧、写侧两处，新增配置极易漏改一侧。

**建议**：抽一张声明式注册表（键 / 类型 / 默认值 / 说明），两侧都从它生成。

### P2-11 每轮评分开始时清空并重写规则表

`_run()` 启动时调 `sync_rules(rv)`，其实现是
`DELETE FROM scoring_rule WHERE rule_version = %s` 后逐行 INSERT（同一事务内）。
窗口期内 `/api/scoring/rules` 会读到空列表；并发跑第二轮也会互相清表。

### P2-12 `/api/health` 暴露连接串信息

```python
# backend/main.py:73-74
return {"ok": True, "db": db.DSN.split("@")[-1]}
```

返回 host:port/dbname。信息量不大，但在无鉴权的前提下没有理由暴露。

### P2-13 开启追踪后每个节点多一次 DB 查询

`trace.py:79` 的 `if not enabled()` 在**每次节点调用**里都执行，
而 `enabled()` 每次都查 `db.get_setting("trace_enabled")`。
开启追踪后，图路径的 11 个节点会额外产生 11 次设置查询。

**建议**：进程内缓存 + 设置变更时失效。

### P2-14 数据保留会留下语义不一致

`retention.PURGEABLE` 包含 `chat_message`（按 `msg_time` 秒级裁剪），
但 `eval_case.messages_hash`（对话指纹）与 `writeback_ledger`（回写水位）
都**不在**清理范围内。删掉历史消息后，评估样本会集体「漂移失效」，
而水位类数据仍在 —— 两类数据的保留期语义没有对齐，文档里也没有说明。

## 4. 值得保留的设计（评审中确认有效）

1. **三条铁律有代码级强制**：`AssessmentOut` 的总分/等级字段不接受模型回填；
   `confidence.compute()` 不读模型自述；`analyze._attach_evidence()` 回链失败即丢弃并留痕。
2. **护栏集中且有对照测试**：`hooks` 把散落的 `if` 收敛为 4 个判定点，
   `REASON_TO_WB_STATUS` 保证改造前后状态映射一致，`test_hooks.py` 做逐组合对比。
3. **双路径灰度**：`use_graph_session` 让 LangGraph 路径与旧串行路径并存，
   `test_graph_session_parity.py` 断言 `raw_score` / `grade` 差异为 0 —— 很成熟的重构手法。
4. **三个「默认安全」**：回写默认 `dry_run`、等级标签默认 `off`、数据保留默认 `0`（不清理）。
   对外部系统的副作用一律要求人显式打开，方向完全正确。
5. **回写不丢失**：assessment 与 outbox **同事务入队**，配合至少一次投递 + `sending` 卡死回收。
   这是真正解决「回写永久丢失」的做法，而不是把重试次数调大。
6. **上下文的取舍有论证**：`③` 增量可砍、`④` 关键历史尽量保，理由是
   「维度是不可再生资源，消息是可再生资源」—— 这个判断被完整写进注释并被实现遵守。
7. **可归因四件套**：`rule_version` / `prompt_version` / `schema_version` / `model_name`
   让「分数为什么变了」可以被回答。
8. **观测内建**：`scoring_run.detail` 落了分段计数、裁剪明细、token 用量、
   单会话耗时 p50 / p95 / max、钩子拒绝原因分布 —— 排障不需要再加日志。

## 5. 「这个 Agent 项目没做好的地方」——按主题归纳

### 5.1 交付形态是「能运行」，不是「能被接手」

无 CI、无 lint、无统一测试入口、无锁文件、无迁移框架、无容器化运行路径、
换机即失效的绝对路径、脚本式测试靠人工逐个跑。
结果是：作者之外的人拿到它，第一步就卡住；改动无法被自动验证。

### 5.2 凭据与浏览器耦合太深，且伴随破坏性副作用

整条数据链路依赖一次人工扫码换来的 cookie + `open_sid`，再靠「定时访问后台」续期。
这条链路上有硬编码 Chrome 路径、全局 `taskkill`、`subprocess` 启动 GUI 浏览器、Playwright 连 CDP。
它没有可复制的部署形态，而且**自动化动作会杀掉用户无关的浏览器会话**。

### 5.3 安全与权限基本空白

无应用鉴权；审计主体由客户端自报；真实客户评估结果进了版本库；数据库口令明文入库。
在一个会**真实修改客户分数与标签**的系统上，这四项都需要补。

### 5.4 并发与一致性只在单进程假设下成立

- 同步 / 评分互斥只覆盖了单向（P1-4）；
- outbox 的 `_claim` 与投递分离，注释里承认依赖「单实例调度」，但
  `POST /api/scoring/grade-tags/drain` 与定时 job 可以并发触发同一个 drain；
- `request_guard` 没有任何回收机制（P2-1）。

单实例单进程时没问题，一旦多开一个后端或跑一次脚本就会踩到。

### 5.5 「防御措施存在但未接线」

`idempotency.reap()` 无调用方、`retention` 默认关闭、`trace_enabled` 默认关闭、
`failure_worker` 依赖 job 生效。这类状态最容易误导：看代码的人会认为「已经防住了」，实际并未生效。

**建议**：明确区分「默认开启的保护」与「默认关闭的观测/优化」，并在架构文档里列出清单。

### 5.6 维护成本会随需求增长快速上升

`scoring_service.py` 1784 行承载了候选筛选、上下文装配、LLM 调用、计分、落库、
回写、复核入队、进度统计、护栏判定共 9 类职责；约 50 个配置键散落在一个元组里；
前端 3 个 400+ 行的 SFC。在功能还在快速增加的阶段（本仓库近三次提交都在加护栏与链路），
这会让「改一处、不知影响谁」的概率持续升高。

## 6. 建议的处理顺序

| 顺序 | 事项 | 理由 |
|---|---|---|
| 1 | 移除 `analyze_result_real.json` 并重写历史（P0-1） | 已泄露，越晚越贵 |
| 2 | 收敛 `taskkill`，停止自动杀浏览器（P0-3） | 会真实毁掉用户数据 |
| 3 | 修正 `grade_tag` 借真实客户建标签（P0-4） | 会真实污染客户数据 |
| 4 | 加最小鉴权 + 服务端注入 `actor`（P0-2） | 否则其他修复都缺访问控制 |
| 5 | 路径改配置 + 补 `.env.example` + 提交锁文件（P1-1 / P1-2） | 换机能跑的前置条件 |
| 6 | 跨进程互斥统一到 DB 锁（P1-4） | 数据正确性 |
| 7 | DDL 收敛 + 引入迁移（P1-3） | 后续所有 schema 改动的前提 |
| 8 | 上 CI：pytest + ruff + 编码统一（P2-2 / P2-3 / P2-4） | 让前 7 项不再回退 |
