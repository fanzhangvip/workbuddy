### 1.2 仍存在的重复（按修复价值排序）

## 2. 后端架构

### 2.1 成立的部分

* **模块级 import 无环**（`arch_check.py` §2 报 ✅）—— 依赖方向没有硬伤。
* **横切件已成体系**：`db`（连接/设置/JSONB）、`job_service`（跑批骨架）、
  `audit` + `fingerprint`（观测）、`http_client`（HTTP）、`policy`（策略）、
  `task_runtime`（任务状态机）、`api_common`/`api_guard`（接口层横切）。
* **可辨认的设计模式**（不是硬套，是确实在解决各自的问题）：

| 模式 | 落点 |
|---|---|
| Adapter | `weiban.py` / `ww_chatdata.py`（把微伴、企微的差异包在统一接口后） |
| Registry | `settings_registry.py` + `defaults_manifest.py`（配置的唯一声明源 + 自检） |
| Strategy | `policy.py`（三档策略按置信度选执行方式） |
| Template Method | `job_service.JobService`（骨架固定、列与作业由子类给） |
| Facade | `api_*.py`（对前端只暴露用例） |
| Observer / Pipeline | `hooks.py` + `graph_session.py`（11 个节点的显式钩子） |
| Outbox | `outbox.py` / `grade_tag.py`（至少一次投递 + 独立退避 + 状态记录） |
| Guard Clause / Gate | `api_guard`、`guard_can_start`、Policy 闸、幂等闸 |

### 2.2 要理的三处

**① 三组「软环」：靠函数内延迟 import 绕开，不炸但方向没理顺**

```
scoring_service <-> sync_service       （sync 为读一个设置/常量反向 import 评分服务）
scoring_service <-> eval_runner
scoring_service <-> graph_session
```

`scoring_service.py` 是 1134 行 / 28 个方法的上帝类，且同时依赖 21 个内部模块 ——
**它是所有环的中心**。修法是依赖倒置：把「跑一轮需要的上下文」（db 之外的东西：
设置读取、模型调用、写回、审计）抽成接口/协议模块，让 `eval_runner`、`graph_session`、
`sync_service` 依赖抽象而不是反过来指向评分服务；或把 `scoring_service` 按
「事实计算 / 落库 / 回写 / 编排」拆成 3~4 个模块。

**② 多写入者表（同一张表被 2 个以上模块写）**

> **2026-10-15 晚更新：下表已治理** —— `customer_intent_assessment` / `eval_case` /
> `negative_review` 各配唯一写入口（`assessment_repo` / `eval_case_repo` /
> `review_repo`）；`score_writeback` + `writeback_ledger` 也一并收口到
> `writeback_repo`（那两处的水位 upsert 原先**逐字相同**，是最危险的一处重复：
> 改一处忘一处 → 客户分数重复累加或少写）。
> 核查命令：`rg -l "INSERT INTO|UPDATE |DELETE FROM" backend | ...`（只应剩 repos）。
> 有意保留的两处：`chat_message` 是**列级分工**（sync 写正文，scoring 只写
> `rule_tags`）；`session_failure` 是**生产者/消费者**（scoring 建单、failure_worker
> 拥有其状态机）—— 两者都不是「同一列被两方写」。

去掉了扫描器把 `SET` / `SKIP` 当表名的假阳性后，真实情况是：

| 表 | 写入方 | 判断 |
|---|---|---|
| `customer_intent_assessment` | scoring_service / outbox / api_review / backfill | 列级分工（结果 / 回写状态 / 复核状态 / 历史回填），但**没有单一写入者**，改列名要动 4 处 |
| `eval_case` | api_eval / eval_runner / meta_loop | 标注、跑评估、回流各自写 |
| `negative_review` | scoring_service / api_review / meta_loop | 建单、复核、回流 |
| `score_writeback` + `writeback_ledger` | outbox / scoring_service | **两条回写路径**（同步内联 / 异步排空），口径必须一致 |
| `session_failure` | scoring_service / failure_worker | 建单 + 处理 |
| `chat_message` | sync_service / scoring_service | **列级分工**：sync 写正文，scoring 只写 `rule_tags`（记忆回链），属合理 |

建议：给前三张表各配一个**唯一的写入口函数**（如 `assessment.set_writeback_status()`），
把「谁能改哪一列」写进一处，而不是散在 4 个模块的 SQL 里。

**③ 体量与分层**

* 超长函数 Top：`wb_staff_export.main` 183 行、`scoring_service.build_context` 171、
  `backfill.run` 140、`scoring_service._run` 126 / `start` 120 / `_score_one` 116、
  `sync_service._run` 113。
* API 层直连 SQL：`api_eval` 16 次 / 394 行、`api_scoring` 12 次 / 647 行、
  `api_review` 11 次 / 238 行、`api_chat` 8 次 / 160 行 —— 路由层里既做校验又写 SQL，
  用例逻辑没有独立层。规模还小（<20 人内部用），不必现在就上 Repository；
  但**新增功能时把领域逻辑放进 service，别继续堆在 `api_*.py`**。
* 全局可变状态：`auth_service._state`、`wb_keepalive._last_run`、两个
  `service = XxxService()` 单例 —— 可接受（单进程内嵌运行时），但生命周期要有注释。

## 6. 复查中发现**并已修/待修**的真问题

### 6.1 已修：`ScoreView` 用了 `msg` 却从未声明

`同步标签` / `对齐预演` 两个按钮在 API 成功之后执行 `msg.value = ...` ——
而全文件没有 `const msg`，直接 `ReferenceError`，成功提示永远不出现。
（`{{ msg }}` 倒是写在模板里，所以页面不报错、只是提示空白。）
引入 `useAsyncAction` 时顺带修好；Playwright 实点「同步标签」已验证提示出现。

### 6.2 ✅ 已修：`sync_service.stop()` 停不掉别的进程

**修法**（2026-10-15 晚，DDL 前已备份 `backups/pre-sync-stop-20261015-194500.dump`，59.2 MB）：

· `schema.sql`：`ALTER TABLE sync_job ADD COLUMN IF NOT EXISTS stop_requested BOOLEAN NOT NULL DEFAULT false;`
  （与 `scoring_run` 同一写法；`init_db()` 幂等执行，**漂移检测通过** `drift: False`）；
· `sync_service.stop()`：把停止请求写进 DB 的 running 行（照抄评分那边的做法）；
· `sync_service._should_stop(job_id)`：每轮查一次 `stop_requested`（进程内标志
  或 DB 标志任一命中即停；**查库失败按「不停」处理**，避免一次查询抖动掐掉用户的同步），
  `_run` 的两处循环改用它。

**跨进程端到端验证**（`.workbuddy/tmp/verify_cross_process_stop.py`，真跨进程）：

```
1. 宿主进程起动一次小同步（1 员工 × 2 会话）           → job=84 running
2. 调 **容器** 的 POST /api/sync/stop（另一个进程）      → {"ok":true,…}
3. 宿主进程的同步读到 DB 标志后退出                      → [sync] job=84 stopped 用时 2.5s
   ✅ status != running   ✅ stop_requested=true   ✅ 终态 = stopped
```

证据：

```
backend/scoring_service.py:837   db.execute("UPDATE scoring_run SET stop_requested=true …")   ← 跨进程停止
backend/schema.sql:460           ALTER TABLE scoring_run ADD COLUMN IF NOT EXISTS stop_requested …
backend/sync_service.py: stop()  只有 self._stop = True                                        ← 进程内停止
```

`scoring_service.stop()` 的注释写得很清楚：「**含跨进程**：把 `stop_requested` 写进 DB，
让跑在别的进程的 `_run` 也能看到（**只设进程内标志的话，后端点"停止"停不掉
脚本/调度器里的批量**）」—— 而同步服务正是那个反面。

**实测后果**：调度器里跑的同步（`triggered_by=schedule`）在 UI 上点「停止」，
接口返回 `{"ok": true, "message": "已发出停止信号"}`，但那个进程根本读不到这个标志，
同步继续跑；而同步在跑时**评分被互斥闸挡住**（用户会看到「同步任务进行中」）。
本次验证过程中就真实踩到：一个 44 分钟前启动、进程已被重启杀掉的同步行，
让「开始评分」与「启动同步」双双被拒 15 分钟（直到心跳判死把它标成失败）。

**修法**（3 步，都是加法）：

1. `schema.sql`：`ALTER TABLE sync_job ADD COLUMN IF NOT EXISTS stop_requested BOOLEAN NOT NULL DEFAULT false;`
   （与 `scoring_run` 同一写法，幂等）；
2. `sync_service.stop()`：把标志写进 DB 的 running 行（照抄评分那边的做法）；
3. `sync_service._run()`：每个会话后轮询一次该标志，命中就优雅退出（状态 `stopped`）。

顺带可以补一条：`stop()` 若发现「running 行不属于本进程且心跳已停」，
应直接如实回报（"任务已不在运行"），而不是报「已发出停止信号」。
