## 〇、结论速览

| 问题 | 结论 |
|---|---|
| 需要 **RAG**（向量检索 + 分块）吗？ | ❌ **不需要**。三条硬理由见 §3 |
| 需要 **向量数据库 / embedding** 吗？ | ❌ **不需要**。取数是主键（`staff_id + session_id`），不是语义相似 |
| 需要 **GraphRAG** 吗？ | ❌ **不需要**。关系只有"客户↔员工↔证据消息"，PG 外键足够 |
| 需要 **Ontology 引擎**（Palantir 那一套）吗？ | ❌ **不需要**——但**我们已经在本体建模的思路上了**，见 §6 |
| 需要 **GBrain / Mem0 / Zep 这类记忆框架**吗？ | ❌ **不需要**（已于记忆方案 v1.1 拍板），但文章的三条契约要**内化**，见 §5 |
| 当前真正缺的是什么？ | ✅ **上下文裁剪器**（4 段装配）—— 因为少数长会话确实超预算，见 §3.4 |
| 现有检索手段够用吗？ | ✅ 够。已有 `pg_trgm` + `ILIKE`（`idx_msg_content_trgm`），关键词检索够本阶段用 |

**一句话**：本项目的问题从来不是"从海量文档里找到相关的那一篇"，而是"**这一个客户现在是什么状态**"。
前者是 RAG 的命题，后者是**主键取数 + 记忆读回**的命题。用 RAG 来解决后者，是拿错工具。

## 一、两篇文章要义提炼

### 1.1 第一篇《RAG 解决不了的问题，GBrain 想解决：给 AI Agent 装一个能记事的"第二大脑"》

（公众号「智能体AI」，2026-09-21）

**核心命题**：Agent 缺的不是更长的 Context，而是**一个持续存在、可追溯、可纠正的外部大脑**。

**① 传统 RAG 与"编译式知识"是两件事**

| | 传统 RAG | 编译式知识（GBrain） |
|---|---|---|
| 链路 | Query → Retrieve → Generate | Import → Structure → Link → Compile → Retrieve → Reason |
| 解决的问题 | 从大量文档里找到相关内容 | 把知识提前加工成 Agent 能理解的结构 |
| 类比 | 图书馆现场搜索，甩你十篇文档自己读 | 先把资料整理分类建索引、理清人物与事件关系，再交给你用 |

**② 五种基本对象**（GBrain 的 schema）：Page（知识载体）/ Entity（现实对象）/ Fact（关于 Entity 的事实）/ Timeline（事实变化的时间点）/ Graph（关系网）。
> 原文：「不要把'导入文档'和'建立知识'当成同一件事，前者只是把数据搬进来，后者才是真正在构建 Brain。」

**③ Brain-First 三条行为契约**（本文最可迁移的部分）：

1. **Search-First**：回答前先查 Brain，尤其是项目历史、用户偏好、业务规则、已做出的决策
2. **Write-Back**：产生新的长期有效事实后要写回 Brain
3. **Cite**：使用 Brain 中的知识要标明来源，可追溯"谁写的、来自哪页、何时产生、是否还有效"

> 三者的关系：Search-First 解决"读得到"，Write-Back 解决"存得下"，Cite 解决"信得过"。

**④ ⚠️ 全文最值得记住的一句**：

> **「工具提供的是能力，行为决定的是 Agent 是否真的会用这个能力。」**

即：MCP 接上了 memory 工具，Agent 仍可能完全不调用，直接凭 Context 作答——"我明明接了 Memory，怎么还是失忆？"很多"支持跨会话记忆"的宣传都卡在这一步。

**⑤ 跨 Session A→B 实验**（唯一可信的验证法）：Session A 写入事实 → **彻底关闭**（而不是在 A 里问"你还记得吗"）→ 开零历史的 Session B → 看 B 能否主动检索出来并**引用来源**。

**⑥ 事实会变，Memory ≠ KV 缓存**：更接近「**当前真相 + 完整时间线**」的组合（`compiled truth` + `timeline`）。

**⑦ Memory 会生病**：Knowledge Drift（规则改了旧文档还在）/ Duplicate（重复写入）/ Contradiction（部门说法打架）/ Stale（已过期）/ **Self-Poisoning（最危险：Agent 写错一条事实，之后被当成真相反复引用，形成"错误写入→检索→当事实→产生新结论→继续写入"的自我强化循环）**。
> 治理工具设计上的关键取舍：**发现问题与修改事实分开处理**（GBrain 的 `dream` 只报告不自动改）。

**⑧ 混合架构才是现实答案**：

| 数据性质 | 该用什么 |
|---|---|
| 稳定/半稳定的多来源知识 | **Compiled Brain**（编译式知识） |
| 变化快的实时文档 | **RAG** |
| 实时业务状态（订单/库存/工单） | **Enterprise API** |
| 用户偏好/用户事实 | **Memory Layer** |

**⑨ 选型三问**：① 要记的是"用户"还是"知识"？② 知识变化快不快？③ 是不是多 Agent、多用户共用？

### 1.2 第二篇《从 RAG 到 GraphRAG，再到 Ontology：企业 AI 的演进终于到了"运营层"》

（公众号「智能体AI」，2026-09-23）

**核心命题**：Ontology 不只描述企业里"有什么"，更定义 AI"能对企业做什么"。

**① 一条清晰的演进线**：

```
RAG（让 AI 找到知识）
 → GraphRAG（让 AI 理解知识之间的关系）
 → Agent（让 AI 自主完成任务）
 → MCP（让 Agent 更容易连接外部世界）
 → Ontology（让 AI 理解企业世界）
 → Action（让 AI 在企业世界里执行）
 → Governance（让这一切变得可控）
```

**② Ontology 六个构件**：`Object`（Customer/Order/Product）/ `Property`（name、revenue、riskLevel）/ `Link`（对象间关系）/ `Action`（**决定 AI 是只能看，还是能做**）/ `Function`（把复杂计算纳入业务模型：Object → Function → Decision → Action）/ `Interface`（抽象共性，避免 God Object）。
> 前半三个（Object/Property/Link/Interface）定义**世界长什么样**，后半两个（Function/Action）定义**世界如何变化**。

**③ Ontology ≠ 知识图谱**：知识图谱是 `Entity + Relationship + Knowledge`；Ontology 多了 `Business Logic + Action + Security + Governance`——从"这些东西有什么关系"升级到"**企业允许对它们做什么**"。

**④ 2026 年的关键变化：Ontology MCP GA** —— 外部 Agent 可通过 MCP 读 Ontology、执行**预定义 Action**、调用 Query Functions，并沿用平台权限体系。
> 易混淆点：**Ontology MCP（给消费者用，使用业务世界）≠ Palantir MCP（给构建者用，改业务模型）**。
> 原文关键区分：「AI 的行为被映射成**企业定义好的业务动作**，这和让 LLM 随便调用 `update_database` 完全不是一回事。」

**⑤ 供应链案例**（说明 Action + Governance 的价值）：Agent 沿 `Order → Vehicle → Battery → Supplier` 追出瓶颈 → 查备选供应商 → 用 Function 算成本/交付/产能/风险 → 给建议 → **Human Approval** → 执行 Action → 更新业务状态 → **留下审计记录**。

**⑥ ⚠️ 全文最重要的边界声明**：

> **「千万别把 Ontology 当成所有企业 AI 的标准答案。Ontology 是一种很重的企业能力。」**

**⑦ 什么场景才值得考虑 Ontology**（四条同时偏多才需要）：
1. 业务对象非常复杂（制造/金融/医疗那种）
2. 数据孤岛影响决策（同一个 Supplier 在五个系统里不是同一个）
3. AI 不只回答问题，还要**执行动作**（改订单、调库存、触发审批）
4. 需要强治理和审计（金融/医疗/制药/制造/能源）

**⑧ 反面清单**：只查订单 → SQL 够；搜内部文档 → RAG 够；分析文档里的人物事件关系 → GraphRAG 可能更合适；做 BI 报表 → 数仓 + BI 就够。

**⑨ 企业 Agent 的完整公式**：`Model + Context + Tools + Ontology + Harness + Governance`。
> 原文：「模型能力只是 Agent 的**上限**，企业语义和工程体系决定了 Agent 的**下限**。」

## 二、判断的地基：本项目的数据形态（实测）

任何选型判断都必须落在数据的真实形态上。以下是 2026-10-14 在真实库上实测的结果：

### 2.1 "知识"有多小

| 项 | 实测值 |
|---|---|
| `rules.json` 全文件体积 | **5,199 字节** |
| 注入提示词的规则文本（`rules_brief_for_prompt`） | **1,061 字符 ≈ 600–700 token** |
| 规则条数 | 加分 8 条 + 扣分 7 条 = **15 条** |
| 规则变化频率 | 极慢（版本化，人工改） |

**整个"知识库"700 token，被 100% 完整注入每一次评分调用的提示词里。** 全程没有"检索"这个环节——也不需要。

### 2.2 "数据"有多大

| 项 | 实测值 |
|---|---|
| 消息总数 / 会话总数 | 32,758 条 / 782 个 |
| 单会话消息数 min / avg / p50 / p90 / p99 / max | 1 / 42 / **35** / 77 / 171 / **320** |
| 单条消息正文平均字数 | **169 字**（p50 126、p90 348） |
| 单会话正文总字数 平均 / 最大 | **7,083 字 / 38,194 字** |
| 单会话 token 估算 平均 / 最大 | ≈ **4.7k / 25k token** |

**换算结论（关键）**：

| 分位 | 单会话 token | 加规则 0.7k 后 | 是否装得进 12k 预算 |
|---|---|---|---|
| p50（35 条） | ≈ 3.9k | ≈ 4.6k | ✅ 宽裕 |
| p90（77 条） | ≈ 8.6k | ≈ 9.3k | ✅ 可以 |
| p99（171 条） | ≈ 19k | ≈ 20k | ❌ **超预算** |
| max（320 条） | ≈ 25k | ≈ 26k | ❌ **超预算** |

→ **约 1%–3% 的会话"整段塞不下"。这是本项目唯一真实的"规模问题"。**

### 2.3 现有的检索设施

| 能力 | 现状 |
|---|---|
| 关键词检索 | ✅ `pg_trgm` 扩展 + GIN 索引（`idx_msg_content_trgm`、`idx_session_name`）+ `ILIKE` 查询（`api_chat.py`） |
| 语义/向量检索 | ❌ 无。全库代码 grep `embedding/vector/faiss/chroma/milvus/pgvector/langchain` **零命中** |
| 相似度排序 | ❌ 无 |
| 需求文档里的"RAG" | 仅出现在**规则条文**里（"已学习一段时间…含实操、API、**RAG**、Agent 等"）—— 那是"客户学过 RAG"的打分信号 |
| 需求文档里的"知识库" | 仅出现在**举例的 evidence 文本**里（"客户描述公司需要搭建知识库"）—— 那是客户的需求描述 |

> **注意**：本项目代码与需求里**从来没有"系统要建知识库/上 RAG"这个需求**。之前的印象源于规则条文和证据例句里的词面重合。

## 三、为什么不需要 RAG：三条硬理由

### 3.1 理由一：知识太小，装得下 —— RAG 解决的问题在我们这里不存在

RAG 的存在前提是"**知识量超出上下文窗口，必须按需检索**"。
本项目：知识 700 token，预算 12k token，**知识占比 6%**。

在这种量级上引入 RAG，付出的代价是真实的、收益是零：

| RAG 带来的 | 对本项目的实际影响 |
|---|---|
| 分块 + embedding 管道 | 新增一条可失败的链路（换模型/换切分策略都要重跑） |
| 召回率这个新失败模式 | **新增**一类 bug：规则明明在库里却没被检索到 → 判分依据凭空消失 |
| 检索延迟与成本 | 每会话多一次调用；而现状是规则直接进 prompt，零延迟 |
| 可解释性下降 | 现状"15 条规则恒定全量参与"是完全可复现的；检索则引入不稳定 |

> 原文佐证（第一篇 §1.1 的类比）：传统 RAG 是"现场搜索，甩你十篇文档自己读"，而编译式知识是"先把资料整理好"。**本项目已经处于更靠后的状态——15 条规则是人工精写、结构化、带版本号，比任何自动编译都干净。**

### 3.2 理由二：取数是主键，不是相似度

| 问题 | 传统 RAG 场景 | 本项目 |
|---|---|---|
| 要检索什么 | "哪段文档与这个问题相似？" | "**这个客户现在什么状态？**" |
| 用什么键 | 语义相似度（**因为不知道答案在哪**） | `staff_id + session_id`（**已知**） |
| 备选键 | — | `rule_id`（关键历史消息）、`msg_time`（增量） |
| 精度 | 相似度必然带噪声、带冲突 | 主键查询**无噪声、无冲突** |

**RAG 的前提是"不知道答案在哪一篇里"，而我们永远知道。** 给一个已知主键的查询加一层向量检索，是把确定性降级为概率性。

### 3.3 理由三：文档是"短对话"，不是"长文档" —— 分块会直接破坏语义

这是最容易被忽略的一条。RAG 的必需工序是 **chunk（分块）**，而**分块对聊天记录是有害的**：

- 单会话中位数 **35 条消息**、平均 **42 条**——绝大多数会话本身就是"一个整块"，强行切分只会把完整语境切碎；
- 聊天是**强时序依赖**的：第 200 条"这个价格能接受吗"依赖第 50 条谈的价格；第 300 条"算了，我自己学"依赖前面所有的铺垫。**一旦分块，跨块语义必然丢失**；
- 语义恰恰藏在"变化"里：需求从"想学"→"报班"→"自学"——**这是本系统最重要的信号，而它天然是跨消息的**。分块会把这个信号切成互不相干的碎片。

> 反证：p50 会话整段才 3.9k token，**读全文比检索更准、更省、更可解释**。对 97%+ 的会话，"检索"是在人为制造信息损失。

### 3.4 那么"1%–3% 装不下的长会话"怎么办？—— 用裁剪，不用检索

**"装不下"有两种解法**：

| 解法 | 做法 | 适用于 |
|---|---|---|
| (a) RAG 检索 | 分块 → 向量 → 取 Top-K 块 | 长文档、多文档、语义相似度高、无强时序 |
| (b) **结构化裁剪** | 只取"最近 + 增量 + 关键历史" | **时序对话、主键已知、有结构化标签** |

**本项目选 (b)**，而且**方案已经设计好了**——就是记忆方案 v1.1 §4.5 的**四段装配**：

```
① 客户档案（记忆读回）      ← 早期重要事实以摘要形式永久保留（解决"早期信息被挤掉"）
② 上次评分明细              ← 供前后分比较
③ 增量消息（自上次分析后）   ← 新鲜度最高，200 条软上限
④ 关键历史消息（rule_tags）  ← 需求 §6.1 第 5 条，≤30 条，每 rule ≤3
⑤ 兜底窗口                  ← 仅信息量不足时补 60 条
```

**④ 段就是"结构化检索"**：用 `chat_message.rule_tags TEXT[]` + GIN 索引，按 `rule_id` 精确匹配取回历史关键证据。
它达成了 RAG 想达成的目标（**找回过往的关键信息**），但用的是**规则表里已经定义好的维度**做键——**比 embedding 更准、更可解释、零额外成本、无召回率风险**。

> 换句话说：**我们需要的"检索"是"按已知标签精确过滤"，不是"按语义模糊猜测"。**

## 四、逐项判定汇总

| 技术项 | 判定 | 理由 |
|---|---|---|
| RAG（分块 + 向量检索） | ❌ 不需要 | 知识 700 token 全量可注入（§3.1）；主键取数非相似度（§3.2）；短对话分块破坏语义（§3.3） |
| 向量数据库 / embedding | ❌ 不需要 | 同上；记忆条目是结构化槽位不是自由文本 |
| GraphRAG | ❌ 不需要 | 关系只有"客户↔员工↔证据消息"三层，PG 外键 + 外键索引足够；无多跳推理需求 |
| Ontology 引擎（Palantir 式） | ❌ 不需要 | 文章自己声明"很重的企业能力、不是标准答案"；我们不满足它的四条前提（业务对象复杂度、数据孤岛、AI 执行动作、强审计）中的多数 |
| GBrain / Mem0 / Zep / Letta | ❌ 不需要 | 已于记忆方案 v1.1 拍板；本项目取数是主键、记忆主体是客户状态 |
| **"关键历史消息"检索** | ✅ **需要** | 需求 §6.1 第 5 条；但实现方式是 **`rule_tags` 标签精确匹配**，不是向量 |
| **上下文裁剪器（4 段装配）** | ✅ **需要** | 1%–3% 长会话超 12k 预算；方案见记忆方案 §4.5 |
| 关键词全文检索 | ✅ 已有 | `pg_trgm` + GIN + `ILIKE`，本阶段够用 |

## 五、不该上 RAG，但该内化第一篇的三条契约

第一篇的价值不在"GBrain 这个工具"，而在**它指出的失效模式**。对照本项目（记忆方案 v1.1）：

| 文章契约 | 本项目对应物 | 状态 |
|---|---|---|
| **Search-First**（回答前先查） | `build_context()` 的 ① 客户档案 + ② 上次评分明细读回 | ⚠️ **设计完成（M1），未实现** |
| **Write-Back**（新事实写回） | `update_memory()` 四态写入（ADD/UPDATE/SUPERSEDE/SKIP） | ⚠️ 设计完成（M0），未实现 |
| **Cite**（标明来源） | 证据回链 A1 + `rule_tags` + `customer_memory_event.evidence_msg_ids` | ⚠️ A1 是 M1 的前置；rule_tags 属 M3 |

**⚠️ 但文章那条最重要的警告必须变成我们的检查项**：

> 「工具提供的是能力，**行为**决定的是 Agent 是否真的会用这个能力。」

翻译到本项目：**光有 `customer_memory` 表和 `build_context()` 函数是不够的——必须确保评分链路真的在调它。**

这不是理论担忧。本项目历史上已经出现过同型问题：
- `_candidates(force=True)` 的 `force` 参数**完全未被使用**（2026-10-14 记录的 A3 项，P0 bug）；
- `scoring_fetch_tags` 默认 False，导致 `positive_attended_class` 的 +2 档**默认不可达**（F3/D1）；
- `compute_facts` 取标签整段 `except Exception: pass`，工具失败被静默吞（G1）。

**全部是"能力存在但没被真正使用"**。所以 M1 落地时必须配套：

1. **调用点唯一性**：`build_context()` 只允许有一个调用点，且**禁止 `build_conversation` 残留调用**（落地时全局 grep 断言）；
2. **读回可观测**：每次评分在 `scoring_run` 或审计里记录"本次上下文各段条数/字符数"，让"记忆有没有真的被读进去"**看得见**；
3. **A→B 式验证**：沿用记忆方案 M1 的验收法——`msg_count>60` 的会话连跑两次 `force`，比较结果一致性。这是本项目版本的"跨 Session 实验"。

## 六、第二篇的真正启示：我们已经在做"轻量本体"，但不要升级

第二篇讲的是 Palantir 的 Ontology。**照搬是错的（文章自己这么说），但它给了一面镜子——本项目的设计已经天然落在这个思路上**：

| Ontology 构件 | 本项目的对应物 | 位置 |
|---|---|---|
| **Object** | 客户（`chat_session.target_id`）、员工（`staff_id`） | 现有 |
| **Property** | `customer_memory.facts` 的 **8 个槽位**（position/company/city/need/budget/timeline/concerns/competitor） | 记忆方案 §4.3 表 4.3-2 |
| **Link** | 客户↔员工↔证据消息；`rule_tags` 把消息链到规则维度 | 记忆方案 §4.3 |
| **Function** | `rules.compute_score()` / `compute_facts()` / `grade_of()` | 现有 |
| **Action** | 回写评分（`/open-api/external_user/score/add`）、加等级标签、进重点跟进名单 | 现有（回写）；未做（重点跟进/导出） |
| **Governance** | `dry_run` 开关、负分复核队列（`negative_review`）、`audit_log`、`validate_items` 丢弃非法项 | 现有 |

**这正是本项目"模型只出证据、分数由代码算、回写走 dry_run"这些设计的理论名字——叫轻量 Ontology。**

而且第二篇文章里最有价值的一句，恰好印证了本项目的一条核心不变量：

> 「AI 的行为被映射成**企业定义好的业务动作**，这和让 LLM 随便调用 `update_database` 完全不是一回事。」

→ 对应本项目的 **H4 不变量：模型无工具调用权，只输出 JSON；所有副作用（取标签、解密、回写）由代码显式调用**。这不是"还没做工具调用"，而是**刻意的治理设计**。

**但结论是：不要升级。**

- 我们只有 **2 类业务对象**（客户、员工）、**15 个判定维度**、**782 个会话**——距离 Ontology 的四条前提（复杂对象体系、数据孤岛、AI 执行动作、强审计）差得很远；
- 从"8 个 JSON 槽位"升级到"Object/Property/Link/Action 建模引擎"，是**用一个重型框架替换掉一个 5KB 的 JSON 文件**；
- 真正需要保留的只有它的**思路**：把业务语义显式化（这已经在 8 槽位 + 规则表里做到了），以及**Action 必须是受治理的**（这已经在 dry_run + 复核队列里做到了）。

## 七、什么时候才需要 RAG：触发条件清单

和"多 Agent 升级条件"一样，把判据写下来，日后对照判断，避免拍脑袋：

| # | 触发条件 | 说明 | 那时的正确做法 |
|---|---|---|---|
| **T1** | 要引入**外部稳定文档**（课程讲义、产品手册、售后政策、培训资料），总量 **> 10 万字** | 注意：这是**新功能**（"销售知识助手"），**不是评分链路的一部分** | 那才值得 chunk + embedding；或按第一篇建议做"编译式知识" |
| **T2** | 规则表从 15 条膨胀到 **100+ 条**，且每条带大量正反例，**超出 prompt 预算** | 优先级最低——**首选仍是结构化**：规则表是结构化的，按 `rule_id` 精确命中永远优于语义检索 | 先做"规则分层"（核心规则全量注入 + 长尾规则按需加载），再谈检索 |
| **T3** | 需要**跨客户相似案例检索**（"跟这个客户情况类似的客户，上次是怎么谈成的"） | **这是本项目唯一真实的向量检索场景**（因为此时"答案在哪"确实未知） | 记忆方案 §4.6 已定性为**二期**；且本质是知识库检索而非记忆检索 |
| **T4** | 要做**基于公司资料的问答**（客服/售前自助） | 独立产品线，与评分链路并行不悖 | 标准 RAG 架构 |
| **T5** | 单会话消息数常态突破 **1000 条**，且**早期信息不可摘要** | 目前 max=320，且早期信息可用"记忆摘要"保留 | 先检查 4 段装配是否失效，再考虑语义检索 |

**在 T1–T5 全部未触发前，上 RAG 属于"为架构而架构"。**

> 补充一个技术细节（留给 T3 真正发生时用）：现有 `pg_trgm` 对中文的支持有限（trigram 按字符切，中文短词召回一般）。真要做中文全文检索，正确顺序是 **`zhparser`/`pg_jieba` 全文索引 → 再考虑向量**，而不是直接跳到向量库。

## 九、一句话回答

> **不需要 RAG。**
> 因为本项目要回答的问题不是"哪段文档和这个问题最像"，而是"**这个客户现在是什么状态**"——
> 前者需要检索，后者需要**主键取数 + 记忆读回**。
>
> 我们的"知识"只有 700 token（全量注入即可），我们的"数据"是 35 条一组的短对话（读全文比检索更准），
> 我们唯一真实的规模问题是 1%–3% 的长会话超预算——而它的解法是**结构化裁剪（4 段装配）**，不是向量检索。
>
> **真正该做的，是把记忆方案的 M0 + M1 落地，并盯住"工具提供了，行为有没有真的用上"这条警告。**
