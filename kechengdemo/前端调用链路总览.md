# 前端调用链路总览（全页面）

> 日期：2026-10-16 ｜ 覆盖：`App.vue` + 8 个视图 ｜ 依据：前端源码 + 后端路由/服务源码 + 对运行中服务的实测
> 与 `AGENTS.md` 的关系：这份是"页面视角"的调用图；写代码时**复用规则**仍以 `AGENTS.md` 的 Reuse Before Rewrite 为准。

## 0. 一句话

八个页面走的是同一套骨架：**视图 → `api.js` → `/api/*` 路由 → 领域模块（`scoring_service` / `sync_service` / `eval_runner` / `grade_tag` / `review_repo` / `auth_service`）→ PostgreSQL 或外部接口（微伴 / 企微）**。
路由器只有 8 条路径、`api.js` 只做 HTTP 封装（不含业务判断），业务判断全部在 `backend/`——所以**同一件事不会有两份实现**。

## 1. 页面 → 链路（按页面）

### 1.1 `App.vue`（顶栏，所有页面共用）

| 元素 | 处理 | 接口 | 后端 | 数据 |
|---|---|---|---|---|
| 退出 | `doSignOut()` | `DELETE /api/auth/session` | `security.revoke_session` | 删 `login_session` 行 + 清 `wb_session` cookie |
| 右上凭据状态点（每 15s） | `load()` | `GET /api/auth/status` | `api_auth.status` → `auth_service.status` | 读 `.cache/ww_bootstrap.json` |
| 顶部导航 | `router-link` | — | — | 纯前端路由 |

### 1.2 `LoginView`（`#/login`，登录本系统）

| 元素 | 处理 | 接口 | 后端 | 数据 |
|---|---|---|---|---|
| 提交（表单 / 回车） | `submit(ev)` | `POST /api/auth/session` | `api_auth.sign_in` → `security.verify` + `create_session` | 写 `login_session`（sid/username/expires_at/UA/IP）→ `Set-Cookie wb_session` |
| 首屏已登录 | `onMounted` | `GET /api/auth/me` | `security.resolve_session` | 直接 `replace` 到 `to` 或 `/chat` |

细节做得对：提交时**从 DOM 读值**（Chrome/1Password 自动填充只触发 `change` 不触发 `input`，只读 `v-model` 会得到空值 —— 用户实测踩过）。

### 1.3 `AuthView`（`#/auth`，数据源凭据 = 微伴/企微扫码）

> ⚠️ 与 1.2 是**两件不同的事**：这里是"抓数据的凭据"，不是"登录本系统"。代码里名字刻意分开。

| 元素 | 处理 | 接口 | 后端 | 数据/外部 |
|---|---|---|---|---|
| 开始扫码登录 | `startLogin()` | `POST /api/auth/login {wait_sec:300}` | `auth_service.start_login` | **在宿主机拉起 Chrome**，抓 cookie + `open_sid` → 写 `.cache/` |
| 复制命令 | `copyHint()` | — | — | 复制 `browser.host_command`（容器部署下给宿主机指引） |
| 验证凭据 | `doVerify()` | `POST /api/auth/verify` | `auth_service.verify` | 用现有凭据调一次 `jsapi_sign` |
| 阶段轮询（3s） | `load()` | `GET /api/auth/status` | 同上 | 阶段：`waiting_login → capturing → done` |

容器里 `browser.available=false` → 按钮**禁用**并显示宿主机命令（这块是全项目处理得最好的一个降级）。

### 1.4 `DashboardView`（`#/dashboard`，总览）

### 1.7 `ReviewView`（`#/review`，负分复核）

| 元素 | 处理 | 接口 | 后端 | 数据流向 |
|---|---|---|---|---|
| 进页面 / 每 5s | `refresh()` | `GET /api/review/stats`、`/api/review/list` | `api_review.*` | 读 `negative_review`（按 `status` 过滤）+ 统计 |
| 切 tab / 查询 | `switchTab` / `search` | 同上（`status`、`staff_id` 等） | 同上 | 只读 |
| 点一条 | `open(r)` | `GET /api/review/detail` | `api_review.detail` | 复核记录 + 该会话最近 60 条消息 |
| **提交人工打分** | `submit()` | `POST /api/review/submit` | `review_repo.submit` + `assessment_repo.mark_review_done` + `audit` + **`meta_loop.link_review_to_case`** | 写 `negative_review(status=done, human_*)`、写 `assessment.verification_status`（`verified/corrected/rejected`）、**改判立刻回流 `eval_case`** |
| 标记已忽略 / 退回未打分 | `setStatus()` | `POST /api/review/status` | `review_repo.set_status` | 改 `negative_review.status` |

这条链是全项目**闭环设计最完整**的一处：人工结论 → `verification_status` → 回流评估集 → 下次门禁拿它当金标准。
审计主体由**服务端**推导（`security.actor()`），客户端自报的 `reviewer` 只进 `detail.reported_actor` ✓。

### 1.8 `EvalView`（`#/eval`，评估集）

已在前几轮梳理并修复（抽样 / AI 预标注 / 判对 / 保存修改 / 锁定 / 标争议 / 跑评估 / 对照跑分 / 设为基线 / 回流 / 导出）。
链路要点：写操作全部走 `/api/eval/*` → `eval_case_repo`（**唯一写入口**，同事务审计）；跑分走 `eval_runner`；门禁相关走 `eval_runner.gate_decision`。

### 1.9 `SyncView`（`#/sync`，同步中心）

已在上一轮完整梳理并修复（开始/停止、固定间隔、日常任务、保活间隔、立即保活 + 轮询）。

## 2. 数据流向总图

```
微伴 OpenAPI ─┐
企微 getchatdata ─┤→ sync_service ─→ staff / chat_session / chat_message / sync_cursor
                 │                        │
                 │                        ├→ scoring_service ─→ customer_intent_assessment
                 │                        │                      ├→ negative_review（负分转人工）
                 │                        │                      ├→ writeback_outbox ─→ 微伴「加评分」（累加）
                 │                        │                      ├→ grade_tag_outbox ─→ 微伴「打/删标签」
                 │                        │                      └→ policy_decision（策略快照）
                 │                        └→ eval_runner（评估集 / 门禁 / 回归）
人工（本系统）──→ review_repo ─→ negative_review + assessment.verification_status
                           └──→ meta_loop ─→ eval_case（回流，成为门禁金标准）
LLM ──→ analyze / contracts / confidence（只产出结构化判定，分数由本地规则算）
```

## 4. 维护提示

- 新增页面/按钮时：先 `rg` 搜概念（`AGENTS.md` 的硬规则），判定的逻辑放 `api.js` 或后端领域模块并导出，不要在两个 `.vue` 里各写一遍。
- 新增**写外部系统**的动作（微伴分数/标签、清理数据）必须有二次确认 + 审计；已有的正例：`rules/publish` 的 `force`、`grade-tags/align` 的范围闸、`eval_restore --apply`。
- 新增轮询一律走 `usePolling`（已带可见性/降频），别再手写 `setInterval`。
