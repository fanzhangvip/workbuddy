## 一、先说结论：架构不动

**保持「单 Agent + 确定性编排」——即一次大模型调用 + 本地规则引擎，不拆多 Agent。**

任务形态是「单轮无依赖判定」：输入（会话正文 + 规则表 + 规则引擎事实）→ 输出（命中项 JSON）。
没有子任务交接、没有 DAG 依赖、没有长时运行、秒级返回。多 Agent 的价值来自「多个专业能力的协同」，
本场景只有一个专业能力（判断对话命中了哪几条规则），硬拆只会让每个 Agent 都拿到同一份上下文却只看局部规则，
更容易互相矛盾；成本上，单会话一次调用 8~15 秒，拆成 3 个 Agent 就是 3 倍调用、3 倍延迟、3 倍失败率。

**当前实现已经天然满足文章强调的「推理与控制分离」**：

| 文章的要素 | 现有实现 |
|---|---|
| 模型只给建议，业务控制给裁决 | LLM 只出命中项 + 证据；总分/等级由 `rules.py` 本地算 |
| 硬指标交给确定性程序 | `engine=rule` 的「48h 未回复」由 `compute_facts()` 算，模型不许判 |
| 入参校验 | `rules_mod.validate_items()` 丢弃非法 rule_id 与分值，留痕 `invalid_items` |
| 运行轨迹 | `scoring_run` + `audit_log` + 进度快照 |
| 幂等 | `score_writeback UNIQUE(assessment_id)` |
| 副作用控制 | 回写默认 `dry_run` |
| 人机协同 | 负分进 `negative_review` 队列人工打分 |

所以下面的改动都围绕**判定质量与可靠性**，没有一条是加 Agent。

## 二、改动清单

### P0 — 建议尽快做

#### A1. 证据回链校验（防幻觉，收益最高）

**问题**：`analyze.py::analyze()` 只校验 `rule_id` 是否存在、`score` 是否在允许档位，
**完全不校验 `evidence` 是否真的出自原文**。模型完全可以编一条听起来合理的证据，
而这条证据会原样落进 `customer_intent_assessment.positive_items / negative_items`，
并在前端「会话管理」页当成交付依据展示。

**改法**：在 `analyze.py` 里加一个纯确定性函数，在 `validate_items` 之后调用。

```python
def _norm(s: str) -> str:
    """归一化：去掉空白与常见中英文标点差异，用于模糊定位。"""
    drop = " \t\r\n，。！？、；：\"'（）()【】[]《》…—-_~·"
    return "".join(ch for ch in (s or "") if ch not in drop).lower()

def verify_evidence(items: list, conversation: str) -> tuple:
    """evidence 必须能在对话原文中定位到，定位不到则丢弃该项。"""
    hay = _norm(conversation)
    kept, dropped = [], []
    for it in items:
        evs = it.get("evidence") or []
        if not evs:
            dropped.append({**it, "reason": "无证据（证据不足不得命中）"})
            continue
        hit = [e for e in evs if _norm(e)[:24] and _norm(e)[:24] in hay]
        if not hit:
            dropped.append({**it, "reason": "证据无法在原文中定位（疑似编造）"})
            continue
        kept.append({**it, "evidence": evs, "evidence_verified": len(hit)})
    return kept, dropped
```

调用顺序（`analyze()` 内）：

```python
pos_valid, pos_bad = rules_mod.validate_items(data.get("positive_items"), rules)
neg_valid, neg_bad = rules_mod.validate_items(data.get("negative_items"), rules)
pos_valid, pos_ev_bad = verify_evidence(pos_valid, conversation)   # ← 新增
neg_valid, neg_ev_bad = verify_evidence(neg_valid, conversation)   # ← 新增
# invalid_items = pos_bad + neg_bad + pos_ev_bad + neg_ev_bad
```

**策略选择**：先用「至少一条证据命中就保留」（宽松版），跑一批真实会话看丢弃率。
若丢弃率 > 15%，说明提示词对证据引用格式的要求不够明确，回头改 `SYSTEM_PROMPT` 第 2 条
（现在是"引用聊天中的原话片段"，可改成"必须逐字复制原文连续 8 字以上"）。

**验收**：手工构造一条模型编造证据的输入，确认该项被丢弃并出现在 `invalid_items` 里。

#### A2. 失败分类重试（现在是一刀切重试 3 次）

**问题**：`scoring_service._llm_analyze()` 对**所有**异常都无脑重试 3 次：

```python
for i in range(3):
    try:
        return analyze.analyze(conversation, facts_text, rules)
    except Exception as e:
        last_err = e
        time.sleep(1.2 * (2 ** i))
```

文章专门讲了这件事：临时性故障才值得重试；输入/业务校验失败重试没有意义；
权限与安全问题更不能靠重试绕过。当前实现下，一次 401（API Key 失效）会白等 1.2+2.4=3.6 秒 ×200 个会话，
把整轮评分拖成半小时，最后全部失败。

**改法**：按异常类型分流。可重试 = 网络类 + 限流 + 服务端 5xx；不可重试 = 认证失败、配置缺失、
参数错误（4xx 且非 429）。区分方式看 `llm.py` 抛的是什么异常（`requests.RequestException` /
`json.JSONDecodeError` / 自定义），按实际补 `except` 分支，不要用 `except Exception` 一把抓。

同时把「JSON 解析失败」单独处理：重试同一 prompt 基本无效（温度 0.2 下大概率复现），
更划算的做法是**重试一次并追加一句纠正提示**，仍失败则丢弃该会话、计入 `llm_failed`。

**验收**：模拟一次 401，确认只调用 1 次且立即返回失败，不 sleep。

#### A3. `_candidates` 的 `force` 参数实际未生效（疑似 bug）

**问题**：`ScoringService._candidates(self, staff_ids, limit, min_messages, force, rv)` 签名接收 `force`，
但函数体内 `params` 和 SQL **完全没有用到 `force`**——WHERE 里的增量条件恒为：

```sql
AND (last.assessment_id IS NULL
     OR last.a_last IS NULL
     OR last.a_last < c.last_msg_time
     OR last.rule_version IS DISTINCT FROM %(rv)s)
```

也就是说 `start(force=True)` 只把 `scoring_run.kind` 标成了 `full`，**实际筛选逻辑仍是增量**，
「全量重评」按钮点下去不会真的全量评。`scoring_service.py` 顶部 docstring 里写的
"force 触发全量重评"与实现不符。

**改法**：SQL 里加条件分支。

```python
cond = "" if force else """
   AND (last.assessment_id IS NULL
        OR last.a_last IS NULL
        OR last.a_last < c.last_msg_time
        OR last.rule_version IS DISTINCT FROM %(rv)s)
"""
```

**验收**：用 `force=True` 跑一次，确认候选数 = 满足 `msg_count >= min_messages` 的全部会话数，
而不是仅有新消息的那部分。跑完对比 `scoring_run.session_total`。

### P1 — 有余力再做

#### B1. 输出契约加版本号

`rules.json` 有 `rule_version` 并且参与候选筛选（规则变了自动重评），但**提示词和输出 Schema 没有版本号**。
将来改了 `SYSTEM_PROMPT` 或 JSON 结构，历史评估与新评估会混在一起，排查「为什么同一段对话结论变了」会很痛苦。

- 在 `analyze.py` 定义 `PROMPT_VERSION = "p1"`，写进返回结果；
- `customer_intent_assessment` 加一列 `prompt_version TEXT`；
- `_candidates` 的增量条件里补一条 `OR last.prompt_version IS DISTINCT FROM %(pv)s`。

#### B2. `validate_items` 缺跨列表极性校验

`analyze()` 是把 `data["positive_items"]` 和 `data["negative_items"]` 分开传给 `validate_items` 的，
而 `validate_items` 只查 `rule_id` 存在 + 分值在档位内，**不校验该规则的 polarity 是否与所在列表一致**。

后果：模型如果把 `negative_refuse`（-3）误放进 `positive_items`，它会通过校验进入 `pos_valid`，
`compute_score` 把它当加项累加，得出 `positive_total = -3`，写进评估记录。
（回写环节因为 `score >= 1` 才写，侥幸没造成外部副作用，但数据已经脏了。）

改法：`validate_items(items, rules, expect_polarity=None)` 加一个可选参数，不匹配就进 `invalid`。

#### B3. `scoring_run.status` 加 `partial` 状态

现在只有 `running / success / stopped / failed`。一轮跑完但中间有会话失败时，状态仍显示 `success`，
误导性较强。建议：跑完时若 `llm_failed > 0`，状态置 `partial`，前端用黄色标记。
（对应文章的"任务状态要区分成功、失败和部分完成"。）

#### B4. `_score_one` 的「正文过少」判定太粗

现在写死 `if len(conv) < 20: return "skipped"`——按字符数判，一条 25 字的单轮对话也会进入模型调用，
白花一次 8~15 秒的调用。建议改成按**有效消息条数**判定，阈值走 `app_setting`（如 `scoring_min_effective_msgs`，默认 3），
并在 `scoring_run.detail` 里区分「因正文过少跳过」和「因其他原因跳过」两个计数。

## 三、待确认项（需要拍板，不是改动）

- **D1 `scoring_fetch_tags` 默认关闭，导致「实际到课 +2」这一档默认不可达。**
  `rules.json` 的 `positive_attended_class` 标注 `external_event_preferred: true`，
  hint 写明"实际到课以直播/课程平台事件或微伴到课/完课标签为准；仅凭聊天记录不得直接给 +2"；
  `analyze.py` 的提示词里也重申了这条冲突规则。但 `_score_one` 里
  `fetch_tags = setting_bool("scoring_fetch_tags", "SCORING_FETCH_TAGS", False)` **默认 False**，
  也就是模型看不到任何标签，只能给 +1。到底是有意保守、还是忘了打开，需要确认。
  （打开会多一次微伴 `get_custom_fields` 调用，200 会话就是 200 次额外请求，有性能代价。）

- **D2 ✅ 已确认（2026-10-14）：微伴评分接口是「累加」语义。**
  即连续调用 `POST /open-api/external_user/score/add` 会对同一客户**累加**分数
  （不是覆盖）。这直接推翻了现在 `_writeback` 的写法——它每次都把本次
  `positive_total` **整值**写回去（`scoring_service.py:342`），
  同一客户被重评 N 次，微伴分数就被叠加 N 次 → 虚高到离谱。

  **必须连带做的改动（新增一条，编号 D2-1）**：
  1. **回写从「整值写」改为「差值写」**：维护一张**客户级回写水位**
     （记录该客户已回写的累计分），每次只写 `本次 positive_total − 已回写累计`；
     差值为 0 则**不调接口**。现有 `score_writeback UNIQUE(assessment_id)` 只能防"同一评估写两次"，
     **防不住"不同评估反复累加"**，所以必须补这张客户级水位。
     （对账手段：`weiban.list_external_users()` 返回的 `score` 可读回当前累计分，
     可用它反推"我们已写进去多少"来做校验。）
  2. **累加语义下没有减法，分数下调做不到**：接口 `score` 必须 > 0（错误码 20215），
     累加不会减小，所以当客户意向**回落**（本次分 < 上次）时，
     **微伴端分数无法下调**，只能"不动"。→ 若业务要求微伴分能反映"当前意向值"，
     累加语义根本满足不了，只能改用「**达阈值标记**」策略
     （例如只在首次进入 S 级时写一次 +N，之后不再累加）。
  3. **✅ 已查明（2026-10-14，微伴开放平台官方文档）**：微伴「客户评分」**只有 `score/add` 一个写接口，
     没有"设置 / 修改 / 覆盖"接口**（文档里的"客户积分管理"是另一套独立的**积分**体系，不等于客户评分）。
     官方对该能力的定位原文是——「根据客户不同行为自定义标签、客户动态及**客户评分**，
     例如客户进入 X 页面，可添加对应的客户动态 / 评分」，即**事件驱动地加分**。
     → 结论：**微伴「客户评分」的设计语义就是"累计行为分（只增不减）"，不是"当前意向值"**。
     把它当"当前意向分"来**整值回写，属于用错接口语义**。
  4. **据此确定的回写策略**：
     - **微伴评分 → 走"差值累加"**：只写正向增量，微伴分 = 客户**累计展现的正向意向热度**，天然只增。
     - **"当前等级（S/A/B/C/D）"这种可升可降的语义，不要靠微伴分表达**——
       改用**微伴标签**（接口支持增 / 删标签，可"先删旧等级标签、再加新等级标签"，等价于覆盖），
       或直接用本系统自己的出口（重点跟进人群 / Excel / 飞书 / 对外 API，见需求 §7 / §8）。
     - 若业务坚持"微伴里要看到当前意向分"，**累加接口满足不了**，
       需先向微伴确认是否有可覆盖的接口，否则只能放弃回写评分、改用标签。

- **D3 §5.1「公开课节奏复核 S/A」——✅ 已拍板（2026-10-14），F2 实现方式已确定**

  **① 需求原文（全库仅 3 处提到"公开课"）**
  - §5.1：「每一次有效互动后应重新评分；**公开课前一天、公开课后及每日早会前应复核 S/A 客户**。」
  - §5.4：S 级建议「每日重点跟进；**课后 30 分钟内跟进并推动关单**」；
    B 级建议「隔日有效跟进，以价值内容和**公开课邀约**培育」。
  - §5.5 / §12.2：「实际到课 +2」优先接入直播/课程平台到课事件；
    目前微伴客户标签里有「到课 / 完课」标签，能取到就按标签打分。

  **② 这句话在说什么**
  公司靠「**公开课（免费直播）→ 付费课**」做转化，公开课是销售节奏的锚点，
  整条链路是「课前蓄水 → 课中转化 → 课后关单」。
  「复核 S/A 客户」＝**只对当前评级 S / A 的高意向客户，在三个业务时点重跑评分**，
  产出一份"此刻最该跟进谁"的名单：

  | 时点 | 复核目的 |
  |---|---|
  | 公开课**前一天** | 定明天该邀课 / 催到课的名单 |
  | 公开课**后** | 到课已发生（+2），且是关单黄金窗口，立即刷新 |
  | **每日早会前** | 销售早会要对齐"今天跟谁"，交出当日最新名单 |

  **③ 为什么必须是一个独立任务（F2），不能复用现有增量评分**
  现有 `auto-scoring` 是**消息驱动**（会话有新消息才评）。这三个时点要的是
  **时间驱动**（到点就评，不管有没有新消息），原因有三：
  ①「连续 48 小时不回复 −2」是**随时间自动产生**的，没有任何新消息触发，
     消息驱动永远发现不了 → 客户本该掉级却还显示 S；
  ②「实际到课 +2」的事件发生在**聊天之外**（客户上了课但一句话没说），
     只能靠"课后重算 + 读到课标签"拿到；
  ③ 这三份名单是**给人用的调度产物**，必须准点可用，与消息是否到达无关。

  **④ ✅ 已拍板（2026-10-14）——F2 的实现方式已确定**

  | 决策点 | 你的答复 | 落到实现 |
  |---|---|---|
  | 公开课排期 | **不定期**，先做手动按钮 | 做**方案 B**：后台「公开课复核」手动触发入口；**不做**排期表驱动 |
  | 早会时刻 | **不写死在代码里**，做成配置项 + UI 可改 | 触发时刻存 `app_setting`（如 `scoring_morning_cron`），前端给输入框；代码只读配置 |
  | 复核方式 | **增量刷新** | 先重算确定性事实（48h / 标签）；仅"事实变了或来了新消息"才重调模型 |
  | S/A 口径 | 未特别指定 | 默认按**最新一次有效评估等级**（可改） |

  **⑤ 最终实现方案（方案 B + 增量刷新）**
  - **一个定时任务**：`morning-sa-review`，cron 表达式**从 `app_setting` 读**（UI 可改，默认早会前跑完），
    只扫**最新等级 = S/A** 的关系，走增量刷新。
  - **一个手动入口**：`POST /api/scoring/public-class-review`（前端"公开课复核"按钮），
    参数含 `mode`（课前 / 课后）与范围；**课后模式强制重调模型**
    （到课对分数影响最大、且是关单窗口），课前模式走增量刷新。
  - **两者共用同一套"增量刷新"逻辑**：先重算 `compute_facts`（48h 未回复 + 微伴到课/完课标签），
    事实未变且无新消息 → 沿用上次结论，**不调模型**。
  - **依赖**：必须打开 `scoring_fetch_tags`（F3 / D1），否则课后拿不到到课 +2，这个任务就白做。
  - **不再需要**：`public_class` 排期表（改手动后不需要）。
    若将来排期固定，再升级为"日期表驱动 + 课前/课后两个 cron 点"。

## 四、升级为多 Agent 的触发条件（现在不满足，先记着）

出现以下**任意两条以上**，才值得考虑把链路拆开：

1. 评分开始依赖**多源串行取数**——例如必须先取课程平台到课事件、订单系统成交记录，才能判「邀课成功」「成交」，

# 第二批：对照《企业级 Agent 记忆系统》的新发现

> 来源：《万字硬核拆解：如何从零搭建一套企业级 Agent 记忆系统？（附架构设计）》

## 背景：本项目为什么适用「记忆系统」这套框架

本项目不是对话式 Agent，但确实存在一个记忆层：
`chat_message`（原始对话）+ `customer_intent_assessment`（历史结论）+ `rules.json`（外部知识）
+ `sync_cursor`（任务状态）+ `negative_review`（人工反馈）。
文章的两个核心判断对本项目直接成立：
**「聊天记录解决的是保存问题，记忆系统还要解决筛选、组织、检索和更新问题」**，
以及**「只设计写入，不设计更新」是五坑之一**。下面的问题全部落在这一带。

### 六阶段建设顺序对照

| 文章的阶段 | 本项目现状 | 状态 |
|---|---|---|
| ① 当前任务状态管理 | `sync_cursor` 水位 + `scoring_run` 进度 + `app_setting` | 已具备 |
| ② 建立持久化记忆 | `chat_message` / `customer_intent_assessment` / `scoring_rule` 表齐备 | 已具备 |
| ③ 提取和分类 | 有提取（画像、命中项），但不区分临时指令与长期事实 | 部分 |
| ④ 多路检索和融合 | **只有单路**：最近 60 条原始对话，无长期记忆召回 | **缺失** |
| ⑤ 安全与治理 | `audit_log` 有；凭据与密钥管理裸奔（见 E6） | 部分 |
| ⑥ 建立评估体系 | 只有「人工与 AI 一致率」一个指标 | 部分 |

短板集中在 **④** 和 **⑥**。

## E1（P0）只写不读：历史评估结论从不被复用

**证据**：全库 grep `customer_profile_summary` / `profile_summary` / `sales_strategy`，
只命中 `scoring_service.py:418,426`（INSERT 语句）与 `analyze.py`（提示词与打印）。
**没有任何一处把这些值读回来作为下次评分的输入**。`_score_one()` 每次都执行
`build_conversation(staff_id, session_id, limit=60)`，从原始消息重新拼 prompt。

**危害**：`build_conversation` 只取**最近 60 条**（`ORDER BY msg_time DESC LIMIT 60`）。
会话一旦超过 60 条，早期关键信息（例如客户 3 个月前说过"公司下季度要上 AI 客服项目"）
在重评时完全不在模型视野内 → 对应加分项漏判 → 分数虚低。
而水位机制「有新消息就重评」保证了这种带病重评会持续发生，
且**每次重评都丢弃上一次已得出的结论**。

**严重度更正（2026-10-14 复核需求文档后）**：这不是「优化建议」，而是**需求未实现**。
需求文档 §6.1「分析输入」明确要求每次分析应包含第 3 项「**上一次有效评分、等级、画像总结及已通知等级**」，
第 4 项「自上次分析后新增的消息和必要的近期上下文」，
第 5 项「相关历史关键消息，例如需求、报价、邀约、到课、拒绝等」，
并紧接着写明：「**不得无限量发送全部历史聊天记录；应保留长期画像摘要，并按需加入近期与关键历史消息**」。
当前实现只做到第 4 项（且是硬切最近 60 条，不是"新增消息 + 必要上下文"），
第 3 项与第 5 项完全没做。严重度从 P0 建议升格为**需求缺项**。

**改法（分两步，先做便宜的）**：
1. 把最近一次评估的 `profile_summary` + 命中项作为「历史结论」段落注入 prompt，
   明确标注"以下为上次分析结论（{{ analyzed_at }}），仅供参考，需与本次对话核对"；
2. 再做结构化：把画像里的岗位 / 需求 / 时间节点 / 预算拆成带证据的字段，
   下次直接喂结构化字段而不是自由文本。

**验证方式**：找一个 `msg_count > 60` 的会话，连续跑两次评分（第二次用 `force`），
比较两次的 `positive_items` 是否一致；不一致即证明"结论不可复现"。

## E2（P0）评估结果没有过期机制，也没有「当前有效」标记

**证据**：
- 全库 grep `valid_until|superseded|is_current|expire|stale|freshness`，
  只命中登录态凭据（`auth_service.py`），`customer_intent_assessment` **无任何时效字段**；
- `api_scoring.py:131` 的列表查询是 `ORDER BY a.assessment_id DESC`，**没有去重**，
  同一 `relationship_key` 的历史评估会全部并列出现在「评分中心」列表里。

**危害**：
- 一个客户 8 个月没消息，去年评的 S 级至今仍显示 S 级，界面上没有任何"已过期"提示；
- 列表页同一客户重复出现多行，使用者无法一眼判断哪条是当前有效的——
  这正是文章 STEP 08 举的"预算 100万 / 120万 / 110万 三条并列"的例子；
- 未来做「重点跟进人群（≥5 分）」时，这些永不失效的旧高分会被反复捞出来。

**改法**（二选一，建议后者）：
- 简单版：前端列表按 `relationship_key` 去重只显示最新一条，并加"距今 N 天"标注；
- 完整版：`customer_intent_assessment` 加 `is_current BOOLEAN`（或 `superseded_by`），
  每次写入新评估时把同 `relationship_key` 的旧记录置为 `false`，
  列表查询改 `WHERE a.is_current`。同时约定「`last_msg_time` 超过 N 天未更新 → 前端标灰」。

## E3（P1）模型自由文本零校验就变成「记忆」

`customer_profile_summary` 和 `sales_strategy` 是模型生成的自由文本，
**无任何校验、不要求证据、直接落库、直接展示在复核页**。
比第一批 A1（`evidence` 回链）影响面更宽：A1 影响**分数**，E3 影响**人工判断**——
复核人员看到"客户有明确采购意向"可能就直接打分了。

文章原话：「模型推断出来的内容，不应该未经验证就变成长期事实」。

**改法**：画像拆成带证据的结构化字段（见 E1 第 2 步），自由文本降级为"摘要"，
决策依据只认结构化字段 + 证据。

## E4（P1）`confidence` 与 `needs_human_review` 由模型自报

`analyze.py:178-179` 把 `confidence` 和 `needs_human_review` 直接从模型输出取值并落库。
让可能出错的组件自己决定"要不要人看"，等于自证清白。
文章把置信度定位为「置信度**或验证状态**」，并要求有"明确的确认机制"。

**改法**：`needs_human_review` 改为**规则决定**——例如「模型自报置信度低于阈值」
或「命中 +2 档」或「总分落在等级边界 ±1」时强制进复核队列。
`confidence` 字段改名或明确标注为 `model_confidence`，与人工验证状态分开。
另外 `negative_review.status='done'` 已是一次人工验证，可考虑回写到 assessment 的验证状态上。

**只停留在记录里**：不改提示词、不调规则、不改进候选筛选。

产出**每条规则的误报率排行榜**，直接指出哪条规则的 `criteria` 写得不够清楚。

否则新档位会被静默截断——`rules.py::compute_score` 里 `min(pos_total, bounds["max"])`
不会报错、不会留痕，只会让分数变小。建议在 `sync_rules()` 时加一条一致性断言。

# 第四批：Harness 与 Loop 的分层建设指引

> 来源：《Agent、Harness、Loop 到底是什么关系？一文讲透 AI 系统的分层架构》
> （公众号「智能体AI」，2026-10-04）
> 核对日期：2026-10-14　状态：**仅有分析，未改动任何代码**

## 文章核心命题

1. **`Agent = LLM + Harness`**。模型本身只干一件事：输入 → 推理 → 输出。
   "现在该不该继续、该不该调工具、什么时候收手、上一步出错怎么办、这个操作有没有权限"
   **统统不是模型该管的事**，全部归 Harness（包在模型外的运行时控制系统）。
   平时说的 ReAct（思考→行动→观察→再思考）就是 Harness 内置的一个小循环。
   原文：「没有 Harness，ReAct 会失控、越权、频繁产生幻觉，根本没法在生产环境里站住脚。」
2. **两层循环**：「内循环解决'这一步做没做对'，外循环解决'这件大事到底走完了没有'」。
   Harness 的内循环兜不住长任务——任务拆解、进度记录、失败兜底、多 Agent 调度、
   何时让人工介入、何时判定终止、事后复盘，全部属于**外循环（Loop）**。
3. **谁管谁**：「管 Agent 的是 Harness，管 Agent 生命周期的是 Loop。」
   分层自外向内：Loop Engineering → Agent 调度/状态/失败恢复 → Agent → Harness（ReAct/Tool Use/Memory）→ LLM。
4. **Loop 的六块构成**：目标管理、任务规划、调度、状态管理、失败恢复、结果验证。
5. **Loop ≠ 放养的 Workflow**。Workflow 路径写死（A→B→C）；Loop 是**系统按当下执行状态动态决定下一步**。
   但「Loop 灵活，不代表可以完全放养」——能上生产的 Loop 必须齐备：
   **状态机、循环次数上限、超时机制、权限控制、成本预算、检查点、护栏规则、人工审批**。
   少了这些，所谓的 Agent Loop 很容易变成不知道什么时候才会停下来的死循环。
6. **别数 Agent 数量，看指标**：任务完成率、端到端成功率、出错后能否自恢复、平均耗时、
   token 消耗、工具调用失败率、人工介入频率、长期运行稳定性。
   原文：「真正决定一套系统能不能扛住生产环境的，是背后的 Runtime、Harness 和 Loop 搭得够不够扎实。」

## 一、先定位：本项目谁是 Harness，谁是 Loop

| 文章的分层 | 本项目的落点 |
|---|---|
| LLM | `llm.chat()`（DeepSeek 单次调用，`llm.py`） |
| **Harness**（单会话回路） | `ScoringService._score_one()` + `build_conversation()` + `compute_facts()` + `_llm_analyze()` + `rules_mod.validate_items()` + `_writeback()` + `_enqueue_review()` |
| Agent | 就是这一次 LLM 调用本身（单 Agent，见第一批结论） |
| **Loop**（批任务 + 定时循环） | `ScoringService._run()` 批量遍历 + `scheduler.py` 三个定时任务 + `sync_cursor` 水位 |
| 多 Agent 协同 | **无**（本场景不需要，见第四批末尾判定） |

**一句话结论**：本项目的 **Harness 基本成型**，真正的缺口集中在 **Loop 的四块**——
失败恢复、检查点、超时与预算、终止与验证闭环。
这与前两批的结论一致：**不加 Agent，补 Loop 的护栏。**

## 二、Harness 层：单会话回路怎么建

Harness 的七项职责逐一对照本项目实现：

| Harness 职责 | 本项目现状 | 判定 |
|---|---|---|
| 上下文维护 | `build_conversation(limit=60)` 硬切最近 60 条 + `compute_facts()` | 缺层（见 E1/F1） |
| 工具调用 | `weiban.get_custom_fields()` 取标签、`ww_chatdata` 解密正文 | **失败被静默吞（G1）** |
| 权限控制 | `validate_items`（结构校验）+ `dry_run`（副作用控制） | 缺语义校验（A1）、极性校验（B2） |
| 状态保存 | 落 `customer_intent_assessment`，非法项留痕 `invalid_items` | ✅ 已具备 |
| 错误处理 | `_llm_analyze` 对所有异常一刀切重试 3 次 | 缺分类（A2） |
| 记忆 | **只写不读**，从不把上次结论读回来 | 缺（E1） |
| 结果验证 | 只有结构校验，且校验结果只决定"丢弃"，**不触发"重来"** | **缺内循环（G2）** |

### G1（Harness / P0）工具调用失败被静默吞掉

**证据**：`compute_facts()` 取微伴标签的整段是 `try: ... except Exception: pass`（`scoring_service.py:116-128`）。
一旦 `weiban.get_custom_fields` 因凭据过期、限流、网络问题失败，**异常被完全吞掉，不留日志、不留痕**，
最终 `tags=[]`，模型与规则引擎**都以为"这个客户没有到课标签"**。

**危害**：这正是文章开篇点名的反面案例——「工具调错了没人发现」。
`scoring_fetch_tags=True` 后，「实际到课 +2」这一档完全依赖标签；标签静默丢失会**把 +2 静默降级为 +1 或漏判**，
而且分数会写得像"正常结果"一样，事后无从分辨。这是本项目 Harness 层最隐蔽的一个坑。

**改法**：
- 捕获后至少写一条日志（`print` 到 `keepalive.log` 同类的运行日志），并让 `compute_facts` 返回值带上
  `tag_fetch_ok: bool`；
- 区分"客户确实没有标签"与"取标签失败"两种状态，后者在 `facts["text"]` 里显式写明
  「（标签获取失败，本项按未知处理）」——让模型知道这是**未知**，而不是**没有**；
- 计数进 `scoring_run.detail`（新增 `tag_fetch_failed`），纳入 Loop 的可观测指标。

### G2（Harness / P1）结果验证缺"通过或重来"的内循环

**证据**：`analyze()` 里校验结果只用于**丢弃**非法项（`invalid_items`），**没有任何"重来"语义**。
文章第 6 块讲得很明确：「不能让 Agent 自己说'我做完了'就算数，得有一个**执行完 → 校验 → 通过或者重来**的机制」。

**改法**（在 A1/A2 落地之后）：
把"校验失败"接回一次**受控重试**——这是本项目 Harness 层唯一需要补的"内循环"：
1. 第一次调用后跑 `validate_items` + `verify_evidence`；
2. 若存在**证据无法回链**的命中项 → 组装一句修正提示
   （「你引用的以下证据无法在原始对话中定位，请重新引用**逐字原文**：…」）→ **重试 1 次**；
3. 仍不合格 → 丢弃该项、计入 `llm_low_confidence`，**不阻塞整轮**。
这样 Harness 就从"一次性的 one-shot"升级为文章所说的"内置小循环"，但**仍不引入第二个 Agent**。

## 三、Loop 层：批任务 + 定时循环怎么建

### 3.1 Loop 六块构成 vs 本项目

| Loop 构成 | 本项目现状 | 判定 |
|---|---|---|
| ① 目标管理 | 隐式的"跑完这一批"，无成功标准、无达成判定 | 弱（G5） |
| ② 任务规划 | 扁平候选列表，**无优先级排序**（只按 `last_msg_time DESC`） | 弱（G7） |
| ③ 调度 | 单线程串行 `for cand in cands`，无并发、无优先级队列 | 可用（规模够） |
| ④ 状态管理 | `scoring_run` 轮级快照 + `sync_cursor` 水位 | 缺会话级明细（G5） |
| ⑤ 失败恢复 | 会话失败只 `print` + 计数；LLM 一刀切重试 | **最弱（G5/G6）** |
| ⑥ 结果验证 | `validate_items`；轮末无自检、无"达标判定" | 弱（G2/G5） |

### 3.2 文章强调的 8 条 Loop 护栏 vs 本项目

| 护栏 | 本项目现状 | 缺口 |
|---|---|---|
| 状态机 | `scoring_run.status`（running/success/failed/stopped） | 加 `partial`（B3） |
| 循环次数上限 | `max_sessions`（默认 200） | ✅ 有 |
| **超时机制** | 单次 LLM 调用 `timeout=120s` | **缺整轮总超时 + 单会话熔断（G3）** |
| 权限控制 | `dry_run` 回写 + `validate_items` | 够（上 `live` 前先验证 D2） |
| **成本预算** | **无** | **缺 token / 调用预算上限（G4）** |
| 检查点 | 靠水位隐式续跑 | 回写失败无重试通道（G6） |
| 护栏规则 | `engine=rule` 禁止模型判、`validate_items` | 补极性校验（B2） |
| 人工审批 | `negative_review` 复核队列 | ✅ 有 |

### G3（Loop / P0）缺整轮总超时，停止粒度也太粗

**证据**：`_run()` 的 `if self._stop: break` 只在**每个会话开始时**检查一次（`scoring_service.py:467-469`）。
若某会话正卡在 `_llm_analyze` 内（最多 3 次重试 × 120s 超时 + 退避 ≈ 6 分钟），
点"停止"要等这个会话跑完才生效。整轮也**没有总时长上限**——200 个会话若每个都慢，
可以跑到第二天早上还不停。

**改法**：
- `scoring_run` 增加 `deadline`（启动时 `now + 预算时长`），主循环每轮检查 `time.time() > deadline` 即优雅退出，
  状态置 `partial` 并写明"因超时提前结束，剩余 N 个未评"；
- 单会话加熔断：把 `_score_one` 包一层超时/重试上限，连续失败 N 次直接跳过并记录（见 G5）。

### G4（Loop / P0）缺成本预算

**证据**：全库无任何 token / 调用次数预算。一次 `force=True` 全量重评会**无上限地调用大模型**，
200 会话约 200 次调用（8~15 秒/次）。若误点全量、或规则版本频繁变更，成本不可控且无告警。

**改法**：`scoring_run` 增加 `max_llm_calls`（默认取 `app_setting`，如 500）。
主循环内当 `llm_calls >= max_llm_calls` 时停止并置 `partial`，detail 写明"因预算耗尽提前结束"。
这是文章"成本预算"护栏的最小实现，改动仅十几行。

### G5（Loop / P0）失败会话被计入"完成"，且无会话级失败记录

**证据**：`_run()` 里单会话异常时执行 `self._bump(run_id, llm_failed=1, session_done=1)`（`scoring_service.py:481-483`）——
**失败会话同时被计入 `session_done`**。于是 `session_done / session_total` 这个"完成率"会**把失败也算成完成**，
读者无法从数字上看出这轮到底成功了多少。且失败只 `print` 到控制台，
**没有任何一张表记录"哪个会话失败了、失败原因、失败了几次"**。

**危害**：文章的"连续失败次数太多就交给人工"在本项目**无法实现**——因为没有失败计数载体。
文章也把"任务完成率、端到端成功率"列为头号指标，本项目当前口径是失真的。

**改法**：
- 失败不再加 `session_done`，新增独立计数 `session_failed`；
- 新增轻量表（或复用 `audit_log`）记录 `run_id + session_id + error + attempt`；
- `_candidates` 或独立重试队列把"连续失败 ≥ N 次"的会话标出，前端可查、可转人工。

### G6（Loop / P0）回写失败没有重试通道（检查点漏洞）

**证据**：`_candidates` 的增量条件是
`last.assessment_id IS NULL OR last.a_last < c.last_msg_time OR last.rule_version <> rv`。
`_score_one` 是**先落库 assessment、后回写微伴**，且 `score_writeback` 有 `UNIQUE(assessment_id)`。
于是：**若 assessment 落库成功但回写失败**（`status='failed'`），该会话的 `a_last` 已等于 `last_msg_time`，
**下次筛选不会再选中它** → 回写**永久丢失**；即使手动重跑，`ON CONFLICT(assessment_id) DO NOTHING`
也会让这次回写**不产生新记录**。这是"检查点"护栏的真实漏洞。

**改法**：给回写单独一条重试通道——
- 方案 A（推荐）：`_candidates` 的增量条件补一条
  `OR EXISTS (SELECT 1 FROM score_writeback w JOIN customer_intent_assessment a2
  ON a2.assessment_id=w.assessment_id WHERE a2.relationship_key=... AND w.status='failed')`；
- 方案 B：做一个独立的「回写重试」任务，扫 `score_writeback WHERE status IN ('failed','pending')` 重投。
- 注意 `ON CONFLICT DO NOTHING` 要改成 `DO UPDATE`，否则重投不落新状态。

### G7（Loop / P1）缺优先级调度

**证据**：`_candidates` 只 `ORDER BY c.last_msg_time DESC`。S/A 客户与 D 级客户**同等权重、同队排队**。
当 `max_sessions` 截断时（例如候选 500 个只跑 200 个），被截掉的可能是**最该先评的高意向客户**。

**改法**：排序改为「等级优先（S/A 在前）+ 有新消息优先 + 未评过优先 + 规则版本变更优先」，
`max_sessions` 截断时先保高价值客户。

## 四、Loop 判定：本项目该不该"变成真 Loop"？

文章区分 Workflow 与 Loop：Workflow 路径写死，Loop 按状态动态决策。
**本项目当前形态 = 写死的 Workflow 外层（`_run` 顺序遍历）+ 状态驱动的筛选（水位）**。

**结论：不要为了"像 Loop"而变成真 Loop。** 本项目的会话之间**没有依赖**，
天然可并行、可任意顺序——这是任务形态简单带来的红利（与第一篇"单 Agent"结论同源）。
真正该做的是**把上面的护栏补齐**，让这个 Workflow 成为"可靠的 Workflow"，而不是追求动态分支。

**唯一值得加的一个 Loop 特征——meta-loop（元循环，复盘优化）**：
文章最后与《记忆系统》一文都强调"事后复盘优化"。本项目现在**完全没有这一层**。
最小实现就是第一批 E5 那条：按 `rule_id` 聚合复核改判数据，产出**每条规则的误报率排行榜**，
反馈给规则维护者。这是"系统根据执行结果调整自己"的第一步，也是从 Workflow 迈向真 Loop 唯一有价值的切口。
**注意：它改的是规则和提示词，不是加 Agent。**

**什么时候才真的需要多 Agent（沿用第一批触发条件，此处复述）**：
出现任意两条以上——① 评分依赖多源串行取数且需等待/重试/断点恢复；
② 人工审批成为流程中的节点且改变后续执行路径；③ 单轮判定准确率上不去且分组多次调用也救不回。
现在**一条都不满足**。

# 第五批：生产级 Agent 六层架构对照

> 来源：《生产级 Agent 落地全景：架构拆解、Harness 工程、FDE与组织重构》
> （公众号「智能体AI」，2026-08-23）
> 核对日期：2026-10-14　状态：**仅有分析，未改动任何代码**

## 文章核心

**六层架构**（自上而下）：入口层 / 编排层 / 上下文工程层 / 工具层 / 运行时与沙箱层 / 状态与记忆层。
**Harness 五层**（模型之外）：记忆 / 工具 / 权限 / 钩子（Hooks）/ 可观测性。
Harness 归成三件事：**让 Agent 动起来、让 Agent 记得住、让 Agent 不容易挂掉**。

关键事实与论断（原文）：

- **数据**：同一个模型不换，只把 Harness 从简陋版升到完整版，通用终端任务基准分数 **从 52.8% 跳到 66.5%**（+13.7pt）。
- **幂等**：入口层最容易被忽视的细节——「同一个业务事件如果被重复推送两次，Agent 不能傻乎乎地执行两遍」。
- **编排**：「工作流和 Agent 循环不是一回事。工作流负责确定性的部分……Agent 循环负责那些没法提前写死的判断。
  生产系统往往**两者都要，缺一不可**。」
- **上下文**：「信息不是越多越好——把整段历史记录、整份文档全塞进去，模型反而会**迷失在噪音里**。」
- **工具**：「每个工具的名称和描述都会**原封不动地进到模型看到的提示词里**，你接入的每一个第三方工具，
  本质上都是模型会读取的一段『可信文本』。一个写得不严谨甚至恶意的工具描述，完全可能在你还没输入任何东西之前，
  就已经把 Agent 的行为带偏了。」
- **钩子**：真正能做到「无论如何都拦得住」的，是那种**以特定状态码退出、能无条件阻断工具调用**的钩子机制——
  「这是提示词层面永远做不到的强制力」。
- **评估**：要看过程、看行为、看**最终的业务状态有没有真正改变**（工单是不是真关掉了、数据库记录是不是真改对了），
  而不只是看输出的文字像不像那么回事。
- **安全**：问题已经从「模型会不会说错话」变成「**模型犯错之后，最多能造成多大的损失**」，
  靠的是**权限、沙箱、网络出口**这三道实打实的边界。
- **踩坑**：「成功就保持安静，只有失败才输出详细信息」——否则几千行通过日志塞进上下文，模型反而开始失忆。

## 一、六层架构 → 本项目落点

| 层 | 文章职责 | 本项目落点 | 判定 |
|---|---|---|---|
| ① 入口层 | 接住触发信号（用户 / webhook / 定时 / 别的 Agent），关键细节是**幂等** | `scheduler.py` 三个定时 job + `api_scoring.py` 手动端点 + 前端按钮 | 有；**互斥不对称（H1）** |
| ② 编排层 | 工作流（确定性）+ Agent 循环（判断），**两者都要** | 工作流 = `_run()` 骨架；Agent 循环 ≈ `_score_one` 单次调用 | **重工作流、轻 Agent 循环——符合任务形态** |
| ③ 上下文工程层 | 在**正确的时机**递材料，不是越多越好 | `build_conversation(limit=60)` + `compute_facts()` | **最弱层（E1 / F1）** |
| ④ 工具层 | 权限 / 超时 / 重试 / 结果校验 / 审计日志 | 微伴 API、企微解密、LLM；`weiban.py TIMEOUT=30` | 超时✓ 权限✓ 重试✗ 校验✗ **审计弱（H2）** |
| ⑤ 运行时与沙箱层 | 资源隔离、网络出口策略 | FastAPI 单进程 + `threading.Thread` | **无需沙箱**，风险低 |
| ⑥ 状态与记忆层 | 会话状态 / 工作记忆 / 长期记忆 / **检查点** | `scoring_run` / `sync_cursor` / `assessment` / `chat_message` | 表齐；**缺检查点（G6）与记忆读取（E1）** |

**六层一层不缺**——这是好消息。问题不在"缺哪层"，而在"层内的强制力与可见性"。

## 二、Harness 五层 → 本项目落点

| Harness 层 | 本项目 | 判定 |
|---|---|---|
| 记忆 | 表齐但**只写不读** | 缺（E1） |
| 工具 | 全部由**代码**调用，模型无工具权 | **优点（H4）**；但错误处理弱（G1 / A2） |
| 权限 | `dry_run` 回写 + `validate_items` | 基本具备 |
| **钩子 Hooks** | **无显式机制**（护栏散落在各处的 `if`） | **缺（H3）** |
| 可观测性 | `scoring_run` 表 + 前端轮询进度 | 缺关键指标（H5 / G5） |

**三件事的完成度**：让 Agent 动起来 ≈ 够用；**让 Agent 记得住 = 最弱**；让 Agent 不容易挂掉 ≈ 半成品。

## 三、本批新发现（H 系列）

### H1（入口层 / P1）定时同步与评分的互斥**不对称**

**证据**：`scheduler.py` 里两个任务体的互斥检查不一致——

```python
def _job():                       # 定时同步
    if service.is_running():      # 只检查「同步自己」
        return
    service.start(...)

def _scoring_job():               # 定时评分
    if service.is_running():      # 同步
        return
    if scoring.is_running():      # 评分
        return
    scoring.start(...)
```

**危害**：评分正在跑时，**定时同步会照常启动**——评分任务可能在"同步写了一半"的数据上做候选筛选与打分。
文章把入口层的幂等单列出来讲，这里不是幂等问题，是**互斥不完整**。

**改法**：`_job()` 补一句 `if scoring.is_running(): return`（与 `_scoring_job` 对称）。
另外把这条互斥规则抽成一个共享判断函数，避免以后再不对称。

### H2（工具层 / 可观测性 / P1）自动评分链路不写 `audit_log`；参数变更大多不留痕

**证据**：全库 grep `audit_log` 的写入点，只有：
- `api_review.py:141 / 173 / 190` —— 复核提交、改状态；
- `api_scoring.py:203` —— **仅**切换回写模式时才写。

也就是说：**批量评分链路 `scoring_service._run()` 全程不写 `audit_log`**；
`set_settings` 里 `max_sessions` / `min_messages` / `fetch_tags` 三个参数变更**完全不留痕**。

**危害**：回答不了这些问题——"上周三那轮评分为什么只跑了 50 个会话？"
"谁把 `fetch_tags` 打开的？什么时候打开的？"文章把可观测性列为 Harness 独立一层，这就是缺口。

**改法**（改动很小）：
- `_run()` 在**启动 / 结束 / 失败**三个节点各写一条 `audit_log`（action = `scoring_start` / `scoring_done` / `scoring_failed`，
  detail 带 `session_total` / `llm_failed` / `elapsed_sec`）；
- `set_settings()` 对**每个**变更的 key 都写一条，不要只写 `writeback_mode`。

### H3（Harness 钩子层 / P1）没有显式 Hooks，护栏散落在代码里

**证据**：本项目最接近"钩子"的东西，是散落各处的硬编码 `if`：
`validate_items()` 丢弃非法项、`_writeback` 里 `mode == "off"/"dry_run"` 拦截、`score >= 1` 才回写、
`_engine_rule_ids()` 阻止模型判 48h 规则。**没有统一的拦截点**，改一条护栏要翻好几个文件。

文章把钩子单列一层，强调它必须能"**以特定状态码退出、无条件阻断**"。本项目的逻辑其实是对的
（拦截都在代码里、不在提示词里），缺的只是**组织形式**。

**改法**（不必上框架，抽象 3~4 个函数即可）：在关键动作前抽显式钩子点，统一返回 `(allow, reason)`：

```
before_llm_call(ctx)      # 预算/超时/正文长度检查   → 对应 G3 / G4 / B4
after_llm_output(res, ctx) # 结构+极性+证据校验       → 对应 A1 / B2 / G2
before_writeback(ctx)      # 回写开关/幂等/模式检查   → 对应 dry_run / D2
before_persist(row)        # 落库前最终体检
```

护栏规则集中到这几个函数里，"改规则只改一处"。这正是文章说的"提示词层面永远做不到的强制力"的最小落地。

### H4（工具层 / **优点，明确不改**）模型无工具调用权，天然免疫"工具描述注入"

文章用一整段警告"工具描述进提示词"的注入风险。本项目**不适用**——
`_score_one()` 里模型只输出 JSON，取标签（`weiban.get_custom_fields`）、解密正文（`ww_chatdata`）、
回写评分（`weiban.add_customer_score`）**全部由代码显式调用**，模型没有 function calling 通道。

**这是架构级的优点**，建议写进设计文档：即使模型被注入、产生幻觉，它**最多只能在评分 JSON 里捣乱**，
无法直接触达任何外部系统；所有副作用都由代码控制、且回写默认 `dry_run`。
对应文章的"模型犯错之后最多能造成多大损失"——本项目的答案很小，这是**刻意设计换来的，不要动**。

### H5（可观测性 / P1）缺生产级关键指标

文章给的指标清单 vs 本项目 `scoring_run` 现有字段：

| 文章指标 | 本项目 | 状态 |
|---|---|---|
| 任务完成率 / 端到端成功率 | `session_done / session_total` | 有，但口径失真（G5） |
| 出错后能否自恢复 | — | **缺**（无恢复机制，G5/G6） |
| 平均耗时 | `elapsed_sec`（整轮） | 有；**缺单会话耗时分布** |
| **token 消耗** | — | **缺**（G4） |
| **工具调用失败率** | — | **缺**（失败被吞，G1） |
| 人工介入频率 | `review_new`（新增数） | 有；缺"占比 / 人均" |
| 长期运行稳定性 | `scoring_run` 历史 | 有 |

→ 与 G1 / G4 / G5 互补，建议放在一起补。

## 四、本批架构设计结论

**一句话：六层不缺层、Harness 不缺层，缺的是"层内的强制力与可见性"。**

按性价比排序的补法：

1. **上下文工程层（最弱）** → E1 / F1：把上次结论读回来 + 分层上下文（长期摘要 + 新增消息 + 关键历史）；
2. **状态记忆层的检查点** → G6：回写失败重试通道；
3. **Harness 钩子层** → H3：抽 3~4 个显式钩子函数，护栏集中；
4. **可观测性** → G1 / G5 / H5：工具失败留痕 + 失败明细 + token；
5. **入口层互斥** → H1：一行对称性修复；
6. **审计** → H2：评分链路三节点 + 参数变更全量留痕。

**明确"不改"的三件事**：
- **不加 Agent**（沿用第一批结论）；
- **不引入沙箱**（本项目不执行任意代码、不写用户文件，无此风险；沙箱是给"能跑代码 / 操作浏览器"的 Agent 用的）；
- **不为了"两者都要"而硬塞一个 ReAct 循环**（判定是单轮的，硬塞只会增加延迟与失败率）。

**最后一个组织视角**：文章提到 FDE（前向部署工程师）——「既要懂怎么把模型能力封装成一套靠谱的系统，
又要懂怎么把这套系统真正塞进一个具体的业务场景里」。对你这套系统而言，**这个人就是现在在拍板 D2/D3 的人**：
微伴评分是覆盖还是累加、公开课节奏怎么排——这些**不是技术问题，是业务对接问题**。
技术上把 Harness 补扎实，业务上把这两个问题问清楚，这套系统就齐了。
