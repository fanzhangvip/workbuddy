## 一、一句话定位

从**微伴助手 OpenAPI** 同步企业微信「员工—客户」**单聊**记录，用「**规则引擎 + 大模型**」按既定规则评估客户意向，输出**需重点跟进的人群**，并把分数**回写微伴**。

**你的三步理解（已对齐）**：

| 你的描述 | 对应环节 | 补充说明 |
|---|---|---|
| ① 先获取聊天记录 | 微伴会话列表 + 会话消息 v2 → 本地消息库 | 需先拿到"已授权员工列表"才能拉全量会话 |
| ② 按需求文档规则判断打分 | 规则引擎（硬指标）+ AI（语义识别+证据） | 规则由**人可修改、需版本化**；AI 只做语义部分 |
| ③ 调用评分接口进行评分 | 回写微伴「添加客户评分」接口 | ⚠️ 存在**分值约束冲突**，见第四节 R1 |

## 二、需求模块提炼

| 编号 | 模块 | 核心内容 |
|---|---|---|
| M1 | 数据来源 | 微伴 `GET /open-api/chat/session/list`、`GET /open-api/chat/message/list/v2` |
| M2 | 唯一标识 | `relationship_key = staff_id + ":" + target_id`；同一客户被多员工服务时**分别评分** |
| M3 | 全量同步 | 首次：拉员工→建会话清单→分页拉历史消息→幂等入库→建水位→首次分析 |
| M4 | 增量同步 | 每晚 20:00–20:20 主增量；每日 03:30 做 48 小时补偿同步 |
| M5 | 增量与去重 | 水位：`start = 上次水位-15min`，`end = 本轮开始-1min`（本轮内固定）；`UNIQUE(staff_id, session_id, message_id)` 幂等 |
| M6 | 评分规则 | 原始分 **-12 ~ +13**；加分维度**取最高档不叠加**、跨维度累加；扣分可叠加 |
| M7 | 等级映射 | ≥6=S，4–5=A，2–3=B，0–1=C，<0=D |
| M8 | AI 分析 | OpenAI Responses API **Structured Outputs**（JSON Schema 强约束）；每项须给证据消息 ID |
| M9 | 重点跟进 | 条件A（新达 ≥5）/ 条件B（变化且当前 >5）；**同结果只生成一次** |
| M10 | 输出 | Excel 导出、飞书日报、对外只读 API `GET /api/v1/high-intent-customers` |
| M11 | 数据模型 | 5 张表：`chat_session`/`chat_message`/`scoring_rule`/`customer_intent_assessment`/`high_intent_notification` |
| M12 | 可靠性安全 | 单会话单任务；失败不阻塞；指数退避；凭据服务端管理；不记完整正文；全程审计 |

## 三、评分规则速查（首期规则）

**加分**（同维度取最高，跨维度累加，上限 +13）
程序员/转型画像 +2/+1｜明确工作需求 +2/+1｜配合认可 +1｜紧迫性 +2/+1｜已学一段时间 +1｜邀课成功 +2/+1｜高转地区 +1｜主动问课 +2/+1

**扣分**（可叠加，下限 -12）
追着问价 -1｜态度差 -2｜配合度低 -1｜认可度低 -1｜要自学 -2｜连续 2 天不回复 -2｜明确拒绝报课 -3

**分工（关键）**
- **规则引擎管**：48h 未回复、评分时间节点、前后分比较、触发与去重
- **AI 管**：语义类加减分、提证据、生成画像与销售建议
- **冲突规则**：有需求时主动问价 → 算"主动问课"；未了解价值只比价 → 才算"追着问价 -1"
- **外部事件优先**："实际到课 +2" 优先取直播/课程平台事件；只有聊天记录**不得直接给 +2**

## 四、关键风险与设计要点（必读）

**R1. 分值约束冲突（最高优先级）**
微伴「添加客户评分」接口要求 `score` 为**大于 0 的整数**（错误码 20215），而本系统原始分范围是 **-12 ~ +13**。必须确定回写策略：
- 方案a：负分/0 分不写或统一写 1；正分原样写
- 方案b：整体偏移（如 `原始分 + 12 + 1`）写入，另存原始分
- **同时必须确认**微伴该接口是**覆盖**还是**累加**语义——若是累加，重复评分会导致分数叠加，必须做幂等/差量处理。

**R2. 标签参与打分**
文档明确"要结合标签来打分，需要加入微伴中拿标签的动作"。需接入微伴标签/自定义字段读取能力（如获取客户详情、客户标签列表），重点取**到课、完课标签**用于"邀课成功"打分。

**R3. 规则可改且需版本化**
规则由人修改 → `scoring_rule` 表 + `rule_version`；每次评分记录所用版本，支持规则变更后重算。

**R4. 成本与上下文控制**
不得把全部历史聊天丢给模型；策略 = 长期画像摘要 + 新增消息 + 关键历史消息（需求/报价/邀约/到课/拒绝）。

**R5. 首期边界**
只做单聊（`type=ext_user`）；不含客户群；不含自动发消息。

**R6. 首次导入的特殊处理**
首次高分客户标记为"**基线高意向客户**"，默认不当作日常"新增重点跟进"重复推送。

## 五、待确认事项（开工前需拍板）

1. **微伴评分回写**：分值 → `score` 的映射方案？覆盖还是累加？（对应 R1，**阻塞第③步**）
2. **到课/完课标签**：在微伴中的确切标签名或字段？能否通过接口读取？
3. **技术栈**：语言（Python？）、数据库（SQLite / MySQL / PostgreSQL？）、部署形态（本机脚本 / 服务？）
4. **大模型选型**：文档同时提到 OpenAI 与 DeepSeek，实际用哪家？是否有可用 API Key？
5. **员工范围**：从哪个接口拿"已授权员工"清单（微伴「获取员工列表」）？按部门还是全量？
6. **评分规则来源**：文档提到"由 Excel 加分表与扣分表初始化"，这两份 Excel 是否已有？
7. **飞书**：日报写入固定文档还是按天新建？应用凭据与目标位置？
8. **人工复核**：哪些角色可查看/修改 AI 评分？人工改后是否覆盖 AI 结果？

## 六、增量实施路线图（建议）

按"每阶段一个可验证闭环"推进，验证通过再进入下一阶段：

| 阶段 | 目标 | 交付/验证 |
|---|---|---|
| **S0 环境** | 配置微伴凭据、AI Key、数据库 | 能取到 access_token；本地库建表成功 |
| **S1 聊天记录同步** | 会话列表 → 消息 → 落库（幂等+水位） | 重复运行不产生重复行；可导出某客户原始记录 |
| **S2 规则引擎** | 评分规则表 + 硬指标计算 | 给定消息能算出确定性的规则分与等级 |
| **S3 AI 分析** | 结构化输出 + 证据 + 画像/策略 | 返回合法 JSON，每项带证据消息 ID |
| **S4 回写与重点跟进** | 回写微伴评分 + 触发判定 + 去重 | 达到 5 分生成一条跟进记录，重复任务不重复生成 |
| **S5 输出** | Excel 导出 + 飞书日报 + 对外 API | 三种出口均可用 |
| **S6 调度与加固** | 定时任务、补偿同步、审计日志 | 断点后可自动补齐；全程可追溯 |

> 建议从 **S1（聊天记录同步）** 开始：它是整条链路的数据底座，且无需大模型即可独立验证。

## 七、验收标准（摘自原文，作为最终检验）

1. 单聊可完整同步，重复拉取不产生重复消息
2. 销售单方发送、客户未回复的消息也能同步作为上下文
3. 每次分析输出可追溯的逐项加减分、总分、等级、画像、销售建议
4. 同维度取最高档、扣分叠加、总分与等级映射正确
5. 达 5 分或变化且 >5 时生成一条重点跟进，重复任务不重复生成
6. 重点跟进可筛选、导出 Excel、写飞书日报、API 查询
7. 任务失败/延迟后，48 小时补偿可自动补齐
8. 每条评分保留规则版本、证据消息、分析时间，支持人工复核
