## 〇、九篇文章的共同结论

把九篇压成一句话：**决定 Agent 能否上生产的，不是模型，而是模型外面那套工程系统。**

两个被反复引用的公式：

```
Agent = LLM + Harness                              （A / B / C / I）
Harness = 记忆 + 工具 + 权限 + 钩子 + 可观测性        （C）
```

一个最硬的量化证据：**同一个模型、什么都不换，只把 Harness 从简陋版升级成完整版，
通用终端任务基准从 52.8% 涨到 66.5%**（C）。这直接说明"换更强的模型"性价比远低于
"把外壳搭扎实"。

另外三条贯穿性判断：

1. **Demo 证明的是"能不能完成一次"，生产要证明的是"能不能稳定做十万次"**（B）。
2. **真正难的工程问题已经从"Prompt 怎么写"挪到了"Loop 怎么设计"**（A）。
3. **企业 AI 最大的问题不是"AI 能不能做"，而是"AI 什么时候可以自己做主"**（G）。

## 一、总纲：三层循环 + 三条边界

### 1.1 三层循环（A / I / H）

| 层 | 管什么 | 典型组件 | 判断"做完没有"的主体 |
|---|---|---|---|
| **内循环**（Harness 内置） | 这一步做没做对 | ReAct、Tool Use、Memory | 模型自己 + 校验器 |
| **外循环**（Loop Engineering） | 这件大事走完没有 | 任务分解、调度、状态管理、失败恢复 | **独立的验证环节** |
| **业务闭环** | 这件事值不值得继续做 | 度量、反馈、规则/提示词迭代 | 人（业务方） |

外循环必须回答七件事（I）：**触发机制、状态记录、执行机制、结果验证、重试策略、
停止条件、人工接管条件**。七件凑齐才算"自主循环"，否则只是"人工遥控的自动化"。

**Loop ≠ Workflow**（A / E / I）：Workflow 路径提前写死，Loop 按当下状态动态决定下一步。
但 Loop 灵活不等于可以放养——**状态机、循环次数上限、超时机制、权限控制、成本预算、
检查点、护栏规则、人工审批，一个都不能少**，否则就是"不知道什么时候才会停的死循环"。

落地姿势：**固定流程 + 局部智能**（I）。主干按制度固定死，只在真正需要专业判断的节点
放手给 Agent。

### 1.2 三条边界分离（E）

1. **规划与执行分离**：规划器产出计划，编排器执行计划。混在一起会导致"出了问题说不清
   哪些任务已完成、哪些结果可复用、当前计划是否仍然有效"。
2. **能力管理与任务调度分离**：能力注册中心维护"有什么能力可用"，调度器决定"这次用谁"。
3. **模型推理与业务控制分离**：模型提出建议，是否允许执行由可验证的业务控制机制决定。

## 二、生产级架构分层

### 2.1 六层容器视图（C）

| 层 | 职责 | 最容易被忽视的点 |
|---|---|---|
| 入口层 | 接住用户输入 / webhook / 定时任务 / 其他 Agent 的请求 | **幂等**：同一事件被推两次，不能执行两遍 |
| 编排层 | 这次任务该怎么跑 | 工作流与 Agent 循环**两者都要**，不是二选一 |
| 上下文工程层 | 在正确的时机递材料 | 信息不是越多越好，塞满反而让模型迷失 |
| 工具层 | 真正动手的接口 | **工具名称与描述会原封不动进提示词**，等于一段"可信文本"，恶意描述能在你输入任何东西之前带偏 Agent |
| 运行时 / 沙箱层 | 真实执行环境 | 没有资源隔离与网络策略，等于把不稳定系统直接暴露在生产数据前 |
| 状态与记忆层 | 任务做到一半怎么办 | 会话状态 / 工作记忆 / 长期记忆 / 检查点，缺一个中断就只能重来 |

### 2.2 完整系统的四层兜底（B）

```
事件接入层    ← webhook / 消息队列 / 定时任务（"任务从哪来"）
Agent 编排层  ← Orchestrator：流程编排、状态机、上下文组装、决定调哪个工具
工具执行层    ← 工具注册中心、身份认证、限流、审计日志（"真正干活"）
可靠层        ← 状态持久化、重试队列、监控告警、心跳、资源隔离（"出问题接住"）
```

## 三、15 个工程域的具体要求

### 域 1 · 权限与身份（B / E / H / I）★最高优先

- **铁律：Agent 不能用自己的身份访问资源，必须用发起请求那个人的身份。**
  反面案例（B）：给 Agent 配统一服务账号，实习生借此读到无权查看的财务文档，
  审计一查谁都说不清算不算数据泄露。
- **权限判断永远不要交给 Prompt。** LLM 不是访问控制系统，它会幻觉、会被绕过、
  会在边界情况下"好心办坏事"。权限必须在**工具调用与资源访问的边界上由确定性系统强制**。
- **权限实现方式：作为 PreToolUse hook，而不是写死在每个工具里**（H）。好处是
  新增工具天然共享同一套拦截规则，MCP 工具也不例外。
- **权限分级**（I）：低风险自动放行 → 中风险留痕 → 高风险人工签字 → 某些操作直接禁区。
- **权限检查必须放在真正执行的位置**（E）：用户在**前端**提出请求 ≠ 后续所有 Agent
  都有权限；即使方案已确认，**执行时仍要验证身份、操作范围、授权条件**。
- **绝不能通过"换一个权限更宽松的 Agent"来绕过权限失败**（E）。

### 域 2 · 审计（B / C / E / I）

一条合格记录要能回答**五个问题**：谁做的、做了什么、什么时候、为什么、结果是什么。

固定字段：**时间戳、工具名称、工具参数、执行结果、审批来源、执行耗时**；
结果分"通过 / 拒绝 / 报错"，审批来源分"用户手动批准 / 策略自动放行"。

工程约定（B）：

- 存储用 **JSONL 追加写**——写入性能高，中断最多丢一行，不会写坏整个文件。
- **按天轮转**，单文件 ≤ 100MB，保留 180 天。
- **参数脱敏**：Token、API Key 必须在写日志前用正则整体替换。
  否则"用来保护安全的日志"本身成为新的泄露源。
- **审计目录权限收紧到只管理员可读写**——运维随手能改操作记录，"可审计"就没有意义。
- **被拒绝的请求尤其要记**：那往往才是真正值得关注的信号。

### 域 3 · 幂等（B / E / H）★出问题概率最高

问题的本质：**"一次调用没有收到成功响应，不等于业务操作一定没有成功"**（E）。
超时重试可能导致同一笔订单创建两次、同一封邮件发两遍。

**三层防护（B）**：

1. **请求层**：幂等键 = 工具名 + 关键参数哈希 + 用户/账户标识 + 时间窗口；
   执行前先查，命中则直接返回上次结果，不重复执行业务逻辑。
2. **工具设计层**：让工具**天然幂等**——创建前先检查是否已存在，更新用"满足条件才更新"，
   写文件用覆盖而非追加。这一层比外挂检测稳固得多。
3. **Agent 循环层**：连续多轮用相同工具 + 相同参数 → 大概率是死循环或错误推理路径。
   **经验值：连续 3 轮命中相同调用签名就告警**，视情况暂停或转人工。

**不要指望模型自己"记得"它刚才做过什么，幂等必须由系统托底。**

### 域 4 · 状态机与检查点（B / E / H）

- 状态流转：`Queued → Running → (Failed → 自动重试 or 转人工) → Completed`。
  实际还需 `Waiting_Approval`、`Paused`、`Cancelled`、`Partially_Completed`（E）。
- **状态定义只是第一步，更重要的是明确状态迁移条件**（E）：
  等待审批的任务不能被调度器误触发；已完成的任务不能被普通重试重启；
  已取消的任务不能继续无限派生子任务。
- **每个关键步骤存一次检查点**，内容不只是"跑到第几步"，还包括**当时的上下文、
  已产出的中间结果、下一步该做什么**（B）。
- **恢复流程**：进程启动时先扫描所有仍为"执行中"的任务 → 重新捞回队列 →
  读各自最后一个成功检查点 → **从下一步继续，而不是从头再来**（B）。
- 早期用 SQLite 存本地就够，规模上来再迁 PostgreSQL（B）——别一上来就上重方案。
- **没有检查点的长任务，本质是在拿运气赌进程不会挂。**

### 域 5 · 重试与错误恢复（B / C / E / H）

先分类，再决定怎么处理（E 分为四类：临时故障 / 输入与业务校验失败 /
模型输出不合格 / 权限与安全问题）：

| 类型 | 处理 |
|---|---|
| **可重试**：429 限流、500/502/503/504、网络超时、连接重置 | 最多 3 次，指数退避，**限流场景等待上限 ~30s + 正负 30% 随机抖动**（避免多实例同时重试造成二次冲击）；服务端给了 `Retry-After` 就优先按它来 |
| **不可重试**：401 / 403 / 404 / JSON 解析失败 | 立即失败。**权限错误被反复重试只会白烧调用次数**，用户看到的是"明明没权限却在那儿转圈圈" |
| **模型幻觉式缺失**（该有的信息漏了） | **尽量只给一次机会**，出错直接标失败走人工复核——模型每次生成有差异，重试并不必然指向修复，反而可能引入新的不一致 |
| 输出被截断（`finish_reason == length`） | 先升 `max_tokens` 重试一次；仍截断说明任务需要分多轮 → 改用**续写提示**（H） |
| prompt 过长 | 重试无解，必须先压缩。用**反应式压缩**，且**只跑一次**（标志位防死循环）；摘要也失败就退化成"对话已被截断"占位文本，保证流程不卡死（H） |
| 连续过载（如连续 529） | 达阈值**切备用模型**，而不是无限重试同一个过载模型（阈值设 2 左右）（H） |

**一个任务失败 ≠ 整条链重跑**（E）：保留已确认有效的前序结果，只恢复失败的那一步
——前提是前序结果仍有效且没有需要重算的业务变化。

### 域 6 · 上下文工程与压缩（C / D / H / I）

**Context Rot**（I）：窗口大不等于更聪明。症状是——忘了最初要干什么、
把已完成的步骤重做一遍、拿过期信息当依据、前后两次推理逻辑对不上。
**这不是模型变笨，是冗余信息把注意力搅乱了。**

压缩要**分层，不要一步到位做摘要**（H）——直接调模型摘要有两个代价：
贵，而且会把"刚执行完还没被模型消化的工具结果"也摘掉。四层递进：

1. **单条超大输出落盘 + 留预览**（阈值以上写文件，上下文里只放约 2000 字预览 + 路径）。
2. **裁剪历史中段，保留头尾**——**绝不能把一个 tool_use 和它对应的 tool_result 拆开**，
   否则模型下一轮看到的是悬空的工具调用，API 直接报错。
3. **早期 tool_result 内容替换**（只留最近三条完整，更早的换成"已压缩，需要时重新执行"）。
4. 前三层都顶不住，**才**调模型摘要；同时把原始对话**落盘成 transcript** 供事后回溯。

摘要必须保留五样，缺一样会话就会变得不连贯：**当前目标、关键发现、改动过的文件、
剩余任务、用户约束**。

**"成功保持安静，只有失败才输出详细信息"**（C）——有团队让 Agent 每改一次代码就跑
一遍完整测试，几千行通过日志灌进上下文后模型开始"失忆"、对着刚读过的文件产生幻觉。

其他要点：

- **system prompt 每轮重建、不缓存**（H）；技能只放**目录**（名字 + 一句话描述），
  完整内容由模型按需 `load_skill` 加载——体积只跟"有多少个技能"挂钩。
- **Prompt Caching**：稳定内容放前面、变化内容放后面（I）。
  **但缓存只让"重复计算"变便宜，不能让"错误的内容"变正确。**
- 上下文的目标从来不是"给得越多越好"，而是**给它做这一次判断所需要的信息**（G / I）。

### 域 7 · 记忆治理（D / F / I）

先分清四个概念（I）：**Session**（一次任务的过程）/ **Knowledge**（稳定的参考资料）/
**Memory**（从历史里提炼的经验）/ **Context**（此刻摆在桌上的全部信息）。

**上下文 ≠ 记忆，聊天记录 ≠ 记忆。** 记忆系统要回答五问（D）：
什么值得记、什么时候去找、找回来怎么用、新信息怎么保存、**什么时候该忘**。

七模块（D）：用户、Agent、记忆触发器、短期记忆、长期记忆、记忆管理器、知识库。
**记忆管理器才是最复杂的一块**——检索、去重、相关性排序、多来源融合、记忆更新、
过期清理、重要性调整，全在这里。存储只是基础设施。

三个最容易做错的地方：

1. **只设计写入，不设计更新**（D）。业务事实是**会变的状态**，不是静态知识。
   正确做法：新增 / 合并 / **更新（把旧记录标记为"已被替代"而非并存）**，
   否则检索时会同时找到两个互相矛盾的日期。
2. **只看相似度，不看来源与时效**（D）。语义相似只回答"看起来像不像"，
   不能回答"这条现在是否有效"。融合排序至少要过五个维度：
   **相关性、时效性、可信度、重要性、冲突关系**。
3. **忽略权限边界**（D）：个人记忆 / 项目记忆 / 组织知识不能不加区分共享；
   Agent 有读取能力 ≠ 当前任务下有权读取。

**必须区分"有效性"与"重要性"**：一条记忆可能很重要但已过期，也可能仍有效但几乎不影响
当前任务。重要性高不等于该永久保留（D）。

模型推断出来的内容**不应未经验证就变成长期事实**——"用户连续三次要求缩短"只是推断，
要变成稳定偏好需要有确认机制或按后续使用逐步提升置信度（D）。

推荐字段（D）：`Memory ID / Content / Type / Source / Created At / Updated At /
Valid Until / Confidence / Scope / Permissions / Status`。

建设顺序（D）：任务状态管理 → 持久化记忆 → 提取与分类 → 多路检索与融合 →
安全与治理 → 评估体系。

### 域 8 · 工具与 MCP（D / F / H / I）

- **Tool 是能力本身，MCP 是接入这些能力的统一协议层**，两者不是平级概念（F / I）。
  "MCP 就像 Agent 世界里的 USB"（I）。
- **工具是给模型看的，不是给人看的 API 文档**（I）：名字要清楚、语义要表达到位、
  输入输出要明确、出错要告诉它错在哪。**描述含糊 → Agent 在几个工具之间来回横跳、
  反复试错，白烧大量 Token。**
- **工具池每轮重新组装，而不是连接时组装一次缓存住**（H）——这样别的线程新连了
  MCP server，主循环下一轮立刻能用上，不需要重启。延迟绑定：连上之前模型看不到该工具。
- 工具层必须配齐：**权限、超时、重试、结果校验、审计日志**（C）。
- 工具编排的真正难点不是"能不能调"，而是**哪些可以并行、哪些必须串行、
  失败了要不要回滚前面已做的事、超时怎么处理**（B）。

### 域 9 · 决策层与策略（G）★新增视角

把"生成"和"决策"拆开：LLM 负责生成与复杂推理，**Decision 负责结构化判断**，
Policy 决定什么时候允许执行，Tools 真正改变世界。

```
AI → Decision + Confidence → Policy → Action
```

典型控制策略：**confidence > 0.95 自动执行；0.80–0.95 二次确认；< 0.80 转人工**。

关键洞察：**传统 LLM 给出的"我有 90% 把握"本身还是生成的文字，没法直接被程序信任**；
决策模型把 probability / confidence 做成结构化结果的一部分，控制流才敢用它。

适用范围：**输出空间有限的判断**（是不是 / 该选哪个 / 有多确定），如
"这条消息是不是退款请求""工单该给哪个团队""这条检索结果相关吗"。
已知边界（G）：不适合复杂数学、精确日期计算、通用多步推理。

### 域 10 · 模型路由与成本（B）

- 先做**任务分级**，再匹配模型。格式转换 / 信息提取 / 短摘要 → 便宜快的模型；
  代码生成 / 多步推理 / 长文档分析 → 强模型。
- 三步走：**① 前置轻量模型或分类器快速判难度 → ② 默认中档，质量不达标自动升级 →
  ③ 按用户/部门统计 token 与成本，超阈值自动降级兜底。**
- **切换模型不只是换 API 端点**：上下文窗口不同 → 压缩触发阈值、保留历史轮数、
  检索分块大小都要跟着自动调整。否则会出现"新模型窗口更小但你还塞着老模型规格的上下文"。
- 成本预算必须能设上限并优雅退出（A / B）。

### 域 11 · 安全边界与提示注入防御（C / I）

- **沙箱决定能进哪些房间，权限决定在房间里能碰哪些东西**（I）。
  低风险自动放行 / 中风险留痕 / 高风险人工签字 / 某些直接禁区。
- 安全边界**是一入职就配好的门禁卡，不是等出了事故才回头补办**（I）。
  很多团队"先图快跑起来，权限管控以后再说"——那个"以后"往往等到真出事故才被提上日程。
- 安全问题的性质变了：**从"模型会不会说错话"变成"模型犯错之后最多能造成多大损失"**，
  靠的是**权限、沙箱、网络出口**这三道实打实的边界（C）。
- **提示注入**（I）：攻击链是——恶意指令混进某份资料 → 资料被读进上下文 →
  模型把它误判成高优先级指令 → 调用工具执行危险操作 → 数据泄露或系统被破坏。
  **所有来自外部的内容都不能被天然当成可信指令，而应被当成需要审查的"外来代码"**。
  防线必须是系统层面的信任边界（权限限制、允许列表、沙箱隔离、高风险强制人工审批、
  钩子检查），**不能只指望模型自己识别恶意内容**。

### 域 12 · 人机协同与审批门控（D / E / H）

- **意图澄清是正常业务流程的一部分，不是异常处理分支**（E）。
  原则：**能依据明确规则补全的可以自动补全；会显著改变业务结果的信息，不要让模型猜。**
- **人机协同不应变成每步都要点确认**（E）：规则明确、风险低的自动执行；
  有歧义请用户选择；高风险按企业权限与审批制度处理。
- **用户确认方案 ≠ 权限检查通过**（E）——执行时仍需验证。
- **把"先计划后执行"从软约束变成硬约束**（H）：teammate 提交计划后被**物理阻塞**，
  主循环检测到 `waiting_plan` 标志就不再执行模型/工具步骤，只轮询收件箱等审批；
  审批响应靠 `request_id` 精确匹配，不能用"收到一条 approve 就放行"（否则会误批准
  另一个待处理请求——多任务并发时这是必须的）。
- 钩子适合安全、日志、经验沉淀这类**通用**问题；
  **不要把核心业务逻辑塞进钩子**，那会让系统难以维护（I）。

### 域 13 · 多 Agent 协作：什么时候才真的需要（A / E / I）

- **多加 Agent 不等于更强的系统。** 没有调度、状态记录、依赖管理、结果校验、
  失败恢复，多个 Agent 只是"多开了几个聊天窗口"（A）。
- **每增加一个 Agent 都会带来额外调用成本、延迟、失败概率和上下文传递开销；
  拆得过细，协调时间可能超过执行时间**（E）。
- 拆分合理性的**检验标准**（I）：如果子 Agent 上手前得把主 Agent 掌握的信息几乎全部
  重学一遍，那这个拆分就是错的。**合理的分工是每人只需要知道跟自己相关的那部分。**
- 常见协作模式（I）：主管带专员 / 计划者 + 执行者 / 分诊台分发。
  长任务常用的三角色（C）：**规划者 + 执行者 + 校验者**。
- 两种委派（H）：**一次性子任务**（独立 messages，中间过程不污染主上下文，
  只回一段摘要——解决上下文隔离）vs **持久 teammate**（独立线程 + 消息总线 +
  空闲轮询任务板——解决长期并行协作）。
- **该不该多 Agent 的判据**（E / I）：能写死就用脚本/固定流程；
  任务需要多个专业能力 + 明确依赖 + 长时间运行 + 人工审批 + 复杂异常处理时，
  独立的规划与编排机制才体现价值。

### 域 14 · 评估与价值度量（B / C / D / I）

- **评估不能只看输出文字像不像，要看业务状态有没有真正改变**（C）：
  工单是不是真的关掉了、数据库记录是不是真的改对了。
- 过程指标（I）：token 消耗、耗时、工具调用次数、重试次数、人工介入次数。
  结果指标（I）：任务成功率、结果准确率、验收通过率、用户满意度、单次任务成本。
  记忆系统另有五类（D）：检索质量、任务效果、记忆准确性、运行成本、安全与权限。
- **Loop 层的关键指标**（A）：任务完成率、端到端成功率、出错后能否自行恢复、
  平均耗时、token、**工具调用失败率**、**人工介入频率**、长跑稳定性。
- **判断 Agent 值不值得继续投入的四个维度**（B）：
  **效率**（上线前后真实数据对比，不是"感觉更快"）·
  **质量**（准确率 + 需人工修正比例——若每次都要大改，净效率可能是负的）·
  **采纳率**（日活、周留存、主动调用频率，比满意度问卷诚实）·
  **ROI**（模型成本 + 运维成本 + 开发投入 vs 节省的人力，算明白账）。
- **可观测性不是加个 print**（I），需要专门的 LLMOps 能力
  （Langfuse / LangSmith，或基于 OpenTelemetry 自建）。
- **运行轨迹**（E）：为一次用户请求生成**唯一任务 ID**，贯穿计划、DAG 节点、
  Agent 调用、工具调用与结果记录，同时记录关键事件、耗时、错误与模型调用指标。
- 用轨迹回答的真实问题：**"这次为什么得出这个结果""为什么比上次慢三倍"
  "究竟是哪个环节返回了错误数据"**（E）。

### 域 15 · 组织与交付（C / I）

- 分工：**平台团队**负责 Harness、模型网关、工具与运行时、评估体系、安全治理；
  **业务团队**负责领域知识、业务流程与本线效果指标（C）。
- **FDE（前向部署工程师）**：从"能演示"到"能交付"最难跨的坎，
  往往不是模型不够强，而是**缺一个能把"客户经验里那些从没写进任何文档的规矩"
  翻译成 Agent 能听懂的语言的人**（C / I）。
- 最终要交付的，是一套**可执行、可恢复、可验证、可看见、可管住**的系统（C）。

## 四、反过度设计：十条"什么时候不该用 Agent"

这部分是九篇文章里最容易被忽视、但落地时最有价值的一组约束。

| # | 判断 | 出处 |
|---|---|---|
| 1 | **能写死就用脚本/固定流程，写不死才轮到 Agent** | I |
| 2 | 一次模型调用能搞定的（翻译、写诗、格式转换）不需要 Agent | I |
| 3 | 不需要为了体现架构复杂度，把每个任务都拆给不同 Agent | E |
| 4 | 多 Agent 不是企业级 AI 的必选项；**任务编排与执行控制才是复杂业务绕不开的问题** | E |
| 5 | 记忆系统"不要什么都记"——先问"如果忘了这条会造成什么" | D / I |
| 6 | 别把 RAG 当完整的记忆系统（它不解决提取、偏好、状态更新、过期清理、用户纠正） | D |
| 7 | 技能是"知识"不是"软件"，别写成塞满分支判断的业务流程 | I |
| 8 | MCP / 微服务 / DDD 重型分层 / K8s 都要先论证必要性 | B / C |
| 9 | 检查点早期用 SQLite 就够，规模上来再迁 PostgreSQL | B |
| 10 | 从小规模工作流开始，先跑通一条真实业务链路再加 Agent | E |

## 五、落地顺序（综合 B / C / D / E）

文章给出的优先级高度一致，可归纳为四批：

**第一批 · 安全与可追溯（没有这层，后面都是裸奔）**
应用鉴权 → 身份传递 → 工具边界权限（PreToolUse hook）→ 审计五问 + 脱敏 →
审计目录权限 → 提示注入信任边界。

**第二批 · 不丢数据（这层决定系统敢不敢跑长任务）**
统一任务状态模型 + 迁移条件 → 检查点持久化 → 进程重启恢复 →
三层幂等 → 错误分类重试 → 循环层重复调用检测。

**第三批 · 不烧钱、不失控**
分层上下文压缩（含"不拆散 tool 配对"）→ 记忆治理（更新/过期/替代）→
成本预算与模型路由 → 工具契约与描述质量 → 停止条件与人工接管。

**第四批 · 越跑越好**
运行轨迹（唯一 task_id）→ 过程/结果指标 → 评估集与回归门禁 →
业务状态验证 → 价值四维度 → 反馈回流。

## 六、生产就绪速查清单（40 项）

> 用法：逐项打勾。**未打勾的项即为"无法生产级落地"的具体缺口。**

**权限与身份**

- [ ] 1. 有应用层鉴权，`actor` 由服务端推导而非请求体自报
- [ ] 2. Agent 用**发起人身份**访问资源，而非统一服务账号
- [ ] 3. 权限检查是工具调用边的确定性拦截，不在提示词里
- [ ] 4. 权限作为 PreToolUse hook，新增工具天然继承
- [ ] 5. 权限分级：低自动 / 中留痕 / 高人工签字 / 禁区
- [ ] 6. 执行时二次校验，且不允许"换权限更宽的 Agent"绕过

**审计与可观测**

- [ ] 7. 审计能回答五问（谁/什么/何时/为何/结果）
- [ ] 8. 记录工具参数，且 Token/API Key 已脱敏
- [ ] 9. 审计写 JSONL、按天轮转、保留期明确
- [ ] 10. 审计文件权限收紧，仅管理员可读写
- [ ] 11. 被拒绝的请求也被记录
- [ ] 12. 唯一 task_id 贯穿计划 / 步骤 / 工具调用 / 结果
- [ ] 13. 过程指标与结果指标都有

**幂等与状态**

- [ ] 14. 幂等键 = 工具名 + 关键参数哈希 + 身份 + 时间窗
- [ ] 15. 有副作用的工具本身幂等（先查后建 / 覆盖写）
- [ ] 16. 循环层检测"连续 N 轮相同调用签名"
- [ ] 17. 任务状态机定义完整，含 Waiting_Approval / Partial / Cancelled
- [ ] 18. 明确状态迁移条件（等待审批不被误触发等）
- [ ] 19. 关键步骤落检查点（含上下文 / 中间结果 / 下一步）
- [ ] 20. 进程重启能扫描并恢复"执行中"任务，从检查点续跑

**错误恢复**

- [ ] 21. 错误分可重试 / 不可重试 / 输出不合格 / 权限，各自策略不同
- [ ] 22. 退避带随机抖动，尊重 Retry-After
- [ ] 23. 截断处理（升 max_tokens → 续写）
- [ ] 24. 上下文超限走反应式压缩且只跑一次，防死循环
- [ ] 25. 连续过载切备用模型
- [ ] 26. 单步失败不清空整链，保留有效前序结果

**上下文与记忆**

- [ ] 27. 压缩分层（大输出落盘 → 裁中段 → 替换早期 → 才摘要）
- [ ] 28. 压缩不拆散 tool_use / tool_result 配对
- [ ] 29. 摘要保留五要素（目标 / 关键发现 / 改动文件 / 剩余任务 / 约束）
- [ ] 30. 成功静默、失败详述
- [ ] 31. system prompt 每轮重建；技能按需加载（只放目录）
- [ ] 32. 记忆有 Valid Until / Status / Source / Confidence，旧值标记"已替代"
- [ ] 33. 记忆融合按相关性 / 时效 / 可信度 / 重要性 / 冲突五维排序
- [ ] 34. 模型推断不直接写成长期事实

**决策、成本与安全**

- [ ] 35. 有独立的 Policy 层：confidence → 自动 / 二次确认 / 转人工
- [ ] 36. 任务分级 + 模型路由 + 成本上限兜底
- [ ] 37. 换模型时同步调整压缩阈值与历史保留轮数
- [ ] 38. 工具描述达到"给模型看"的质量标准
- [ ] 39. 外部内容统一按不可信处理（信任边界 + 允许列表 + 沙箱）
- [ ] 40. 有"停止条件"与"人工接管条件"的显式定义

## 七、九篇文章给本项目最直接的三条冲击

1. **本项目已经有"内循环"（LangGraph 图 + hooks），但缺"外循环"**——
   没有统一的任务状态机与检查点，进程重启只能靠"增量水位"重来（A / B / H）。
2. **本项目把"置信度"算得很扎实（`confidence.py`），但没有把它接成"策略"**——
   现在只用来决定"要不要人复核"，没有形成 `Decision + Confidence → Policy → Action`
   的自动执行门（G）。
3. **本项目的审计主体由客户端自报，且工具参数不落库**——
   在"五问审计"（B）下只能回答"什么时候、做了什么"，回答不了"谁做的、为什么"。
