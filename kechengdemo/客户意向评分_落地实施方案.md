## 总纲：这五件事其实是同一件事的四个面

| 你的问题 | 本质 | 一句话答案 |
|---|---|---|
| 评分规则怎么"落实"、每次都按标准执行 | **强制力** | 规则的权威不在提示词里，**在代码里** |

# 第一部分　让评分规则"每次都按标准执行"

**原则：不要指望模型"自觉遵守"规则。** 提示词里写十条规矩，一次上下文截断、一次足够自信的幻觉就能让它忘光
（这正是《生产级 Agent》那篇讲的"提示词层面永远做不到的强制力"）。
正确做法是给判定链路装**六道闸**，每一道都用代码兜住。

## 闸 1　规则可机读化：给每档补 `examples`（正例 + 反例）

**现状**：`rules.json` 每档只有一句 `criteria` 自然语言（如"在职编程技术岗"），模型只能自己解释。
同一个"做测试的算不算技术岗"这种问题，两次调用可能给出不同答案。

**改法**：每档增加 `examples` 字段，`criteria` 保持人读，`examples` 喂模型。
这是需求 §9.3 本来就要求的字段（见优化建议 F5）。

```json
{
  "rule_id": "positive_coder_profile",
  "dimension": "程序员或转型画像",
  "options": [
    {
      "score": 2,
      "criteria": "在职编程技术岗",
      "examples": {
        "positive": ["我是 Java 后端", "做前端三年了", "运维，平时写脚本"],
        "negative": ["我是产品经理", "做 HR 的，想转行"],
        "ambiguous": "测试岗（按是否写代码判断，能写自动化脚本算 +2）"
      }
    }
  ]
}
```

**验收**：随机抽 20 条判过分的会话，看模型给出的 `reason` 是否引用了 `examples` 里的措辞；若仍在自由发挥，说明提示词没把 examples 用起来。

## 闸 2　强制全覆盖检查：从"命中才输出"改为"逐维度都要表态"

**现状**：提示词是"请输出命中的加分项/扣分项"。模型**可以只输出它想到的那几条**——
于是有两类错误同时存在：**漏判**（某维度压根没检查）和**瞎判**（想到哪写到哪）。
而且你**无法区分**"这条规则没命中"和"这条规则模型忘了看"——两者的输出是一模一样的（都不出现）。

**改法**：改输出契约为**逐维度表态**，代码强制校验覆盖率。

```json
{
  "rule_checks": [
    {"rule_id": "positive_coder_profile", "hit": true,  "score": 2,
     "evidence": ["客户: 我是做 Java 后端的"], "reason": "在职编程技术岗"},
    {"rule_id": "positive_urgency",       "hit": false, "score": null,
     "evidence": [], "reason": "对话中未提及任何时间要求"},
    {"rule_id": "...", "hit": false, "score": null, "evidence": [], "reason": "..."}
  ],
  "customer_profile_summary": "...",
  "sales_strategy": "...",
  "confidence": 0.0,
  "needs_human_review": false
}
```

代码侧加一个覆盖率校验（纯确定性）：

```python
def check_coverage(rule_checks: list, rules: dict) -> set:
    """返回「模型漏检」的 rule_id 集合。"""
    expected = {r["rule_id"] for r in rules.get("positive_rules", [])}
    expected |= {r["rule_id"] for r in rules.get("negative_rules", [])}
    got = {c.get("rule_id") for c in rule_checks or []}
    return expected - got          # 缺失的维度 = 模型没检查
```

**处理策略**：
- `missing` 非空 → 触发**一次重试**，提示里点名"你遗漏了以下维度：..."（这就是 Harness 的内循环，见优化建议 G2）；
- 仍缺 → 缺失维度**按"未命中"处理**，但计入 `unchecked_rules` 指标，
  且**该会话置信度下调**（见第三部分）——你从此能看见"模型偷懒了多少"。

**代价**：输出变长（15 条规则全表态约 +500~800 token）。换来的是**漏判可检测**，这是可靠性上最划算的一笔。

**验收**：`unchecked_rules` 在稳定运行后应趋近 0；若长期 > 0，说明提示词对覆盖率的要求不够硬。

## 闸 3　确定性预筛：能让代码判的，绝不给模型判

**现状**：已有 `engine=rule` 机制（48h 未回复由 `compute_facts()` 算，模型不许碰），这是**目前最正确的一项设计**。

**改法**：把能枚举、能查表的维度**继续往规则引擎搬**：

| 维度 | 可否确定化 | 依据 |
|---|---|---|
| 连续 48h 不回复 | ✅ 已做 | 消息时间戳 |
| 高转地区 +1 | ✅ 可做 | 城市白名单，从标签或会话里的城市名精确匹配 |
| 程序员画像 +2 | ⚠️ 部分 | 微伴若有岗位标签，标签命中即 +2，无需模型 |
| 已学习 ≥1 个月 | ⚠️ 部分 | 若对话中明确提到"学了三个月"，可正则抽取 |
| 邀课成功 +2 | ✅ 已设计 | 微伴到课/完课标签（F3/D1，需打开 `scoring_fetch_tags`） |

**原则**：模型只判**真正需要语义理解**的维度。可确定化一条，模型的自由度就少一分，输出的方差就小一分。

## 闸 4　输出校验 + 重来（结构 / 极性 / 证据）

三道校验，全部纯代码，**不通过不是"丢掉了事"，而是触发一次带修正提示的重试**：

```python
# ① 结构：rule_id 存在 + 分值在允许档位          → rules.validate_items（已有）
# ② 极性：positive 项不得出现在 negative 列表      → 优化建议 B2（缺）
# ③ 证据：evidence 必须能在原文中定位到            → 优化建议 A1（缺）
```

三者任一不通过 → 组装修正提示 → **重试 1 次** → 仍不通过则丢弃该项、计入
`invalid_items` + `llm_low_confidence`。

> 这一条是把《Agent/Harness/Loop》那篇的"**执行完 → 校验 → 通过或者重来**"落到本项目的具体位置。

## 闸 5　温度归零 + 可复现

**现状**：`analyze.py` 里 `temperature=0.2`。

**改法**：评分场景**不需要任何创造性**，改成 `temperature=0`。
这不会让模型 100% 确定（服务端仍有非确定性），但能显著压低方差，让"同一段对话两次评分结果不同"这种问题变少。

配套：把 `prompt_version` 落库（优化建议 B1），这样"结果变了"能归因到"prompt 变了"还是"模型变了"。

## 闸 6　规则版本化 + 回归门禁

**现状**：`rule_version` 已有，规则变更会自动触发全量重评（`_candidates` 里有 `last.rule_version IS DISTINCT FROM rv`），这一步做得对。

**缺的是"改规则之前"的关卡**。补两条：

1. **规则变更必须过评估集**：改 `rules.json` → 跑 `eval/run_eval.py` → 关键指标（命中项一致率、per-rule F1）**不下降**才允许提交。
   这就是"回归门禁"，把"改规则"从"手动调 JSON"变成"有一次可验证的发布"。
2. **规则变更留痕**：`sync_rules()` 时把版本 diff 写进 `audit_log`，回答"上周那批分数为什么变了"。

## 第一部分小结：判定链路的完整形态

```
① 上下文装配（分层：长期摘要 + 新增消息 + 关键历史）      ← 优化建议 E1/F1
② 规则引擎预筛（能确定化的维度先算掉）                    ← 本部分 闸3
③ 大模型逐维度表态（temperature=0）                       ← 闸2 + 闸5
④ 三道校验：结构 / 极性 / 证据                            ← 闸4
   ├─ 通过 → 计分
   └─ 不通过 → 修正提示重试一次 → 仍不过则丢弃 + 降置信
⑤ 本地计分（rules.py，模型永不参与）                      ← 已有
⑥ 落库 + 分流（正分回写 / 负分复核）                       ← 已有
```

# 第二部分　评估集怎么做

**先说结论：评估单位是"命中项"，不是"总分"。**
因为总分由 `rules.py` 算，分数错了必然意味着命中项错了；评估命中项能**直接定位到哪条规则不准**。

## 三层评估集

### L0　金标准集（Golden Set）— 人工精标，冻结

- **规模**：100~200 条真实会话（分层抽样：S/A/B/C/D 各 20~40 条，含边界案例）
- **格式**：`eval/golden_set.jsonl`，一行一条：

```json
{"case_id": "g0001", "staff_id": "...", "session_id": "...",
 "messages_hash": "sha1...",
 "expected_items": [
   {"rule_id": "positive_coder_profile", "score": 2},
   {"rule_id": "positive_urgency", "score": 1}
 ],
 "expected_raw_score": 3, "expected_grade": "B",
 "annotator": "张三", "annotated_at": "2026-10-14", "note": "边界：时间要求含糊"}
```

- **`messages_hash` 很关键**：会话继续增长后，原标注就失效了。跑评估前先比 hash，
  不一致的条目提示"该会话已更新，标注需复核"——**评估集也是会过期的，这一点很多团队都忽略了**。

**冷启动怎么做标注（省力 5 倍的办法）**：
1. 用现系统跑一遍候选会话，导出模型给出的命中项；
2. 人工**只做"确认 / 修正 / 补充"**，不从零标注；
3. 每条标注只花 1~2 分钟，100 条约一个下午。

**争议样本单独存**：多个标注员意见不一致的，拿出来单列 `eval/disputed.jsonl`——
**它们本身就是"规则写得不够清楚"的证据**，直接指向该给哪条规则的 `criteria` 补 `examples`（闸 1）。

### L1　回归集（Regression Set）— 从复核反馈自动积累

- **来源**：`negative_review` 里人工**改判**的记录（AI 判了负分，人工 ignored，或分数不同）
- **特点**：**零成本持续增长**——你每复核一条，评估集就大一条
- **用途**：改提示词 / 改规则后跑一遍，检查"有没有把以前判对的搞坏"

这条正是优化建议 E5（反馈不回流）的落地方式：**复核数据不回流，等于每天生产的标注被扔掉。**

### L2　边界用例集（Edge Cases）— 手工构造

针对规则里**已知容易错**的地方，手工写用例：

| 用例 | 期望 |
|---|---|
| 客户有需求时主动问价 | 判「主动问课 +2」，**不**判「追着问价格」 |
| 客户未了解价值反复比价 | 判「追着问价格 −1」 |
| 正好 47 / 48 / 49 小时未回复 | 只有 ≥48h 判 −2（验证闸 3） |
| 有「实际到课」标签 | +2 |
| 无标签、仅聊天说"会来" | 最多 +1（验证冲突规则） |
| 同维度命中两档（如既想转型又在职编程） | 只取最高档（验证 `compute_score`） |
| 纯图片 / 撤回 / 空会话 | 跳过或低置信，不产生脏分 |
| 上下文截断（>60 条会话，早期需求在第 61 条） | **应命中**——这条专门验证 E1 修没修好 |

## 评估指标（对应文章"看过程、看行为、看最终业务状态"）

| 层级 | 指标 | 说明 |
|---|---|---|
| **规则级** | 每条 rule_id 的 precision / recall / F1 | 最重要。直接告诉你哪条规则不准 |
| **会话级** | 命中项集合完全一致率、`raw_score` 一致率、等级一致率 | 端到端准确度 |
| **过程级** | `unchecked_rules` 数、证据校验通过率、`invalid_items` 数 | 闸 1~4 的效果 |
| **业务级** | 回写后微伴分数一致率、人工改判率 | 最终业务状态是否真的对了 |

> 文章原话：「不能只看输出的文字像不像那么回事，要看**最终的业务状态有没有真正改变**」——
> 在你的场景里，业务状态就是**微伴后台的客户分数**。所以业务级指标必须测到微伴那一端。

## 运行方式

```
eval/
  golden_set.jsonl      金标准
  regression.jsonl      回归集（自动累积）
  edge_cases.jsonl      边界用例
  run_eval.py           跑评估 → 输出 eval_report.json
  baseline.json         当前基线（每次发布前对比）
```

- `python eval/run_eval.py` → 输出 per-rule 混淆矩阵 + 总指标 + 与 `baseline.json` 的对比
- **发布门禁**：改 `rules.json` 或 `SYSTEM_PROMPT` 后必须跑，指标下降则不允许上线
- `eval_report.json` 记录当时的 `rule_version` + `prompt_version`，可追溯

# 第三部分　置信度怎么弄

**核心原则：置信度必须"算出来"，不能"问出来"。**
现状是 `analyze.py:178-179` 直接把模型自报的 `confidence` 落库并展示——**让可能出错的组件自己申报可信度，等于自证清白**（优化建议 E4）。

## 三层置信度

### A. 命中项级（每一条）

```python
# engine=rule 的命中项 → 确定性，置信度恒为 1.0
# 语义命中项 → 由可观测信号合成，而不是问模型
item_confidence = {
    "high":   证据回链成功 且 证据条数 >= 1,
    "medium": 证据回链成功但仅部分匹配,
    "low":    证据无法回链（此时应直接丢弃，见闸 4）,
}
```

### B. 会话级（这个总分可不可信）

```python
session_confidence = 综合(
    命中项平均置信度,
    维度覆盖率        ,   # 1 - len(unchecked_rules)/规则总数
    无效项比例        ,   # len(invalid_items) / 总表态数
    与上次评估的一致性,   # 同一会话两次评分差异大 → 低置信（需 E1 读回历史）
)
```

注意最后一项：**"同一段对话两次评分差很多"本身就是低置信度的证据**——
这正是优化建议 E1 提到的验证法（`msg_count > 60` 的会话连跑两次 force，比较命中项）。

### C. 人工复核触发（把 `needs_human_review` 从模型手里收回来）

现状是模型自报 `needs_human_review`。改成**规则判定**：

```python
needs_human_review = (
    有负分项                                  # 现有硬规则，保留
    or session_confidence < 0.6                # 新增：低置信
    or 总分落在等级边界 ±1                      # 新增：边界样本最需要人看
    or 命中 +2 档但证据只有 1 条及以下          # 新增：高权重 + 弱证据
    or 本次等级与上次不同                       # 新增：翻转样本优先复核
)
```

`confidence` 字段同时**改名或标注为 `model_confidence`**，与人工验证状态分开——
避免复核人员把"模型说它有 0.9 信心"误当成"这条经过验证了"。

# 第四部分　安全与权限怎么弄

文章把安全问题的定义改成了：「模型犯错之后，**最多能造成多大的损失**」，靠**权限、沙箱、网络出口**三道边界。
你的答案是：**损失上限很小，但边界还没画完。**

## 边界 1　模型与副作用隔离 —— 已做到，务必保持

`_score_one()` 里模型**只输出 JSON**，取标签、解密正文、回写评分**全部由代码显式调用**，
模型没有 function calling 通道。所以即使被提示注入、产生幻觉，它**最多只能在评分 JSON 里捣乱**。

> 这是架构级的优点（优化建议 H4）。**任何后续新增功能都不得给模型直接调用工具的通道。**

## 边界 2　角色与权限 —— 目前最缺

**现状**：系统没有用户登录体系。`audit_log.actor` 硬编码为 `"manual"` / `"工作人员"`，
**出了事查不到是谁干的**。

**改法（内部系统，不必上完整 RBAC，但要最小可行）**：

| 角色 | 权限 |
|---|---|
| 管理员 | 改规则、改运行参数、**切换回写 live**、看全部数据 |
| 复核员 | 只能提交 / 修改复核状态，看分配给自己的会话 |
| 只读 | 看报表与统计，不能改任何东西 |

最小实现：
- 加一个「简单 token + 角色」的中间件（可以先用固定 token 分发给几个人）；
- **关键操作强制管理员**：切换 `live`、修改 `rules.json`、改 `max_sessions` / `fetch_tags`；
- `actor` 记录**真实操作人**，不再写死。

**特别提醒**：`wb_staff_export.py` 能把某员工的聊天记录**全量导出**——这是最敏感的能力，
必须限制到管理员，且导出动作写审计。

## 边界 3　副作用开关与配额 —— 有开关，缺配额

- `dry_run` 默认（✅ 已有）
- **上 `live` 的前置条件**：先验证微伴评分接口是"覆盖"还是"累加"（优化建议 D2）。
  这是**没有验证就不能上 live** 的硬门槛。
- **补配额**（防止重评风暴造成异常写入）：
  - 单轮回写总量上限；
  - 单客户单日回写次数上限（如 3 次）；
  - 超限自动降级为 `dry_run` 并告警。

## 边界 4　密钥与网络出口

| 项 | 现状 | 改法 |
|---|---|---|
| `.gitignore` | **不存在**（优化建议 E6） | 立刻补，包含 `.cache/`、`.env`、`node_modules/`、`dist/` |
| 密钥轮换 | 若曾提交过需轮换 | 检查 git 历史，轮换微伴 secret 与 LLM Key |
| 密钥存储 | `.env` 明文 | 至少限文件权限；需求 §10 要求服务端密钥管理机制 |
| 网络出口 | 无控制（微伴 / 企微 / DeepSeek 均为外网） | 出口白名单，避免 SSRF；确保模型无法触达内网 |
| 数据保留 | 未定义 | 定义聊天记录与评估记录的保留期限与删除流程 |

# 第五部分　怎么落地到公司

## 五阶段路线（每阶段都有可验证的产出）

### Phase 0　止血（约 1 周）
- 补 `.gitignore`、检查 git 历史、轮换密钥（**E6，最高优先级**）
- 修 `_candidates` 的 `force` 失效（**A3**）与定时任务互斥不对称（**H1**）
- 建立金标准集：跑一遍系统 → 人工确认修正 100 条 → 冻结 `golden_set.jsonl`

**产出**：密钥安全 + 一个可用的评估基线。

### Phase 1　让规则可信（约 2 周）
- 规则补 `examples`（**闸 1 / F5**）
- 改输出契约为逐维度表态 + 覆盖率校验（**闸 2**）
- 证据回链校验（**A1**）+ 极性校验（**B2**）
- `temperature=0`（**闸 5**）
- 落地 `eval/run_eval.py`，输出 per-rule 指标基线

**产出**：能回答"哪条规则不准"，且漏判可检测。

### Phase 2　让系统可信（约 2 周）
- 置信度改为算出来的（**第三部分 / E4**）
- 复核反馈回流，回归集自动积累（**E5 / L1**）
- 上下文分层，把上次结论读回来（**E1 / F1**）
- 可观测性补全：工具失败留痕、失败明细、token（**G1 / G5 / H5**）

**产出**：指标看板（完成率、一致率、误报率、人工介入率）+ 一张"每条规则误报率排行榜"。

### Phase 3　灰度上线（约 2~4 周）
- 验证微伴评分接口语义（**D2**）——不通过则不上 live
- 加配额与角色权限（第四部分）
- **灰度**：先对 1~2 名销售开 `live`，观察 2 周
- 观察项：回写成功率、分数分布是否合理、人工改判率是否上升

**产出**：小范围真实闭环跑通。

### Phase 4　全量与运营
- 全量开 `live`，配告警（回写失败率、失败会话数、预算耗尽）
- 建立**规则迭代流程**：改规则 → 跑评估 → 过门禁 → 发布 → 通知
- 每周复核会：看误报率排行榜与争议样本

## 组织分工（对应文章的"平台团队 + 业务团队 + FDE"）

| 角色 | 谁 | 负责 |
|---|---|---|
| **规则维护者**（业务） | 销售负责人 / 销运 | `rules.json` 的 `criteria` 与 `examples`，规则增删 |
| **系统维护者**（技术） | 你 | Harness / Loop / 评估集 / 权限 |
| **复核员**（业务） | 一线销售或销运 | 处理 `negative_review` 队列 |
| **FDE 角色** | 横跨两者 | 把业务判断翻译成规则、把系统指标翻译成业务语言 |

> 文章说 FDE 是"Harness 工程师 + 业务翻译官"的结合体。你这套系统里，
> **这个角色就是拍板 D2（评分覆盖/累加）和 D3（公开课节奏）的人**——
> 那两件事不是技术问题，是业务对接问题。

## 两个必须先回答的业务问题（不答就没法收尾）

1. **微伴评分接口是覆盖还是累加？**（D2）——决定 `live` 能不能上、要不要自己维护分数；
2. **公开课按什么节奏排？**（D3）——决定"课前/课后复核 S/A"这个定时任务怎么实现。
