### 交付内容
粘贴任意视频 URL 即可播放的 PySide6 桌面播放器。已验证支持：本地文件、
mp4 直链、HLS 点播、HLS 直播、RTSP、RTMP、局域网 HTTP。播放控制（进度拖动、
音量、静音、倍速、全屏、截图、外部播放器兜底）、拖放即播、窗口状态记忆。

### 关键技术结论（重要，后续阶段勿踩坑）

1. **`PySide6-Essentials` 不含 QtMultimedia**，只有 `.pyi` 存根。必须装
   `PySide6-Addons`（两者版本需一致）。规划阶段误判为 Essentials 已含，实测纠正。
2. **RTSP/RTMP 在 Qt 6.11.2 上是可用的**（本地 mediamtx 端到端验证，解出画面帧）。
   推翻了网上 Qt 6.6 时代"官方 FFmpeg 未编译 rtsp 协议、必然 error 28"的结论。
   因此**不需要 libmpv 后端**，P6 可降级为可选。
3. **`QT_FFMPEG_PROTOCOL_WHITELIST` 必须在 QApplication 之前设置**，否则
   HLS（嵌套 http+crypto）和 RTSP（嵌套 rtp/rtcp/udp）直接失败。放 `main.py` 最顶部。
4. **`QMediaPlayer` 对坏地址常常不发 `errorOccurred`**，会永久停在 Loading。
   必须用 QTimer + 状态检查强制判失败（`_on_load_timeout`）。
5. **直播流 duration 恒为 0**，判定成功的唯一硬证据是"是否收到画面帧"。
   且直播的 `durationChanged` 可能只在加载完成前发一次，加载成功后要重算一次直播态。
6. **Windows 本地路径必须转成 `file://` URL**，直接传 `C:\a\b.mp4` 给
   `QUrl` 会报 "Could not open file"。见 `src/utils/urls.py`。
7. **关闭窗口前若处于全屏，会把全屏尺寸存成下次窗口尺寸**，需先退出全屏再保存。

## 追加：P7 打包为 exe（完成）

同一工作区。产出两个形态，均已通过产物自检（退出码 0，真实解码 640x360 测试片）：

| 形态 | 路径 | 体积 | 启动耗时（实测） |
|---|---|---|---|
| 目录版 | `dist/UniversalURLPlayer/UniversalURLPlayer.exe` | 132.9 MB / 244 文件 | ~420 ms |
| 单文件 | `dist/UniversalURLPlayer-single.exe` | 53.8 MB | ~1700 ms |

### 打包关键结论

1. **PySide6 装完 641 MB，产物只需 133 MB**。剔除办法：`packaging/pack_config.py`
   在构建时枚举 venv 里的 Qt 模块，只保留 Core/Gui/Widgets/Multimedia/
   MultimediaWidgets/Network，其余 53 个排除。依据是**用 pefile 实测的链接期依赖**：
   `Qt6Multimedia.dll -> Core/Gui/Network`，`Qt6Widgets.dll -> Core/Gui`，
   所以排除是安全的。最大的一块 `Qt6WebEngineCore.dll` 单独就 194 MB。
2. **PyInstaller 的 Qt hook 按"实际 import 的模块"递归收集依赖与插件**，
   所以 `excludes` 真的能减小产物体积，不是摆设。
3. **`ffmpegmediaplugin.dll` 依赖 `MSVCP140.dll` / `VCRUNTIME140.dll` /
   `VCRUNTIME140_1.dll`**。PySide6 wheel 自带这几个运行库，PyInstaller 会从
   DLL 同目录解析并打包，所以目标机器**不需要装 VC++ 运行库**。已核对产物里有。
4. **只检查"插件文件存在"不足以判定产物可用**——依赖 DLL 缺失时文件照样在。
   自检里用 `QPluginLoader` 真的 load 一次才是决定性检查。
5. `console=False` 的窗口程序**没有自己的控制台**，`print` 会被丢弃。自检用
   `kernel32.AttachConsole(-1)` + 打开 `CONOUT$` 把输出接回启动它的终端。
   但从脚本 subprocess 调用时（Git Bash/mintty 没有 Windows 控制台）接不上，
   所以验证改走"读自检报告文件"。

### 沙箱新坑：批量删除保护也会打断 PyInstaller

- 现象：`exit code 1`，日志里只有一行
  `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":253,"threshold":50,...}`，
  没有 Python 异常栈，很难看出根因。
- 根因：PyInstaller 每次构建都要清空上次的中间目录（250+ 个文件），单轮删除配额只有 50。
  首次构建跑到空目录上所以能成功，第二次必失败。
- 解法：`packaging/build.py --fresh-work` —— 每次用带时间戳的全新 `--workpath`，
  并把旧产物**改名**成 `*.stale-<ts>` 而不是交给 PyInstaller 删除（改名不算删除）。
- 同类问题还有：验证环节原本要 `unlink` 旧自检报告也会被拦。改成用环境变量
  `VIDEODEMO_SELFCHECK_REPORT` 指定**每次全新的报告路径**，全程零删除。

### 顺带修掉的真 bug

- `src/utils/playback_probe.py` 没做本地路径规范化，传 `C:\a\b.mp4` 给 `QUrl`
  直接 "Could not open file"。主程序走 url_router 时已处理，探测工具漏了。
  已抽出 `src/utils/playback_probe.py` 供 `tools/env_probe.py` 与产物自检共用。
- `selfcheck.py` 早期在源码模式下把插件目录找错（只看 exe 同级），造成假阳性；
  且 `_bundle_roots()` 在单文件模式下会把旁边的目录版产物也算进来。均已修。

## 追加：用户报"RTSP/RTMP 地址都播不了"——排查与改造

用户给的 4 条地址全部播不了。结论：**不是播放器的问题，是网络可达性问题**，
但排查过程暴露了两个真实缺陷并已修复。

### 排查证据链（方法值得复用）

1. 用户地址：`rtsp://wowzaec2demo.streamlock.net/vod/mp4:BigBuckBunny_115k.mov`、
   `rtmp://58.200.131.2:1935/livetv/{hunantv,cctv1,gdtv}`。
2. **同 IP 多端口对照**是关键手段：这两个主机**连 80/443 都超时**（不只是 554/1935），
   说明是主机整体不可达，而非端口被屏蔽。
3. 对照组说明"出网正常"：`mirrors.aliyun.com:443`、`github.com:22` 均通。
4. **但任意 IP:端口 都不通**，而 `www.cctv.com:443`/`www.baidu.com:443` 通 →
   本机出网走**按域名放行的透明代理**（`CODEBUDDY_MCP_CONFIG` 里 `transparent_proxy: true`），
   所以**在沙箱内无法测试任何外部 RTSP/RTMP**。这是环境限制，不是代码问题。
   → 注意：本机 curl 显式 `--noproxy '*'` 仍受限制。

### 排除"代码有问题"的三项硬验证

1. `QUrl` 解析带冒号的 Wowza 路径（`/vod/mp4:BigBuckBunny_115k.mov`）**完全正常**，
   没有转义或截断。
2. 新写 `tools/rtsp_shape_probe.py`：起一个假 RTSP 服务器把收到的请求行打出来。
   结果 `OPTIONS rtsp://127.0.0.1:8555/vod/mp4:BigBuckBunny_115k.mov RTSP/1.0`
   ——**路径原样发送**，含冒号/空格/认证/query 四种形状全部保真。
3. `PlayerController` 实播：`rtsp://127.0.0.1:8554/test`、`rtsp://192.168.110.38:8554/test`
   （局域网 IP，非回环）、`rtmp://127.0.0.1:1935/livetv/hunantv`（**用户地址原形状**）、
   `rtmp://192.168.110.38:1935/livetv/hunantv` —— 全部解出 640x360 画面帧。

### 发现并修复的两个真实缺陷

1. **`src/utils/env_setup.py` 设了不存在的 `QT_FFMPEG_RTSP_TRANSPORT=tcp`**。
   扫描 `ffmpegmediaplugin.dll` + `Qt6Multimedia.dll` 中全部 `QT_*` 字符串，
   6.11.2 只认 `QT_FFMPEG_PROTOCOL_WHITELIST` / `QT_FFMPEG_DEBUG` /
   `QT_FFMPEG_DECODING_HW_DEVICE_TYPES` 等，**没有 rtsp_transport / rtsp_flags**；
   `avformat-61.dll` 里 rtsp 协议别名只有 `rtsp` 和 `rtsps`（没有 `rtspt`/`rtspu`）。
   → **结论：Qt FFmpeg 后端播 RTSP 只能走 UDP，无法改 TCP。** 该变量已删除。
   实测 mediamtx 日志也确认：`is reading from path 'test', with UDP`。
2. **`_protocol_hint` 建议用户"在设置里把 RTSP 传输方式改为 tcp"**——根本没有这个设置。
   已改为如实说明 + 指向唯一可行的替代（外部 VLC/mpv）。

### 主要改造：失败不再只有一句"加载超时"

新增 `src/utils/net_diagnose.py`，把"能不能播"拆成四层并逐层给结论：
`地址解析 → DNS → TCP 连接 → 协议握手`。协议层只做**只读探测**
（RTSP OPTIONS / RTMP C0C1 握手 / HTTP HEAD），不拉流。

接入方式（`PlayerController`）：
- 每次 `_start` 在**后台线程**并行诊断，信号带**代际令牌**防串台，
  队列连接（`Qt.ConnectionType.QueuedConnection`）回主线程。
- **只在 DNS/TCP/TLS 硬性失败时快速失败**；协议握手失败只提示不终止——
  因为有些服务器对 OPTIONS/HEAD 返回 404/405 但实际能正常播放，据此中止会误杀。
- 超时兜底若发现诊断还没跑完，**只顺延一次**（3.5s）去拿真实原因。

实测效果：用户那两条连不上的地址从"干等 10 秒 → 加载超时"变成
**4.0 秒 → "无法连接到服务器" + 分层报告 + 4 条排查建议**；
本地可播的 RTSP/RTMP 未被误杀。

其它配套：
- `logger.install_qt_message_handler()` 把 Qt/FFmpeg 自身日志转发进 app.log
  （窗口程序看不到 stderr，"连上了但播不了"只能靠这个定位）。
- 界面加「诊断」按钮；`VideoWidget.show_message()` 把失败原因留在画面区。
- `tools/net_check.py` 命令行分层诊断；`main.py` 加 `--net-check <地址>`（exe 可用，
  离屏模式不弹窗以免无桌面时阻塞）。

## 追加：打包配置的隐蔽陷阱（excludes 撞上 setuptools 供应商别名）

重新打包时单文件版失败、目录版成功，报错是：

```
ValueError: Target module "distutils" already imported as "ExcludedModule('distutils',)"
```

随后去掉 `distutils` 再打包，**两个形态都失败**，报错换成同一类的 `wheel`：

```
ValueError: Target module "wheel" already imported as "ExcludedModule('wheel',)"
```

### 根因

PyInstaller 有 `utils/hooks/setuptools.py` 这个 pre-safe-import 钩子，一旦依赖图里出现
setuptools，就会把它 vendor 的模块别名过去：

```
alias_module("setuptools._vendor.wheel", "wheel")
```

而 `packaging/pack_config.py` 的 `OTHER_EXCLUDES` 里声明了 `distutils` 和 `wheel`，
别名目标已是 `ExcludedModule` → 直接抛异常，整个构建 exit code 1。

**为什么目录版却过了**：那次构建分析代码时 `src/core/resolver.py`（并行会话新增，
里面有 `import yt_dlp`）还不存在，所以 yt-dlp 的 hook 没触发、setuptools 没进图，
`distutils`/`wheel` 的别名动作也就没发生。**目录版/单文件版表现不一致，纯粹是因为
两次构建之间源码变了**——这种"看运气"的失败极难查。

### 规则（写进了 pack_config 的注释）

> **绝不能排除 setuptools 内部 vendor 的模块。**

名单见 `setuptools/_vendor/`：`distutils`、`wheel`、`packaging`、`pyparsing`、
`jaraco`、`backports`、`tomli`、`typing_extensions`、`importlib_metadata`、`zipp`、
`more_itertools`、`ordered_set`、`platformdirs`。

`tkinter`/`_tkinter`/`pip` 等不在 vendor 名单里，排除是安全的。
`lib2to3` 在 Python 3.13 已移除，排除也无意义，一并去掉。

### 教训

调试打包失败时**先看是不是 excludes 与 hook 冲突**，不要一上来怀疑源码。
另外：`--fresh-work` 的目录版/单文件版是两次独立分析，若源码在两次之间变动，
可能得到不同的结果——**排查这类问题时不要假设两次构建等价**。

## 追加：P2 收尾（yt-dlp 网页地址解析 —— 完成）

P0/P1/P7 之后接上 P2。核心是新增 `src/core/resolver.py`（约 700 行），
把"视频网站页面地址"变成一条能直接交给 `QMediaPlayer` 的流地址。

### 设计要点（都在 resolver.py 的 docstring 里）

- **只挑音视频合一的 progressive 流**：`QMediaPlayer` 一次只接受一条 URL，
  没有合流能力。筛选是三级 —— 单文件 → 仅画面 → 仅声音，
  只有前两级能播（第三级只用来告诉用户"声音流也拿到了"）。
- **绝不把 `format` 传给 yt-dlp**：B 站上会抛
  `Requested format is not available` 并**中断整个解析**，连 formats 列表都拿不到。
  改成让 yt-dlp 用默认格式、自己从 `info["formats"]` 里挑。
- **`vcodec`/`acodec` 三态不能混**：`"none"` = 明确没有该轨（B 站视频流就是），
  `None`/`""` = 未知（generic 抓到的普通 mp4）。把未知当"没有"会把好 mp4 误判成分离流。
- **硬超时**：解析跑守护子线程 + `join(timeout_s)`（默认 25 秒）。
  yt-dlp 的 `socket_timeout` 只管单个 socket，管不住重定向/重试。
- **质量排序键** `(height, width, _codec_rank, tbr…)`：h264 优先，
  av01/hevc 排后（缺解码器会表现为"能解析没画面"）。

### 控制器侧的两个关键改动

1. **代际令牌 `_resolve_token`** + `QueuedConnection`：用户换地址后，
   旧解析结果直接丢弃，不会串台。
2. **`_on_error` 必须用 `_media_loaded` 区分致命/非致命**（本轮最关键的 bug）：
   现象是本地页面解析成功、画面正常，状态栏却显示"播放失败 Demuxing failed"。
   用一个 6 组换源时序实验（`.tools/switch_probe.py`）排除了"换源导致"，
   结论是 **Qt FFmpeg 后端在 `LoadedMedia` 之后约 50ms 会补发一次可恢复错误**
   （FFmpeg 日志显示是 seek/读片段的小问题），六种组合**全都复现**但 mp4 都能正常播。
   → 已加载后的错误只记日志 + 状态栏提示，不弹错误框。
   **以后凡是"日志里报了错但画面正常"的情况，先查这里。**

### 判定踩的坑：`grab_frame()` 不能用来判"有没有出画面"（重要）

第一版我写的是 `ctrl.backend.grab_frame() is not None`，结果在
`--no-degrade`（压根没加载任何媒体）时也报 `画面帧=True` —— 假阳性。

原因在 `qt_backend.grab_frame()`：

```python
if self._last_frame is not None and not self._last_frame.isNull():
    return self._last_frame
pixmap = self._video.grab()          # ← 兜底分支
if not pixmap.isNull():
    return pixmap.toImage()
```

这个"抓控件画面"的兜底是给**截图功能**用的（部分渲染路径下拿不到 sink 帧时
也得能截出图），但副作用是：**离屏模式下控件 `grab()` 永远返回非空图**，
于是"有没有解码"这件事被它掩盖了。

**结论：判"是否真的解出画面"只能用 `QVideoSink.videoFrameChanged`。**
`grab_frame()` 只适合"生成一张截图"，不适合当播放成功的判据。
（`playback_probe.py` 一直是直接连 `QVideoSink` 的，所以它没这个问题；
`selfcheck` 走的就是 playback_probe，也没问题。）

## 分离流合流播放（画面 + 声音同时播）—— 实现并验证通过

### 先做实验再写代码（`.tools/dual_stream_probe.py`）

两个独立 `QMediaPlayer`：一个播 video-only（`QVideoSink` 出画面、不接 audioOutput），

| 启动方式 | 音画偏差 |
| --- | --- |
| 错开 100ms 启动 | 92~137ms |
| **同一次事件循环里启动** | **1~15ms** |
| seek 之后 | 95~270ms，随后自行收敛 |

画面流 `hasAudio=False`、声音流 `hasVideo=False`；497 帧画面 + 声音位置走到
122752ms。两路并行**成立且质量很高**，于是定为方案：不引入任何外部依赖。

1. `backends/base.py`：`supports_extra_audio()` / `set_audio_source()` /

   默认 no-op（mpv 这类原生多流后端将来给等价实现即可）。
2. `backends/qt_backend.py`：第二个 `QMediaPlayer + QAudioOutput` + 500ms 同步心跳。
   以画面为主时钟、偏差 >400ms 才校正、两次校正间隔 ≥3s、seek 后 1.5s 静默期；
   play/pause/stop/seek/rate/volume/mute 全部同步作用于两路。
3. `media_item.py`：新增 `audio_url`（**不持久化**，直链带签名会失效）。
4. `player_controller.py`：`can_play_merged()` / `play_merged()`；
   `_start` 里在 `play()` **之前**挂音轨；`extraAudioFailed` 只降级成无声。

界面：错误框把**「同时播放画面与声音（推荐）」**排在「仅播放画面」之前。

## 追加：分离流改为"自动合流播放"（用户反馈）

**用户报的问题**（原话）：*"为什么复制了 B 站视频地址后还是弹这个框，没有直接播放"*
——截图里是「网页地址解析失败」对话框，按钮已经排好了「同时播放画面与声音（推荐）」。

### 根因：能力做出来了，却没接通

`resolver` 对 B 站这类站点返回的是 **`ok=False`**（它如实报告"没有单文件流"），而
`_on_resolve_ready` 里是 `if not ok: self._fail(...)` —— **两条流明明都拿到了，
却直接走失败弹框**，用户每次都得手动点一下按钮。这不是解析问题，是把"失败"和
"需要用户选一步"混为一谈了。

### 改法

- `_on_resolve_ready` 的 `ok=False` 分支先问 `_can_auto_merge()`：拿到画面+声音两条流、
  后端支持附加音轨、用户没关开关、本轮还没试过 → **直接 `play_merged()` 开播**，
  状态栏说明"该站点只有分离的音视频流，正在自动把画面与声音合起来播放…"。
  做不到才走原来的失败提示（弹框里那两个按钮依然在）。
- 新增设置项 `playback/auto_merge_separate`（默认**开**），设置面板「播放」页可关。
- 两个防呆：`_merged_attempted` 防止"播→失败→再播"死循环；试过之后
  `can_play_merged()` 返回 False，错误框改推「仅播放画面」。
- `tools/page_play_check.py` 与冒烟都跟上：新增 `--expect merged`
  （只认"音轨挂上 **且** 画面在播"这个硬证据，单看 loaded/duration 会被
  "只有画面"骗过去）。

### 19:20 本地反向代理补上"解析器请求头透传"（真 bug）

`local_proxy.url_for()` 原来只接受一个 Referer 字符串，而 `player_controller`
调用 `proxy_url(url)` 时**根本没把 `item.http_headers` 传下去** —— 代理一律用
"由目标地址推导的站点根"当 Referer。对 B 站这类 **CDN 域名 ≠ 页面域名** 的地址，
等于把解析器辛苦拿到的正确 Referer 换成错的，防盗链照样过不去。

改法：
- `url_for(target, referer="", user_agent="")`，新增查询参数 `ua`；
- `proxy_url(target, headers=None)` 收字典，内部用新增的
  `pick_header(headers, name)` **大小写不敏感**地取 `Referer` / `User-Agent`
  （yt-dlp 的 `http_headers` 键名大小写不保证，四种写法都见过）；
- `_outgoing_headers(target, referer, user_agent)` 优先级：
  **调用方显式指定 > 设置里手填 > 由地址推导**。UA 同理。
- `_forward()` 提前把 `user_agent` 解出来，别在 `_outgoing_headers` 里再解析一次。

补了 8 项回归测试（`tests/test_local_proxy.py`，21 → 29 项）：
`PickHeaderTest`（大小写、空值、strip）+ `ProxyUrlHeaderTest`
（解析器 Referer 真的到达源站、小写键名也认、没有 headers 时开关仍然生效）。

对方这次加了一条**合理**的新规则（`player_controller._proxy_route`）：


理由站得住：本机服务没有防盗链问题，而代理自己就监听在回环上，代理回环
地址等于白绕一圈。**但它把我的冒烟检查测挂了**——我那条检查正是拿本地

1. **按真实规矩验证两条路由决策**（不需要真播，直接问 `_proxy_route`）：

   出函数立刻还原。这个 monkeypatch 必须带注释说明"为什么非这么做不可"，
   否则后人会以为是脏 hack。

（`_proxy_route` 里那句 `from src.core.url_router import is_loopback` 在**函数内**，
所以替换模块属性是生效的；如果哪天改成模块顶层 import，这个手法会失效。）

### 19:32 抓到并修掉：两处回环判定行为不一致

项目里有**两个**回环判定，问的是两个不同的问题：

| 函数 | 回答的问题 | 用途 |
|---|---|---|
| `core/url_router.is_loopback` | 该不该走**我们的本地反向代理** | `_proxy_route` 的回环直连 |
| `utils/urls.is_loopback_url` | 该不该绕开**环境里的 `HTTP_PROXY`** | requests 别把 127.0.0.1 丢给环境代理 |

对方新写的前者只比对固定名单 `{localhost, 127.0.0.1, ::1}` —— **整个
`127.0.0.0/8` 都是环回**，`127.1` / `127.0.0.2` / `127.255.255.254` 同样指向
本机，用字符串比较全会漏判，于是这些地址会被拿去绕代理。已修：

```python
try:
    return ipaddress.ip_address(host).is_loopback
except ValueError:
    pass
# ip_address 不认 "127.1" 这类省略写法，套接字层认
try:
    return socket.inet_aton(host)[0] == 127
except OSError:
    return False
```

并把 `0.0.0.0` 补进两边的名单、给 `is_loopback_url` 补上 `*.localhost`
（RFC 6761），让两者对"是不是本机"的结论**完全一致**。
新增 `tests/test_url_router.py::LoopbackTest`（5 项），其中
`test_the_two_helpers_agree` 专门钉"不许漂移"。

**教训（值得写进长期笔记）**：同一概念出现两处实现时，必须有一个用例专门
断言两者结论一致，否则它们一定会在某次改动后悄悄分叉。

## 追加：打包进 exe（含 libmpv 完整内核）

### 关键坑：libmpv dll 不会被 PyInstaller 自动收集

`python-mpv` 在 `OPTIONAL_MODULES` 里，所以打包版会带上**绑定**，但对应的
动态库 `libmpv-2.dll`（115 MB，手动放项目根 `mpv/` 目录）**不在** `binaries`

`python-mpv 已安装但 libmpv 动态库不可用`，退出码 1。

1. `pack_config.py` 新增 `optional_binaries()`：在项目根找
   `mpv/libmpv-2.dll` / `mpv/mpv-2.dll` 等，找到就返回 `[(源, ".")]`，

2. `mpv_backend.find_mpv_dll()` 在 `is_frozen()` 时**额外查 `sys._MEIPASS`**：
   onefile 版 binaries 解压到 `_MEIPASS` 临时目录，而 `app_root()` 指向的是
   exe 所在目录（不是临时目录），不查 `_MEIPASS` 就找不到。

### 产物（退出码 0，自检 + 29 项符号核对全过）

| 形态 | 体积 | 说明 |
|---|---|---|
| onedir | 350 MB / 317 文件 | dll 落在 `_internal/libmpv-2.dll` |
| onefile | 141.7 MB | dll 解压到 `%TEMP%\_MEIxxx\libmpv-2.dll` |

### 教训

- **可选依赖分"绑定"和"动态库"两部分时，打包要一起处理**，否则会产出

- `app_root()`（frozen 下指向 exe 目录）与 `sys._MEIPASS`（PyInstaller 解压目录）
  **不是一回事**，onefile 下两者不同，找打包资源要两个都查。


## B 站「能播/不能播」根因：分离流丢了 Referer（防盗链 403）

现象：`BV1CfixBvEuX` 播不了，`BV1Ebho6BE2J` 能播。两个视频解析层面完全相同
（都是分离的 1080P 画面流 + m4a 声音流）。

真根因（不是 codec、不是 CDN 连通性）：
- B 站有**两种 CDN**，防盗链策略不同：`upos-*.bilivideo.com` 严格校验 Referer
  （必须是 `www.bilibili.com` 的地址，否则 403）；`mcdn.bilivideo.cn` 不校验。
  能播的那个恰好解析到 mcdn，播不了的解析到 upos。
- 程序里 `resolver._build_result` 的**分离流分支**漏了提取 `http_headers`
  （只有「单文件流」分支提了），导致 `result.headers` 为空 → `item.http_headers`
  为空 → 本地反向代理只能用 `default_referer_for` 推导出 CDN 域名自己当 Referer
  → upos 防盗链 403。

修复（三处）：
1. `_build_result` 分离流分支：`result.headers = (video or audio or info) 的 http_headers`。

## 追加：好看视频 haokan.baidu.com 解析支持（新格式 vid 直链提取）

用户报 `https://haokan.baidu.com/v?vid=9615441669695160588&` 打不开。根因与修法：

### 根因

- `haokan.baidu.com/v?vid=...` 是 **React SPA**，首屏 HTML 只有骨架（`<div id="rooot">`），
  没有视频数据，数据靠 JS 动态加载。
- yt-dlp 内置 `BaiduVideo` 提取器的 `_VALID_URL` 只认 **老格式**
  `https?://v\.baidu\.com/(?P<type>[a-z]+)/(?P<id>\d+)\.htm`，不认新格式
  `haokan.baidu.com/v?vid=...` → 报 `Unsupported URL`。

### 修法：从移动端落地页内嵌 jsonData 直接抠直链

- 落地页：`https://mbd.baidu.com/newspage/data/videoshare?nid=sv_<vid>`（无需 Cookie），
  页面内嵌 `window.jsonData`，直链在 `curVideoMeta.clarityUrl`（list，按 `rank`
  升序排清晰度，rank 最高 = 1080p 蓝光），还有 `playurl`（默认超清）、`clarityArr` 备选。
- 直链域名 `vd*.bdstatic.com`，**无需 Referer**（实测 `curl` 不带 Referer 也 200，
  首字节 `ftyp` 确认合法 mp4）。
- 废弃接口 `api.haokan.baidu.com/rest/2.0/video/play`（域名已解析失败）、
  `haokan.baidu.com/videoui/api/videoplay` / `haokan/ui-web/video/play`（均 404）。

### 实现（3 个文件）

1. `resolver.py` 新增 `_is_haokan()` + `_extract_haokan()`，`resolve()` 预检后、
   逐策略解析前加「第 1.5 层」快速路径：`_is_haokan` 命中即先跑 `_extract_haokan`，
   拿到直链直接 `_build_result` 返回；拿不到（如老格式无 vid）落回 yt-dlp。
   关键细节：提取 jsonData 用**花括号配对**截断（`window.jsonData` 里的 JSON 含嵌套
   对象/数组，正则贪婪匹配会截断报 `Extra data`），并兼容 `clarityUrl`/`playurl`/
   `clarityArr` 三种字段形态。
2. `url_router.py` 的 `WEB_HOSTS` 加 `haokan.baidu.com`、`v.baidu.com`（让它们归为
   `WEB_PAGE` 走解析，而不是 UNKNOWN_HTTP）。
3. `_EXTRACTOR_NAMES` 加 `haokan` → 好看视频。

### 验证

- `site_check`：识别为好看视频，0.3 秒拿到 1080P 直链。
- `page_play_check` 全链路：解析成功 → 走本地代理补 Referer → **解出 3 帧画面**，
  时长 262740ms，h264+aac，播放成功。
- 单测 290 项全过（无回归）；老格式 `v.baidu.com/*.htm` 确认正确落回 yt-dlp 内置提取器。

### 教训

- yt-dlp 提取器对新站点改版常滞后（`_VALID_URL` 正则没跟上新 URL 形态），此时
  **不必侵入 yt-dlp 内部注册自定义提取器**（`_extractors_context` 是 `Indirect({})`
  惰性注册，内部 API 易变），更稳的做法是：在 `resolve()` 里加一层**站点专用快速路径**，
  用 requests 直接抓落地页抠数据、构造成标准 yt-dlp 风格 info dict 交给
  `_build_result` 复用后续所有逻辑（含 headers、降级链）。
- 好看视频这类"移动落地页内嵌 JSON"的站点，直链数据源往往在 `window.jsonData` /
  `window.__PRELOADED_STATE__` 里，比旧版 API 接口稳定。

### 打包验证 + pyz_inspect 工具假阴性修复

重新打包（`--fresh-work`，324.7 秒）：onedir 380.6MB / 1025 文件、onefile 155.8MB，
两个形态自检退出码 0、29 项符号核对全过。

用打包产物实跑好看视频地址（`--self-check <地址>`，读报告文件）：
识别为好看视频 → 拿到 1080P 直链 → `LoadedMedia` 时长 262740ms，**播放成功**。

**关键教训：`tools/pyz_inspect.py` 的 `find_in_code` 会假阴性**。它只遍历
`co_consts` 里 `isinstance(const, str)` 的项，而 `WEB_HOSTS` 这类**打包成
tuple/frozenset 的常量**是整体塞在一个 tuple 里的，域名字符串被容器包着、
工具没递归进去 → 误报"没打进去"。已修：新增 `_const_contains()` 递归进
tuple/frozenset 容器查找。**以后用 pyz_inspect 查"域名/列表常量是否进产物"，
先确认工具版本是否含这个递归修复，否则会把"在产物里"误判成"丢了"。**
