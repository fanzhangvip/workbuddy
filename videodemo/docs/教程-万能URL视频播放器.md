## 一、项目定位与教学目标

### 1.1 它解决什么问题

用户手里有一个"视频地址"——可能是本地文件、可能是 `https://.../a.mp4` 直链、
可能是 `rtsp://` 监控流、更常见的是一个视频网站的**页面地址**（比如 B 站
`https://www.bilibili.com/video/BVxxxx`）。用户希望**双击打开、粘贴、回车，就能看**。

这件事听起来简单，实际要处理的问题远比"调一个播放 API"复杂：

| 隐藏的困难 | 真实原因 |
|---|---|
| 页面地址不是视频 | 网页是一堆 HTML/JS，得先"解析"出真正的流地址 |
| 拿到地址也播不了 | 有的站点给的是「画面/声音分离」的两条流 |
| 直链播不了 | 防盗链：服务器校验 `Referer`/`User-Agent`/`Cookie` |
| 一直"加载中" | 播放器对失败经常**不发错误信号**，得自己兜底 |
| 直播和点播不一样 | 直播没有总时长，进度条逻辑要区分 |
| 解析慢或超时 | 站点被墙/改版，要能快速说清"为什么" |

**所以这个项目的价值不在"能播 mp4"，而在它把「从一段文字地址到屏幕上出现画面」
这条链路上的所有坑都系统地填平了。**

### 1.2 适合学什么

这是一个非常适合教学的中型项目（约 9800 行），因为它：

1. **技术栈主流且干净**：Python + PySide6(Qt) + QtMultimedia + yt-dlp。
2. **分层清晰**：核心逻辑、UI、工具、测试分离，适合讲"软件架构"。
3. **充满了真实的权衡**：不是"教科书式正确"，而是"工程上怎么取舍"。
4. **踩坑密度极高**：每个坑都能引出一个深入的知识点（详见第五章）。

### 1.3 建议的学习顺序

```text
理解「地址是什么」        → url_router.py
理解「怎么把页面变流」     → resolver.py + reachability.py
理解「怎么播 + 怎么兜底」  → backends/ + player_controller.py
理解「怎么绕过防盗链」     → local_proxy.py
理解「怎么打包交付」       → packaging/
```

### 2.2 关键设计原则

贯穿整个项目的四条原则，理解了它们就理解了整个项目：

1. **面向接口隔离内核**：UI 不碰 `QMediaPlayer`，只依赖 `PlayerBackend` 抽象接口。
   于是可以有两个内核（Qt 自带 / libmpv），切换时 UI 零改动。

2. **「先做掉，再抱怨」**：能自动完成的绝不弹框。比如 B 站分离流，拿到两条流
   就**自动合流开播**，只有实在做不了才问用户。

3. **失败要"说人话"**：所有底层英文报错都翻译成可操作的中文结论，并区分
   "网络不通 / 要登录 / 有 DRM / 已删除 / 地区限制"——而不是一句"解析失败"。

4. **防御式兜底**：播放器可能不发错误、解析可能卡死、DNS 可能污染……
   每一个"按理不会发生"的坑都有一层主动的兜底。

## 三、分层详解：从入口到播放

### 3.1 入口：`main.py` + `env_setup.py`

**做了什么**：进程一启动，第一件事（在创建 `QApplication` 之前）设置环境变量。

**为什么顺序这么讲究**（核心知识点：**环境变量的读取时机**）：

Qt6 的 QtMultimedia 默认用 FFmpeg 后端，而 FFmpeg **出于安全考虑默认禁止"嵌套协议"**。
所谓嵌套协议，就是一个协议内部再使用另一个协议：

- HLS（`.m3u8`）内部嵌套 `http` + `crypto`（AES-128 解密密钥）
- RTSP 内部嵌套 `rtp` / `rtcp` / `udp`

如果不提前放行这些嵌套协议，m3u8 和 rtsp 会**直接打不开**。而这些配置必须赶在
Qt 初始化之前设置好，否则不生效。

```python
# 关键：必须先于 QApplication 和任何 QtMultimedia 对象
setup_environment()
app = QApplication(...)
```

**知识点扩展**：
- FFmpeg 的协议白名单（`protocol_whitelist`）是一种**安全默认值**设计——宁可默认
  关闭能力，也不默认放开攻击面（比如防止 `file://` 协议被恶意 m3u8 用来读任意文件）。
- 这类"初始化顺序敏感"的问题在 GUI 框架里很常见（OpenGL 上下文、硬件加速、DPI 缩放
  都必须在窗口创建前配置）。

### 3.2 URL 分类：`url_router.py`

**做了什么**：把输入的一段文字地址分成七类：

```text
LOCAL         本地文件        → 转 file:// 直接播
DIRECT_MEDIA  媒体直链        → 直接播
HLS           m3u8 清单       → 直接播（直播态特殊处理）
LIVE_STREAM   rtsp/rtmp 等    → 直接播（实时流）
WEB_PAGE      视频网站页面     → 先解析再播
UNKNOWN_HTTP  无法判定的 http  → 先当直链试，失败再解析
UNKNOWN       其它            → 报错
```

**为什么这么设计**（核心知识点：**URL 的组成部分** + **降级链决策**）：

1. 判断媒体直链时**只看 path 的扩展名**，刻意忽略 `?token=xxx` 这类 query。
   否则 `.../a.m3u8?auth=xxx` 会因带了参数而被误判成"未知地址"。

2. `UNKNOWN_HTTP` 是最微妙的一类：它可能是"一个自建播放页"（需要解析），也可能
   是"一个没扩展名的媒体直链"（需要直接播）。**无法确定时不猜，而是"先试一种，
   失败换另一种"**——这是工程里处理不确定性的通用模式（乐观尝试 + 失败降级）。

**知识点扩展**：
- URL 的完整结构：`scheme://user:pass@host:port/path?query#fragment`。
- 为什么用 `enum`（`UrlKind`）而不是魔法字符串：类型安全、IDE 补全、防拼写错误。
- `frozenset` 存扩展名集合：不可变、可哈希、查找 O(1)。

### 3.3 页面解析：`resolver.py`（本项目的灵魂）

**做了什么**：把视频网站的**页面地址**变成**一条能直接播放的流地址**。底层用
`yt-dlp`（`youtube-dl` 的继任者）。

#### 3.3.1 核心难题：为什么必须是"单文件流"

`QMediaPlayer` 一次只能打开**一条 URL**，它没有"下载两条流再合流"的能力。而
yt-dlp 的默认选择 `bestvideo+bestaudio` 给出的是**两条分离的流**（画面一条、声音
一条）——直接交给播放器只能播其中一条：要么没声音、要么没画面。

所以解析器的目标是：从站点提供的格式里挑出**音视频在同一个文件里**的 progressive 流。

#### 3.3.2 站点只给分离流怎么办（B 站就是）

B 站、YouTube 的 **DASH** 格式把画面和声音放在两条独立的流里。实测 B 站**一条
progressive 都没有**。这时解析器不"报错了事"，而是：

1. 如实报告"只有分离流"；
2. 把画面流、声音流的地址**都带回来**；
3. 交给上层做**双流合流**（详见 3.5）。

#### 3.3.3 三个踩过的坑（每个都是知识点）

**坑 1：不要把 `format` 参数传给 yt-dlp。**

本想用 `best[acodec!=none][vcodec!=none]` 一步到位，但 B 站根本没有这样的格式，
yt-dlp 会抛 `Requested format is not available` 并**中断整个解析**——连 formats
列表都拿不到。正确做法是：让 yt-dlp 用默认格式（只取它的元信息），**自己**从
`info["formats"]` 里挑能单独播的那条。

> 知识点：**让底层工具做它能做的，把判断逻辑留在自己手里**。格式选择是业务逻辑，
> 不该推给第三方工具的 `--format` 语法。

**坑 2：解析必须能硬超时。**

yt-dlp 的 `socket_timeout` 只约束**单个 socket**；站点不停重定向时仍可能长时间
不返回。所以解析跑在**子线程**里，用 `join(timeout)` 兜住，超时当失败返回。

> 知识点：**超时是分层级的**——单次 IO 超时 ≠ 整体操作超时，外层必须再套一层
> 整体 deadline。这是分布式/网络编程的通用原则。

**坑 3：`vcodec`/`acodec` 的三种取值不能混。**

```text
"none"      = 明确没有这条轨（B 站视频流就是 acodec="none"）
None / ""   = 未知（generic 解析器抓的普通 mp4 就是这样）
```

把 `None` 当成"没有"，会把一个好好的 mp4 误判成"分离流"。

> 知识点：**三态逻辑**——"明确没有"和"不知道有没有"是两回事，数据模型要区分，
> 否则会错误降级。

#### 3.3.4 尽可能拿到地址：三层保障

```text
第 1 层  可达性预检（reachability.py）  先花 2~3 秒确认站点连得上
第 2 层  逐策略重试（strategies_for）    换 UA/换接口/补 Referer 再试
第 3 层  JavaScript 运行时（node/deno）  YouTube 没有 JS 运行时会退化
```

**为什么需要第 1 层**：站点被整段拦截时，如果不预检，yt-dlp 会白跑满 25 秒再报
一句"超时"。预检能在 2 秒内说清"是 DNS 污染"还是"根本连不上"，并跳过注定失败
的解析。

**为什么需要第 2 层**：被站点拒绝有很多种"换种方式可能绕过"的情况（机器人校验、
403、抓不到格式）。但**只对可能绕过的失败重试**——网络不通、视频已删除，重试
纯属白等。

**为什么需要第 3 层**：2026 版 yt-dlp 起，没有 JS 运行时 YouTube 解析会退化——
默认只启用 `deno`，而大多数机器上没装 deno。自动探测到 `node` 并切过去，可用接口
立刻变多。

> 知识点：**能力探测 + 优雅降级**。同一个功能（解析 YouTube）在不同环境能力不同，
> 程序要先探测环境有什么，再决定走哪条路。

#### 3.3.5 站点专用快速路径：好看视频案例

`haokan.baidu.com/v?vid=...` 是 React 单页应用，首屏 HTML 只有骨架、没有视频数据；
而 yt-dlp 内置的 `BaiduVideo` 提取器只认旧格式。解法是**不侵入 yt-dlp 内部**，
而是在 `resolve()` 里加一层"站点专用快速路径"：直接用 HTTP 抓移动端落地页
（`mbd.baidu.com/.../videoshare?nid=sv_<vid>`），从内嵌的 `window.jsonData` 里抠出
直链，构造成标准 info 结构复用后续逻辑。

> 知识点：**第三方工具改版滞后是常态**，与其等上游修复，不如在自己可控的地方
> 加一层"专用适配"，同时复用下游的统一处理逻辑。

#### 3.3.6 错误翻译：`friendly_error`

把 yt-dlp 的英文报错翻译成可操作的中文结论。这是一个**有顺序的规则匹配**，顺序
本身就是设计：

```text
"fresh cookies" 必须先于 "login required"      （抖音要匿名 cookie ≠ 会员）
"deleted" 必须先于 "geo"                        （"deleted or geo-restricted" 别误判地区）
"连接被重置" 必须先于 "网络失败"                 （文本里含 connection）
```

> 知识点：**规则引擎的顺序敏感性**——关键词匹配简单但脆弱，规则顺序即优先级，
> 必须为每个顺序写注释说明"为什么排在这里"。

### 3.4 可达性预检：`reachability.py`（DNS 污染与 DoH）

**做了什么**：解析前花 2~3 秒做 DNS + TCP 探测，必要时用 DoH（加密 DNS）兜底。

**核心背景**（这个项目的真实环境）：`youtube.com` 在开发环境里被"DNS 污染"——

```text
系统解析 www.youtube.com → 157.240.7.20（Facebook 的网段！）
真实地址                → 142.251.150.4（Google 的 142.251 段）
```

注意：**DNS 是"成功"的，只是给了一个假地址**。所以"能解析出 IP"绝不能当成
"能连上"。

**DoH 兜底的逻辑**（非常克制）：

```text
系统解析拿到地址却连不上  → 用 DoH 再查一次
DoH 的地址实测能连上      → 才注册改写，让域名解析到可用地址
```

**只有当 DoH 给的地址确实能连上，才改写。** 健康网络里绝不动它——把好好的解析
改坏比不做这件事还糟。

**三条绝不误伤的硬规矩**：
1. 配了代理就跳过预检（走代理时"直连 origin 通不通"与能否播放无关）；
2. 本机地址跳过（回环判定与本地反向代理保持一致）；
3. 结果缓存 60 秒（避免每次都重探测）。

**知识点扩展**：
- **DNS 污染 vs DNS 劫持**：污染是返回错误 IP，劫持是篡改解析过程。DoH/DoT 通过
  HTTPS/TLS 加密 DNS 查询来对抗劫持，但对"污染后 TCP 再拦截"无效（本项目正是后者）。
- **TCP 三次握手**：为什么 TCP 能连上但后续数据超时，说明是"连接建立后的深度拦截"。
- **缓存与失效**（TTL / 60 秒缓存）是网络编程的性能与一致性权衡。

### 3.5 播放控制：`player_controller.py` + `backends/`

#### 3.5.1 后端抽象（`backends/base.py` + `factory.py`）

**面向接口设计**：UI 层只依赖 `PlayerBackend` 这套接口与信号，不直接碰
`QMediaPlayer`。于是可以有两个内核：

| 内核 | 实现 | 特点 |
|---|---|---|
| QtMultimedia | `qt_backend.py` | 内置 FFmpeg 后端，无需额外依赖 |
| libmpv | `mpv_backend.py` | 可选，RTSP 能走 TCP、能发自定义请求头 |

**工厂模式**：`factory.py` 负责选内核——优先用 mpv，**加载失败静默回退 Qt**。
关键设计是"回退静默"：绝不因为"想用 mpv"而播不了。

> 知识点：**面向接口编程（依赖倒置）** + **工厂模式** + **策略模式**。核心价值
> 是"新增一个内核，UI 和控制器代码零改动"。

#### 3.5.2 六个关键设计

1. **加载超时兜底**：`QMediaPlayer` 遇到打不开的地址时，常长时间停在
   `LoadingMedia` 而**不触发** `errorOccurred`。必须用定时器 + 状态检查强制判定失败。

2. **直播识别**：m3u8 直播没有总时长（duration 恒 0），进度条切"不确定态"；
   断流重连而不是当"播放结束"。

3. **诊断先于抱怨**：加载失败时后台并行跑一次分层诊断（见 3.7），发现 DNS/TCP/TLS
   硬性失败就立刻告知具体原因，而不是干等超时。

4. **网页地址先解析再播**：解析是异步的，期间界面可交互，换地址会作废旧任务。

5. **未知地址失败后再解析**：先当直链试，失败交给解析器（对应 url_router 的
   UNKNOWN_HTTP）。

6. **分离流用"第二路音轨"合流**：这是本项目最巧妙的一处（见下）。

#### 3.5.3 双流合流：不转码、不落盘

B 站只给 DASH 分离流。做法是：**两个播放内核实例**——主源播画面，附加音轨播声音，
以**画面为主时钟**做同步校正。

```text
两路在同一时刻 play() 启动（错开启动偏差直接上百毫秒）
以画面为主时钟，偏差 > 400ms 时把声音对齐到画面
（视频 seek 跳帧明显，音频 seek 几乎察觉不到，所以只调音频）
```

**为什么以画面为主时钟**：人眼对视频跳帧很敏感，人耳对音频几毫秒的漂移几乎无感，
所以"让声音去追画面"是感知上最优的选择。

> 知识点：**音视频同步（AV sync）** 是多媒体最经典的问题。这里用的是"主时钟
> 同步法"（master clock），业界还有时间戳比对、PTS/DTS 对齐等更精细的方案。

### 3.6 防盗链与本地反向代理：`local_proxy.py`

**核心问题**：`QMediaPlayer` **没有任何注入自定义请求头的接口**，而防盗链恰恰靠
请求头判断（`Referer` 必须是站点自己的域名，否则 403）。

**解法**：在本机起一个 HTTP 代理，播放器请求
`http://127.0.0.1:<port>/proxy?u=<目标地址>`，由代理带着正确的头去取真实内容，
再原样转回。播放器全程以为自己在跟普通 HTTP 服务器打交道。

**三个必须原样透传的细节**（每个都是知识点）：

```text
Range: bytes=...      必须透传   → 否则拖不动进度条
206 + Content-Range   必须透传   → 否则断点续传失效
Accept-Encoding       必须删除   → 否则 gzip 压缩会让 Content-Length 对不上
```

> 知识点：
> - **HTTP Range 请求**（206 Partial Content）是视频拖动/断点续传的基石。
> - **Content-Encoding 与 Content-Length 的关系**：压缩后长度 ≠ 实际字节数。
> - **请求头大小写**：`Range` 不能写成 `range`，部分 CDN 按字面比对。

**Referer 的优先级**（关键设计）：

```text
解析器从页面拿到的  >  设置里手填的  >  由目标地址自动推导的站点根
```

为什么第一档最关键：B 站的 CDN 域名与页面域名不同，拿站点根当 Referer 等于发了
个错的，防盗链照样过不去。

**如实说明局限**：HLS 清单里的分片地址是相对路径，代理改写不了，硬走只会搞坏
能播的地址，所以如实跳过。

---

### 3.7 分层诊断：`net_diagnose.py`

**为什么需要**：播放器失败往往只说"加载超时"，无法判断是四种情况里的哪种：

```text
地址解析  → DNS  →  TCP  →  协议握手
（写错了）  （解析不出）（连不上）（路径/应用名不对）
```

**设计约束**：
- 只用标准库（冻结进 exe 后不引入额外依赖）；
- 全程只读探测：RTSP 发 `OPTIONS`、RTMP 只握手、HTTP 发 `HEAD`，不真正拉流。

> 知识点：**分层定位问题**——把一个复杂故障拆成串行步骤，哪层断就停在哪层，
> 每层给独立的中文建议。这是"故障排查"的通用方法论（类似网络栈的逐层排查）。

## 四、核心知识点专题

### 4.1 状态机与超时兜底

播放控制器本质上是一个**有限状态机**：`LoadingMedia → LoadedMedia → PlayingState → ...`。
配合"定时器 + 状态检查"的超时兜底，处理了"播放器不发错误信号"这一底层缺陷。

> 扩展：状态机的形式化（状态 + 事件 + 转移），Qt 的 `QStateMachine` 也能实现，
> 但手写状态标志在小项目里更直白可控。

### 4.2 线程与异步

项目里大量用到"工作线程 + 结果回主线程"：

- 解析跑在子线程（`join(timeout)` 兜底超时）；
- 诊断跑在后台线程（并行，不阻塞 UI）；
- 下载跑在工作线程（`requests` 流式）。

而 Qt 要求**所有 UI 操作必须在主线程**，所以线程间通信靠 Qt 的 **Signal/Slot**
（跨线程信号自动排队投递到目标线程）。

> 扩展：Python 的 GIL 意味着 CPU 密集型任务多线程无益，但 IO 密集型（网络、下载）
> 多线程能显著提升响应性。Qt 的信号槽是线程安全的跨线程通信机制。

### 4.3 面向接口与可替换内核

`PlayerBackend` 抽象接口隔离了 Qt 和 libmpv 两个内核。这是"依赖倒置原则"的典型
应用：高层模块（UI、控制器）依赖抽象，不依赖具体实现。

> 扩展：这是**策略模式**和**适配器模式**的组合。类似的思想在"数据库 ORM"、
> "云存储 SDK"等场景反复出现——定义统一接口，换实现不动上层。

### 4.4 持久化与数据一致性

播放列表/历史用 JSON 持久化，两个细节体现了工程严谨：

1. **原子写入**：先写 `.tmp` 再 `os.replace`，断电也不会留下半个文件。
2. **坏文件留档**：文件被外部改坏时，改名为 `.bad-<时间戳>` 再重新开始，而不是
   静默清空。

> 知识点：**原子性**（atomicity）是文件写入的经典问题；`os.replace` 在同一文件
> 系统上是原子操作。坏数据留档体现"不静默破坏用户数据"的原则。

### 4.5 打包与运行时（PyInstaller）

把 Python 程序打包成免环境的 exe，关键点：

- **Qt 模块精简**：Qt6 全装 641MB，只保留用到的 6 个模块，降到 143MB。依据是
  实测的**链接期依赖**（`Qt6Multimedia.dll → Qt6Core/Gui/Network`），不是猜的。
- **动态库打包**：`ffmpegmediaplugin.dll` 依赖 `MSVCP140.dll`/`VCRUNTIME140.dll`，
  缺了会"能启动但一播视频就报错"，必须一起打包。
- **验证产物**：exe 是窗口程序看不到 stderr，所以内置 `--self-check` 入口，
  **真的加载一次媒体插件**（只查文件存在不够，依赖 DLL 缺失时文件照样在）。
- **符号核对**：从 exe 里解出 `PYZ.pyz`（zlib 压缩），确认改的代码真进去了。
  **不能对 exe 明文 grep**——模块被压缩了。

> 知识点：**静态分析 vs 动态验证**的区别；**依赖传递**（A 依赖 B，B 依赖 C，
> 只打包 A 和 B 不够）；**onefile vs onedir** 的启动速度权衡。

## 五、踩坑与工程经验

这一章是项目最有教学价值的部分——每个坑都对应一个可复用的工程原则。

| # | 坑 | 教训 |
|---|---|---|
| 1 | `QMediaPlayer` 失败不发 `errorOccurred` | 不能只信错误信号，必须有超时兜底 |
| 2 | 环境变量设置时机 | 初始化顺序敏感，必须在 `QApplication` 前 |
| 3 | yt-dlp 传 `format` 中断解析 | 业务逻辑留自己手里，别推给第三方语法 |
| 4 | `socket_timeout` 不够 | 整体超时与单次 IO 超时是两层 |
| 5 | `vcodec=None` 被当"没有" | 三态逻辑："无"和"未知"要区分 |
| 6 | DNS 污染 | "能解析出 IP" ≠ "能连上"，要实测 TCP |
| 7 | 防盗链缺 Referer | 本地反向代理补发请求头 |
| 8 | `grab()` 离屏下永远非空 | 判"出画面"只认 `videoFrameChanged` |
| 9 | 浏览器 cookie 被锁 | Chrome 运行中读不了库，提示关闭浏览器 |
| 10 | PyInstaller 批量删除被拦 | `--fresh-work` 绕过，旧目录改名不删除 |
| 11 | 打包插件惰性注册丢失 | `collect_submodules` 整包收，不能只加 hiddenimport |
| 12 | DRM 误报成"没有可播放流" | DRM 要单独识别，否则用户误以为加 cookie 能解 |

## 六、扩展方向与思考题

### 6.1 可继续做的功能

1. **下载后转码**：当前下载分离流需要 ffmpeg 合流，可扩展到格式转换（mp4→mkv 等）。
2. **播放记录续播**：记住每个视频的播放位置，下次打开从上次继续。
3. **字幕支持**：yt-dlp 能抓字幕，Qt 播放器可叠加字幕轨。
4. **多格式码率切换**：解析出多个清晰度，让用户手动选（当前自动选最高）。
5. **移动端 / 网页版**：把解析逻辑抽成服务，前端用 `<video>` 播（Web 前端是
   `<video>` 直接支持 HLS/直链，无需 Qt）。

### 6.2 思考题（可用于教学讨论）

1. **为什么"双流合流"选"第二路音轨"而不是"转码合并成一条"？** 提示：考虑延迟、
   资源消耗、实时性。

2. **`friendly_error` 用关键词顺序匹配，它的优缺点是什么？** 什么场景下会失效，
   更好的方案是什么？（提示：正则、异常类型、站点专属映射表）

3. **DoH 兜底"只在实测能连才改写"这个克制设计的理由？** 如果不加这个限制会怎样？

4. **本地反向代理为什么只绑 `127.0.0.1`？** 如果绑 `0.0.0.0` 会有什么风险？

5. **为什么"原子写入"要先写 `.tmp` 再 `os.replace`，而不是直接写目标文件？**

6. **面向接口隔离内核，换来的是"换内核零改动"。** 它的代价是什么？什么时候这种
   抽象是过度设计？

### 6.3 延伸阅读

- **音视频**：HLS/DASH 协议、FFmpeg 协议白名单、AV sync 主时钟同步
- **网络**：HTTP Range 请求、DNS 污染与 DoH/DoT、TCP 三次握手、反向代理
- **Qt**：信号槽跨线程通信、`QMediaPlayer` 状态机、插件加载机制
- **工程**：依赖倒置、工厂/策略/适配器模式、原子写入、超时分层、PyInstaller 打包
